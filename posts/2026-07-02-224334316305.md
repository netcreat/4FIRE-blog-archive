# OCT가 바꾸는 우주 인터넷: 진짜 병목은 속도가 아니라 “서로를 찾는 시간”이다

Original Naver post: https://blog.naver.com/4-fire/224334316305

[SDA OCT Standard v4.0.0](https://www.sda.mil/wp-content/uploads/2024/07/SDA_OCT_Standard_4.0.0_final-20240701.pdf)

**✅ 서론**

- - 우주 통신에서 Optical Communications Terminal, 즉 **OCT**는 쉽게 말해 **우주용 레이저 인터넷 포트**다. 위성에 달린 작은 광통신 단말이 다른 위성, 지상국, 항공기, 해상 플랫폼을 향해 아주 좁은 레이저 빔을 쏘고, 그 빔 위에 데이터를 실어 보낸다.
  - 하지만 OCT를 단순히 “빠른 레이저 통신 장비”로 이해하면 핵심을 놓치게 된다. 진짜 어려운 부분은 데이터 전송 그 자체보다, **서로 움직이는 두 위성이 수백 km에서 수천 km, 때로는 2만 km 떨어진 거리에서 아주 가느다란 레이저 빔을 서로 정확히 맞추는 과정**이다.
  - SDA의 OCT 표준은 바로 이 문제를 다룬다. 이 표준은 여러 업체가 만든 OCT들이 서로 다른 위성이나 플랫폼에 탑재되더라도, 같은 방식으로 링크를 잡고, 같은 방식으로 데이터를 주고받게 만들기 위한 상호운용 규격이다. v3.2.0 문서 기준으로 SDA OCT 표준은 S2S, 즉 위성-위성뿐 아니라 S2G 위성-지상, S2A 위성-항공기, S2M 위성-해상 단말 링크까지 포함하는 방향으로 정리되어 있다.
  - 엄밀히 말하면 초기 문서는 **OISL Standard**라고 불렸고, v3.0부터 **OCT Standard**라는 이름이 본격적으로 쓰인다. 그래서 “OCT 1.0부터 4.0까지”라고 말할 수는 있지만, 더 정확히는 **OISL v1/v2에서 OCT v3/v4로 발전했다**고 보는 것이 맞다.

---

**✅ OCT 표준의 진화: 실험적 레이저 링크에서 우주 네트워크 인터페이스로**

- - 초기 OISL 표준은 “위성끼리 레이저로 통신하려면 어떤 기본 파장, 변조, 오류정정, acquisition 시간이 필요할까”를 정하는 성격이 강했다. 그러나 v3 이후에는 단순한 레이저 링크를 넘어, **Ethernet frame을 광 프레임으로 캡슐화하고, 오류정정하고, ACK/재전송하고, 시간 동기와 위치 정보까지 함께 운반하는 우주 네트워크 인터페이스**로 발전한다.
  - SDA v3.2.0 문서의 revision history를 보면, 2020년 Transport Layer Tranche 0 RFP용 draft에서 시작해 v2.0, v3.0, v3.0.1, v3.1.0, v4.0.0, v3.2.0으로 이어진 흐름이 정리되어 있다. 흥미로운 점은 v4.0.0 final이 2024년에 나오고, v3.2.0 final이 2025년에 나왔다는 점이다. 즉 v3.2.0은 “v4보다 오래된 문서”라기보다 **3.x branch의 최신 보강판**에 가깝다.
  - 버전별 의미를 아주 간단히 정리하면 이렇다.

|  |  |  |
| --- | --- | --- |
| **구분** | **의미** | **핵심 변화** |
| **OISL v1 / 2020** | 초기 뼈대 | 파장, OOK-NRZ, LDPC, acquisition 100초 같은 기본 방향 제시 |
| **OISL v2.1.2** | Tranche 0용  실질 표준 | PAT, spiral scan, tracking tone, Ethernet encapsulation, ranging/timing 구체화 |
| **OCT v3.0** | Tranche 1용  본격 OCT 표준 | 5G NR LDPC 기반 1.25Gbps Manchester / 2.5Gbps OOK-NRZ 구조 정리 |
| **OCT v3.2.0** | 3.x branch의 최신 실전형 | 2.5G/1.25G/625M/312.5M rate family, ARQ, PVTR, eTWTT, beam divergence 정리 |
| **OCT v4.0.0** | 장거리·불리한 링크 확장 | 20,000km burst mode, asymmetric comms, laser linewidth, center frequency accuracy, frame-loss metric 추가 |

- - 여기서 중요한 점은 **SDA OCT v4.0이 곧 100Gbps나 400Gbps 표준이라는 뜻은 아니라는 점**이다. SDA v3.2/v4.0의 공개 표준은 기본적으로 2.5Gbps급 이하의 상호운용 baseline을 정의한다. Skyloom 같은 업체가 말하는 100Gbps, 400Gbps 로드맵은 SDA 표준을 기반으로 하되, 그 위에 올라가는 vendor roadmap 또는 proprietary 확장에 가깝다.

---

**✅ OCT는 무엇으로 구성되는가**

- - OCT는 단순한 레이저 송수신기가 아니다. 실제로는 다음 기능들이 하나의 단말 안에 묶여 있다.

|  |  |
| --- | --- |
| **구성 요소** | **역할** |
| **Optical head / telescope** | 레이저를 송신하고 수신하는 광학부다. |
| **PAT system** | Pointing, Acquisition, Tracking. 상대를 찾고, 조준하고, 계속 따라간다. |
| **Fine steering mirror / gimbal** | 위성 본체의 거친 자세제어보다 훨씬 미세하게 빔 방향을 조정한다. |
| **Optical modem / PHY** | 빛의 ON/OFF 패턴을 bit stream으로 바꾼다. |
| **FEC engine** | LDPC 같은 오류정정 코드로 깨진 bit를 복원한다. |
| **Framing / ARQ logic** | 데이터를 frame으로 나누고, ACK/NAK와 재전송을 처리한다. |
| **Timing / ranging logic** | TWTT, eTWTT, PVTR 같은 시간·거리·궤도 관련 정보를 처리한다. |
| **Host interface** | 위성의 router/switch, payload computer, bus와 연결된다. |

- - 즉 OCT는 위성 입장에서 보면 **우주용 광 포트 + 모뎀 + 정밀 조준장치 + link controller + timing interface**다.
  - 쉽게 말하면, OCT는 단순한 손전등이 아니라 **망원경이 달린 초정밀 레이저 손전등, 자동 조준 장치, 데이터 모뎀, 오류 수정 장치가 하나로 합쳐진 장비**다.

**✅ OCT는 데이터를 어떻게 보내는가**

- - OCT가 링크를 잡은 뒤에는 데이터를 광 채널 위의 frame으로 운반한다.
  - SDA OCT v3.2.0은 5G NR LDPC 기반 protocol set을 사용하고, 2500MHz, 1250MHz, 625MHz, 312.5MHz optical signaling rate와 OOK-NRZ / Manchester encoding 조합을 정의한다.

    - 예를 들어 2500MHz OOK-NRZ는 2500Mbps, 2500MHz Manchester는 1250Mbps로 정의된다.
    - 여기서 **OOK-NRZ**는 빛을 켜고 끄는 방식으로 0과 1을 표현하는 구조다. 같은 signaling rate에서 데이터 효율이 높다.
    - 반면 **Manchester**는 bit 안에 반드시 전환이 생기도록 만드는 방식이다. 동기 잡기에는 유리하지만, 같은 optical signaling rate에서 실제 데이터율은 OOK-NRZ보다 낮다.
  - 쉽게 말하면 이렇다.

    - **OOK-NRZ**(On-Off Keying Non-Return-to-Zero)는 “불 켜짐 = 1, 꺼짐 = 0”에 가깝다.

      - 말 그대로 빛을 켜고 끄면서 데이터를 표현하는데, 비트 하나가 유지되는 동안 중간에 굳이 0으로 돌아가지 않는다는 뜻이다.
      - 장점은 **효율이 좋다**는 점이다.

        - 2.5GHz optical signaling rate를 쓰면 OOK-NRZ는 이론적으로 **2.5Gbps급** 데이터를 표현할 수 있다.
      - 단점은 긴 1이나 긴 0이 이어지면 수신기가 clock timing을 잡기 어렵거나, threshold 판단이 까다로워질 수 있다는 점이다.

        - 예를 들어 데이터가 이렇게 길게 이어진다고 하자.
        - 1111111100000000
        - 그러면 수신기 입장에서는 “언제 bit 경계가 바뀌는지”를 별도 clock recovery로 잘 잡아야 한다.
    - **Manchester**는 “한 박자 안에서 밝기 변화 패턴으로 0과 1을 구분하는 방식”이다.

      - SDA OCT 문서 방식으로 보면 대략 이렇게 정의된다.

        - 0 → 01
        - 1 → 10
      - 즉, 한 비트를 표현하기 위해 두개의 optical symbol이 필요하다.
      - Manchester는 더 친절하게 박자를 알려주지만, 그만큼 같은 시간에 담을 수 있는 정보량은 줄어든다.

|  |  |
| --- | --- |
| **방식** | **2.5GHz에서 표현 가능한 nominal rate** |
| **OOK-NRZ** | 2.5Gbps |
| **Manchester** | 1.25Gbps |

> ***OOK-NRZ는 빠르지만 더 까다롭고, Manchester는 느리지만 더 안정적인 방식이다.***

- - SDA OCT modem frame은 구조적으로도 꽤 명확하다.

    - OTA frame은 preamble, fixed-length header, data bits, CRC, variable parity bits로 구성된다.
    - v3.2.0 기준으로 preamble은 64bit, header는 960bit, information payload는 8416bit, payload CRC는 32bit이며, parity bit 수는 설정된 FEC code rate에 따라 달라진다.
  - 이것을 쉽게 풀면 다음과 같다.

    - 먼저 “이제부터 frame 시작한다”는 preamble을 보낸다.
    - 그다음 frame 번호, ACK/NAK, timestamp 같은 header를 보낸다.
    - 그 뒤에 실제 데이터를 보낸다.
    - 마지막으로 CRC와 LDPC parity를 붙여, 수신기가 오류를 찾아 고치게 한다.
  - 사용자 데이터는 보통 Ethernet frame으로 들어온다. 그런데 OCT는 Ethernet frame을 그대로 레이저로 쏘지 않는다. 큰 Ethernet frame은 여러 FSO frame으로 쪼개고, 작은 frame은 하나의 FSO frame 안에 묶는다. 수신 쪽에서는 다시 Ethernet preamble, SFD, interpacket gap을 붙여 Ethernet frame으로 복원한다. SDA v3.2.0은 이 packing and segmentation 과정이 큰 Ethernet frame을 하나 이상의 FSO frame으로 segment한다고 설명한다.
  - 그래서 OCT는 네트워크 입장에서 보면 **Ethernet packet을 우주 레이저 frame으로 바꿔서 운반하는 투명한 광 운반 계층**처럼 동작한다.

**✅ 진짜 핵심은 PAT: Pointing, Acquisition, Tracking이다**

- - OCT에서 가장 중요한 기술은 data rate보다 **PAT**다.

|  |  |
| --- | --- |
| **단계** | **의미** |
| **Pointing** | 상대가 있을 방향으로 대략 조준한다. |
| **Acquisition** | 실제 상대의 레이저 신호를 찾아낸다. |
| **Tracking** | 찾은 뒤에는 계속 놓치지 않고 따라간다. |

- - RF 통신은 빔이 상대적으로 넓다. 대충 방향만 맞아도 어느 정도 신호가 잡힌다. 하지만 레이저는 다르다. OCT의 빔은 매우 좁고, 상대 위성은 빠르게 움직이며, 두 위성 모두 자세 오차와 진동, 열변형, 궤도 예측 오차를 가진다.
  - 더 어려운 점은 **링크가 열리기 전에는 OCT끼리 실시간으로 대화할 수 없다는 점**이다.

    - SDA v3.2.0은 OCT acquisition이 real-time side channel 없이 수행되어야 하고, 통신 채널이 열리기 전에는 real-time OCT-to-OCT communications가 없기 때문에 두 단말의 acquisition process가 공통 clock에 맞춰 잘 choreograph되어야 한다.

**✅ Acquisition은 어떻게 진행되는가**

- - SDA OCT의 acquisition 절차는 상태기계(state machine)로 정의된다. 대략 다음 흐름이다.

[![](https://mblogthumb-phinf.pstatic.net/MjAyNjA3MDJfNTgg/MDAxNzgyOTczMDc1MjQz.OHPxFnvNzkM7zNb1SQvM_46RTt4ddZ9IY1ojbjM_3eQg.Gczuf7nPqdFNargVxJA_VzcAe9KB57LS5rkXVBZhPEog.PNG/image.png?type=w800)](#)

- - 각 단계의 의미는 다음과 같다.

**📌** **Setup: 먼저 대략 그쪽을 본다**

- - 두 위성은 먼저 궤도 정보와 예측 위치를 바탕으로 상대가 있을 방향을 계산한다. 이때 필요한 것이 ephemeris, PVTR, clock synchronization, calibration이다.

> ***Ephemeris****는 위성이 시간에 따라 어디에 있는지 나타내는 궤도 정보다.*
>
> ***PVTR****는 “내 위치·속도·시간 기준 정보”에 가깝다*
>
> ***Clock synchronization****은 “둘이 같은 시계를 보고 움직이는 것”이다*
>
> ***Calibration****은 “위성 본체가 아는 방향”과 “OCT가 실제로 보는 방향”을 맞추는 작업이다*

- - 여기서 calibration이 중요하다. 위성 본체의 좌표계와 OCT optical axis는 완벽히 일치하지 않는다. 발사 진동, 조립 오차, 열변형 때문에 미세하게 틀어질 수 있다. 이 오차가 크면 “상대가 있을 것으로 예상되는 영역”이 커진다. 그 영역이 커질수록 search 시간이 길어진다.

**📌** **TUC: 찾을 영역을 원뿔로 본다**

- - OCT는 상대가 있을 가능성이 있는 영역을 **Starting Uncertainty Cone**, 즉 TUC로 본다. v3.2.0 문서는 TUC를 circular cone radius로 보고되는 search cone으로 설명한다. 만약 이 cone이 시스템의 field of view보다 크면 수동 개입이 필요할 수도 있다.
  - 쉽게 말하면 이렇다.

    - 상대가 정확히 어디 있는지 알면 바로 레이저를 맞추면 된다.
    - 그런데 “저쪽 하늘 어딘가” 정도만 알면 그 영역 전체를 훑어야 한다.
    - 그 훑어야 할 원뿔이 TUC다.

**📌** **Acquisition 1A: lead가 먼저 훑고 follow가 잡는다**

- - SDA OCT는 lead/follow 전략을 사용한다. Phase 1A에서는 **lead OCT가 starting cone of uncertainty를 scan**한다. follow OCT는 그 빛을 감지하면 pointing adjustment를 수행해 uncertainty를 줄인다.
  - 즉 한쪽이 먼저 레이저로 하늘을 나선형으로 훑고, 다른 쪽은 “아, 신호가 살짝 보였다”는 hit를 감지해 방향을 보정한다.

**📌** **Acquisition 1B: 이번에는 역할을 바꾼다**

- - Phase 1B에서는 반대로 **follow OCT가 남은 uncertainty cone을 scan**하고, lead OCT가 hit를 감지해 조정한다. 이렇게 양쪽이 번갈아가며 상대를 찾으면서 불확실성을 줄인다.
  - 이 단계가 중요한 이유는 multi-vendor 환경 때문이다. 한 회사 장비끼리만 쓴다면 vendor-specific 방식으로 대충 맞출 수도 있다. 하지만 SDA는 서로 다른 업체의 OCT가 만나야 하므로, 누가 언제 scan하고 누가 언제 기다릴지 표준화해야 한다.

**📌** **Acquisition 2: 더 좁은 영역을 다시 훑는다**

- - Phase 2에서는 한쪽 또는 양쪽 OCT가 남은 cone을 더 좁게 scan한다. 여기서 목표는 상대 신호를 fine acquisition sensor의 field of view 안으로 넣는 것이다.
  - 이제 “상대가 저쪽 하늘 어딘가”가 아니라, “거의 저 지점 근처” 수준으로 좁혀지는 단계다.

**📌** **Fine Acquisition: 안정적인 tracking으로 들어간다**

- - Fine Acquisition에서는 미세한 pointing 오차를 더 줄인다. 이때 fine steering mirror, tracking sensor, control loop가 작동한다. 단순히 빛이 한 번 보였다고 끝나는 것이 아니다. **연속적이고 안정적인 tracking이 가능해야 한다.**

****

**📌** **Communication: 이제 데이터가 흐른다**

- - 마지막으로 tracking이 안정화되고 bidirectional data link가 established되면 Communication 상태가 된다. 이때부터 Ethernet packet이 FSO frame으로 바뀌어 광 링크 위로 흐른다.

**✅ 왜 acquisition은 오래 걸리는가**

- - SDA OCT 표준은 cold start와 warm start 모두에서 PAT acquisition time을 **100초 이하**로 요구한다. v3.2.0은 이 100초가 post-calibration PAT activity 전체에 적용된다.

> ***Cold start는 이런 상황이다.***
>
> **
>
> *친구가 넓은 운동장 어딘가에 있다.*
>
> *대충 저쪽 방향이라는 것만 안다.*
>
> *그래서 손전등으로 넓은 영역을 원을 그리며 천천히 훑어야 한다.*
>
> *시간이 오래 걸린다.*
>
> **
>
> ***Warm start는 이런 상황이다.***
>
> **
>
> *방금 전까지 친구가 어디 있었는지 알고 있다.*
>
> *잠깐 눈을 돌렸다가 다시 찾는 상황이다.*
>
> *그래서 그 근처만 비추면 된다.*
>
> *훨씬 빨리 찾을 수 있다.*

- - 그런데 일반인 입장에서는 “레이저를 켜고 상대를 보면 되는 것 아닌가?”라고 생각할 수 있다. 실제로는 그렇지 않다. acquisition이 오래 걸리는 이유는 크게 다섯 가지다.

    - 첫째, **문제가 통신 문제가 아니라 공간 탐색 문제**다.

      - 상대와 아직 통신이 열리지 않았기 때문에 “왼쪽으로 조금 더 돌려” 같은 실시간 협조가 불가능하다. 두 단말은 미리 정해진 시간표대로 움직여야 한다.
    - 둘째, **찾아야 하는 영역이 조금만 커져도 시간이 크게 늘어난다**.

      - SDA v3.2.0은 baseline spiral scan으로 constant velocity Archimedes spiral scan을 설명한다. 여기서 scan time은 search radius와 scan step의 비율 제곱에 비례하는 형태로 설명된다. 즉 훑어야 할 반경이 커지면 시간이 선형이 아니라 제곱에 가깝게 늘어난다.
    - 셋째, **빨리 훑으면 놓칠 수 있고, 촘촘히 훑으면 오래 걸린다**.

      - scan step을 transmit beam 폭과 비슷하게 잡으면 overlap loss가 8.64dB가 될 수 있고, step을 FWHM 수준으로 촘촘히 줄이면 overlap loss는 3dB로 줄지만 scan 시간이 2.9배 길어진다.
    - 넷째, **cold start와 warm start가 다르다**.

      - 최근에 이미 상대를 추적한 적이 있으면 TUC가 작고, Phase 1을 건너뛸 수 있다. 이런 경우 warm start는 훨씬 빠르다. 반대로 처음 잡는 cold start는 TUC가 크고, Phase 1A/1B를 거쳐야 하므로 시간이 길어진다.
    - 다섯째, **위성 자체가 완벽히 안정적인 플랫폼이 아니다**.

      - reaction wheel의 진동, 구조물 열변형, 태양광에 의한 thermal load, 자세제어 오차, 궤도 예측 오차, 상대 위성의 기동, background light가 모두 영향을 준다.
  - 쉽게 비유하면 이렇다.

    - 두 사람이 아주 먼 운동장 양끝에 서 있다.
    - 각자 레이저 포인터를 들고 있는데, 빔은 바늘처럼 가늘다.
    - 둘 다 계속 움직이고 있고, 전화 통화도 안 된다.
    - 그래서 미리 정한 시간에 한 명은 원을 그리며 비추고, 다른 한 명은 그 빛이 보이는지 기다린다.
    - 빨리 훑으면 상대를 놓칠 수 있고, 천천히 훑으면 시간이 오래 걸린다.
    - 이것이 acquisition이 오래 걸리는 이유다.

---

**✅ AM tracking tone: “나 여기 있어”라고 깜빡이는 신호**

- - Acquisition과 tracking에서 중요한 보조 신호가 **AM tracking tone**이다. 이것은 데이터 신호 위에 낮은 주파수의 진폭 변조를 얹는 방식이다.
  - v3.2.0은 AM tracking tone을 40kHz 또는 50kHz로 software command를 통해 선택할 수 있게 하고, 500ppm 이상의 frequency accuracy를 요구한다. 또한 acquisition scan 단계에서는 modulation index를 높게, fine acquisition 이후에는 낮게 운용할 수 있는 phase-dependent MI 요구도 추가되어 있다.
  - 쉽게 말하면, OCT는 빔을 찾을 때 이렇게 한다.

    - “데이터는 아주 빠르게 깜빡이지만, tracking sensor가 찾기 쉽게 그 위에 느린 깜빡임을 하나 더 얹는다.”
  - acquisition 중에는 더 눈에 띄게 깜빡인다. 링크가 잡힌 뒤에는 너무 크게 흔들리지 않도록 modulation을 낮출 수 있다.

**✅ OCT 4.0에서 가장 중요한 변화**

- - OCT 4.0은 단순히 속도를 올린 버전이 아니다. 오히려 핵심은 **더 멀고, 더 불리한 링크를 안정적으로 닫기 위한 현실적 요구사항 강화**다.

**📌** **Laser linewidth ≤ 5GHz FWHM**

- - v4.0은 modulated laser linewidth가 5GHz FWHM을 넘지 않아야 한다는 요구를 추가했다.

    - **FWHM**은 **Full Width at Half Maximum**의 약자다.
    - 한국어로는 보통 **반치전폭**, 또는 풀어서 **최대값의 절반 높이에서 측정한 전체 폭**이라고 한다.
    - 쉽게 말하면, 어떤 신호나 빔이 가장 강한 지점을 기준으로, **그 세기가 절반으로 떨어지는 양쪽 지점 사이의 폭**을 말한다.
  - 레이저의 색깔 또는 주파수 폭이 너무 넓게 퍼지면 안 된다는 뜻이다. 주파수 폭이 넓으면 옆 채널을 침범하거나 수신기가 약속한 채널 안에서 신호를 안정적으로 받기 어려워진다.

**📌** **Center frequency accuracy ±2.5GHz**

- - v4.0은 송신기의 center frequency가 ±2.5GHz 안에 들어와야 한다고 요구한다. 100GHz grid를 쓰는 C-band 광 채널에서 “약속한 채널 중앙에서 너무 벗어나지 말라”는 의미다.
  - 쉽게 비유하면 이렇다.

    - 라디오 주파수를 93.1MHz에 맞춰야 하는데, 송신기가 자꾸 92.7MHz나 93.6MHz로 밀리면 깨끗하게 들리지 않는다.
    - 레이저 통신에서도 같은 문제가 생긴다.
    - 그래서 중심 주파수를 정확히 맞추라는 요구가 생긴 것이다.

**📌** **BER보다 post-FEC frame loss 중심으로 이동**

- - 기존에는 post-FEC BER, 즉 오류정정 후 bit error rate가 중요한 지표였다.
  - v4.0은 이를 **post-FEC frame loss 8E-6** 중심으로 재정의한다.

    - 8E-6는 0.000008 : 백만 프레임당 약 8개 손실, 즉 125,000 프레임당 1개 손실을 의미함.
    - 이 조건이 특정 시험 조건에서는 BER 10-9와 동등하다.
  - 이 변화는 중요하다. 실제 네트워크 운영자가 체감하는 것은 “bit 몇 개가 틀렸나”보다 **Ethernet frame이 살아남았나, packet이 손실됐나**에 더 가깝다. 따라서 v4.0은 더 운영 친화적인 지표로 이동한 것이다.

**📌** **Asymmetric communications**

- - v4.0은 송신 rate와 수신 rate를 다르게 조합할 수 있는 asymmetric communications를 추가한다. 즉 한 방향은 빠르게, 반대 방향은 느리게 운용할 수 있다.
  - 이는 실제 운용에서 중요하다. 많은 위성 mission은 payload data를 내려보내는 downlink성 traffic이 크고, 반대 방향 command/control traffic은 작을 수 있다. 양방향을 항상 같은 속도로 맞출 필요가 없어진다.

**📌** **Long-range burst mode**

- - v4.0의 가장 큰 변화 중 하나는 **20,000km 장거리 burst mode**다.
  - v4.0은 BM12와 BM16이라는 두 개의 burst-mode protocol을 정의한다.
  - 둘 다 **2.5GHz clock, Manchester encoding, PL4 LDPC code rate 0.5**를 사용하며, 20,000km operating range와 6µW/m2 minimum receive aperture irradiance를 기준으로 한다. payload data rate는 BM12가 48.9Mbps, BM16이 36.7Mbps다.

    - 앞서 OOK-NRZ와 Manchester Code의 차이를 살펴봤듯이 Manchester Code를 사용하면 일단 대역폭이 절반으로 낮아지는데,
    - PL4 LDPC code rate 0.5 또한 가장 강한 오류정정을 위해 보내는 정보와 같은 양의 패리티를 보내는 것이기 때문에 대역폭은 다시 절반으로 낮아진다.
    - BM12와 BM16은 계속 보내는 것이 아니라 1/12시간 또는 1/16시간만 burst로 보내는 것을 의미하기 때문에 대역폭은 여기서 한번 더 낮아진다.

|  |  |  |
| --- | --- | --- |
| **단계** | **BM12** | **BM16** |
| 2.5GHz Manchester 후 | 1.25Gbps | 1.25Gbps |
| Duty cycle 적용 | ÷12 | ÷16 |
| 평균 line-rate | 104.17Mbps | 78.13Mbps |
| PL4 code rate 0.5 적용 | 약 52.08Mbps | 약 39.06Mbps |
| overhead 제외 payload | 약 48.9Mbps | 약 36.7Mbps |

- - 여기서 주의할 점은 BM12의 104.17Mbps, BM16의 78.13Mbps 같은 숫자는 line-rate 또는 coded rate 관점이고, 실제 payload data rate는 더 낮다는 점이다. burst mode는 빠른 속도를 위한 모드라기보다, **멀고 불리한 링크를 닫기 위해 평균 데이터율을 낮추고 순간 peak power를 높이는 방식**이다.

- - 비유하면 이렇다.

    - 가까운 친구에게는 계속 말해도 잘 들린다.
    - 아주 멀리 있는 친구에게는 계속 작게 말하는 것보다, 짧게 강하게 외치는 편이 낫다.
    - burst mode는 그런 방식이다.

**📌** **ARQ와 latency의 trade-off**

- - ARQ는 Automatic Repeat Request다. 수신자가 frame을 제대로 받으면 ACK를 보내고, 송신자가 ACK를 못 받으면 재전송한다. v3.2.0에서도 ARQ가 정리되어 있고, v4.0에서도 ACK를 받지 못한 frame을 ARQ\_MAX\_RETX 횟수까지 재전송하는 요구가 들어간다.
  - 하지만 ARQ는 공짜가 아니다. 재전송은 신뢰성을 높이는 대신 latency를 늘린다. 특히 위성 간 거리가 길어질수록 왕복 지연이 커지고, ARQ window와 holdoff를 더 크게 잡아야 한다. 그래서 OCT는 항상 **속도, 거리, 신뢰성, latency** 사이에서 균형을 잡아야 한다.

**✅ OCT가 위성에 탑재될 때 필요한 조건**

- - OCT를 위성에 붙인다고 해서 바로 우주 인터넷 노드가 되는 것은 아니다. 위성 자체가 OCT를 제대로 지원할 수 있어야 한다.
  - 필요 조건은 대략 다음과 같다.

|  |  |
| --- | --- |
| **조건** | **설명** |
| **Field of Regard** | OCT가 충분히 넓은 방향을 볼 수 있어야 한다. 태양전지판, 안테나, payload 구조물이 시야를 가리면 안 된다. |
| **정밀 자세제어** | 위성 bus가 상대 위성 방향으로 coarse pointing을 해주고, OCT가 fine pointing을 한다. |
| **낮은 jitter** | reaction wheel, 구조 진동, thermal deformation이 µrad 수준 pointing error로 이어질 수 있다. |
| **전력과 열 관리** | 레이저, detector, modem, control electronics는 전력을 먹고 열을 낸다. |
| **정확한 시간과 궤도 정보** | clock, ephemeris, PVTR 정확도가 acquisition time을 좌우한다. |
| **Router/Switch 연동** | OCT 뒤에는 Ethernet packet을 처리할 router/switch 또는 payload computer가 필요하다. |
| **Link scheduler** | 어느 위성과 언제 연결할지 contact plan이 있어야 한다. |
| **Software update** | v3.2.0은 OCT가 on-orbit reprogrammable해야 하며, protocol과 software/firmware update capability를 가져야 한다고 요구한다. |

- - 즉 OCT는 “위성에 카메라 하나 붙이는 것”이 아니라, 위성의 자세제어, 전력, 열, 데이터 처리, 네트워크 orchestration 전체와 결합되는 시스템이다.

**✅ 왜 Starlink는 여러 개의 OCT를 다는가**

- - Starlink는 좋은 비교 사례다. Starlink의 공개 기술 설명은 각 Starlink 위성이 **3개의 space lasers, 즉 Optical Intersatellite Links**를 가진다고 설명한다. 또 Starlink 2024 progress report 검색 결과에서도 각 위성이 3개의 space lasers를 갖고, 최대 200Gbps급으로 운용된다고 설명된다.
  - 왜 하나가 아니라 세 개일까?
  - OCT 하나는 한 방향 링크를 잡는 데 쓰인다. 하지만 위성 네트워크는 단순한 일대일 연결이 아니다. LEO constellation에서는 보통 다음 연결이 필요하다.

    - 같은 궤도면 앞쪽 위성
    - 같은 궤도면 뒤쪽 위성
    - 인접 궤도면 또는 cross-plane 위성
    - handover 또는 relay 링크
  - OCT가 하나뿐이면 동시에 여러 방향과 연결하기 어렵다. 특히 위성들이 계속 움직이기 때문에 링크가 끊기기 전에 다음 링크를 먼저 잡는 **make-before-break handover**가 중요하다.
  - Muon Space와 Starlink mini laser 발표는 이 점을 잘 보여준다.

    - Muon은 Starlink mini laser가 최대 4,000km 거리에서 25Gbps link speed를 목표로 하고, Starlink의 in-space laser mesh를 통해 위성이 terrestrial PoP까지 연결될 수 있다고 설명한다.
    - 또한 단일 terminal은 handover 시 짧은 interruption이 있을 수 있지만, multi-terminal 구성은 make-before-break handover로 일반적인 LEO 운용에서 99% 이상의 uptime을 가능하게 한다고 설명한다.
  - 즉 여러 OCT를 다는 이유는 단순히 속도를 높이기 위해서만이 아니다. 더 중요한 이유는 **연결을 끊기지 않게 유지하고, 여러 방향으로 mesh network를 만들기 위해서**다.

**✅ OCT에서 앞으로 개선되어야 할 부분**

- - 내가 보는 OCT의 핵심 개선 포인트는 여섯 가지다.

**📌** **Acquisition time 단축**

- - SDA 표준은 100초 이하를 요구하지만, 실제 대규모 LEO mesh network에서는 100초도 길 수 있다. 특히 temporary cross-plane link나 dynamic routing이 많아질수록 acquisition 시간이 곧 network efficiency를 갉아먹는다.
  - 개선 방향은 다음과 같다.

    - 더 정확한 ephemeris와 clock sync
    - 더 좋은 calibration
    - 더 넓은 acquisition sensor FOV
    - 더 빠른 fine steering mirror
    - AI/예측 기반 pointing
    - warm-start 재사용
    - multi-terminal make-before-break handover

**📌** **Jitter와 thermal distortion 저감**

- - OCT는 µrad 수준의 pointing stability가 중요하다. 위성 본체가 조금만 흔들려도 수천 km 밖에서는 큰 오차가 된다. 따라서 위성 bus의 자세 안정성, reaction wheel vibration isolation, optical bench thermal control이 중요해진다.

**📌** **Higher throughput 표준화**

- - SDA v3/v4의 공개 표준은 2.5Gbps급 상호운용 baseline에 가깝다. 하지만 시장은 이미 10Gbps, 25Gbps, 100Gbps, 400Gbps 로드맵을 말하고 있다. 앞으로는 더 넓은 optical bandwidth, WDM, coherent 방식, 더 강한 FEC, 더 정교한 modulation이 필요할 수 있다.
  - 다만 vendor proprietary 방식만 늘어나면 상호운용성이 약해진다. 결국 미래에는 **고속 OCT도 표준화된 방식으로 서로 붙을 수 있느냐**가 중요해진다.

**📌** **Adaptive coding and modulation**

- - 현재 표준은 정해진 rate/encoding 조합을 사용한다. 미래에는 거리, pointing error, SNR, atmospheric fade, background light에 따라 자동으로 rate, FEC, modulation을 바꾸는 adaptive link가 중요해질 가능성이 크다.

**📌** **Optical ground station의 날씨 문제**

- - 위성-위성 링크는 진공에서 이뤄지지만, 위성-지상 링크는 대기와 구름을 통과해야 한다. 구름, 대기 난류, 강수, 낮 시간 배경광은 S2G optical link의 가장 큰 병목이다. 그래서 미래 우주 네트워크는 OCT만 좋아지면 끝나는 것이 아니다.
  - 필요한 것은 다음이다.

    - 여러 optical ground station
    - site diversity
    - weather-aware routing
    - RF backup
    - store-and-forward
    - dynamic path selection

**✅ 쉬운 버전 요약**

- - OCT는 우주에 있는 **레이저 인터넷 포트**다.
  - 초기 버전은 이렇게 말했다.

    - “위성끼리 레이저로 연결하자. 파장과 속도와 오류정정은 이런 방향으로 가자.”
  - v3부터는 이렇게 발전했다.

    - “이제 여러 회사 장비가 서로 붙어야 하니, 레이저를 어떻게 찾고, 어떻게 frame을 만들고, 어떻게 오류를 고치고, 어떻게 Ethernet packet을 실어 보낼지 정하자.”
  - v4는 이렇게 확장했다.

    - “이제 가까운 LEO 위성끼리만이 아니라, 훨씬 먼 거리와 불리한 조건에서도 링크를 닫을 수 있게 하자. 그래서 laser linewidth, center frequency, frame loss, burst mode를 더 엄격히 정하자.”
  - 가장 중요한 acquisition은 이렇게 이해하면 된다.

    - 두 사람이 아주 먼 거리에서 가느다란 레이저 포인터로 서로를 찾아야 한다.
    - 그런데 전화 통화는 안 된다.
    - 그래서 미리 정한 시간표대로 한 명은 나선형으로 빛을 훑고, 다른 한 명은 그 빛을 찾는다.
    - 찾으면 역할을 바꾸고, 점점 더 정확히 맞춘다.
    - 빛이 한 번 보인다고 끝이 아니라, 계속 안정적으로 따라갈 수 있어야 진짜 링크가 열린다.
    - 그래서 OCT의 진짜 난제는 단순히 “몇 Gbps냐”가 아니다.
  - 진짜 핵심은 다음이다.

    - **얼마나 빨리 찾는가.**
    - **얼마나 정확히 조준하는가.**
    - **얼마나 오래 안정적으로 tracking하는가.**
    - **handover 때 끊기지 않는가.**
    - **여러 OCT와 router/switch가 하나의 우주 mesh network처럼 움직이는가.**
  - 결국 OCT는 단순한 통신 단말이 아니라, 미래 우주 데이터 네트워크의 가장 중요한 물리 계층이다.
  - 그리고 그 네트워크의 경쟁력은 단말 속도 하나가 아니라 **acquisition, pointing, timing, routing, orchestration이 얼마나 잘 결합되는지**에서 결정될 가능성이 크다.
