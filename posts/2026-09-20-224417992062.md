**✅ 10,000개의 물리 큐비트로 800개의 논리 큐비트를 만들 수 있을까?**

[![](https://mblogthumb-phinf.pstatic.net/MjAyNjA5MjBfMTQx/MDAxNzg5OTAyNzQxOTY4.MagQqm19vtqgBCKiqZyfFJfpTRRrtNFeUjA6MKZ7MUYg.zgevRIeJaymVZduKer7RnYuga2DbZFMoPF6jEIUUAVIg.PNG/image.png?type=w800)](#)

- - IonQ의 공식 로드맵에 따르면 2027년 Superion 10K의 목표는 물리 큐비트 10,000개와 논리 큐비트 800개다.
  - 동시에 논리 오류율(Logical Error Rate)은 10−7 미만을 목표로 하고 있다.
  - 단순히 계산하면 논리 큐비트 1개당 평균 12.5개의 물리 큐비트를 사용하는 셈이다.
  - 하지만 실제 Fault-Tolerant Quantum Computer(FTQC)에서는 논리 큐비트를 저장하는 Memory Block 외에도 Magic Factory, Cat Factory, Ancilla, Beacon, Reservoir 및 이온 운송을 위한 추가적인 물리 큐비트가 필요하다.
  - 따라서 단순히 10,000개를 12.5개씩 나누는 것으로 실제 시스템 구성을 설명할 수는 없다.
  - 그렇다면 IonQ는 어떻게 10,000개의 물리 큐비트로 800개의 논리 큐비트를 구현할 수 있을까?
  - 현재 공개된 QEC 코드를 기준으로 필요한 물리 자원을 계산하고, 새로운 코드가 등장할 가능성까지 살펴보고자 한다.

**✅ 1. 현재 IonQ가 공개한 Q70과 Q102**

**📌 Q70과 Q102의 코드 파라미터**

- - IonQ는 2026년 발표한 Walking Cat Architecture 논문에서 Q70과 Q102라는 두 가지 QEC 코드를 소개했다.
  - 두 코드는 IonQ 연구진이 기존 BB(Bivariate Bicycle) 및 GB(Generalized Bicycle) 코드 계열을 기반으로 설계한 새로운 코드다.
  - Q70은 빠른 논리 연산을 지원하는 구조이며, Q102는 하나의 Memory Block에 많은 논리 큐비트를 저장하는 고밀도 구조다.
  - 논문에서는 Q70의 빠른 Clifford 연산과 Q102의 높은 논리 큐비트 저장 밀도를 각각 다른 아키텍처 구성에 활용한다.

|  |  |  |
| --- | --- | --- |
| **구분** | **Q70** | **Q102** |
| 코드 계열 | BB | GB |
| 코드 파라미터 | [[70,6,9]] | [[102,22,9]] |
| Data Qubits | 70 | 102 |
| Logical Qubits | 6 | 22 |
| Code Distance | 9 | 9 |
| Encoding Rate | 8.6% | 21.6% |

- - 여기서 [[n,k,d]]는 물리 데이터 큐비트 수(n), 논리 큐비트 수(k), 코드 거리(d)를 의미한다.
  - Q102는 Q70보다 물리 데이터 큐비트를 약 46% 더 사용하지만, 논리 큐비트는 약 3.67배 많이 인코딩한다.
  - 두 코드의 Code Distance는 동일하게 9다.
  - 그러나 Q102가 더 많은 논리 큐비트를 저장한다고 해서 모든 논리 연산에서 Q70보다 더 빠르거나 효율적이라는 뜻은 아니다.

**📌 Q54는 Magic Factory로 사용한다**

- - Walking Cat 논문에서는 Q54 [[54,2,10]] 코드를 이용한 CH2 Magic Factory도 제시한다.
  - Magic Factory는 일반적인 데이터 저장용 Memory Block과 달리, T Gate 등 비클리퍼드 논리 연산에 필요한 Magic State를 생산하는 역할을 한다.
  - 따라서 10K의 실제 논리 큐비트 수를 추정하려면 Q70과 Q102 같은 Memory Block뿐 아니라 Magic Factory에 배정되는 자원도 고려해야 한다.

**✅ 2. 현재 Q70과 Q102를 이용해 10K를 구성한다면?**

**📌 10,000 Physical Qubits에서의 가상 구성**

- - 현재 공개된 Q70과 Q102보다 효율적인 새로운 QEC 코드가 아직 개발되지 않았다고 가정한다.
  - Memory Block은 Q70과 Q102를 사용하고 Magic Factory에는 Q54 기반 CH2를 사용한다.
  - Magic Factory 4개를 배치하고, Cat Factory, Reservoir 및 기타 보조 자원을 고려하여 가상 시스템을 구성한다.
  - 이때 논리 큐비트의 저장 밀도와 논리 연산 능력을 함께 고려한 혼합 구성도 생각할 수 있다.

| Q70 전용 | 30개 | 180개 |
| Q70 + Q102 혼합 | 22개 | 388개 |
| Q102 전용 | 20개 | 440개 |

- - 위 수치는 실제 Superion 10K의 설계도가 아니라, 앞서 가정한 Memory Block과 Magic Factory 배분을 바탕으로 계산한 개략적인 추정치다.
  - 특히 Cat Factory의 공유 방식과 Transport Qubits의 필요량은 실제 배치에 따라 달라지므로, 위 수치를 현재 코드의 확정적인 최대 용량으로 해석해서는 안 된다.

**✅ 3. 그렇다면 800 Logical Qubits를 구현하려면?**

**📌 기존 Q102의 Encoding Rate를 역산해 보자**

- - 기존 Q102는 102개의 물리 데이터 큐비트로 22개의 논리 큐비트를 인코딩한다.
  - Memory용 Cat Factory까지 포함하면 블록당 약 376개의 물리 큐비트가 필요하다.
  - 기존 블록 크기와 앞서 가정한 보조 자원 배분을 그대로 유지한다면 10K에 Q102 Memory Block 약 20개를 배치하는 구성을 생각할 수 있다.
  - 이 경우 800개의 논리 큐비트를 만들기 위해 각 Memory Block이 인코딩해야 하는 논리 큐비트 수는 다음과 같다.

- - 따라서 기존 Q102의 물리 데이터 큐비트 수를 유지하면서 블록당 논리 큐비트를 22개에서 40개로 증가시킬 수 있다면, 20개의 Memory Block으로 800개의 논리 큐비트를 인코딩할 수 있다.

**📌 필요한 Encoding Rate**

- - 기존 Q102의 Encoding Rate:

- - 가상의 새로운 코드에서 필요한 Encoding Rate:

|  |  |  |
| --- | --- | --- |
| **구분** | **기존 Q102** | **역산한 목표 코드** |
| Data Qubits | 102 | 102 |

| Encoding Rate | 21.6% | 39.2% |

- - 즉, 기존 Q102와 동일한 102개의 물리 데이터 큐비트에서 논리 큐비트 수를 약 1.82배 늘리는 코드가 필요하다는 계산이 나온다.
  - 다만 이것은 기존 블록 크기와 보조 자원 배분을 그대로 유지했을 때의 역산 결과이며, 800개를 달성하는 유일한 방법은 아니다.
  - 실제로는 새로운 코드의 등장뿐 아니라 Magic Factory, Cat Factory 및 기타 보조 자원의 효율 개선도 논리 큐비트 수를 늘리는 데 기여할 수 있다.

**✅ 4. BB5와 BB6에서 새로운 가능성을 찾아볼 수 있다**

**📌 동일한 물리 큐비트 수에서 논리 큐비트를 더 많이 만들 수 있다**

- - IonQ 연구진인 Min Ye와 Nicolas Delfosse는 2025년 논문 Quantum Error Correction for Long Chains of Trapped Ions에서 BB5라는 새로운 QEC 코드 계열을 제안했다.
  - BB5는 Stabilizer의 Check Weight가 5인 코드이며, 기존 BB 코드 계열인 BB6는 Check Weight가 6이다.
  - 두 코드 계열에서는 동일한 30개의 물리 데이터 큐비트를 사용하면서도 서로 다른 논리 큐비트 수와 Code Distance를 가진 코드를 구성할 수 있다.

|  |  |  |
| --- | --- | --- |
| **구분** | **BB5** | **BB6** |
| 코드 파라미터 | [[30,4,5]] | [[30,8,4]] |
| Data Qubits | 30 | 30 |
| Logical Qubits | 4 | 8 |
| Code Distance | 5 | 4 |
| Encoding Rate | 13.3% | 26.7% |

- - BB5와 BB6는 서로 다른 코드 계열이므로 BB5를 단순히 업그레이드하여 BB6를 만들었다는 의미는 아니다.
  - 그러나 동일한 물리 데이터 큐비트 수에서 논리 큐비트 수와 Code Distance 사이의 균형을 다르게 설계할 수 있다는 사실을 보여준다.
  - BB5와 BB6의 사례에서는 Code Distance가 5인 구성보다 Code Distance가 4인 구성에서 논리 큐비트 수가 두 배 많다.

**📌 그렇다면 Q102에도 같은 접근이 가능하지 않을까?**

- - 현재 Q102는 [[102,22,9]] 코드다.
  - 새로운 GB 계열 코드가 개발된다면 동일한 102개의 물리 데이터 큐비트에서 논리 큐비트 수를 늘리는 대신 Code Distance를 낮추는 방법을 생각할 수 있다.
  - 예를 들어 [[102,40,7]]이라는 가상의 코드가 만들어진다면 102개의 물리 데이터 큐비트로 40개의 논리 큐비트를 인코딩할 수 있다.

|  |  |  |
| --- | --- | --- |
| **항목** | **기존 Q102** | **가상의 새로운 코드** |
| 코드 파라미터 | [[102,22,9]] | [[102,40,7]] |
| Data Qubits | 102 | 102 |
| Logical Qubits | 22 | 40 |
| Code Distance | 9 | 7 |
| Encoding Rate | 21.6% | 39.2% |
| 임의 오류 정정 보장 | 최대 4개 | 최대 3개 |

- - 이 경우 20개의 Memory Block으로 다음과 같이 800개의 논리 큐비트를 인코딩할 수 있다.

- - 하지만 [[102,40,7]]은 목표 논리 큐비트 수를 바탕으로 역산한 가상의 코드 파라미터다.
  - 이러한 코드가 실제로 존재한다거나 IonQ가 개발 중이라고 확인된 것은 아니다.
  - 또한 기존 Q102와 동일한 물리 데이터 큐비트 수를 사용하더라도 새로운 코드의 Syndrome Extraction 회로, Cat Factory 요구량 및 논리 연산 성능은 달라질 수 있다.

**✅ 5. Code Distance가 낮아져도 괜찮을까?**

**📌 Code Distance와 오류 정정 능력의 관계**

- - Code Distance는 QEC 코드가 물리 오류로부터 논리 정보를 얼마나 보호할 수 있는지를 나타내는 중요한 지표다.
  - Code Distance가 dd
  - d일 때 보장되는 임의 물리 큐비트 오류 정정 개수는 다음과 같다.

|  |  |
| --- | --- |
| **Code Distance** | **보장되는 임의 오류 정정 개수** |
| d=3 | 1개 |
| d=4 | 1개 |
| d=5 | 2개 |
| d=7 | 3개 |
| d=9 | 4개 |

- - 예를 들어 Distance 5인 BB5는 오류 위치를 모르는 상태에서도 최대 2개의 임의 물리 큐비트 오류를 정정하도록 보장한다.
  - 오류가 3개 이상 발생하면 더 이상 모든 오류 패턴에 대한 정정이 보장되지 않지만, 반드시 논리 오류가 발생하는 것은 아니다.
  - 마찬가지로 Q102의 Code Distance를 9에서 7로 낮춘다면 임의 물리 오류에 대한 정정 보장 범위가 4개에서 3개로 감소한다.

**📌 Code Distance가 낮아지면 논리 오류율도 반드시 높아질까?**

- - 일반적으로 다른 조건이 동일하다면 Code Distance가 높은 코드가 더 많은 오류를 정정할 수 있다.
  - 그러나 실제 Logical Error Rate는 Code Distance만으로 결정되지 않는다.
  - 물리 게이트 충실도, 오류의 종류와 상관관계, Syndrome Extraction 회로, 디코더 성능 등이 함께 영향을 미친다.
  - 따라서 물리 오류율이 개선되고 오류 정정 회로와 디코더가 최적화된다면, 이전보다 낮은 Code Distance에서도 특정 논리 오류율 목표를 만족할 가능성이 있다.

**✅ 6. IonQ의 로드맵에서 필요한 Code Distance를 역산할 수 있을까?**

**📌 2027년의 핵심 조건은 Logical Error Rate 10****-7****이다**

- - 첨부한 IonQ 로드맵에 따르면 2027년 목표는 다음과 같다.

|  |  |
| --- | --- |
| **항목** | **2027년 목표** |
| Physical Qubits | 10,000 |
| Logical Qubits | 800 |
| Logical Error Rate | 10⁻⁷ 미만 |

- - 여기에 물리 게이트 충실도 99.99%를 가정하면, 이를 오류 확률로 환산한 값은 p=10−4가 된다.
  - 다만 물리 게이트 오류율이 곧바로 한 번의 오류 정정 사이클에서 개별 데이터 큐비트가 겪는 전체 오류 확률을 의미하지는 않는다.
  - 따라서 아래 계산은 실제 하드웨어에 대한 예측이 아니라, 각 데이터 큐비트에서 독립적으로 10−4의 오류가 발생하는 이상화된 모델이다.

**📌 102개의 물리 데이터 큐비트에서 오류가 발생할 확률**

- - 각 물리 데이터 큐비트의 오류 확률이 10−4라고 가정한다.
  - Code Distance에 따라 정정 보장 범위를 초과하는 물리 오류가 발생할 확률을 계산하면 다음과 같다.

- - 여기서 r은 오류가 발생한 물리 데이터 큐비트의 개수다.
  - 이를 이용하여 정정 보장 범위를 초과하는 오류가 발생할 확률을 계산한다.

|  |  |  |
| --- | --- | --- |
| **Code Distance** | **정정 보장 개수** | **정정 보장 범위 초과 확률** |
| d=3 | 1개 | 약 5.1 × 10⁻⁵ |
| d=5 | 2개 | 약 1.7 × 10⁻⁷ |
| d=7 | 3개 | 약 4.2 × 10⁻¹⁰ |
| d=9 | 4개 | 약 8.3 × 10⁻¹³ |

- - 이 계산에서 d=5는 정정 보장 범위를 초과하는 오류의 발생 확률이 로드맵의 10-7보다 약간 높다.
  - 반면 d=7은 약 4.2×10−10으로 계산되어 상당한 여유가 있다.
  - 따라서 독립적인 데이터 큐비트 오류만 고려한 이번 모델에서는 d=7을 목표 논리 오류율과 비교해 볼 수 있다.
  - 그러나 위 수치는 실제 Logical Error Rate가 아니라 정정 보장 범위를 초과하는 물리 오류의 발생 확률이다.
  - 실제 QEC 사이클의 게이트 오류, 측정 오류, 오류 전파 및 디코더 성능을 포함하면 결과는 달라질 수 있다.
  - 특히 IonQ의 로드맵에 표기된 오류율을 개별 논리 큐비트당, QEC 사이클당 또는 전체 논리 연산당 오류율 중 어떤 기준으로 적용할 것인지도 확인해야 한다.

**📌 그렇다면 [[102,40,7]]이 800개의 논리 큐비트를 구현할 수 있을까?**

- - 논리 큐비트 수를 기준으로 보면 20개의 Memory Block으로 800개의 논리 큐비트를 인코딩할 수 있다.
  - 이번 단순 오류 모델에서도 d=7은 10-7 목표를 검토할 만한 코드 거리다.
  - 따라서 [[102,40,7]]은 800개의 논리 큐비트 수량 목표와 오류율 목표를 함께 분석할 수 있는 하나의 가상 설계 기준점이 된다.
  - 그러나 이것만으로 새로운 코드의 존재나 실제 FTQC 시스템에서의 오류율 목표 달성이 증명되지는 않는다.

**✅ 7. 2029년 이후의 로드맵은 또 다른 힌트를 제공한다**

**📌 논리 큐비트당 물리 자원 사용량이 두 배로 증가한다**

- - IonQ의 로드맵에서 2027년과 2028년에는 논리 큐비트 1개당 평균 12.5개의 물리 큐비트가 사용된다.
  - 반면 2029년과 2030년에는 논리 큐비트 1개당 평균 25개의 물리 큐비트가 사용된다.
  - 동시에 논리 오류율 목표는 10−7미만에서 10−12 미만으로 강화된다.

|  |  |  |  |  |
| --- | --- | --- | --- | --- |
| **연도** | **Physical Qubits** | **Logical Qubits** | **Physical / Logical** | **Logical Error Rate** |
| 2027 | 10,000 | 800 | 12.5 | <10⁻⁷ |
| 2028 | 20,000 | 1,600 | 12.5 | <10⁻⁷ |
| 2029 | 200,000 | 8,000 | 25 | <10⁻¹² |
| 2030 | 2,000,000 | 80,000 | 25 | <10⁻¹² |

- - 이는 2029년 이후 단순히 논리 큐비트 수를 늘리는 것뿐 아니라 더 강력한 오류 보호에 추가 자원을 배분하는 설계와도 부합한다.
  - 예를 들어 Code Distance를 높이거나, 오류 정정에 더 많은 보조 큐비트를 사용하거나, Magic State의 품질을 개선하는 방법을 생각할 수 있다.
  - 다만 논리 큐비트당 물리 자원이 두 배로 증가한다는 사실만으로 IonQ가 실제로 Code Distance를 높인다고 단정할 수는 없다.
  - 실제 변화는 새로운 QEC 코드의 도입, 시스템 구조 개선, 오류율 목표에 따른 자원 재배분 등이 복합적으로 작용한 결과일 수 있다.

**✅ 결론 — Superion 10K의 800 Logical Qubits, 새로운 QEC 코드의 등장을 기대한다**

- - 지금까지의 계산을 통해 확인한 것은 기존 Q70과 Q102의 자원 배분을 그대로 확장하는 것만으로는 Superion 10K의 800 Logical Qubits라는 목표를 설명하기 어렵다는 점이다.
  - 그러나 이것이 기존 QEC 코드의 한계를 의미하거나 IonQ가 반드시 새로운 코드를 개발해야만 목표를 달성할 수 있다는 뜻은 아니다.
  - Magic Factory, Cat Factory, Reservoir 및 Transport Qubits의 자원 배분을 최적화하는 방법도 있으며, 기존 Q102보다 높은 Encoding Rate를 제공하는 새로운 QEC 코드가 등장할 가능성도 있다.
  - 특히 BB5 [[30,4,5]]와 BB6 [[30,8,4]]의 사례처럼 동일한 물리 데이터 큐비트 수에서 논리 큐비트 수와 Code Distance의 균형을 다르게 설계할 수 있다는 점은 흥미롭다.
  - 이러한 관점에서 기존 Q102 [[102,22,9]]를 출발점으로 삼아, 가상의 [[102,40,7]]과 같은 새로운 코드가 등장할 수 있을지 생각해 볼 수 있다.
  - 물론 102개의 물리 데이터 큐비트로 40개의 논리 큐비트를 인코딩하면서 Code Distance 7을 유지하는 코드가 실제로 존재하는지, 그리고 목표 Logical Error Rate를 만족하는지는 아직 검증되지 않았다.
  - IonQ의 Walking Cat Architecture는 다양한 QEC 코드와 자원 배분 방식을 지원하도록 설계되어 있으며, 응용 분야와 오류율 요구 조건에 따라 서로 다른 구성을 사용할 수 있다.
  - 개인적으로 앞으로 가장 기대하는 것은 IonQ가 새롭게 공개할 QEC 코드다.

    - Q70과 Q102보다 높은 Encoding Rate를 달성하면서도 충분한 Code Distance와 낮은 Logical Error Rate를 유지하는 새로운 코드가 등장한다면, Superion 10K의 800 Logical Qubits라는 로드맵 목표를 이해하는 데 중요한 단서가 될 것이다.
    - 새로운 코드의 개발뿐 아니라 이를 실제 Walking Cat Architecture에 적용했을 때의 Syndrome Extraction 성능, Magic Factory와의 호환성, 실제 물리 큐비트 사용량 및 논리 오류율까지 공개되기를 기대한다.
  - 앞으로 IonQ가 발표할 새로운 QEC 코드가 800 Logical Qubits라는 숫자의 의미를 얼마나 구체적으로 설명해 줄지 지켜보고자 한다.
