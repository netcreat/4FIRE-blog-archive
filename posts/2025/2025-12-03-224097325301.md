# IonQ, TorchQuantumDistributed 발표

> IonQ의 Martin Roetteler 박사가 QML을 위한 라이브러리를 발표했는데, 어떤 기능이 있고, 이 발표가 무엇을 의미하는지 살펴보겠다.

[TorchQuantumDistributed](https://arxiv.org/html/2511.19291v1)

**📌 연구 목적**

IonQ 팀은 **대규모 양자 회로 시뮬레이션**과 **양자 머신러닝(QML)** 연구를 가능하게 하기 위해, PyTorch 기반의 **TorchQuantumDistributed(tqd)** 라이브러리를 개발했다.

tqd는 **statevector 시뮬레이션을 여러 GPU/가속기에서 분산 처리**할 수 있어 기존 프레임워크의 확장 한계를 해결한다.

**🔑 주요 특징**

|  |  |
| --- | --- |
| **항목** | **설명** |
| **분산 statevector 시뮬레이션** | 복수의 GPU에 상태벡터를 나누어 저장(sharding) |
| **Accelerator-agnostic** | NVIDIA CUDA, AMD MI250X 등 PyTorch가 지원하는 어떤 하드웨어도 사용 가능 |
| **Differentiable** | 미분 가능하도록 설계되어 QML 학습 최적화에 활용 가능 |
| **Shot noise 모델링 제공** | 정확 multinomial sampling + differentiable Gaussian approximation |
| **Invertible computation** | unitary 역연산을 활용해 메모리 사용 절감 |

**🚧 기존 문제점 & tqd의 개선점**

|  |  |
| --- | --- |
| **기존 프레임워크 문제** | **tqd 해결 방식** |
| 단일 GPU 한계로 큰 회로 불가 | statevector를 여러 GPU에 분산 저장 |
| 샘플링 시 미분 불가능 | Gaussian 근사로 differentiable sampling 지원 |
| 백엔드 하드웨어 종속성 | PyTorch 기반으로 범용 지원 |
| 고차원 텐서 연산 속도 저하 | qubit grouping + MoveDim 최적화 구조 |

**⚙️ 구현 핵심**

- - **Statevector Sharding 방식**

    - 텐서의 일부 dimension을 GPU 개수에 맞게 분할하여 저장
    - qubit 이동과 regrouping은 reshape/permute 기반
    - 최소 2개의 unsharded qubit 유지

**📊 실험 결과 (Profiling)**

- - AMD MI250X GPU 1~1024개 사용
  - 18~28 qubit ansatz 회로 benchmark 수행
  - Strong & Weak scaling 모두 **전반적으로 이상적인 power-law scaling**
  - 통신 비용(NCCL all-to-all)은 증가하지만 성능 저하 최소화

**💡 Shot noise 처리 방법**

|  |  |  |
| --- | --- | --- |
| **방식** | **장점** | **단점** |
| **정확 multinomial sampling** | 실제 양자 measurement와 동일 | 미분 불가, 속도 느림 |
| **Gaussian 근사 (reparameterization)** | 빠르고 미분 가능 | 근사 오차 존재 |

**📦 결론**

- - tqd는

    - **확장 가능한 하드웨어 가속 분산 시뮬레이터**
    - **QML 학습에 적합한 미분 가능한 framework**
    - **대규모 ansatz 연구 가능**
  - 앞으로의 과제로는

    - Circuit cutting / knitting 기술 병합
    - GPU 메모리 및 통신 최적화 추가 검증

**1️⃣ PyTorch**

    - 연구자 + 산업 전반에서 **표준**

  - **특징**

    - TPU/CPU/GPU 상에서 **연산 속도·메모리·전력 효율 극대화**
    - 딥러닝 모델의 inference & training 성능을 크게 개선

| 하드웨어 | 주로 GPU | GPU + TPU | TPU + GPU + CPU |

**⚙️ 구현 핵심**

[![](https://arxiv.org/html/2511.19291v1/img/TQD_Tensor.png)](#)

- - 위 그림은 아홉 개의 큐비트로 이루어진 상태벡터(statevector)를 나타내는 TQD 분산 텐서의 예시적인 차원 배치도이다.

    - Single Qubit (2) - 1 큐비트
    - Three Grouped (8) - 3 큐비트
    - Two Grouped (4) - 2큐비트
    - Single Qubit (2) - 1 큐비트
    - Shard #1 (2) - 1 큐비트
    - Shard #1 (2) - 1 큐비트
  - 이 예에서는 두 개의 큐비트가 샤딩(sharding)되어 있다.

    - Sharding은 statevector를 여러 GPU에 나누어 저장하는 것을 의미함.
    - Statevector는 큐비트 (N)를 표현하기 위해서 복소수를 사용하는데, 2N 개 형태로 지수 증가가 일어나기 때문에,
    - 여러 GPU에 분산해서 저장을 하게 된다.
  - TQD는 항상 **첫 번째 차원과 마지막 차원**을 예약해 두는데,

    - 첫 번째 차원: **batching(배치 처리용)**

      - **딥러닝처럼 여러 개를 한꺼번에 처리하는 용도**
      - **양자 상태 자체와는 상관 없는 “외부적인” 차원**
    - 마지막 차원: **복소수의 실수부와 허수부 저장용(real/imag)**

      - **양자 statevector는 복소수 : a = x + i y**
      - **PyTorch 텐서는 복소수를 직접 다루기 불편하니까, 마지막 차원을 복소수 저장 전용으로 따로 둠**
      - **그래서 마지막 차원의 크기는 항상 2(실수, 허수)**
      - **그림에서는 Complex Dim (2)**
  - 샤딩된 큐비트는 마지막 차원(real/imag 직전 차원)들에 대응하며,

    - PyTorch의 분산 텐서 구조가 뒤쪽 차원을 샤딩하는 데 최적화되어 있기 때문에, 텐서의 뒤쪽(마지막 근처)에 둠
  - 최소 두 개의 **샤딩되지 않은(unsharded)** 큐비트 차원은 항상 묶이지 않은 상태(ungrouped)로 유지된다.

    - 게이트 연산을 하려면 큐비트 차원을 **MoveDim**으로 앞으로 옮겨야 하는데, 이미 grouping되거나 sharding된 차원은 다루기 어렵기 때문에 최소 2개의 큐비트는 single qubit 차원으로 보존함
    - 그림의 첫번째 "Single Qubit"과 중간 "Single Qubit"이 그런 목적임.

**📊 실험 결과 (Profiling)**

[![](https://arxiv.org/html/2511.19291v1/img/scaling.png)](#)

- - **Strong scaling**: 동일한 문제(24qubit)를 GPU 몇 개로 돌리면 속도가 얼마나 빨라지나?

    - GPU를 많이 붙일수록 속도는 빨라지고, GPU당 메모리 사용은 줄며, 통신 비용도 관리 가능한 수준이다.
    - → 즉, TQD는 대규모 GPU 클러스터에서 잘 스케일된다.
  - **Weak scaling**: GPU가 늘어날수록 문제 크기도 같이 늘리면, 성능이 얼마나 유지되나?

    - GPU 개수를 늘리면서 회로 크기도 늘렸는데,
    - 통신/메모리/실행 시간이 모두 “정상적으로 증가”하며 폭발하지 않았다.
    - → TQD는 더 큰 회로로 확장해도 성능이 무너지지 않는다.

**✅****QML에서도 GPU가 또 필요해?**

**1. Statevector 시뮬레이션 비용이 엄청나게 큼**

- - q개의 qubit을 시뮬레이션하려면 2^q 개의 복소수 배열을 저장해야 한다.

|  |  |  |
| --- | --- | --- |
| **Qubit 수** | **Statevector 크기** | **메모리 요구량** |
| 30 | 2^30 ≈ 1B amplitudes | ~16GB |
| 40 | 2^40 ≈ 1T amplitudes | ~16TB |
| 50 | 2^50 ≈ 1P amplitudes | ~1PB |

- - 이 계산을 CPU로 하면 **너무 느리고 불가능함**.
  - 그래서 GPU 가속이 필요하고, 여러 GPU로 **분산 메모리**가 필요한 것.

**2. QML은 학습(gradient, optimization)이 필요**

- - QML 모델은 보통 아래 구조로 되어 있다:

    - 입력 → 양자 회로 → 측정 → Loss → Gradient → 최적화
  - 즉, **딥러닝과 비슷하게 backpropagation 연산이 필요**함.

    - Gradient 계산은 행렬곱, 텐서곱 연산 → GPU가 빠름
    - 대규모 미분 가능 시뮬레이션 → GPU로 병렬화
  - 그래서 PyTorch 기반(tqd)이 등장한 것.

**3. 실제 QPU는 access latency가 크고 비용이 비쌈**

|  |  |  |
| --- | --- | --- |
| **항목** | **QPU** | **Simulator(GPU)** |
| 실행 시간 | 밀리초~초 | 나노초~마이크로초 |
| 비용 | Shots당 과금 | 무료 / 정액제 |
| 안정성 | 잡음 있음 | 완전히 통제 |
| 디버깅 | 어려움 | 쉬움 |

- - 연구자는 아래 워크플로우로 학습함:
  - GPU 기반 시뮬레이터에서 모델 설계 및 학습 ↓ QPU에서 실제 inference 또는 benchmarking

**4. 샷 노이즈 모델링도 GPU에서 시뮬레이션**

- - 실제 QPU는 measurement shot noise가 있음.
  - 이를 반영한 **multinomial 샘플링 + reparameterization** 계산 → GPU가 빠름.

> ***QML은 실제 양자컴퓨터에서 실행될 ML 알고리즘을 연구하는 과정이고,***
>
> ***현재는 구동의 대부분이 GPU 기반 시뮬레이터에서 이루어지기 때문에 GPU가 필수적이다.***

---

> 그럼 QPU의 성능이 충분히 올라가면, QPU는 필요 없나?
>
> 아니다. 여전히 필요하다.

**🔥 왜 QPU가 커져도 PyTorch/QML 프레임워크가 계속 필요한가**

- - 미래의 대규모 QPU 시대(FTQC, Fault-Tolerant Quantum Computing)에서도 여전히 필요하다고 보는 핵심 이유는 다음과 같다.

**1️⃣ QPU는 계산 장치일 뿐, 모델링/학습 플랫폼은 아니기 때문**

- - QPU가 아무리 커져도 **Gradient Descent, Optimization Loop, Data Loader, Autograd** 같은 기능을 제공하지는 않음.
  - 예:

    - 입력 데이터 → 양자 모델 → 측정 → Loss → Gradient → Weight Update
  - 이 전체 과정의 orchestration은 여전히 **PyTorch / TensorFlow / JAX** 같은 클래식 ML 스택이 담당.
  - QPU는 양자 회로 실행 + 측정 (Forward) 부분을 담당

**2️⃣ 하이브리드 구조는 앞으로도 필수**

- - 실제 QML 연구 방향은 **Hybrid QPU + GPU/CPU** 구조.
  - 예:

    - VQE, QAOA, QML classifier, QNN
    - Loss 계산 & optimizer는 classical side가 수행
    - 회로 실행은 QPU가 수행
  - 즉, PyTorch는 **운영 체계**이고 QPU는 **연산 엔진**이 됨.

**3️⃣ 대규모 QPU에서도 시뮬레이터는 여전히 필요**

- - 앞으로도 시뮬레이터는 사라지지 않음:

|  |  |
| --- | --- |
| **이유** | **설명** |
| 디버깅 | 하드웨어 디버깅 불가능 |
| 테스트 | 회로 최적화, 파라미터 초기화, 알고리즘 튜닝 |
| 빠른 prototyping | QPU queue 기다릴 필요 없음 |
| 비용 | QPU 사용 비용은 매우 비쌈 |

- - Simulator = 연구 및 개발용 QPU = 실제 운영 및 프로덕션용 inference

**4️⃣ Differentiable Programming은 계속 classical ML 스택에서**

- - QPU는 자동 미분, Optimizer, Batch 처리, DDP, Model parallelism 등을 지원하지 않음.
  - 이 기능들이 필요한 이유:

    - Training → gradient 계산 반복
    - ML workflow와 연결 (데이터 파이프라인)
    - Multi-QPU orchestration
    - classical-quantum 코드 통합
  - 그래서 PyTorch-기반 quantum frameworks는 계속 확장될 가능성이 큼.

---

**🚀 QML이 기존 ML 대비 가지는 핵심 장점**

**1️⃣ 고차원 힐베르트 공간 표현 능력**

- - n개의 qubit → **2****n** **차원 Hilbert space**
  - 즉, 50 qubit만 있어도:

    - 250 ≈ 1 quadrillion 차원 표현 가능
  - 이는 classical ML로는 **표현 불가능한 feature space**를 자연스럽게 활용할 수 있다는 의미.
  - 예시:

    - 커널 기반 학습에서 feature space mapping을 지수급으로 확장 가능
    - 복잡한 패턴, 상관관계를 압축해 표현 가능

**2️⃣ 양자 중첩·얽힘을 통한 병렬 연산 효과**

- - Quantum superposition & entanglement을 이용하면 하나의 회로에서 **여러 상태를 동시에 계산**할 수 있음.
  - 이는 다음 문제들에서 구조적으로 유리:

    - 조합 폭발 최적화 (routing, scheduling, 금융 리스크)
    - 양자 화학 시뮬레이션 (분자 에너지 계산)
    - QAOA 기반 그래프 문제 (최단 경로, 최대 컷)

**3️⃣ 특정 분배 형태 / 복잡한 확률 모델링에 강함**

- - Probability amplitude를 직접 조작하는 계산 구조는 classical ML이 근본적으로 다루기 어려운 분포를 처리할 수 있음.
  - 예: Variational Quantum Circuits

    - |ψ(θ)⟩ → Measurement → Probability Distribution
  - → 확률 기반 학습 / 생성 모델 / anomaly detection에 유리

**4️⃣ 양자 화학·재료 시뮬레이션에서 절대적 우위**

- - Chemistry Hamiltonian을 직접 시뮬레이션하면 classical보다 **지수급으로 효율적**.

    - 신약 개발
    - 신소재
    - 배터리, 촉매, 에너지 모델링

> ***Classical ML이 못하는 영역을 QML이 열어줌***

**5️⃣ 학습 파라미터 수 절감 가능**

- - 양자 회로는 parameter 효율적 (compact).
  - 예:

    - classical NN 수백만~수억 파라미터 필요
    - quantum circuit은 수백 개 parameter로 same expressivity 가능 (이론적 연구 다수)

**6️⃣ Hybrid(QPU + GPU) 구조에서 강력한 synergy**

|  |  |
| --- | --- |
| **Classical ML** | **QML** |
| pattern recognition, inference | combinatorial search, optimization, simulation |
| 데이터 기반 | 물리 기반 |
| brute-force parameter search | structure-driven 공간 탐색 가능 |

- - 둘을 결합하면:
  - Quantum planning → Classical evaluation & simulation → Feedback → Quantum update

> ***QML은 고차원 상태공간, 양자 얽힘, 확률 진폭 조작을 통해 classical ML이 접근하기 어려운 문제(최적화, 시뮬레이션, 복잡 분포)를 근본적으로 더 효율적으로 해결할 수 있는 잠재력을 가진다.***

**✅PyTorch 기반의 TorchQuantumDistributed(tqd) 라이브러리의 장점**

**🎯tqd는 IonQ 전용인가?**

- - **accelerator-agnostic** differentiable quantum state vector simulation”
  - PyTorch가 돌아가는 환경이면
  - → NVIDIA, AMD, CPU, 어떤 클라우드든 상관없이 사용 가능

> ***“IonQ가 만든, IonQ 전용 도구”가 아니라***
>
> ***“IonQ가 만든, 누구나 자기 GPU 위에서 돌릴 수 있는 오픈 소스 시뮬레이터”*********

**🎯 IonQ가 tqd(시뮬레이터용 QML 라이브러리)를 공개한 핵심 이유**

- - **1️⃣ QML 연구자 & 개발자 커뮤니티를 IonQ 생태계로 끌어오기**

    - 현재 QML 연구자들은 대부분:

      - PyTorch / JAX 기반의 ML 연구자들
      - GPU 시뮬레이터를 사용해 학습 및 개발
      - 아직 QPU를 직접 쓰지 않음
    - 즉, **시장 대부분이 시뮬레이터 단계에서 싸우고 있음**

      - → 이 단계에서 **개발자 기반을 확보하는 게 가장 중요**
    - tqd는 PyTorch 기반이기 때문에:

      - 기존 DL 연구자들이 진입장벽 없이 QML로 넘어올 수 있음
    - → **생태계 리더십 확보 = 미래 QPU 고객 확보**
  - **2️⃣ 대규모 QML 연구는 현재 QPU로 불가능 → 시뮬레이터가 필수**

    - QPU는 아직:

      - 제한된 qubit 수
      - 높은 오류율
      - 긴 latency
      - 고비용
    - 대형 QML 모델 학습은 현실적으로 **GPU 시뮬레이터에서만 가능**
    - 결국 지금 QML 경쟁은:

      - 누가 더 강력한 시뮬레이터 환경을 제공해 연구자들을 끌어오느냐
    - IonQ의 전략은:

      - “우리가 최고의 연구용 QML 시뮬레이터를 제공할 테니, 나중에 실제 QPU 실행도 자연스럽게 우리에게 와라.”
  - **3️⃣ PyTorch 기반 → AI 산업과 직접 연결**

    - 현재 AI 업계의 표준은 PyTorch

      - → AI + Quantum 융합 시장을 선점하려면 PyTorch 통합이 필수
    - 다른 프레임워크 상황:

      - Qiskit → IBM 중심, PyTorch와 약함
      - Cirq → Google 중심
      - Pennylane → 범용이지만 미분 + 분산 시뮬레이션 약함
    - IonQ가 만든 tqd는:

      - AI 연구자 ⟶ QML 연구자 ⟶ IonQ QPU 사용자 로 이어지는 **전략적 파이프라인 구축**
  - **4️⃣ 실제 QPU 준비가 되면 backend로 자연스럽게 연결**

    - 현재

      - TorchQuantumDistributed = 시뮬레이터 프론트엔드 IonQ QPU = 미래 inference backend
    - 즉, 지금은 시뮬레이터지만, 미래에는 PyTorch 모델을 IonQ QPU에서 그대로 실행할 수 있는 backend 모드를 추가할 가능성이 매우 높음.
  - **5️⃣ AWS / IBM / NVIDIA와 차별화 전략**

    - IonQ의 경쟁 포지션: QML = high-value enterprise 실전 문제 해결
    - IBM이나 Google은

      - 자체 QPU 스택
      - 자체 프레임워크
      - 폐쇄적 구조
    - NVIDIA는 GPU 플랫폼 장악

      - → QML은 NVQLink + CUDA-Q로 끌어오려는 전략
    - IonQ는:

      - 우리는 열린 PyTorch 기반 QML 강화 → 누구든지 붙을 수 있는 개방형 중심 플랫폼 → 시장의 중심이 되려는 전략
