**Part I 분석: “Bitcoin and the Quantum Problem – Discrete Logs are Hard”**

**글의 전체 목적**

1. 1. **비트코인이 양자컴퓨팅에 가장 취약한 시스템 중 하나**라고 주장
   2. **암호학적 기반 구조인 ECDSA / Schnorr / secp256k1의 핵심을 설명**
   3. **왜 elliptic curve discrete logarithm problem(ECDLP)이 비트코인의 핵심 방어선인지 이해시키기**
   4. **양자컴퓨터가 등장하면 어떤 문제가 생기는지 다음 글에서 이어 설명**
   - 즉, 지금 글은 **ECDLP가 왜 역산이 불가능한지 직관을 제공하는 설명편**.

**🔐 비트코인의 암호학적 구조와 흐름**

- - 비트코인은 다음과 같은 보안 체인을 기반으로 한다:

|  |  |  |
| --- | --- | --- |
| **단계** | **설명** | **중요 포인트** |
| 1 | 256비트 난수 선택 → private key | 단순한 큰 정수, 무작위성 확보 |
| 2 | ECC 곡선(sec256k1)에서 G \* k → public key | 실제 연산은 **덧셈의 반복** |
| 3 | public key 해시 → 주소 | P2PKH 방식: SHA256 + RIPEMD160 |
| 4 | UTXO 솔빙을 위해 서명 + public key 제공 | 이 때 public key가 노출! |
| 5 | 다른 노드가 signature 검증 | “private key를 알고 있음”을 증명 |

🔑 **비트코인의 근본적 보안:**

> private key → public key는 매우 쉽다.
>
> public key → private key는 사실상 불가능해야 한다.

- - 이 “불가능함”이 바로 **ECDLP(elliptic curve discrete logarithm problem)**.

**🧮 프로토콜 관점에서 바라보는 비트코인**

1. 1. 256비트(1부터 2256)로 이루어진 정수에서 무작위(Random 또는 요즘에 자주 사용하는 entropy)로 선택

      - 2256 → 1.16 × 1077

        - 우주에 존재하는 추정 원자 수 ( ~ 1080)에 거의 근접한 수준의 조합 수다.
        - 현재 우주 전체를 컴퓨터로 만드다 해도 brute-force로 풀수 없는 조합이라서 256비트면 충분히 보안 강도가 강함
        - → 512비트는 overkill
      - 예를 들어 다음과 같은 **개인키(Private Key)**가 있다고 가정하자.

        - 50d858e0985ecc7f60418aaf0cc5ab587f42c2570a884095a9e8ccacd0f6545c
        - 16진수(hex)로 표현된 32바이트 길이의 문자열
        - 1 hex는 4비트(half-byte)이므로 실제 위 문자열의 길이는 64자리
   2. 이 정수를 ECDSA에서 사용하기로 전 세계적으로 합의한 **secp256k1** 타원곡선의 특수한 곡선 방정식에 입력한다.

      - 구체적으로는 이 값을 k로 두고, secp256k1 곡선 상에서 공개적으로 알려진 기준점(base point) G에 대해 **스칼라 곱**을 수행한다.
      - 즉, k×G — G라는 점을 k번 자신에게 더해가는 연산을 한다.
      - 이 결과물인 k×G가 곧 우리의 **공개키(public key)**가 된다. 예시에서, 해당 공개키의 16진수 표현은 아래와 같다:

        - 02 4033389cf6632a172546748fda79e7fbabce944b552db5dba81b16c01fec377b

          - 02는 y좌표의 짝/홀을 나타내틑 prefix

            - 02는 y가 짝수
            - 03는 y 가 홀수
          - 뒤의 4033...이 x좌표(32바이트)

            - 원래 타원곡선 위의 점은 (x, y)인데, 곡선 방정식으로 y를 x에서 복원할 수 있으니까
            - **x + 짝/홀 정보만 저장하는 게 압축 공개키**다. (33바이트)
   3. 기존 비트코인의 **P2PKH(Pay-to-Public-Key-Hash)** 형식 주소를 얻기 위해서는 이 공개키에 대해 SHA-256과 RIPEMD-160 해시를 순차적으로 적용한다.

      - 그러면 다음과 같은 주소가 생성된다:

        - 17oFBXabB2LLgDoUfu5P5bPxWvNepHQ96T
        - 이것이 우리가 익숙하게 알고 있는 비트코인 주소다.
        - 물론 이는 유일한 주소 형식이 아니며, 2021년 이후 도입된 **Schnorr 서명**에서도 동일한 곡선(secp256k1)을 사용하지만 구조적으로 단순하고 추가적인 유용성을 가진다.
   4. 이제, 이 주소에 일정량의 비트코인이 들어 있다고 가정하자. 더욱 정확히 말하면, 현재 비트코인 UTXO 집합에는 해당 주소를 락킹 스크립트(잠금 조건)로 포함하는 미사용거래출력(UTXO)이 존재한다고 가정한다. 우리가 흔히 “비트코인을 소유한다”고 말할 때 의미하는 바는 곧,

      - 해당 UTXO를 잠금 해제할 수 있는 **개인키의 지식**을 가지고 있다는 사실이다.
      - 예시로, 블록체인에 존재할 수 있는 UTXO는 다음과 같이 표현될 수 있다:
      - value: 0.50000000 BTC
      - scriptPubKey:

        - OP\_DUP
        - OP\_HASH160
        - 4a8fba212554eac0a6f956d7d34ef783a7a16ca2
        - OP\_EQUALVERIFY
        - OP\_CHECKSIG
      - 여기서 4a8f…는 앞서 언급한 압축 공개키의 해시(20바이트)이다.

        - → 공개키를 공개하는 대신 "이 해시에 대응하는 공개키를 가진 사용자만 사용할 수 있다"는 의미.
        - 해시는 역변환이 안되기 때문에, 소지하고 있는 공개키를 입력하면 공개키의 해시가 같은지 다른지만 확인하여, 같을 경우에만 코인을 사용할 수 있게 하는 원리
   5. P2PKH 출력(UTXO)을 사용(spend)하기 위해서는 네트워크 노드들에게 **서명(signature)과 공개키**를 제공해야 한다. 개인키(50d858e…)를 보유한 지갑은, 트랜잭션 데이터의 해시(이전 UTXO 스크립트, 입력·출력 정보 등)에 대해 ECDSA 서명을 생성한다.

      - 네트워크상의 다른 노드들은 공개키를 해싱하여 해당 결과가 블록체인에 기록된 주소 해시와 일치하는지 확인한 후, 제공된 공개키와 트랜잭션 해시를 기반으로 서명의 유효성을 검증한다.
      - 즉, 서명을 공개한다는 것은 곧, “**나는 이 UTXO에 기록된 공개키에 대응하는 개인키를 알고 있다**” 라고 선언하는 것이다.
      - 여기서 중요한 점은,

        - **비트코인을 받을 때는 공개키가 드러나지 않지만, 보낼 때는 공개해야 한다는 사실**이다.
      - 이 점을 반드시 기억해야 한다.
   - 실제 코인 사용 예

     1. 트랜잭션 본문이 생성됨

        - input TXID, output 정보, amount 등이 포함됨
        - 이 내용만을 기반으로 메시지(해시) 생성 → 서명을 만들기 위해서 필요함.
     2. 개인키로 메시지(해시)에 서명해서 Signature 생성
     3. 트랜잭션에 Signature와 Public Key를 첨부함

        - 1.에서 생성한 트랜잭션 본문에, 2.에서 생성한 Signature와 기존에 보유중인 Public 키를 추가함.
     4. 이제 만들어진 최종 트랜잭션을 네트워크에 전송
     5. 트랜잭션을 받은 노드는 **디지털 서명 알고리즘(ECDSA 또는 Schnorr)을** 이용해 유효한 서명인지 확인

        - 네트워크 노드는 전체 TX 데이터를 받으면, 서명과 공개키를 제외한 나머지데이터만 해시해서 메시지를 생성
        - 이제 서명과 공개키를 방금 생성한 메시지와 합쳐서 서명 알고리즘을 실행하여 true 또는 false 의 값을 얻음.
        - 만약 Private key 없이 만든 서명이거나, 조작된 서명이라면 검증 실패 → 노드가 거부
        - **서명은 오직 해당 개인키를 가진 사람만 만들 수 있다.**
        - **하지만 서명이 맞는지 확인하는 것은 공개키만으로 누구나 할 수 있다.**

**🧮 왜 ECDLP가 어렵나? (시각적 + 수학적 설명)**

- - **ECC 곡선과 모듈러 공간**

    - secp256k1 곡선: y2 = x3 + 7 (mod p)

      - 이 “곡선(curve)”은 매우 거대한 유한 공간(field) 위에 존재하며, x축과 y축 모두 p에 의해 제한된다.
      - 만약 어떤 연산 과정에서 좌표 값이 p보다 커지면, 그 값을 p로 나눈 나머지(modulo 연산 결과)만 남기게 된다.
      - 이를 통해 모든 계산은 유한한 영역 안에서 이루어진다.
      - **왜 비트코인은 y****2** **= x****3** **+ 7 (mod p)라는 secp256k1 곡선을 사용했는가?**

        1. **구조가 매우 단순하고 투명하다**

           - 암호 체계 내부에 임의 파라미터가 없기 때문에 비트코인의 철학인 탈중앙화, 신뢰 최소화와 부합한다.
        2. **연산이 빠르다.**

           - secp256k1은 **Koblitz curve** 계열로,특정 수학적 특성 때문에 다음 연산들이 매우 빠르다:

             - 스칼라 곱(scalar multiplication)
             - 점 덧셈(point addition)
             - 점 doubling
           - 즉, 서명 및 검증 속도가 빠르고 연산 비용이 낮기 때문에 수천개의 서명을 처리해야 하는 시스템에서 큰 장점
        3. **보안성 매우 강함 - 더 작은 키, 더 강한 보안, 더 빠른 연산**

           - secp256k1의 보안 수준은 ECC 256비트로, 대칭키 기준 AES-128 수준의 보안 강도와 동등하다.
           - 작은 키로 강력한 보안과 빠른 연산을 제공

             - 아래 표에서 알 수 있듯이 비트코인에서 사용되는 동일한 강도를 위해서는 RSA 3072비트가 필요
             - ECDLP는 RSA의 소인수분해 문제보다 **훨씬 더 어렵다**

               - RSA는 2048비트 기준 약 617 decimal digit 정도
               - Shor 알고리즘에 의해 다항 시간에 해결 가능
             - ECC는 타원 곡선 이산로그 문제를 기반으로 하여,

               - O(√n) 수준 이상의 탐색 공간 필요
               - 기울기, 방향성, 패턴을 전혀 사용할 수 없음
               - **유한체 한정 공간에서 wrap-around(kernel) 구조**로 인해 어떤 수학적 단서를 활용할 수 없음
               - 알고리즘 연구가 훨씬 적고 구조적 약점이 없음

|  |  |
| --- | --- |
| **알고리즘** | **같은 보안 강도에 필요한 키 길이** |
| RSA | 3072 bit |
| ECC (secp256k1) | **256 bit** |
| AES | 128 bit |

1. - - - 1. **미국 NSA가 설계한 secp256r1(P-256)을 피하려는 의도**

            - ECDSA 주류 곡선인 **secp256r1 (NIST P-256)** 은 NSA가 난수 파라미터를 설정했기 때문에, **숨겨진 백도어 의혹**이 오래도록 제기되어 왔다.

              - 비트코인 창시자 사토시 나카모토는 이를 의심한 것으로 보인다
              - 그래서 **파라미터가 없는 단순 곡선 secp256k1**을 선택
              - 신뢰할 수 없는 기관이 만든 암호 구조를 쓰지 않겠다는 정치 철학적 선택임
         2. **곡선의 군 구조가 매우 좋은 특성을 가짐**

            - Large prime order (큰 소수 차수)
            - 작은 cofactor (=1)
            - 부드러운 subgroup 구조 없음 (subgroup attack 방지)
            - 성능과 균형적 보안의 최적점
     - p는 256비트 소수 → 1077 × 1077 크기의 정수 공간

       - 타원곡선 좌표는 x 와 y 두 축에 대해 각각 0∼p−1 범위를 가진다.
       - 따라서 전체 2D 공간의 점 후보 개수는 대략: 1077 × 1077=10154
     - 실제 공간은 **도넛(토러스) 형태의 finite field**

- - - - 비트코인이 사용하는 실제 곡선은 앞서 보았던 연속(real number) 곡선과는 전혀 다른 모습을 가진다.
      - **secp256k1 곡선을 모듈러(modular) 방식, 즉 ‘이산(discrete)’ 방식으로 구성함으로써**, 이 연산 체계의 규칙을 명확히 정의하고, 모든 참여자가 동일한 합의된 방식으로 계산을 수행할 수 있도록 한다.
      - 이는 계산 과정에서 무한대(infinity)나 특수한 경계 문제(edge cases)가 발생하지 않도록 하기 위한 조치다.
    - **비트코인의 곡선을 실제로 ‘눈으로 본다’는 것은 사실상 불가능하다.**

- - - - 가령 표준 HD 디스플레이가 약 **200만(2M) 픽셀**로 이루어져 있으며, 각 픽셀이 하나의 정수(integer)에 대응한다고 가정해보자. 비트코인의 격자(grid)는 약 1077 × 1077=10154 개의 정수 영역을 차지한다. 따라서 HD 화면에서는 전체 곡선 공간의 **10****-74**, 즉 거의 의미 없는 극히 미세한 부분만 표시될 것이다.

        - 200만 = 2 × 106 → 한 축으로 보면 103
        - 103 ÷ 1077
        - =10-74
      - 실제로는 **단 하나의 점조차 화면에 나타나지 않는다.**
      - 하나의 점을 확인하기 위해서는 두 축 각각을 **약 10****38.5** 배씩 축소해야 할 정도이다.
    - 임의 점 사이의 **거리/방향/기울기 개념 없음**
    - 점을 따라 이동할 때 **위치 기준으로 진행 방향을 추정할 수 없음**
    - → 역산이 너무나 힘듦
  - **스칼라 곱 = 반복 덧셈**

    - k \* G는 단순한 k번 더하기

      - 우리는 k라는 개인키 값을 선택하고, 기준점 G에서 출발하여, **G를 계속 더해 가며(k번) 새로운 점에 도달한다.**
      - 이 최종 점이 바로 **공개키**이며, 타인은 **몇 번 더해졌는지(k)** 알 수 없다.
    - 이를 시각적으로는 다음과 같은 방식으로 표현한다.

      - 같은 점을 더할 때는 **접선(tangent)** 을 이용하여 계산한다
      - 두 점을 더할 때는 두 점을 연결하는 **직선을 긋고** 그 직선이 곡선과 만나는 다른 점을 찾은 뒤 그 점을 **x축 대칭(reflection)** 시켜 결과 점을 얻는다
    - **1단계 — Doubling (G → 2G)**

[![](https://substackcdn.com/image/fetch/%24s_%21lgmC%21%2Cw_1456%2Cc_limit%2Cf_auto%2Cq_auto:good%2Cfl_progressive:steep/https://substack-post-media.s3.amazonaws.com/public/images/db287686-2898-495f-9314-a7d4a9afc0a5_1559x1110.png)](#)

- - - - G에서 접선(tangent)을 그린다
      - 곡선과 다시 만나는 점을 G′라 한다
      - G′를 x축 대칭시키면 나오는 점이 **2G**
    - **2단계 — Addition (G + 2G = 3G)**

[![](https://substackcdn.com/image/fetch/%24s_%21DQid%21%2Cw_1456%2Cc_limit%2Cf_auto%2Cq_auto:good%2Cfl_progressive:steep/https://substack-post-media.s3.amazonaws.com/public/images/71f39eb2-6d59-487b-8be5-f4b76e56af69_1559x1110.png)](#)

- - - - 두 점 G와 2G를 연결하는 직선(chord)을 긋는다
      - 그 직선이 곡선과 다시 만나는 점을 R이라고 한다
      - R을 x축 기준으로 반사(reflection)하면 그 점이 **3G**
    - **3단계 — Doubling again (2G → 4G)**

[![](https://substackcdn.com/image/fetch/%24s_%21BURX%21%2Cw_1456%2Cc_limit%2Cf_auto%2Cq_auto:good%2Cfl_progressive:steep/https://substack-post-media.s3.amazonaws.com/public/images/2787156a-9bd3-4cbe-bbe5-84ee0181542c_2045x1264.png)](#)

- - - - 2G에서 접선을 이용하여 다시 곡선과 만나는 점 R2를 찾는다
      - 그 점을 x축 반사하면 **4G**
    - 짝수 배수는 홀수를 여러번 더해도 가능하지만 “doubling” 연산이 훨씬 효율적이다.

      - 로그스케일 속도(O(logk)) 계산 가능
      - 공개키 계산: 256번 doubling + 128번 add → 연산량 manageable

        - 단순 계산시 최악의 경우 1077 번 연산이 필요한 것에 비하면 엄청난 효율성을 보임.
  - **역방향 불가**

    - 순방향시

      - 위에서 확인했듯이 개인키 k를 이용하여 공개키kG를 만드는 계산은 엄청나게 쉽다.
      - k → G → 2G → 3G → ... → P
    - 역방향 시:

      - 하지만, 공개키를 이용하여 k를 찾는 것은 극도로 어렵다.
      - P → (???) → k
      - 경우의 수는 2256 ≈1.16×1077

        - 우주 전체에서 원자 개수보다 크기 때문에 현재 컴퓨터로는 절대 불가능
  - **움직임이 뒤섞인다.**

    - 실수 공간에서는 곡선 모양이 부드럽게 보이지만,
    - **mod p** 연산을 적용하면

      - wrap around (순환)
      - 점들이 예측 불가능하게 튐
      - 방향성 개념이 사라짐 (기울기도 의미 없음)
      - **패턴 없이 점 구름처럼 흩어진다**
    - 미분 같은 연속적 방정식 적용 불가
    - **힌트가 없기 때문에 brute-force 외에 방법 없음**

**💣 비트코인이 ‘특히’ 위험한 이유**

|  |  |
| --- | --- |
| **요소** | **의미** |
| 공개키는 사용 시점에 노출됨 | 주소는 해시이므로 안전하지만 spend 시 public key 공개 |
| 양자컴퓨터의 Shor 알고리즘 | discrete log 역산이 다항식(polynomial) 시간 가능 |
| 노출된 public key = 공격 대상 | 서명 시점에 steal 가능 |

- - 즉, 비트코인 주소 상태에서는 안전 하지만 비트코인을 보내는 순간, 양자공격자가 private key를 역산할 수 있음
  - 이는

    - 은행 계좌처럼 key rotation이 자연스러운 구조가 아님
    - 수백만개의 기존 UTXO가 이미 공개된 public key 상태
    - → 양자 등장 시 **즉시 털릴 위험**

**💡 UTXO란 무엇인가?**

- - UTXO는 **Unspent Transaction Output** 의 약자이다.
  - 직역하면: **아직 사용되지 않은 거래 출력값, 즉 현재 내가 소유하고 있는, “쓸 수 있는 비트코인 단위”를 의미한다**.

**🧠 왜 ‘잔고(balance)’가 아니라 UTXO인가?**

- - 비트코인에는 은행 계정처럼 이런 식의 상태(state)나 계정(account)이 존재하지 않는다.
  - 대신:

    - 과거 모든 거래들의 결과(출력 output) 중
    - **아직 아무도 사용하지 않은** 출력 값이
    - **사람들이 가진 비트코인**을 구성한다.
  - 즉, 비트코인 잔고란: 내 소유의 UTXO들의 합계

**🧠****예를 들어:**

- - 누군가 당신 주소로 0.5 BTC를 보냈다 → 이 때 0.5 BTC짜리 **UTXO가 생성**된다.
  - 또 다른 사람이 0.8 BTC를 보냈다 → 0.8 BTC짜리 UTXO 하나 더 생성된다.
  - 이제 당신의 지갑은 실제로 이렇게 표현한다:
  - UTXO1 = 0.5 BTC
  - UTXO2 = 0.8 BTC
  - Total = 1.3 BTC

**💸 비트코인을 쓸 때는?**

- - 예를 들어 1 BTC를 보내고 싶다.
  - 이때 계좌 시스템처럼 1 BTC를 그냥 차감하는 것이 아니라:

    - 0.5 + 0.8 → 두 UTXO를 통째로 입력(input)으로 사용하고 수신자에게 1.0 BTC 지급
    - 남는 0.3 BTC는 **새로운 UTXO로 거슬러 받음(change output)**
    - Input:

      - UTXO1 (0.5)
      - UTXO2 (0.8)
    - Output:

      - Receiver: 1.0 BTC
      - Change to me: 0.3 BTC ← 새로운 UTXO 생성
  - 사용한 UTXO는 **소멸(Spent)** 되고
  - 새로운 UTXO가 생성된다.

**🔐 UTXO와 개인키, 공개키 관계**

- - UTXO는 **주소의 hash(pubkey hash)** 에 잠겨 있다.
  - 이를 해제(spend)하려면 그 주소의 공개키 + 서명(개인키 기반) 을 제출해야 한다.
  - 즉:

    - 개인키 → 공개키 → 주소 → UTXO 잠금(lock)
    - 지불할 때 → 공개키 제출 + 서명으로 잠금 해제(unlock)

**🔥 비트코인 양자 공격과 UTXO**

- - 양자 컴퓨터 위험 논의에서 중요한 점:

|  |  |
| --- | --- |
| **상태** | **위험 수준** |
| **아직 공개키가 공개되지 않은 UTXO** | 상대적으로 안전 |
| **이미 공개키가 공개된 UTXO** | 양자 공격에 매우 취약 |

- - UTXO는 **쓰려고 방송(tx)** 할 때 공개키가 노출된다.
  - (평소에는 공개키 대신 hash만 보임)
  - 그래서 공격자가 하는 일:

    - 공개키가 이미 드러난 UTXO를 스캔
    - → Shor 알고리즘으로 개인키 추출
    - → 먼저 spend해서 훔침 가능

**🔥 공개키가 공개되었지만, 아직 소멸되지 않은 경우 - 가장 위험한 상태**

- - 비트코인 주소에는 두 종류가 있다:

|  |  |  |
| --- | --- | --- |
| **방식** | **설명** | **공개키 노출 시점** |
| **P2PK (Pay-to-Public-Key)** | 공개키 자체로 잠김 | 처음부터 공개 |
| **P2PKH (Pay-to-PubKey-Hash)** | 공개키 해시로 잠김 | **사용(tx spend)할 때 공개** |

- - 초기 비트코인(2009~2012)에는 **P2PK**가 많이 사용되었다.

    - 예: 사토시의 초기 코인, Coinbase block reward outputs
  - 이 코인들은:

    - 주소에 공개키가 이미 기입되어 있어
    - **이미 공개 상태로 잔고가 남아 있다**
  - 또한, **P2PKH 주소라도** 다음 상황에서는 위험하다:

    - **어떤 UTXO는 이미 사용 중(tx in mempool)인데 미확정 상태로 남아 있을 수 있음**

      - 나: UTXO를 쓰려고 트랜잭션 생성 → 네트워크에 방송
      - (이 순간 공개키 노출) 채굴 미포함 →
      - mempool에서 몇 시간~며칠 정체
      - 그 순간:

        - 공개키는 이미 블록체인에 기록되었거나 mempool에 떠 있음
        - 하지만 잔고는 아직 실제로 소비되지 않았음
        - → **양자 공격자가 달려들 수 있는 상태**

**⚡ 공격 시나리오**

- - 공격자: mempool 스캔
  - 공개키 노출된 UTXO 탐색
  - Shor 알고리즘으로 개인키 추출
  - 내가 그 TX가 블록에 기록되기 전에 재생성해서 먼저 spend
  - → 먼저 도달한 거래가 들어가므로:

    - 잔고를 훔칠 수 있다 (double spend by key theft)

**🧠 실제로 이런 UTXO들이 존재하는가?**

- - **✔ 존재한다**

    - 초기 채굴된 P2PK 코인들 (≈ 2M BTC 추정)
    - 사토시의 자산 약 1.1M BTC 포함
    - 오래된 지갑(초기 유저)에서 아직 안 움직인 것들

      - 이들은 직접 P2PKH로 바꿀 수 없다.

        - P2PK → P2PKH로 바꾸려면 해당 UTXO를 **spend**해야 하며, spend 과정에서 **개인키 서명이 필요**하기 때문이다.
        - 즉, **해당 비트코인의 소유자가 직접 이동(move)** 시키지 않으면 절대 바뀌지 않는다.
    - 멤풀에서 방치된 거래들
    - Taproot 스크립트 가능한 주소 중 미사용 경로가 있는 경우

      - Taproot는 스크립트의 **유연성과 프라이버시**를 높이기 위해 도입되었다.
      - Taproot 주소는 이렇게 두 가지 경로 중 하나로 코인을 인출할 수 있다:

        - Key Path Spend : 단일 공개키로 서명이 되어 공개키가 노출될 수 있음
        - Script Path Spend : 여러 조건 중 하나 수행하는 방식, 스크립트 중 사용한 부분만 노출

          - 하지만, 어느 스크립트가 사용될지 모르는 상태에서 특정 경로는 실제로 한번도 사용되지 않을 수도 있기 때문에 공개키가 드러날 수 있음.

| --- | --- | --- | --- |
| **유형** | **잔고 존재** | **공개키 상태** | **양자 취약성** |
| P2PK (초기코인) | O | O (처음부터 노출) | 최고 위험 |
| Mempool pending TX | O | O (최근 노출) | 매우 위험 |
| Taproot key-path spend + 남은 script-path | O | O | 매우 위험 |
| P2PKH 주소 | O | X (hash만 공개) | 비교적 안전 |
