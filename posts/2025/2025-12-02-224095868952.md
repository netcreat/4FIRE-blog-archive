# AI, 과연 거품인가? (2) - 두 번째 락인(lock-in)을 막기 위한 반격

Published: 2025-12-02T19:36:40.423000+09:00

Original Naver post: https://blog.naver.com/4-fire/224095868952

---

> *거대 연합군의 등장 — 엔비디아 제국에 맞서는 개방형 표준 전쟁*

**🥊 서론 — 모두가 두 번째 CUDA를 두려워한다**

- - AI 1차전에서 엔비디아가 승리한 이유는 단순히 GPU 성능 때문이 아니었다.
  - **CUDA라는 강력한 소프트웨어 생태계**를 구축했기 때문이다.
  - 연구자, 엔지니어, 클라우드, 슈퍼컴퓨터, 국방 연구소, 로봇 기술까지 “CUDA 없이는 개발할 수 없는 세상”을 만들어냈다.
  - 이제 엔비디아는 같은 전략을 양자 시대까지 연장하려 한다.
  - 바로 **NVQLink + CUDA-Q = 양자 하이브리드 컴퓨팅의 사실상 표준화**.
  - 만약 이 전략이 그대로 성공한다면, 우리는 AI에 이어 **양자 컴퓨팅에서도 엔비디아 세금**을 내야 한다.

> ***그래서 지금, 업계 전체가 움직이기 시작했다.***
>
> *두 번째 CUDA 독점 구조를 막기 위한 거대한 반격이 시작된 것이다.*

---

**🧨 1장 — 왜 개방형 표준 전쟁이 필요한가?**

- - 엔비디아 중심 구조는 단기적으로 빠른 혁신을 이끌 수 있다.
  - 하지만 업계는 다음 위험을 알고 있다.

|  |  |
| --- | --- |
| **리스크** | **설명** |
| **벤더 종속 (lock-in)** | NVQLink 기반 구조가 사실상의 표준이 되면 갈아탈 수 없음 |
| **혁신 속도 저하** | 한 회사가 기술 방향을 독점하면 경쟁이 사라짐 |
| **보안·주권 문제** | 국가/군사/과학 연구에서 단일 기업 의존은 위험 |
| **비용 구조 왜곡** | GPU 가격이 AI 가격 = 경제·산업적 독점 |
| **QPU 산업의 종속화** | 양자 컴퓨터가 GPU의 “확장 카드”로 전락 |

- - 그래서
  - **클라우드 3대장(AWS·Google·MS)**
  - **반도체 경쟁 진영(Intel·AMD·Arm)**
  - **양자 플레이어(IonQ·Quantinuum·OQC·Rigetti 등)**
  - **표준화 기구(IBTA, CXL Consortium, QIR Alliance)** 까지
  - 전부 “엔비디아 중심 구조를 막아야 한다”는 데 공감하고 있다.

**📌 CXL(Compute Express Link)이란?**

> ***CPU / GPU / NPU / QPU / 메모리를 하나의 공유 패브릭으로 묶는 개방형 고성능 인터커넥트 표준***

|  |  |  |
| --- | --- | --- |
| **항목** | **NVLink / NVQLink** | **CXL** |
| 소유·통제 | **엔비디아 독점** | **개방형 컨소시엄** |
| 참여 기업 | NVIDIA 중심 | Intel, AMD, Google, MS, Meta, AWS, Arm 등 |
| 사용 목적 | GPU-to-GPU, GPU-to-QPU | CPU-GPU-NPU-QPU-Memory 통합 패브릭 |
| 표준화 | 사실상 독점 API | 산업표준, 누구나 구현 가능 |
| 미래 방향 | 폐쇄형 상용 솔루션 | 데이터센터 OS 같은 역할을 목표 |

> ***CXL이 성공한다면, “가속기 독립 시대”가 열린다.***
>
> ***QPU는 GPU의 부속품이 아니라, 패브릭 위의 동등한 노드가 된다.***

**📌 CXL(Compute Express Link)의 장단점**

|  |  |  |
| --- | --- | --- |
| **항목** | **NVIDIA NVLink / NVSwitch** | **CXL 3.0 / 4.0** |
| **대역폭** | NVLink 4: GPU 간 양방향 **1.8TB/s** **수준** | CXL 3.0: **CXL.io 64GB/s, CXL.mem/cache 포함 256GB/s급** |
| **지연(latency)** | 매우 낮음 (GPU 최적화) | PCIe 기반 → NVLink보다 높음 |
| **주 사용 목적** | GPU ↔ GPU 초고속 통신 | CPU·GPU·NPU·DPU·메모리 확장 및 공유 |
| **연결 방식** | 폐쇄형(엔비디아 생태계 안에서만) | **개방형 표준**, 다양한 벤더 호환 |
| **메모리 풀링** | 제한적 | **핵심 기능** |

> ***속도는 NVLink > CXL,***
>
> ***호환성·메모리 확장성·AI/HPC 시스템 구성 유연성은 CXL > NVLink***

**🎯 왜 CXL이 NVLink보다 중요한 영역이 있는가?**

- - **메모리 풀링 / 공유**

    - 여러 CPU·GPU·NPU가 **하나의 거대한 메모리 풀을 공유**
    - 서버 전체에서 메모리 자원을 효율적으로 사용
    - TB급 메모리를 필요로 하는 AI 모델 (GPT-4, Grok-4 등)에 중요
  - **이기종 가속기 환경 통합**

    - NVIDIA + AMD + Intel + ARM + AI ASIC 등을 동일 구조로 연결 가능
    - 반면 NVLink는 **오직 NVIDIA 환경 전용**
  - **데이터센터·AI 인프라의 구조적 혁신**

    - 기존 NUMA 구조(Non-Uniform Memory Access) 한계 극복
    - 리소스를 유연하게 조립 가능한 **Lego-style disaggregation architecture**

****

**🔍 CXL만으로 QPU를 직접 제어할 수 있나?**

> ***CXL만으로는 QPU(양자처리장치)를 직접 연결하거나 실시간 제어용 인터커넥트로 사용하기 어렵다.***
>
> ***물리 게이트 구동(μs·ns 단위 제어)에는 별도의 실시간 제어 하드웨어(FPGA/ASIC/DSP/RT-controller)가 반드시 필요다.***

- - QPU 단일 게이트 타이밍은 매우 정교해서

    - FPGA AWG, ADC, DAC, Timing Sequencer 같은 장치가
    - **나노초 단위로 파형을 생성/동기화**해야 가능하다.
  - CXL은 이런 실시간 제어용이 아니라 **데이터 전송과 메모리 공유**가 목적이다.

> NVQLink 자체를 완전히 대체할 수 있는 기술은 현재 없다.
>
> 그나마 있는 작은 희망은 DOE가 QBlox와 함께 Quantum Instrumentation Control Kit 공공-민간 협력 모델을 발표했다는 것이다.

**🔍다른 후보 기술은 진정 없다는 말인가?**

- - QBlox도 NVQLink의 제어 시스템 개발사로 협력중인 업체라서 완전 독립적일 수 없는 상태다.

|  |  |  |
| --- | --- | --- |
| **후보** | **가능성** | **설명** |
| **UCIe (chiplet interconnect)** | 🚧 연구 & 초기 상용화 | 다이 간 연결 → GPU-Chiplet 구조 가능 |
| **Optical Interconnect (silicon photonics)** | 📈 급성장 | 차기 세대에서 NVLink 수준 대체 가능성 |
| **Co-Packaged Optics (CPO)** | 📈 고대역 | GPU 클러스터 전용 광링크 |
| **Quantum interconnect(?)** | future | 실시간 계산 링크가 아니라 QKD/비트 전송 |

> ***그러나, 현실적으로는 최소 3 ~ 5년 동안 NVQLink는 GPU 주도의 QPU 클러스터링에서 절대적 우위를 유지할 것이고, 지금읜 GPU/CUDA처럼 Lock-in이 될 가능성도 상당히 큰 편이다.***

**🎯 표준안에 대한 가장 현실적인 접근 방법**

- - QPU 실시간 제어(펄스/타이밍)는 **FPGA/ASIC**을 둬서 별도로 담당하고,
  - 그 위의 수평적 클러스터 레벨 연결은 **CXL / InfiniBand / RoCE / Ethernet** 기반으로 구성할 수 있다.
  - 즉, NVIDIA NVQLink라는 개찰구를 강제 통과할 필요 없는 개방형 구조가 가능해지는 것이다.

|  |  |  |
| --- | --- | --- |
| **영역** | **가능 여부** | **설명** |
| QPU–QPU 분산 실행 | ⭕ | Optical link + IB 기반 cluster |
| QPU–GPU 하이브리드 워크로드 | ⭕ | CUDA-Q / QIR / OpenQASM orchestration |
| QPU–HPC–AI 공동 메모리 풀 | ⭕ | CXL pooling 이용 |
| QPU 데이터 고속 전송 | ⭕ | IB / RoCE / Ethernet |
| 실시간 게이트/펄스 제어 | ❌ CXL insufficient | FPGA/ASIC local control 필요 |

**🧠 4장 — 반격 3: OpenXLA / MLIR / oneAPI — heterogeneous compute OS의 등장**

|  |  |  |
| --- | --- | --- |
| **기술** | **목적** | **의미** |
| **OpenXLA** | 다양한 AI 가속기용 통합 컴파일러 | CUDA 종속 탈출 |
| **MLIR** | 여러 연산자/디바이스를 통합 표현 | classical-quantum 통합 준비 |
| **oneAPI** | cross-vendor compute 표준 API | GPU/FPGA/NPU 통합 가능 |

**📌OpenXLA**

- - 구글·메타·AMD·NVIDIA·AWS 등이 참여한 **오픈 AI 컴파일러 프로젝트**
  - 목표:

    - TensorFlow / PyTorch / JAX 모델을
    - GPU / TPU / NPU / AI ASIC 같은 다양한 하드웨어 위에서
    - **동일 성능으로 실행**하기 위한 통합 컴파일러

**📌MLIR**

- - Multi-Level Intermediate Representation (Google 개발, LLVM 계열)
  - 역할:

    - 다양한 언어 / 다양한 HW 백엔드 사이의 **중간 컴파일 언어(IR)**
    - 코드 최적화 및 lowering 과정 표준화
  - QIR이 양자 명령을 표현하는 IR 표준이라면, MLIR은 모든 영역(AI / HPC / 컴파일러 / 그래프 / DSP / GPU / TPU / quantum 포함)을 정의하기 위해 작정하고 만든 범용 IR 플랫폼

**📌oneAPI**

- - Intel이 만든 범용 가속기 통합 개발 플랫폼
  - 목표:

    - CPU / GPU / FPGA / AI ASIC을 **하나의 API로 프로그램**
    - CUDA처럼 vendor lock-in 방지

**📌 종합 비교**

|  |  |  |  |
| --- | --- | --- | --- |
| **항목** | **OpenXLA** | **MLIR** | **oneAPI** |
| 목적 | AI 컴파일 최적화 | 범용 IR | 범용 가속기 프로그래밍 |
| 대상 | AI Frameworks → HW | 컴파일러 내부 계층 | CPU·GPU·FPGA |
| 산업적 의의 | HW 독립 AI | 컴파일 생태계 표준화 | CUDA 독점 해소 |
| 플레이어 | Google, Meta, NVIDIA, AMD | LLVM, Google | Intel, Codeplay |

> ***클래식 연산을 다시 오픈 표준으로 돌려놓아야, QPU까지 넓힐 수 있다.***

**✅ 6장 — 양자 시대에도 CUDA 독점 구조가 반복될까?**

**💡****시나리오 1 – “CUDA 2.0 현실화” (엔비디아 초강세)**

- - NVQLink + CUDA-Q가 가장 먼저 상용 하이브리드 솔루션을 장악
  - QPU 벤더들이 “일단 엔비디아랑 붙으면 고객/투자/마케팅이 편하다”고 생각
  - 빅테크도 단기 경쟁력 때문에 NVDA 스택을 깊게 도입
  - 결과:

    - 양자-고전 하이브리드의 중심이 **사실상 CUDA-Q**가 됨
    - 나중에 갈아타기 매우 어려운 lock-in 구조
  - → **가능성 있음.** 지금 엔비디아가 노리는 게 딱 이 그림.

**💡****시나리오 2 – “멀티 폴라 구조” (여러 표준 공존)**

- - AWS: Trainium+Braket, Google: TPU+자체 QPU, MS: QIR + 여러 QPU 파트너, IBM: Qiskit+자체 QPU
  - classical–quantum 스택이 **클라우드/빅테크별로 다르게 발전**
  - 대신 IR 수준 (QIR, OpenQASM, MLIR)에서는 어느 정도 호환성 유지
  - → 현실적으로 꽤 가능성이 높고, **현재 이미 이 방향으로 진행 중**.

**💡****시나리오 3 – “벤더 중립 표준 승리”**

- - 국가/국제 프로젝트, 표준화 기구, 클라우드/빅테크 연합이

    - QIR / MLIR / OpenXLA / CXL + 개방형 인터커넥트를 강력히 채택
  - NVDA도 결국 이 표준을 지원하지 않을 수 없게 됨 (GPU 팔려면 따라와야 함)
  - 결과:

    - CUDA-Q는 단일 독점이 아니라, 여러 옵션 중 하나가 됨
  - → 이상적인 방향이지만, **상용화 속도+엔비디아의 힘**을 생각하면 자연적으로 이렇게 되진 않고, “정책/표준/연합”이 필요함.

---

**✅ 투자 관점: NVDA vs AMZN vs GOOGL vs MSFT vs IONQ**

**💡****NVIDIA (NVDA)**

- - 강점:

    - 이미 **AI 1차전 승자**
    - CUDA + GPU + Omniverse + (이제는) CUDA-Q + NVQLink → “AI+양자 풀스택”을 노리는 유일한 플레이어
  - 리스크:

    - **규제 / 반독점 / 경쟁사 자체 칩(Trainium, TPU, Gaudi, MI300 등)** 로 인해 마진 구조 압박
    - 양자 시대까지 CUDA 독점이 연장될 경우: 규제 리스크 더 커짐

**💡****AWS (AMZN)**

- - 강점:

    - 클라우드 1위 + Trainium/Inferentia + Braket (멀티 QPU 연동)
    - NVDA에 비해 **“하드웨어 자체를 팔기보다 서비스/플랫폼” 중심**
  - 전략적 포인트:

    - “엔비디아 의존도를 줄이는 방향” + “멀티 QPU 통합”
    - NVQLink 대신 네트워크 기반 QaaS 구조 선호

**💡****Google (GOOGL)**

- - 강점:

    - TPU + 자체 QPU + JAX/XLA + Cirq
    - **AI + 양자 + 클라우드 + 소프트웨어 스택**을 모두 직접 만들 수 있는 드문 회사
  - 전략:

    - NVDA에 의존하지 않고 full-stack을 직접 만들 수 있는 위치
    - 다만 상업화 속도와 매출 가시성은 NVDA보다 느리게 보일 수 있음

**💡****Microsoft (MSFT)**

- - 강점:

    - Azure + QIR + 여러 QPU 파트너(Quantinuum, IonQ, Rigetti 등)
    - “하드웨어 벤더 중립 OS / 개발 툴” 역할 가능 (예전 Windows+Office 포지션처럼)
  - 전략:

    - CUDA-Q와 경쟁하는 **벤더중립 양자 IR/런타임 표준**을 주도할 수 있음

**💡****양자 순수 플레이어: IonQ 등**

- - 강점:

    - QPU 하드웨어 기술 자체의 IP
    - 정부/국방/특수 목적 (센싱, 안전 통신, 고에너지 물리, 재료, 국방 C4ISR 등) 시장
  - 리스크:

    - 지금 당장은 매출 규모·수익성·밸류에이션 변동성이 큼
    - **어느 쪽 classical 스택과 붙을지**에 따라 미래 power가 달라질 수 있음
    - NVQLink/디팩토 표준에 너무 깊게 종속되면 **독자적 교섭력이 소멸**할 수도 있음
