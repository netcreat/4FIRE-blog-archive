**✅****QEC 사이즈별 디코더 용량 계산**

QEC 계산을 위해서 고전 컴퓨터의 도움이 필요한데, 과연 어느정도의 컴퓨팅 용량이 필요한지 알아보자.

결론을 먼저 말하자면 작은 칩하나로 끝나기에는 생각보다 데이터/메시지 양이 꽤 크다. 일단 아래와 같이 기본적인 조건으로 계산을 해보겠다.

- 가정

  - QEC code =Surface code
  - 거리 d= 9 ~ 31
  - 스태빌라이저 수 =2d(d−1)
  - 측정 주기 f = **1 MHz** (5 MHz는 대역폭 ×5)

    - 한 라운드가 1us면, 주파수로는 1MHz
    - 5배의 대역폭은 회로/ADC/데이터링크가 최소한 **기본 측정 속도의 5배**까지 신호를 안정적으로 전달할 수 있도록 여유(bandwidth margin)를 둔다는 의미
  - 신드롬 전송은 1비트/체크 + 헤더 등 **×2 오버헤드**

    - **오버헤드 : 대략적으로 50%이상으로 선정함.**

      - 프레임 헤더
      - 동기화 비트
      - 패리티/CRC
      - 패킷 인코딩 규칙(예: 8b/10b)
  - BP/Relay-BP 스타일 메시지 패싱: 체크당 차수 4, **8비트 고정소수점**, **5회 반복**(보수적)

    - 체크당 차수 4 : 한 체크는 한 라운드에 4개의 변수 노드(데이터 큐비트와 비슷함)로 메시지 전송
    - 8비트 고정소수점 : 메시지를 실수 대신 8비트 정밀도로 표현해서 메모리와 연산량을 줄임
    - 5회 반복 : BP는 반복으로 수렴하므로, 보수적으로 5회 반복을 잡아 계산함

**💡****신드롬 입력 대역폭(외부 I/O)**

|  |  |  |  |
| --- | --- | --- | --- |
| **d** | **체크 수** | **라운드당 비트(×2OH)** | **대역폭 @1MHz** |
| 9 | 144 | 288 | **0.29 Gbps** |
| 13 | 312 | 624 | **0.62 Gbps** |
| 17 | 544 | 1088 | **1.09 Gbps** |
| 21 | 840 | 1680 | **1.68 Gbps** |
| 25 | 1200 | 2400 | **2.40 Gbps** |
| 31 | 1860 | 3720 | **3.72 Gbps** |

> **위 표는 양자컴퓨터에서 디코더로 “들어오는” 신드롬 입력만 계산한 것이기 때문에, 수 기가비트 수준으로 실제보다 작아 보일 수 있음.**

- 실제 디코더 내부 연산에서는:

  - 각 체크에서 여러 변수로 메시지 전송
  - 반복(iteration)
  - 왕복(체크→변수→체크)
  - 내부 버퍼링
  - 때문에 **내부 데이터 흐름량이 수십~수백 배 커진다**
- 즉, 외부 I/O만 보면 “기껏해야 수 기가비트”처럼 보이지만, **고전 컴퓨터 내부에서는 수백 기가비트/초 수준의 스위칭과 메모리 접근이 필요**할 수 있다.

**💡****내부 BP/Relay-BP 메시지 트래픽(온칩/메모리)**

|  |  |  |  |
| --- | --- | --- | --- |
| **d** | **Tanner 그래프 에지 수(≈4×체크)** | **라운드당 메시지 비트(양방향×8bit×5회)** | **내부 대역폭 @5MHz** |
| 9 | 576 | 46,080 | **230 Gbps** |
| 13 | 1,248 | 99,840 | **500 Gbps** |
| 17 | 2,176 | 174,080 | **870 Gbps** |
| 21 | 3,360 | 268,800 | **1.35 Tbps** |
| 25 | 4,800 | 384,000 | **1.92 Tbps** |
| 31 | 7,440 | 595,200 | **2.98 Tbps** |

- **에지 수(Edges)**

  - 태너 그래프에서 **노드 간 연결선**

    - **변수 노드**(데이터 큐비트) ↔ **체크 노드**(안실라/스태빌라이저) 사이의 연결 하나가 **에지 1개**.
    - 평균 체크 차수(한 체크가 연결된 변수 수)를 dc라고 하면
    - 에지 수 E=C×dc
  - 여기서 C는 체크(스태빌라이저) 개수.
  - Surface code 안쪽 셀은 보통 dc≈4라서 **대략** E≈4C로 잡아 계산한다
- **라운드당 “내부” 메시지 비트 계산 (BP/Relay-BP 가정)**

  - BP류는 **양방향 메시지 패싱**(체크→변수, 변수→체크)을 **여러 번 반복**.
  - 메시지 정밀도: b 비트(예: 8-bit 고정소수점)
  - 반복 횟수: *I* 회
  - 에지 수: *E*
  - 2: 양방향(→, ←)
  - f : 라운드 주파수
  - 그럼 **라운드당 내부 대역폭**:

- **“외부” 신드롬 입력 비트 (참고)**

  - 체크 하나는 신드롬 1비트.
  - 프로토콜 오버헤드(헤더/동기/인코딩 등)를 계상해 **×OH**(보수적으로 2) 곱한다.

- **Surface code에서 체크 수(스태빌라이저) C**

  - 정사각형 패치(일반적 표기)면 C  =  2 d (d−1)

> 디코더 내부의 메시지 패싱/버퍼링/임시상태가 **수백 Gbps** 급이라,
>
> d가 커지면 **HBM(고대역폭 메모리)이나 다중-FPGA**가 현실적으로 필요해진다.
>
> 5 MHz 사이클이면 위 수치가 **×5**로 튄다(예: d=25 → **~1.92 Tbps** 내부 트래픽).

**💡****왜 그렇게 커질 수밖에 없나?**

1. **신드롬 데이터량이 큐비트 수와 코드 거리 d에 따라 급증**

   - Surface code 기준, d가 커질수록 안실라 큐비트 수 ~ O(d2)로 늘어남
   - 각 안실라가 주기적으로 측정값을 생성 → 초당 수십~수백 Gbit급 스트림
   - 예: d=25, 수 µs 주기 측정 → 수천 안실라 × MHz 급 샘플 → 수십 GB/s급 데이터
2. **디코딩 알고리즘의 메모리 접근 패턴이 비순차적**

   - MWPM이나 BP는 그래프/행렬 접근이라 캐시 효율 낮음
   - FPGA 내부 Block RAM만으로는 용량·대역폭 부족 → 외부 HBM 필요 가능성 큼
3. **병렬 처리 리소스 소모**

   - Relay-BP 같은 BP 변형은 메시지 패싱을 노드·엣지 단위로 병렬화
   - 병렬도 높을수록 LUT·DSP·BRAM 사용량 폭증

****

**💡****해석 요약**

- **입력 I/O**는 그리 크지 않지만, **내부 연산/메모리 대역폭**이 병목.
- **CPU**: 구현은 쉬우나 **지연·지터가 커서** 실시간 FTQC에 부적합.
- **GPU**: 메모리 대역폭은 충분하지만 **I/O·스케줄링 지연** 발생.
- **FPGA/ASIC**: 외부 메모리 대역폭은 덜 필요, 대신 **하드 파이프라인 + 결정적 지연**으로 마이크로초 내 피드백 가능.
- 그래서 실전에선 **HBM 달린 Vertex/Stratix 계열**이나 **다중-FPGA 파티셔닝**을 고려해야 함.

  - FPGA 칩 패키지 안에 HBM 스택을 직접 붙인 SoC 방식
  - 다중-FPGA 파티셔닝

    - 여러 FPGA를 병렬로 처리하는 방

**💡****플랫폼별 비교**

|  |  |  |  |
| --- | --- | --- | --- |
| **항목** | **CPU(서버)** | **GPU(HBM)** | **FPGA(HBM/대형)** |
| 외부 입력(신드롬) 수용 | 쉬움 | 쉬움(PCIe/NVLink 필요) | 가장 쉬움(직결/SerDes) |
| 내부 대역폭 | 수백 GB/s급 DRAM, 캐시 의존 → **불규칙** | **수 TB/s** HBM으로 충분 | HBM 달린 FPGA면 수백 GB/s–1 TB/s |
| **왕복 지연(측정→디코딩→보정)** | **수십–수백 µs** (OS/캐시/NUMA 영향) | **수십 µs**(PCIe/NVLink + 커널 런치/스케줄링) | **수–수십 µs** 이하로 **결정적**(파이프라인) |
| 지터(변동폭) | 큼 | 중간~큼 | **매우 작음** |
| 실시간 조건부 게이트 | 우회 필요(컨트롤러 연동 난이도) | 가능하나 경로 길어짐 | **직결 가능** |
| 개발 유연성 | 높음(코드수정 쉬움) | 중간(커널/프레임워크) | 낮음(HDL/합성), 대신 PR로 완화 |

**💡****언제 CPU/GPU가 유용한가?**

- **오프라인/반실시간**: 실험 로그 디코딩, 파라미터 스윕, 시뮬/튜닝.
- **작은 d, 낮은 측정률**: 교육·데모·QRAM 없는 소규모 장치.

  - **CPU****:** **d ≈ 7–11**
  - **GPU****:** **d ≈ 13–17** **(퍼시스턴트 커널, NVLink/GPUDirect 등 조건 좋을 때)**
- **하이브리드**: **FPGA 전처리(집계/윈도잉)** + GPU 후처리(복잡 매칭)로 타협.

**💡****실전 권장 구조(요약)**

- **FPGA를 QPU 근처**에 붙여 신드롬 스트림을 직접 흡수(SerDes/Aurora).

  - **SerDes (Serializer/Deserializer)**

    - **Ser**ializer/**Des**erializer의 줄임말
    - 병렬 데이터를 **직렬화(Serializer)** 해서 한두 개의 고속 선로로 보내고, 받는 쪽에서 다시 **병렬화(Deserializer)** 하는 회로
    - 장점

      - 핀 수를 줄이고, 속도는 크게 늘림 (10~112 Gbps per lane 가능)
      - 고속 시그널링 프로토콜(Ethernet, PCIe, Aurora 등)의 물리 계층 기반
  - **Aurora**

    - Xilinx(AMD) FPGA 전용의 **경량 고속 직렬 링크 프로토콜**
    - **SerDes 위에 얹는 얇은 프로토콜 레이어**
    - TCP/IP처럼 무겁지 않고, 거의 raw data 스트리밍 수준
    - 지연(latency)이 매우 낮음 → 수백 ns 단위
- **온칩 파이프라인**으로 BP/Relay-BP 메시지 패싱(필요시 HBM 사용).
- 결과만 **컨트롤러에 즉시 피드백**(조건부 게이트/리셋).
- 통계·로그는 천천히 CPU/GPU로 백그라운드 전송.

****

**💡****요약**

- 중급 FPGA(HBM 없음): 대략 d ≈ 11–17
- 대형 FPGA + HBM: 대략 d ≈ 21–31
- 다중-FPGA 분할: d ≈ 31+도 가능
- 진짜 실시간(1 MHz): CPU/GPU는 실전용으론 사실상 d 한 자릿수 후반~두 자릿수 초반이 상한, 안정성 떨어짐.
- 주파수 낮추거나 배치 허용하면 GPU가 d 20대까지 넉넉히 처리(오프라인/준실시간).

> QEC 디코더를 FPGA로 구성하는 건 단순히 “작은 보드에 얹는 소형 칩 하나” 수준이 아니라, 고속·대용량 스트리밍 처리를 위한 꽤 묵직한 하드웨어 설계가 필요하다.

**💡****HBM까지 고려하는 이유**

- HBM(High Bandwidth Memory)는 FPGA 패키지에 붙어 있는 고대역폭 DRAM
- 장점: 수백 GB/s~1TB/s급 메모리 대역폭, 낮은 지연
- 대규모 QEC 디코딩에서는

  - 신드롬 버퍼링
  - 그래프/행렬의 엣지 가중치 저장
  - 중간 상태 메시지 저장
  - 등에 HBM이 유용
- 특히 다중 코드 패치(논리 큐비트 여러 개)를 동시에 디코딩하는 경우 **HBM급 대역폭이 사실상 필수**로 갈 수 있음

****

- **소형**: Xilinx Artix, Intel Cyclone (테스트·소형 QEC 코드)
- **중형**: Kintex, Arria (단일 논리 큐비트, 중간 d)
- **대형/HBM급**: Xilinx Vertex HBM, Intel Stratix 10 MX (대규모 d, 다중 논리 큐비트)

**✅****ASIC vs FPGA**

**💡** **ASIC (Application-Specific Integrated Circuit)**

- **정의**: 특정 용도(애플리케이션)에 맞춰 설계·제작된 전용 칩
- **특징**

  - 설계가 고정 → 제작 후 회로 변경 불가
  - 목적에 최적화 → 속도, 전력 효율, 크기에서 최고 성능
  - 반도체 제조 공정(실리콘 웨이퍼)으로 생산 → 단가가 높지만, 대량 생산 시 유리
- **장점**

  - 최고 성능·최저 전력 소모
  - 소형화 가능
- **단점**

  - 설계·제작 비용 매우 높음(수백만~수천만 달러)
  - 한번 제작하면 수정 불가 → 재설계 필요

**💡** **FPGA (Field-Programmable Gate Array)**

- **정의**: 사용자가 직접 회로 구성을 프로그래밍할 수 있는 재구성 가능 칩
- **특징**

  - 반도체 내부에 **프로그래머블 로직 블록**과 **스위칭 매트릭스**가 있어 회로를 재배치 가능
  - 설계 변경 및 반복 테스트 가능
  - 속도·전력 효율은 ASIC보다 낮지만, 개발 유연성 뛰어남
- **장점**

  - 제작 없이 회로 수정 가능 → 빠른 개발 및 검증
  - 초기 비용 낮음
- **단점**

  - ASIC보다 전력 소모 크고, 속도 느림
  - 동일 기능 구현 시 칩 면적 더 큼

**💡** **간단 비교표**

|  |  |  |
| --- | --- | --- |
| **구분** | **ASIC** | **FPGA** |
| **목적** | 특정 용도 전용 설계 | 다양한 회로 재설계 가능 |
| **성능** | 최고 수준(속도·전력 효율) | 낮음(ASIC 대비) |
| **유연성** | 없음 (고정) | 높음 (재프로그래밍 가능) |
| **개발 비용** | 높음 | 낮음 |
| **수정 가능성** | 불가 | 가능 |
| **적합 사례** | 대량생산, 상용화 제품 | 프로토타입, 연구·개발, 저량 생산 |
| **QEC 디코더 사용시** | 알고리즘이 확정되고, 상용 FTQC에서 초저지연·저전력 필요할 때 사용 | 연구/프로토타입 단계, 알고리즘 자주 수정해야 할 때 적합 |

**💡****FPGA 고려사항**

FPGA 디코더는 “지금 당장” 실시간성을 뽑아내기에 양컴 업체 입장에선 훨씬 현실적인 선택이다. 다만 현장에서 바로 부딪히는 고려사항/과제가 꽤 많다.

****

- **기술/아키텍처 이슈**

  - **왕복 지연(latency) 예산**: 측정→전송→디코딩→보정 명령까지 합쳐 **수십–수백 ns~수 µs** 안에 끝내야 함. 케이블 길이, 직렬화/역직렬화(SerDes), PCIe/Ethernet hop 수가 곧 성능.
  - **대역폭 & 병렬성**: d가 커지면 신드롬 스트림이 기하급수적으로 증가. BRAM/URAM, DSP, HBM이 달린 FPGA 사용 여부, 타일링/파이프라이닝 설계가 관건.
  - **알고리즘 매핑**:

    - *MWPM*은 그래프 매칭이 하드웨어화 까다롭고 리소스 많이 먹음.
    - *BP/Relay-BP*는 규칙적이고 병렬화가 쉬우나 **고정소수점 정밀도**와 반복 횟수(cap) 튜닝이 핵심.
  - **정밀도 vs 리소스**: 고정소수점 비트폭을 줄이면 자원은 절약되지만 디코딩 성능/임계값이 떨어질 수 있음. 하드웨어-인-더-루프로 최적 비트폭 탐색 필요.
  - **메모리 구조**: 로컬성 높은 접근 패턴으로 **은행 충돌** 줄이기. 행렬/그래프를 **스트림화**하거나 **엣지-리스트 압축** 필수.
  - **시계 도메인/동기화**: QPU 클럭, 파형생성기, 판독체인과 **deterministic**하게 맞물려야 함. CDC, 지터, 위상정렬 관리가 까다로움.
  - **패킷 드롭/에러 처리**: 신드롬 누락 시 안전 보정 전략(erasures, 재시도 창, 타임아웃 폴백)이 필요.

****

- **시스템 통합 이슈**

  - **물리적 배치**: PCIe 카드로 랙에 둘지, 컨트롤러 근처(혹은 크라이오 상단)에 붙일지. 케이블 길이/EMI/열 설계가 지연과 신뢰성에 직결.
  - **인터커넥트**: PCIe는 편하지만 레이턴시가 애매할 수 있음. **Aurora/SerDes, CXL, 저지연 이더넷** 등 선택지 비교 필요.
  - **실시간 피드백 경로**: 디코더 출력이 게이트 시퀀서/마이크로파 컨트롤러로 **조건부 분기**를 즉시 걸 수 있어야 함(펄스 테이블 스위즐, 미드서킷 reset/flip).
  - **소프트웨어 스택 연동**: 런타임/컴파일러와의 API, 마이크로코드/펌웨어 업데이트 파이프라인, 버전 호환성 관리.
  - **캘리브레이션 연동**: 에러모델이 변하면 디코더 파라미터(BP 메시지 스케일, 가중치)도 바꿔야 함. 부분 재구성(PR)로 다운타임 최소화.

- **운영/제품화 이슈**

  - **합성 시간 & 벤더 락인**: 대형 FPGA 비트스트림은 합성/배치배선이 **수시간~수십시간**. Xilinx/Intel 툴체인 종속성, 라이선스 관리.
  - **검증**: 정형검증/CDC 검증, HIL 테스트, fault-injection으로 **오류 시나리오**를 다 털어봐야 함.
  - **스케일아웃**: 다중-FPGA에서 디코딩 영역을 **분할/경계 통신**해야 함(코드 패치 경계에서 메시지 교환). 패브릭 토폴로지 설계가 관건.
  - **전력/열**: 랙 밀도 높아지면 수백 와트 열이 금방 쌓임. 팬/덕트/히트싱크 계획 선행.
  - **보안/IP**: 비트스트림 암호화, 펌웨어 서명, 디버그 포트(ILA, JTAG) 접근 통제.

****

- **R&D → 상용 전환 로드맵 팁**

  - **FPGA(유연성)로 알고리즘/파라미터 동결**
  - **부분 재구성/파라미터화로 운영 경험 축적**
  - **핫스팟 커널을 하드 코어화→ ASIC PoC**
  - **생산량/성능 임계점** 넘으면 ASIC로 이전(NRE 감당 가능 시)

****

- **체크리스트(실무)**

  - 목표 **왕복 지연(ns/µs)** 수치와 **신드롬 스루풋**을 먼저 고정
  - 정밀도 스윕(고정소수점 비트폭) × 성능/논리오류율 트레이드오프 맵 작성
  - 데이터 경로 스트림화(폭×주파수)와 **백-프레셔** 설계
  - 실시간 분기 API(조건부 게이트) 사양 확정
  - 합성/배치 자동화 파이프라인(CI) 구축, 회귀 벤치 포함
  - 다중-보드 스케일아웃/링크 예산(대역폭·지연) 문서화

- **정리**

  - FPGA 디코더는 “작은 제어보드” 수준으로 시작할 수 있지만, 실제 FTQC 스케일(d≥31)에서는 대역폭·메모리 요구가 워낙 커서 HBM급 FPGA나 다중 FPGA 보드 구성이 현실적이다.

**💡****어디서부터 ASIC을 고민하나?**

- 알고리즘/파라미터가 사실상 굳었고, **전력/지연/밀도**를 더 줄여야 할 때
- **d≥31**에서 1–5 MHz 라운드를 **여유 있게** 커버하려면,

  1. HBM-FPGA 다중 보드 **또는**
  2. **ASIC**로 커널 고정화가 보통의 경로

**✅****디코더를 QPU에 연결하는 방법**

개념적으로는 **디코더를 양자컴퓨터(QPU) 쪽에 “붙여버리는”** 게 지연(latency) 측면에서는 최적이다.

**💡 왜 좋은가**

- **측정 → 디코딩 → 보정** 경로가 **QPU 로컬에서 끝남**

  - → PCIe/NVLink/네트워크 hop 없이 바로 피드백 가능
- 왕복 지연이 **케이블 길이 + 로직 지연** 수준으로 떨어짐

  - (수 ns~수백 ns 레벨까지 가능)
- 조건부 게이트, 미드서킷 리셋, 즉시 피드백 연산 같은 **진짜 FTQC 필수 기능**을 제약 없이 구현 가능
- QPU 제어 시스템(마이크로파/레이저 컨트롤러)과 **동일 클럭·동일 타이밍 도메인**에서 동작

  - → 동기화 문제 최소화

****

**⚠️ 하지만 실제 구현 시 고려·제약**

1. **물리적 환경**

   - 초전도: 디코더는 상온 영역에 있어야 함 → 크라이오-상온 연결에서 최소 지연 인터페이스 필요
   - 이온트랩/광자: QPU 제어기 근처 랙에 장착 가능하지만, **EMI·온도** 설계 필요
2. **발열/전력**

   - FPGA/HBM급은 수십~수백 W 소모 → QPU 랙 전원·냉각 설계에 부담
3. **공간**

   - 기존 QPU 컨트롤러 섀시에 FPGA 보드를 넣을 공간이 있는지
   - 경우에 따라 **백플레인 통합** 설계 필요
4. **펌웨어·업데이트**

   - 알고리즘 바뀌면 로컬 하드웨어 비트스트림 교체 필요 → 안정적인 원격 업데이트/롤백 체계 필수
5. **EMI / 타이밍 간섭**

   - 디코더 클럭, 고속 I/O 신호가 QPU 아날로그 제어라인(파형 발생기, 측정기)에 **잡음 유입** 가능 → 신호 분리·쉴딩 필요
6. **개발 난이도**

   - QPU 컨트롤러 + FPGA 디코더를 하나의 시스템으로 동작시키는
   - **하드웨어·펌웨어·소프트웨어 통합 설계**가 필요

**📌 정리**

이 방식이 **성능·지연 면에서는 최고**다.

- 프로토타입/실험 단계 → **별도 랙·케이블로 연결된 FPGA**
- 상용/대규모 단계 → **QPU 컨트롤러 내부에 FPGA/ASIC 디코더 내장**
- 이 순서로 가는 경우가 현실적이다.

****

**💡이온트랩 계열 QPU는 비교적 가능?**

**이온트랩 계열 QPU**라면 디코더를 QPU 제어 시스템 바로 옆(혹은 내부)에 두는 게 상대적으로 훨씬 구현이 쉽다.

1. **상온 동작**

   - 초전도 QPU처럼 극저온(10–20 mK) 환경이 필요 없어, 디코더 FPGA/ASIC을 같은 랙이나 인접 섀시에 설치 가능
   - 크라이오-상온 인터페이스에서 오는 지연·신호 감쇠 문제 없음
2. **광학/전자 제어 분리 구조**

   - 레이저·전압 제어기(DC, RF, 마이크로파)와 디코더를 같은 타이밍 도메인에 쉽게 묶을 수 있음
   - 고속 디지털 제어라인(Trigger, TTL, LVDS)로 직접 연결 가능
3. **공간/전력 여유**

   - 광학 테이블/랙 구조라서 고성능 FPGA 보드나 HBM 모듈 추가 장착 여지가 큼
   - 수십~수백 W급 발열도 적절한 랙 냉각으로 처리 가능
4. **낮은 인터페이스 지연**

   - 이온 측정 → 광검출기 → 디지타이저 → FPGA 디코더 → 보정 파형 출력까지 수백 ns~수 µs 가능
   - 광학 신호 변환 단계를 제외하면 hop 수가 적음

**💡이온트랩 계열 QPU에서 고려해야 할 과제**

- **광검출 신호 처리 속도**

  - 포토멀티플라이어(PMT)/APD/SPAD에서 오는 신호를 디지털화하는 지연이 전체 루프에 포함됨
- **디코더-FPGA와 제어기 간 동기화**

  - 마이크로파·RF 펄스 시퀀서와 클럭/트리거 동기 정확히 맞춰야 함
- **레이저 안정화/보정 피드백 통합**

  - 디코더 결과를 레이저 주파수·위상·진폭 제어에 즉시 반영하려면, 광학 제어 소프트웨어와 실시간 경로 설계 필요
- **소프트웨어 업데이트 체계**

  - 알고리즘 변경 시 FPGA 비트스트림 재배포 및 안정성 검증 필수

**💡이온트랩 계열 QPU에 연결 가능한 디코더 조건 유형**

1. **안전형(검증·프로토타입)**

   - **플랫폼**: 이온트랩, PMT/APD 판독
   - **라운드 주기**: **200 kHz** (주기 5 µs)
   - **코드 거리**: **d ≈ 13–17**
   - **디코더**: BP/Relay-BP, **3회 반복**, 8-bit 고정소수점
   - **하드웨어**: **중급 FPGA**(HBM 없음), Aurora/SerDes 직결
   - **목표 왕복 지연**(측정→디코딩→보정): **≤ 20–40 µs**

     - 완전 실시간(라운드마다 즉시 보정)은 아니어도, 1~수 라운드 내 피드백으로 실험 안정화에 충분
2. **공격형(실시간 FTQC 지향)**

   - **라운드 주기**: **1 MHz** (주기 1 µs)
   - **코드 거리**: **d ≈ 21–31**
   - **디코더**: Relay-BP, **5회 반복**, 8–10-bit 고정소수점
   - **하드웨어**: **HBM 달린 대형 FPGA**(Versal/Stratix MX), 판독·제어기와 **동일 랙/섀시** 배치
   - **목표 왕복 지연**: **≤ 2–5 µs** (라운드 내 즉시/다음 라운드 직전 보정)
