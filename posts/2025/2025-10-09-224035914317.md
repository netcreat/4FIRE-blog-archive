**✅****PQC 4종 세트**

- - **CRYSTALS-Kyber → ML-KEM**(FIPS 203, 최종) : 키 합의/교환용 KEM.
  - **CRYSTALS-Dilithium → ML-DSA**(FIPS 204, 최종) : 전자서명 표준의 주력.
  - **SPHINCS+ → SLH-DSA**(FIPS 205, 최종) : 해시 기반 서명(보수적 백업).
  - **Falcon → FN-DSA**(FIPS 206, *초안 준비/발표 중*) : 소형 서명, 부동소수점 구현 이슈.

---

**✅****이름의 유래와 의미**

**💡****CRYSTALS (Kyber, Dilithium의 패밀리명)**

- - **뜻**: *CRYptographic Suite for Algebraic Lattices* 의 약자.
  - 즉, **격자 기반 암호 모음집**이라는 의미의 약자 이름이다.
  - 동시에 “Crystal(수정, 결정체)”라는 단어는 **투명·단단·깨지지 않는** 이미지를 주고, 암호학적 안정성을 상징하기도 한다.
  - 여기서 두 알고리즘이 파생:

    - **Kyber** (키 교환)
    - **Dilithium** (서명)

**💡****Kyber (카이버)**

- - Cyber(사이버)에서 따온 **신조어**.
  - “Kyber Crystal”은 사실 **스타워즈(Star Wars)** 세계관에서 광선검(Lightsaber)의 에너지원으로 나오는 결정 이름이기도 함
  - 따라서 “Kyber”는 **사이버 보안 + SF 결정체**라는 이중적 의미를 담은 셈이다.

**💡****Dilithium (딜리튬)**

- - **실제 화학 명칭**: Li2 (리튬 두 개가 결합된 화합물)
  - 하지만 대중적으로는 **스타트렉(Star Trek)** 시리즈에서 우주선의 워프 드라이브를 구동하는 **딜리튬 크리스탈**로 유명하다.
  - “미래 우주 엔진을 돌리는 핵심 자원”이라는 이미지 → **안정적이고 강력한 서명** 알고리즘이라는 상징성을 담았다고 볼 수 있다.

**💡****SPHINCS+**

- - **뜻**: *Stateless Practical Hash-based Incredibly Nice Cryptographic Signature*
  - 이름 자체가 약간 농담조로 만들어졌다 (“Incredibly Nice” 같은 표현).
  - 동시에 “Sphinx(스핑크스)”라는 고대 신화 속 존재를 연상시킴.
  - 해시 기반 서명은 **아주 오래된 원리 위에 세워진, 영속적이고 단단한 보안**을 상징하기에 “스핑크스”라는 이름이 어울린다.

**💡****Falcon**

- - **뜻**: *Fast Fourier Lattice-based Compact Signatures over NTRU* 의 약자.
  - 동시에 매(독수리)라는 뜻의 보통명사 → 빠르고 날렵하다는 이미지를 주죠.
  - Falcon은 실제로 Dilithium보다 **서명이 작고 빠르다**는 특징이 있는데, 이름과도 잘 맞다.

---

**✅PQC 알고리즘**

**💡****FIPS 203 - ML-KEM (Module-Lattice-Based Key-Encapsulation Mechanism)**

**첨부파일**

NIST.FIPS.203.pdf

[파일 다운로드](https://download.blog.naver.com/open/9d088137221617a3866e0f3800e59fe64317eb39/EFsQaLZKxLbO9tJdLuoSggWaFwbSq-pjY1cRJWkk_gMvH4q-UnUh6vm4D4IO5E9Pqgr6bkf77ntdK91RGQm5xKJ61XQqI8M/NIST.FIPS.203.pdf)

- - **기능**: 키 캡슐화 메커니즘(KEM), 즉 키 교환·세션 키 생성.
  - **원래 이름**: CRYSTALS-Kyber
  - **특징**:

    - 공개키/암호문 크기가 작음.
    - 연산 속도가 빠르고 TLS, VPN, 이메일 보안 등에 바로 적용 가능.
    - 하이브리드 모드(ECDHE+Kyber)가 이미 Chrome, Cloudflare 등에서 시험/배포 중.
  - **장점/주의**

    - 키·암호문이 작고 빠르며, 네트워크 핸드셰이크에 적합. Chrome/서버에서 실전 배포가 진행 중.
    - **KyberSlash**(타이밍 채널)류 구현 취약점이 보고된 바 있음 → **상수시간(decap) 패치/라이브러리 업데이트** 필수. 표준 자체가 깨진 게 아니라 **취약 구현** 문제.
  - **표준 파라미터와 크기 (****FIPS 203****)**

|  |  |  |  |  |
| --- | --- | --- | --- | --- |
| **수준** | **스위트** | **공개키** | **개인키** | **암호문** |
| NIST Cat-1 | **ML-KEM-512** | 800 B | 1,632 B | 768 B |
| NIST Cat-3 | **ML-KEM-768** | 1,184 B | 2,400 B | 1,088 B |
| NIST Cat-5 | **ML-KEM-1024** | 1,568 B | 3,168 B | 1,568 B |

- - - 보안 강도 카테고리

      - 대략적으로, **기존 암호와 비교되는 안전 수준**을 뜻한다.

        - **Cat-1**: 약 RSA-2048, AES-128과 비슷한 보안 강도.
        - **Cat-3**: 약 AES-192와 비슷.
        - **Cat-5**: 약 AES-256 수준의 보안 강도.
      - Cat 숫자가 높을수록 더 강력하지만, 키 크기나 속도도 커지고 느려짐
    - 스위트

      - Kyber(ML-KEM)의 구체적 변형(variant)을 의미.
      - 뒤 숫자(512, 768, 1024)는 내부 격자 차원(파라미터 크기)에 따른 이름이지, 키 크기를 직접 나타내는 건 아님
    - 의미

      - **보안 수준**(Cat-1/3/5)에 따라 Kyber 파라미터가 다르고, 그에 따라 **키 크기·암호문 크기도 달라짐**.
      - Cat-1은 가볍고 빠르지만 보안 강도 낮음, Cat-5는 강하지만 키/암호문 크기가 큼.
      - 실제로는 균형점인 ML-KEM-768 (Cat-3)이 많이 권장됨 (Chrome, Cloudflare, AWS 실험에서도 주로 이걸 씀).

**💡****FIPS 204 – ML-DSA (Dilithium 기반)**

**첨부파일**

NIST.FIPS.204.pdf

[파일 다운로드](https://download.blog.naver.com/open/60f57cccdc818458759bf2c3f81b621bbbec14f4da/EFsQaLZKxLbO_t82E-QRigSVEg-Y6uFydEYGIXwPkAUuGYq-Wnou5Pu9Du82-C4krkydQVP5PVe-oZ_wrIGN7gJDigtLwA/NIST.FIPS.204.pdf)

- - **기능**: 전자서명(디지털 서명 표준의 주력).
  - **원래 이름**: CRYSTALS-Dilithium
  - **특징**:

    - 격자 기반, 구현이 단순하고 안전성 검증이 잘 됨.
    - 서명 크기가 Falcon보다 크지만, 안정성과 속도에서 균형이 좋음.
    - 코드 서명, 소프트웨어 업데이트, 인증서 서명 등에서 권장.
  - **장점/주의**

    - 부동소수점 없이 구현이 단순하고 상수시간 구현 용이, 검증 속도가 준수.
    - 서명이 Falcon보다 **크다** → 인증서 체인/대역 예산을 고려
  - **표준 파라미터와 크기 (****FIPS 204****)**

|  |  |  |  |  |
| --- | --- | --- | --- | --- |
| **수준** | **스위트** | **공개키** | **개인키** | **서명** |
| Cat-2 | **ML-DSA-44** | 1,312 B | 2,560 B | 2,420 B |
| Cat-3 | **ML-DSA-65** | 1,952 B | 4,032 B | 3,309 B |
| Cat-5 | **ML-DSA-87** | 2,592 B | 4,896 B | 4,627 B |

- - - 보안 강도 카테고리

      - 대략적으로, **기존 암호와 비교되는 안전 수준**을 뜻한다.

        - **Cat-2**: 대략 AES-128 수준 (RSA-3072 정도와 비교).
        - **Cat-3**: 약 AES-192와 비슷.
        - **Cat-5**: 약 AES-256 수준의 보안 강도.
      - Cat 숫자가 높을수록 더 강력하지만, 키 크기나 속도도 커지고 느려짐
    - 스위트

      - ML-DSA 알고리즘의 **구체적 변형(variant)**.
      - 뒤 숫자(44, 65, 87)는 내부 파라미터(다항식 차수 등)를 나타내고, Cat-2/3/5 보안 수준에 대응
    - 의미

      - **ML-DSA는 안정적이고 안전하지만, 서명 크기가 크다** → 인증서 체인이나 대역폭이 제한된 시스템에서는 부담
      - 그럼에도 불구하고 **구현 단순성·안정성·보안성** 때문에 NIST가 **주력 전자서명 표준**으로 채택했음
      - Falcon(FN-DSA)는 더 작지만 구현이 까다로워서 보조적 표준으로 늦게 따로 나온다.

**💡****FIPS 205 – SLH-DSA (SPHINCS+ 기반)**

**첨부파일**

NIST.FIPS.205.pdf

[파일 다운로드](https://download.blog.naver.com/open/03961facb6e7e73b16f891a09b780178d88f779763/EFsQaLZKxLbO9d5ZLuoSggWaFwbSq-pjY1cRJWkk_gMvH4q-UnUu7vy6DoYOhysnrTKLbkf77hobRZ_DVrRMCjTTll-wNXE/NIST.FIPS.205.pdf)

- - **기능**: 전자서명(백업/보수적 대안).
  - **원래 이름**: SPHINCS+
  - **특징**:

    - 해시 기반(stateless hash-based signature).
    - **수학적 보수성이 가장 강력** — 해시 함수만 의존.
    - 서명 크기가 매우 크지만, 격자류 전체가 위험해졌을 경우를 대비한 **백업용** 표준.
  - **장점/주의**

    - **수학적 보수성 최고**(해시만 의존). 구현 단순, 부채널 리스크 낮음.
    - 서명이 크고 서명·검증이 상대적으로 느림 → 대역 민감한 인증서 체인에는 부담.
  - **표준 파라미터와 크기 (****FIPS 205** **— s: 작은 서명, f: 빠른 서명)**

|  |  |  |  |
| --- | --- | --- | --- |
| **수준** | **스위트(예)** | **공개키** | **서명** |
| Cat-1 | **SLH-DSA-SHAKE-128s** | 32 B | **7,856 B** |
| Cat-1 | **SLH-DSA-SHAKE-128f** | 32 B | **17,088 B** |
| Cat-3 | **…-192s / 192f** | 48 B | 16,224 / 35,664 B |
| Cat-5 | **…-256s / 256f** | 64 B | 29,792 / 49,856 B |

- - - 보안 강도 카테고리

      - 대략적으로, **기존 암호와 비교되는 안전 수준**을 뜻한다.

        - **Cat-1**: 대략 AES-128 수준
        - **Cat-3**: 약 AES-192와 비슷.
        - **Cat-5**: 약 AES-256 수준의 보안 강도.
      - Cat 숫자가 높을수록 더 강력하지만, 키 크기나 속도도 커지고 느려짐
    - 스위트 (s/f 버전)

      - **s (small)**: 서명이 더 작음, 하지만 서명 속도가 느림.
      - **f (fast)**: 서명이 더 큼, 하지만 서명 속도가 빠름.
      - 즉, “속도 vs 크기” 트레이드오프가 존재다.
    - 의미

      - SPHINCS+는 해시 기반이라 **가장 보수적이고 안전**다. (양자컴퓨터가 해시를 깨기는 훨씬 어렵기 때문)
      - 하지만 **실제 서명 크기가 너무 커서** 일반 서비스용 주력 서명으로는 비효율적이다.
      - 그래서 **백업 표준**으로만 채택:

        - Dilithium(ML-DSA)에 치명적 취약점이 발견될 경우 대비
        - 장기 보관(국가기록, 아카이브)이나 **극도의 안정성**이 필요한 경우에만 고려

**💡****FIPS 206 - FN-DSA (Falcon) — (*****초안 단계*****)**

**첨부파일**

[파일 다운로드](https://download.blog.naver.com/open/c154dd6e7d2d25f9d43a536259bac3ba1a4db554eb/EFsQaLZKxLbO9t5dLuoSggWaFwbSq-pjY1cRJWkk_gMvH4q-U30i7va3CIMO22tDrQ2Hbkf77iJ4MWoJXZpqMnBd-RC-WcE/NIST.FIPS.206-perlner_2.1.pdf)

- - Falcon은 **서명 크기가 작고 검증 속도가 빠르지만**, 구현이 복잡하고 부동소수점 연산에 의존한다는 단점이 있어 Dilithium에 비해 채택 속도가 늦음.
  - 향후 DNSSEC, 블록체인 등 대역폭 제한 환경에서 주로 활용 예상.
  - **전형적 크기(저자/커뮤니티 레퍼런스)**

    - **Falcon-512**: 공개키 ≈ **897 B**, 서명 **~666 B(평균)**
    - **Falcon-1024**: 공개키 ≈ 1,793 B, 서명 ~1,280 B
    - (정확 값/인코딩에 따라 약간 변동; 고정길이 옵션도 존재)
  - **장점/주의**

    - 같은 보안수준에서 **가장 작은 서명/검증 고속**.
    - **부동소수점·가우시안 샘플링**으로 구현 난이도↑, 검증/밸리데이션이 까다로움 → 표준(FIPS 206)에서 구현 가이드가 보강되는 중.

**💡****어디에 무엇을 쓸까 (실무 체크리스트)**

- - **전송(세션) 보안/TLS·QUIC 키 합의**

    - → **ML-KEM-768(또는 1024) + ECDHE 하이브리드** 추천. 이미 Chrome/서버에서 대규모 실험·배포 중. **핸드셰이크 크기 증가**(ClientHello가 ~1KB+ 커짐)와 미들박스 호환성을 사전 점검.
  - **코드/펌웨어 서명, 일반 인증서**

    - → **ML-DSA(=Dilithium)** 주력. 구현이 단순하고 빠르며 생태계 지원이 가장 활발. (단, 서명 크기 고려)
  - **대역/저장소가 매우 빡빡한 서명(DNSSEC 등)**

    - → **Falcon(FN-DSA)** 검토 가치 큼(서명·PK가 매우 작음). 다만 **FIPS 206이 아직 초안 단계**이므로 구현 가이던스와 부동소수점 이슈를 면밀히 추적.
  - **최대 보수성/장기 신뢰 보장 필요**

    - → **SLH-DSA(SPHINCS+)** 병행 또는 백업 채택. 서명 크기·속도 트레이드오프를 감안해 정책적으로 선택.

**💡****구현/운영 팁 (필수 체크)**

- - **상수시간 구현**: Kyber 계열은 **KyberSlash**류 타이밍 이슈가 있었음 → 최신 라이브러리(패치 완료판)로 링크, CI에서 TVLA/마이크로벤치로 회귀검증.
  - **하이브리드 전환**: TLS 1.3 **하이브리드 KEX** 초안(IETF)과 Chrome 배포 참고. 방화벽/프록시의 ClientHello 크기 제한 튜닝.
  - **인증서 체인 크기**: ML-DSA/SLH-DSA는 체인 크기 증가 → MTU/핸드셰이크 분할, OCSP 스테이플링, SCT/증명 데이터 최적화 고려. (수치 예산은 위 표를 합산해 산정)
  - **암호 민첩성(crypto-agility)**: API를 KEM/DSA 추상화로 감싸 교체 가능하게 설계.
  - **인증 모듈 밸리데이션**: Falcon(FN-DSA)은 **부동소수점 결정성/검증 난이도**가 별도 과제 → NIST 발표자료의 검증 가이드를 추적.

**✅****PQC 알고리즘의 장점과 단점**

**🔑 왜 PQC가 양자 공격에 안전한가?**

- - 현재 우리가 쓰는 RSA, ECC는 양자컴퓨터에 취약하다:

    - **RSA, ECC** → 큰 정수 소인수분해, 이산 로그 문제 기반
    - **쇼어 알고리즘(Shor’s Algorithm)**: 양자컴퓨터에서 이 문제를 **다항시간에 풀어버림** → 현재 공개키 암호 대부분이 깨짐
  - 따라서 새로운 알고리즘들은 **양자컴퓨터에서도 풀 수 없는(또는 매우 어려운) 수학적 문제**를 기초로 한다. 예를 들어:

    1. **격자 문제 (Lattice problems)**

       - Kyber, Dilithium, Falcon → **LWE (Learning With Errors), NTRU, Module-LWE**
       - 고차원 격자에서 최단 벡터 찾기(SVP)나 근접 벡터 문제(CVP)는 **고전/양자 모두에서 지수 시간** 필요
    2. **해시 기반 문제**

       - SPHINCS+ → 해시 함수의 충돌/프리이미지 저항성
       - 양자컴퓨터는 그루버 알고리즘(Grover’s Algorithm)으로 해시 탐색 속도를 **제곱근 가속**할 수 있지만, 여전히 **완전 무력화는 불가능**
       - 즉, 해시 크기를 두 배로 늘리면 안전성 유지 가능
    3. **다변수 다항식 문제 (Multivariate polynomial problems)**

       - 다른 후보군(MQ - Multivariate quadratic equations - 다변수 이차식) 기반 서명 등)

         - Rainbow - 최종 후보였으나 채택 안됨
         - GeMSS - 구현 효율성과 보안성 문제로 채택안됨
       - NP-hard 문제 → 양자에서도 풀기 어려움

**📦 왜 키/서명 크기가 커졌나?**

- - 기존 RSA/ECC는 **아주 우아한 수학적 구조** 덕분에 키가 작았고, 속도도 빠름.
  - PQC는 훨씬 **더 난해하고 일반적인 수학적 문제**(격자, 해시 트리 등)를 쓰기 때문에,

    - 키/서명이 **수 KB ~ 수십 KB**로 커지고,
    - 연산량도 커져서 속도가 느려지는 경우가 많음.
  - 즉, 크기가 커진 건 부작용이지 **보안성의 직접 원인**은 아니다.

**📌 PQC 알고리즘 안전한가?**

- - **안전성의 본질** = RSA/ECC처럼 양자에 깨지는 문제 대신, **양자 알고리즘에도** **어려운 문제**(격자·해시·다변수 등)를 사용한다는 것.
  - **크기와 속도 변화** = 그 대가로 나타난 현상.
  - 그래서 NIST는 “안전하면서도 성능이 현실적인 후보”만 골라 표준화한 것이다.
  - 이제 걱정할 필요가 없나?

    - 아니다. 완벽한 것은 없다.

**💡****NIST PQC가 “완벽”이 아닌 이유**

- - NIST PQC는 “현재 알려진 수학·공격 모델에서 **매우 강력하고 실용적인 선택**”일 뿐, 언제든 **새 공격/구현 취약점**이 발견될 수 있다.
  - **가정 기반 안전성**: ML-KEM/ML-DSA는 격자(LWE/Module-LWE), SLH-DSA는 해시 강도에 기댄다. “증명된 무조건 안전”이 아니라 **양자 포함 계산적 난이도 가정**이다.
  - **구현/운영 리스크**: 표준은 안전해도 **사이드채널(타이밍/캐시/전력)**, 랜덤성/키관리, 잘못된 통합으로 취약해질 수 있다.

    - 그래서 NIST는 **지금 바로 이 3종(FIPS 203/204/205)을 쓰되** 향후 백업 표준도 병행 검토 중이라고 못 박음
  - 암호 민첩성(agility)이 전제: NIST의 전환 가이드(IR 8547 초안)는 **교체 가능한 구조**로 배치하라고 권고한다.

**💡****그럼 QKD가 “해답”인가?**

- - 그렇다고 **QKD가 대체제가 아니다. 단지 보완재**이다.

    - 전 세계 인터넷에 바로 깔 수 있는 기술은 **PQC** 쪽이고,
    - **QKD**는 특수한 구간형(전용 광·위성) **키 분배**에 한정됨.
    - 디지털 서명·소프트웨어 업데이트 같은 건 **QKD로 대체 불가**임.
  - **부분적으로, 특정 상황에서만** 해당됨. QKD의 성격을 딱 정리하면:

    - **역할**: 통신 양단이 **대칭키를 분배**하는 기술(양자 채널+고전 채널).

      - **서명/신원확인/소프트웨어 서명은 못한다.**(그래서 인터넷 전반의 PKI를 대체 못 함)
    - **인증이 필수**: QKD 자체도 **고전 채널 인증**이 필요하고, 여기엔 고전 암호(이제는 PQC 서명)가 쓰인다.

      - 즉, **QKD를 사용해도 PQC가 필요**함.
    - **배포성·비용·물리 한계**: 전용 광(감쇠), 거리/중계(**trusted node** 필요), 장비 보안/운영 난이도.

      - **도시망/국가 백본/위성 등 특수 구간**엔 실증이 있지만 범용 인터넷에 즉시 깔 수 있는 성격은 아님.
    - **실장 취약점**: 이론은 정보론적 안전성이지만, **현실 장치의 사이드채널**(검출기 블라인딩, 레이저 타이밍 편차 등)로 약점이 나온. (Micius 관련 취약점 분석 등) ⇒ **장치·운영 보안**이 성패를 좌우.

      - 아래 논문은 중국의 세계 최초 양자위성 묵자가 해킹가능하다는 것을 설명한다.

- - - **장점**: 구축만 잘 되면 **장기 키 안전성**(정보론적)과 **양자도청 탐지**가 가능하여, **국가기간 통신/금융 백본/데이터센터 간 전용망** 같은 **초고가치 링크**에 매력. 위성-QKD/지상 혼합 사례도 진전 중.

**💡****무엇을 선택할까 (실무 가이드)**

- - **기본 원칙**: 인터넷 전반, 소프트웨어 서명, TLS, VPN, 전자문서 서명은 **PQC 우선**. 지금 바로 ML-KEM(키합의) + ML-DSA(서명)로 전환을 시작해야함. (FIPS 203/204/205 **확정**)
  - **하이브리드 권장**: 과도기엔 **기존(ECDHE/ECDSA)+PQC** 하이브리드로 배치해 상호운용/후퇴 안전장치 확보. (NIST 전환 권고)
  - **QKD는 선택적 보강**: **전용 광/위성 구간**에서 “가용성·비용을 감수하고도” **최고 수준의 링크 보안**을 원하는 경우 **PQC+QKD 병행**을 검토. 다만 클래식 인증(PQC 서명)은 계속 필요함함
  - **민첩성 확보**: 라이브러리 업데이트, 키/서명 길이 예산, 인증서 체인 팽창 관리, 사이드채널 테스트(TVLA 등), 교체 가능한 암호 추상화 계층을 준비.
