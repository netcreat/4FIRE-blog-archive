**✅ 최대”와 “항상”은 다르다**

[![](https://mblogthumb-phinf.pstatic.net/MjAyNjAzMDNfMjcw/MDAxNzcyNTEwOTM5MjQz.F8LV47wviINGVzJ2brbRwIVQSGXvWMaKUB3Yr24L-Ogg.claiOy8lCDK70YpK46p_vbN3JzA1Jy8iDAdL_spjPuEg.PNG/image.png?type=w800)](#)

- - Tbps 달성 = 기술 이벤트
  - 99.9% 가용성 = 운영 체계의 결과
  - 레이저는:

    - 성능 압도적
    - 구름 앞에서는 0
  - 고객은 0을 허용하지 않음
  - 그래서 질문이 바뀐다:

    - 얼마나 빠른가? ❌
    - 언제나 되는가? ✅

**1️⃣ 병목의 이동 (****1~4편 요약)**

- - 고차 QAM 가능
  - Coherent DSP 가능
  - FPGA vs ASIC 논의 완료
  - 방사선 대응 구조 설명
  - Merchant DSP 현실성 분석
  - ➡️ “가능한가?”는 거의 정리됨
  - **이제 남은 질문******

    - 수천 위성
    - 수백 OISL
    - 다중 게이트웨이
    - 동적 트래픽
  - 이 상황에서 병목은 어디?

    - 👉 광학?
    - 👉 DSP?
    - 아니다.
  - 👉 **운영(Orchestration)**

****

**2️⃣ OISL이 늘어나면 벌어지는 일**

- - 링크 상태는 매 순간 변함
  - 가시권이 계속 바뀜
  - 기상 영향 존재
  - 큐가 몰림
  - 경로가 재구성됨
  - 즉, 우주망 = 동적 분산 시스템

**3️⃣ Ground Segment의 재정의**

- - 지상국 ≠ 망원경
  - 지상국 = 운영 플랫폼
  - **3개 층으로 나뉨**

    1. **물리 계층**

       - Optical gateway
       - RF fallback
       - 전력/열/사이트 인프라
    2. **네트워크 계층**

       - 경로 계산
       - QoS
       - 우선순위
       - 혼잡 제어
    3. **운영 계층 (진짜 핵심)**

       - 인벤토리 모델링
       - 서비스 오케스트레이션
       - 텔레메트리 수집
       - 자동 복구 루프
       - 정책 배포
  - ➡️ Tbps는 ③에서 결정된다

**4️⃣ 여기서 Nokia / Ciena가 등장하는 이유**

- - 우주망이 커지면:

    - 👉 통신사 백본과 닮아간다
  - **왜?**

    - 멀티도메인
    - 멀티레이어
    - SLA 요구
    - 트래픽 엔지니어링
    - 자동화 필수

**5️⃣ Nokia는 어떤 포지션인가**

- - **Nokia DNA**

    - IP 라우팅
    - Optical transport
    - 해저 케이블
    - 통신사 코어망
    - 운영 자동화 플랫폼(NSP)
  - 특징:

    - 광 + IP + 운영을 패키지로 묶음
    - “통신사식 운영”에 강함
    - 멀티도메인 통합 설계 경험
  - 우주망이 커질수록:

    - 👉 Nokia형 DNA가 필요해짐

**6️⃣ Ciena는 어떤 포지션인가**

- - **Ciena DNA**

    - Coherent DSP 강자
    - WaveLogic 계열
    - DCI/해저 최적화
    - 광 성능 중심 철학
  - 특징:

    - 광 엔진 최적화에 집중
    - 고차 QAM/OSNR tolerance 강점
    - 하이퍼스케일러 레퍼런스 많음
  - 우주 트래픽이 지상으로 내려올 때:

    - 👉 Ciena형 DNA가 강해짐

**7️⃣ DSP는 심장, 플랫폼은 신경계**

- - DSP = 속도 만든다
  - 운영 플랫폼 = 서비스 살린다
  - 링크가 죽는 순간:

    - 재라우팅
    - 게이트웨이 전환
    - 레이트 조정
    - 캐싱 전략 실행
    - 정책 재배포
  - 이걸 자동으로 해야 한다.

**8️⃣ 우주망 운영 루프**

1. 1. 관측

      - OSNR
      - BER
      - 큐 깊이
      - pointing margin
      - 가시 시간
   2. 판단

      - 정책 엔진
      - 우선순위
      - 미션 등급
      - 비용 모델
   3. 실행

      - 게이트웨이 변경
      - adaptive modulation
      - 경로 재구성
      - rate shaping
   4. 검증

      - KPI 회복 확인
      - SLA 유지 여부 판단
   - 👉 NOC는 조종사가 아니다
   - 👉 NOC는 **컴파일러**다

**✅ 결론**

**📌** **병목은 이동한다**

- - Tbps는 더 이상 기술 이벤트가 아니다.
  - 고차 QAM도, Coherent DSP도, 우주 환경 대응 설계도 이미 구현 가능한 영역에 들어왔다.
  - 문제는 속도가 아니라 **지속성**이다.

**📌** **링크 → 경로 → 운영**

- - OISL이 수십 개일 때는 링크 품질이 전부다.
  - 수백 개가 되면 경로 계산이 병목이 된다.
  - 수천 개가 되면 네트워크는 동적 분산 시스템이 된다.
  - 그때부터 성능은 광 엔진이 아니라 **오케스트레이션이 결정한다.**
  - 재라우팅, 게이트웨이 전환, 적응 변조, 정책 재배포, SLA 복구 루프.
  - Tbps는 ③, 즉 운영 계층에서 완성된다.

**📌** **그러나 기술은 멈추지 않는다**

- - 최근 Mynaric은 상용 CONDOR 터미널을 활용해 Free-Space QKD 실증에 성공했다.

  - 기술은 멈추지 않는다.

**📌** **그래서 승부는 어디서 나는가**

- - Skyloom을 비롯한 OCT 업체들은 이제 단순 전송 성능 경쟁에 머물 수 없다.
  - 적응 변조, 강력한 FEC, 링크 오케스트레이션, 보안 통합.
  - 우주망은 더 이상 실험이 아니다.
  - 통신사 백본처럼 설계되고, 데이터센터처럼 운영되며, 보안 네트워크처럼 진화하고 있다.
