**📌 Processor 부분**

- - 가운데 있는 박스는 GPU/CPU/ASIC 같은 Compute die
  - 그 안에:

    - **HBM Controller**
    - **PHY**
    - **I/O 인터페이스**
  - 이 있으며,
  - HBM Controller가 HBM에 직접 접근

**📌 HBM 부분**

- - 양쪽에 HBM stack이 쌓여 있음

    - DRAM die는 TSV(Through-Silicon Via)로 서로 연결됨
    - 맨 아래 Logic Die가 HBM의 메모리 컨트롤 및 PHY 담당
  - ✔ **DRAM → 데이터 저장 부분**
  - ✔ **Logic Die → DRAM 제어 + 하부 I/O + PHY**

****

**📌 Silicon Interposer**

1. 1. **초고밀도 신호 라우팅**

      - HBM과 Processor를 다음과 같이 연결:

        - HBM PHY ↔ Interposer ↔ Processor PHY
      - 왜 필요한가?

        - 일반 substrate(PCB)는 배선 pitch가 너무 큼
        - HBM은 수천 개의 I/O lane이 필요
        - 그래서 실리콘 기반의 높은 배선 density 필요
   2. **전원 공급 안정화 Capacitor 내장**

      - 그림에 보이는 두 가지:

        - ✔ **Embedded capacitor**
        - ✔ **On-interposer decoupling capacitor**
      - 이것들은:

        - 전압 드롭 방지(PDN 안정)
        - high-speed에서 noise 감소
        - current surge 대응
      - 특히 HBM은 전력 transients가 커서 매우 중요함

**📌 TSV + μBump**

- - **HBM 내부 DRAM TSV**

    - → 수직 DRAM stacking 연결
  - **Interposer TSV**

    - → 인터포저 → 기판(substrate)으로 연결
  - μBump는 다음 연결에 사용:

    - DRAM ↔ Logic Die
    - Logic Die ↔ Interposer
    - Processor ↔ Interposer

**📌 왜 이렇게 복잡한 구조가 필요한가?**

- - 엄청난 메모리 대역폭 요구 때문
  - Ex) HBM3 대역폭

    - 한 스택 = 819 GB/s
    - NVIDIA H100 → HBM3 5개 = 약 **3.9 TB/s**
    - B200 → HBM3E 8개 = **10 TB/s 수준**
  - 일반 DDR은 최대 60GB/s 정도니까 비교가 안 됨
  - **장점**

    - ✔ 초고대역폭 (TB/s급)
    - ✔ 낮은 지연시간
    - ✔ 높은 효율 (메모리 병목 완화)
    - ✔ 고밀도 패키징 가능
  - **단점**

    - ✔ 제조 비용 비쌈 (인터포저 공정 + TSV 공정)
    - ✔ 수율 문제
    - ✔ 발열 집중 → 냉각 설계 어려움
    - ✔ 실리콘 인터포저가 커질수록 웨이퍼 비용 상승

**📌 Memory Architecture Scaling**

- - 세 개 다 세대가 진행될수록 증가하는데 증가율이 다름:

    - **Bandwidth (파란선)** → **가장 빠르게 증가**
    - **Capacity (녹색선)** → 그 다음 증가
    - **Data rate (빨간선)** → 상대적으로 완만
  - HBM의 스케일링은 단순히 data rate만 올리는 것이 아니라 병렬성(I/O)과 stack 수, die 용량 확장으로 이루어짐

**📌 전송 속도(Bandwidth)**

- - **Data Rate (Gb/s per pin)**

    - **각 I/O(개별 비트 라인) 하나가 동작하는 속도**

      - 몇 Gb/s 로 한 라인이 데이터를 밀어내는가
    - 예:

      - HBM3E → **8 Gb/s per pin**
  - **Bandwidth (GB/s per stack)**

    - **전체 HBM stack 전체가 전송 가능한 총량**

      - 데이터 rate × I/O 수
    - Bandwidth ≈ Data rate × (# of I/O pins) / 8

      - (8로 나누는 건 bit → Byte 변환 때문)
  - **예시 계산**

    - HBM3E 기준:

      - Data rate = **8 Gb/s**
      - I/O = **1024 pins**
    - 계산:

      - 8 Gb/s × 1024 = 8192 Gb/s = 1024 GB/s ≈ 1.0 TB/s
    - → 이게 HBM3E의 스펙과 정확히 일치

**📌 전송 속도의 한계**

- - **per-pin data rate scaling에는 강한 물리적 한계**가 존재
  1. **신호 무결성(SI: Signal Integrity) 한계**

     - pin을 너무 빠르게 밀어붙이면 다음 문제들이 터짐:

       - **crosstalk (핀 간 간섭)**
       - **jitter (타이밍 변동)**
       - **ISI (inter-symbol interference)**
       - **return loss / insertion loss 증가**
       - **skew 보정 비용 증가**
     - 특히 HBM은 **수천 개의 핀을 병렬로** 쓰기 때문에,
     - “핀 하나는 버텨도 전체는 못 버티는 문제”
     - 즉 확률적으로 error rate가 폭증함
  2. **전력(전압 swing) ↔ 속도 trade-off**

     - 고속 신호는 더 큰 전력 소모 발생:

       - P ∝ C × V2 × f
     - per-pin data rate = 주파수 f 에 해당
     - 그래서 f를 두 배로 늘리면 전력도 거의 두 배 이상 증가
     - HBM4 들어가면 HBM3E 대비 스택당 전력 40~80W

       - → 공정상/패키지 열 한계에 걸림
  3. **채널 길이와 주파수 한계**

     - HBM 구조는

       - HBM die ↔ μBump ↔ Silicon interposer ↔ Controller
     - 이 구조는:

       - 채널이 **짧아서 좋은 대신**
       - **임피던스/리턴 경로 설계**가 촘촘하고 민감
     - 주파수 올리면 손실 커짐
     - 실제로 HBM3 이후부터는 LC/RC 손실 + 패키지 모델링 문제가 병목
  4. **열(thermal) 병목**

     - 속도 올릴수록:

       - 전력 증가 → 열 증가 → 온도 상승 → 누설 증가 → error 증가 → 다시 전력 증가…
     - HBM 같은 stack 구조는 열 배출이 어려워서 특히 불리

       - 그래서 HBM4부터 **D2C liquid cooling**이 언급됨

|  |  |  |
| --- | --- | --- |
| **방식** | **장점** | **단점** |
| **per-pin speed scaling** | 쉬움, 기존 방식 | 전력/열/신호 한계 빨리 등장 |
| **I/O 넓히기(parallel scaling)** | 선형적으로 BW 증가 가능 | 패키지/실리콘 인터포저 복잡 |
| **stack 용량 늘리기** | 모델 크기 대응 | 발열, 공정, 수율 문제 |

**📌 용량(Capacity)**

- - Capacity/die × # of Stack die / 8

    - (8로 나누는 건 bit → Byte 변환 때문)
  - **예시 계산**

    - HBM3E 기준:

      - Capacity/die = **24 Gb**
      - Stack = **8 or 12**
    - 계산:

      - 24 Gb × 8 = 192 Gb = 24 GB
      - 24 Gb × 12 = 288 Gb = 36 GB
    - → 이게 HBM3E의 스펙과 정확히 일치

> ***대역폭이 부족하면 작동은 되지만 느려지는 성능 병목(bottleneck) 문제***
>
> ***용량이 부족하면 작동이 아예 불가한, 적재 가능성(feasibility) 문제***
