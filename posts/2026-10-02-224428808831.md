# HBM 디스펙 이후, NVIDIA가 바꾸려는 것은 무엇인가?

Published: 2026-10-02T00:48:55+10:00

Original Naver post: https://blog.naver.com/4-fire/224428808831?fromRss=true&trackingCode=rss

---

**✅ 1. HBM 디스펙 논란, 정말 수요가 줄어드는 것일까?**

- - 2026년 9월 30일 Micron의 회계연도 4분기 실적 발표에서 흥미로운 질문이 등장했다.
  - TD Cowen의 Krish Sankar는 Micron CEO인 Sanjay Mehrotra에게 한 대형 고객이 HBM 사양을 낮추고 있다는 소문을 어떻게 생각하는지 질문했다.
  - HBM의 생산에 많은 DRAM 웨이퍼가 투입되는 만큼, 사양을 낮추고 남은 생산능력을 일반 DDR 생산으로 전환하면 공급에 어떤 변화가 생길지도 물었다.
  - 해당 고객의 이름이 공개적으로 확인된 것은 아니지만, 시장에서는 NVIDIA의 차세대 Rubin Ultra를 중심으로 이 문제를 논의하고 있다.
  - 사실 이번 논란은 갑자기 등장한 이야기가 아니다.
  - TrendForce는 이미 8월 4일 NVIDIA가 Rubin Ultra의 기존 12-Hi HBM4E 설계 외에 다른 구성을 검토하고 있다고 보도했다.

|  |  |  |
| --- | --- | --- |
| **검토 대상** | **적층 수** | **메모리 규격** |
| 기존 기준 설계 | 12-Hi | HBM4E |
| 대안 1 | 8-Hi | HBM4E |
| 대안 2 | 12-Hi | HBM4 |
| 대안 3 | 8-Hi | HBM4 |

- - 최종 사양은 아직 확정되지 않았다.
  - TrendForce가 지목한 원인은 2027년까지 이어질 DRAM 공급 제약과 12-Hi HBM4E의 검증 및 수율 확보 일정이다.
  - 중요한 것은 NVIDIA가 단순히 HBM 원가를 절감하기보다는 높은 I/O 속도를 우선하면서 생산 가능한 GPU 수까지 고려하고 있다는 점이다.

**📌 Micron의 답변은 정반대의 방향을 가리킨다**

- - Mehrotra CEO는 고객이 메모리 구성을 최적화하더라도 전체 메모리 수요가 감소하는 것은 아니라고 설명했다.
  - 오히려 고객들은 더 많은 AI 가속기를 출하하고 성장 기회를 확보하기 위해 이러한 최적화를 진행한다는 것이다.
  - Micron은 2027년과 2028년에도 HBM 수요가 일반 메모리 시장보다 빠르게 증가하고, 메모리 공급 상황은 계속 빠듯할 것으로 전망했다.
  - 삼성전자 역시 9월 29일 HBM이 2027년 전체 DRAM 웨이퍼 생산능력의 약 30%를 차지할 수 있다고 전망했다. 현재의 약 20%에서 상당히 증가하는 수준이다.
  - 따라서 이번 사건을 단순히 HBM 수요 감소의 신호로 해석하기는 어렵다.
  - 오히려 **한정된 HBM 생산능력으로 얼마나 많은 AI 연산능력을 확보할 것인가**라는 문제가 등장한 것으로 볼 수 있다.
  - 그렇다면 여기에서 또 다른 질문이 생긴다.
  - GPU 한 개에 장착하는 HBM 용량을 줄이면서도 AI 시스템 전체의 성능을 높이는 방법은 무엇일까?

---

**✅ 2. HBM은 용량과 대역폭을 구분해서 봐야 한다**

**📌 적층 수를 줄인다는 것은 무엇인가?**

- - HBM은 여러 개의 DRAM 다이를 수직으로 적층하고 TSV(Through-Silicon Via) 등을 이용해 연결하는 메모리다.
  - 일반적으로 적층 수가 늘어나면 하나의 HBM 스택에 더 많은 메모리 용량을 담을 수 있다.
  - 반면 생산 과정에서는 더 많은 DRAM 다이가 필요하고 적층과 패키징의 복잡성도 증가한다.
  - 단순한 예를 들어보자.

|  |  |  |
| --- | --- | --- |
| **구분** | **12-Hi** | **8-Hi** |
| DRAM 다이 수 | 12 | 8 |
| 동일 용량 다이 기준 상대 용량 | 100% | 66.7% |
| 스택당 DRAM 다이 사용량 | 100% | 66.7% |
| 추가 효과 | 높은 용량 | 다이 사용량 감소 |

- - 동일한 DRAM 다이를 사용하고 적층 수만 줄인다는 가정하에 8-Hi는 12-Hi보다 스택당 DRAM 다이 사용량이 약 33% 적다.
  - 다만 실제 생산량과 수율은 다이 크기, 적층 공정, 패키징 수율 및 제품 구성에 따라 달라지므로 다이 사용량 감소가 곧바로 동일한 비율의 GPU 출하량 증가를 의미하지는 않는다.

**📌 하지만 용량 감소가 반드시 대역폭 감소를 뜻하지는 않는다**

- - HBM에서 중요한 성능 지표는 용량뿐 아니라 메모리 인터페이스의 폭과 데이터 전송 속도다.
  - 동일한 인터페이스 폭을 유지하면서 핀당 전송 속도를 높이면 적층 수를 줄이더라도 높은 대역폭을 유지할 수 있다.
  - 다만 적층 구조, 채널 구성 및 전력 제약에 따라 실제 성능은 달라진다.
  - NVIDIA의 Rubin GPU는 공개 사양 기준 288GB HBM4와 최대 22TB/s의 메모리 대역폭을 제공한다.
  - NVIDIA가 Rubin Ultra에서 어떤 HBM 구성을 최종 선택할지는 별개이지만, 이번 사양 변경 검토에서 I/O 속도가 주요 고려사항이라는 점은 주목할 만하다.
  - 결국 용량과 대역폭을 분리해서 살펴봐야 한다.

    - **Capacity는 얼마나 많은 데이터를 보관할 수 있는가의 문제다.**
    - **Bandwidth는 그 데이터를 얼마나 빠르게 공급할 수 있는가의 문제다.**
  - 이 둘을 반드시 같은 비율로 증가시킬 필요는 없다.
  - 그리고 이 차이에서 앞으로의 메모리 아키텍처 변화가 시작된다.

---

**✅ 3. HBM을 33%나 줄이면서 성능을 유지할 수 있을까?**

- - 여기서 한 가지 중요한 의문이 생긴다.
  - NVIDIA가 HBM의 적층 수를 12-Hi에서 8-Hi로 줄이는 방안을 검토하고 있다면, 단순히 원가 절감이나 공급량 확대만으로 설명하기에는 부족하다.
  - 동일한 용량의 DRAM 다이를 사용한다는 가정하에 적층 수를 줄이면 스택당 메모리 용량이 약 33% 감소하기 때문이다.
  - 대역폭을 유지하더라도 줄어든 메모리 용량 때문에 실행할 수 있는 모델이나 동시 처리 가능한 작업이 제한된다면 결국 성능 저하가 발생할 수 있다.

    - 그렇다면 NVIDIA는 왜 이런 선택을 검토하는 것일까?
    - 메모리 용량보다 대역폭 병목이 훨씬 심각하기 때문일까?
    - 아니면 감소한 HBM 용량을 다른 방식으로 보완할 수 있는 기술을 확보했기 때문일까?
  - 이 질문에 답하기 위해서는 현재 AI 컴퓨팅에서 발생하는 병목부터 구분할 필요가 있다.

**📌 AI의 병목은 메모리 대역폭인가, 용량인가?**

- - 결론부터 이야기하면 둘 다 중요하다.
  - 다만 AI가 어떤 작업을 수행하는지에 따라 병목의 원인이 달라진다.

|  |  |
| --- | --- |
| **AI 작업** | **주요 병목** |
| LLM 학습 | 연산, 메모리 용량, GPU 간 통신 |
| LLM Prefill | 주로 연산 성능 |
| LLM Decode | 주로 메모리 대역폭 |
| 긴 Context 추론 | 메모리 용량 및 대역폭 |
| 대규모 동시 추론 | 용량, 대역폭, 연산 성능 |

- - 일반적인 LLM Decode에서는 새로운 토큰을 생성하는 과정에서 모델 가중치를 반복적으로 읽어야 한다.
  - 동시 처리량이 적으면 연산 장치의 성능보다 메모리가 데이터를 공급하는 속도가 병목으로 작용하기 쉽다.
  - 반대로 동시 사용자 수나 Context 길이가 증가하면 KV Cache가 빠르게 커진다.
  - 이 경우 HBM에 데이터를 얼마나 많이 보관할 수 있는지가 중요한 문제가 된다.
  - 따라서 메모리 용량보다 대역폭이 훨씬 중요하기 때문에 HBM을 줄인다는 해석은 모든 AI 작업에 적용할 수 없다.
  - 오히려 NVIDIA가 용량을 줄이려면 그만큼 다른 메모리 관리 기술이 중요해진다는 뜻이다.

**📌 디스태킹으로 실제 얼마나 손해를 보는가?**

- - 이해를 돕기 위해 288GB HBM을 사용하는 가상의 GPU를 생각해 보자.
  - 동일한 용량의 DRAM 다이와 동일한 HBM 스택 수를 유지한 상태에서 12-Hi를 8-Hi로 변경한다고 가정한다.

|  |  |  |
| --- | --- | --- |
| **항목** | **12-Hi** | **8-Hi** |
| GPU당 HBM 용량 | 288GB | 192GB |
| 용량 변화 | 기준 | -33.3% |
| HBM 대역폭 | 기준 | 인터페이스 구성에 따라 달라짐 |
| 스택당 DRAM 다이 수 | 12개 | 8개 |

- - 위 수치는 설명을 위한 가정이며 Rubin Ultra의 확정 제품 사양이 아니다.
  - 적층 수를 줄이더라도 인터페이스 폭과 전송 속도를 유지하면 메모리 대역폭은 유지될 수 있다.
  - 더 빠른 I/O를 사용한다면 대역폭을 높이는 것도 가능하다.
  - 그러나 메모리 용량은 명확하게 줄어든다.
  - 예를 들어 기존 작업이 240GB의 메모리를 필요로 한다면 288GB GPU에서는 실행할 수 있지만 192GB GPU에서는 그대로 실행하기 어렵다.
  - 이를 해결하려면 모델 자체를 분할하거나, 데이터를 압축하거나, 다른 메모리에 일부 데이터를 보관해야 한다.
  - 결국 **대역폭을 유지하는 것과 감소한 메모리 용량을 보완하는 것은 완전히 다른 문제**다.

**📌 그렇다면 NVIDIA는 어떤 기술을 준비했는가?**

- - NVIDIA가 이미 공개한 기술을 살펴보면 메모리 용량 문제를 해결하기 위한 몇 가지 접근을 발견할 수 있다.
  - 다만 아래 기술들이 모두 Rubin Ultra의 디스태킹을 위해 개발됐거나 해당 제품에 적용된다는 의미는 아니다.

|  |  |  |
| --- | --- | --- |
| **기술** | **역할** | **용량 감소 보완 방식** |
| NVFP4 양자화 | 데이터 크기 감소 | 모델·KV Cache 압축 |
| NVLink / Fusion | 고속 가속기 연결 | 여러 GPU의 분산 메모리 활용 |
| EGM / NVLink-C2C | GPU 메모리 접근 범위 확장 | CPU 메모리 활용 |
| Dynamo | 추론 자원 관리 | Prefill·Decode 분리 및 KV Cache 이동 |
| CMX | Context 전용 저장 계층 | 비활성 KV Cache 외부 보관 |

- - 특히 주목할 부분은 NVIDIA가 단순히 메모리 인터페이스의 속도만 높이고 있는 것이 아니라는 점이다.
  - 메모리가 필요한 양 자체를 줄이고, 분산된 메모리를 활용하며, 사용 빈도가 낮은 데이터를 외부로 이동시키는 소프트웨어와 하드웨어를 함께 개발하고 있다.
  - **① 양자화 — 메모리 요구량 자체를 줄인다**

    - NVIDIA는 NVFP4를 통해 모델 가중치와 KV Cache의 메모리 사용량을 줄이는 기술을 개발하고 있다.
    - 예를 들어 FP8 형식의 KV Cache를 NVFP4로 변환하면 이론적으로 데이터당 비트 수가 절반으로 줄어든다.
    - 실제 메모리 절감률은 스케일링 정보, 메타데이터 및 구현 방식에 따라 달라진다.
    - 또한 낮은 정밀도로 인해 모델 정확도가 영향을 받을 수 있으므로 모든 작업에 무조건 적용할 수는 없다.
    - 가상의 작업에서 모델 가중치가 112GB, KV Cache가 96GB, 기타 작업 공간이 24GB라고 가정해 보자.

|  |  |  |
| --- | --- | --- |
| **항목** | **기존** | **KV Cache 압축 후** |
| 모델 가중치 | 112GB | 112GB |
| KV Cache | 96GB | 48GB |
| 기타 작업 공간 | 24GB | 24GB |
| 총 필요 용량 | 232GB | 184GB |

- - - 기존에는 232GB가 필요하므로 192GB HBM에서 실행할 수 없다.
    - 그러나 KV Cache를 절반으로 줄일 수 있다면 총 184GB로 감소해 192GB 안에 들어갈 수 있다.
    - 물론 실제 시스템에서는 운영에 필요한 여유 공간과 메모리 단편화까지 고려해야 한다.
    - 중요한 것은 HBM 용량 감소를 다른 기술로 보완하는 것이 실제로 가능하다는 점이다.
    - 다만 모델 가중치가 200GB를 초과하는 경우처럼 기본 메모리 요구량 자체가 지나치게 크다면 KV Cache 압축만으로는 해결할 수 없다.
  - **② NVLink — 여러 GPU의 HBM을 활용한다**

    - NVLink는 여러 GPU 사이에서 고속 데이터 교환과 원격 메모리 접근을 지원한다.
    - NVLink Fusion은 이러한 기능을 타사의 Custom XPU까지 확장할 수 있도록 한다.
    - 모델과 작업을 여러 가속기에 분산하면 개별 GPU에 모든 데이터를 보관해야 하는 부담을 줄일 수 있다.
    - 그러나 이것은 메모리 용량을 새롭게 만들어 내는 기술이 아니다.
    - 다른 GPU에 이미 존재하는 HBM을 활용하는 것이다.
    - 또한 원격 메모리 접근은 로컬 HBM보다 낮은 대역폭과 추가 지연시간의 영향을 받는다.
    - 따라서 대규모 데이터 분산에 적합한 작업과 그렇지 않은 작업을 구분해야 한다.
  - **③ EGM과 CPU 메모리 — HBM 바깥으로 확장한다**

    - NVIDIA는 NVLink-C2C를 통해 GPU와 CPU를 고속으로 연결한다.
    - 지원되는 플랫폼에서는 EGM(Extended GPU Memory)을 통해 GPU가 CPU 메모리에도 접근할 수 있다.
    - HBM보다 용량이 큰 CPU 메모리를 활용해 일부 데이터의 보관 위치를 변경하는 방식이다.
    - 그러나 CPU 메모리 자체의 대역폭은 로컬 HBM에 미치지 못한다.
    - NVLink-C2C가 높은 전송 대역폭을 제공하더라도 CPU 메모리에서 실제로 데이터를 공급할 수 있는 속도에는 별도의 한계가 존재한다.
    - 따라서 자주 읽어야 하는 모델 가중치를 무조건 CPU 메모리로 이동시키는 것은 좋은 해결책이 아닐 수 있다.
  - **④ Dynamo와 CMX — 사용하지 않는 데이터를 외부로 이동한다**

    - AI 추론에서는 모든 데이터를 항상 같은 빈도로 사용하는 것이 아니다.
    - 특히 대규모 동시 사용자 환경에서는 KV Cache의 관리 방식이 중요해진다.
    - NVIDIA의 Dynamo는 Prefill과 Decode를 분리하고 KV Cache 이동 및 추론 자원 할당을 최적화한다.
    - CMX는 GPU HBM과 공유 스토리지 사이에 Context 데이터를 위한 별도의 저장 계층을 제공한다.
    - 이러한 기술을 활용하면 사용 빈도가 낮은 KV Cache를 반드시 HBM에 유지할 필요가 없다.
    - 필요한 시점에 데이터를 다시 가져올 수 있도록 관리하는 것이다.
    - 다만 현재 사용 중인 KV Cache를 계속 외부에서 읽어야 한다면 추가적인 데이터 전송과 지연이 발생할 수 있다.
    - 결국 자주 사용하는 데이터와 그렇지 않은 데이터를 정확하게 구분하는 능력이 중요하다.

**📌 그런데 NVIDIA가 디스태킹을 검토하는 더 직접적인 이유가 있다**

- - 지금까지는 줄어든 메모리 용량을 기술적으로 어떻게 보완할 것인지 살펴봤다.
  - 하지만 HBM 사양 조정을 이해하기 위해서는 또 하나의 관점이 필요하다.
  - 바로 HBM 공급량이다.
  - AI 가속기에 대한 수요가 빠르게 증가하더라도 HBM을 충분히 공급할 수 없다면 완제품 GPU의 출하량이 제한될 수 있다.
  - 적층 수를 줄이는 것은 한정된 DRAM 다이 생산량을 더 많은 HBM 스택에 배분할 수 있다는 의미이기도 하다.
  - 가령 전체 HBM 생산에 사용할 수 있는 DRAM 다이의 양이 동일하다고 가정해 보자.

- - 단순한 계산이지만 중요한 의미를 가진다.
  - 동일한 HBM 다이 총량을 사용하면서 GPU 수를 50% 늘릴 수 있는 이론적인 경우다.
  - 실제로는 HBM 수율, 인터페이스 설계, 첨단 패키징, GPU 다이 및 전력 공급 등 다양한 제약이 존재하므로 이 비율을 실제 출하량 증가율로 해석해서는 안 된다.
  - 다만 Micron CEO가 최근 실적 발표에서 설명한 내용과 연결되는 부분이다.
  - 일부 고객이 메모리 구성을 최적화하는 이유는 전체 메모리 수요가 감소해서가 아니라 더 많은 제품을 출하하고 성장 기회를 확보하기 위한 것이라는 설명이다.
  - 여기서 기존의 질문이 달라진다.

    - GPU 한 개에 HBM을 최대한 많이 장착하는 것이 유리할까?
    - 아니면 HBM을 조금 줄이고 더 많은 GPU를 출하하는 것이 유리할까?
  - 이에 대한 답은 실제 AI 워크로드의 메모리 요구량에 따라 달라진다.
  - 메모리 용량보다 연산능력과 대역폭에 의해 처리량이 제한되는 작업에서는 더 많은 GPU를 활용하는 구성이 유리할 수 있다.
  - 반대로 대용량 모델이나 긴 Context를 처리하면서 이미 HBM 용량이 병목인 작업에서는 GPU 수를 늘리는 것만으로 문제를 해결하기 어렵다.

**📌 그렇다면 이번 디스태킹의 진짜 의미는?**

- - 현재 공개된 내용을 바탕으로 보면 세 가지 요인을 구분할 수 있다.
  - **첫째, 한정된 HBM 공급량이다.**

    - 현재까지 공개된 보도와 메모리 제조사의 발언에서 가장 직접적으로 확인되는 요인이다.
    - GPU당 필요한 HBM의 양을 조정하면 제한된 메모리 공급량으로 더 많은 AI 가속기를 출하할 여지가 생긴다.
  - **둘째, 대역폭과 용량의 분리다.**

    - HBM의 적층 수를 줄인다고 반드시 대역폭까지 같은 비율로 감소하는 것은 아니다.
    - NVIDIA가 I/O 속도를 중요하게 고려하고 있다는 점은 이번 사양 변경 검토에서 주목할 부분이다.
    - 용량을 줄이는 대신 높은 대역폭을 유지하거나 개선할 수 있다면 일부 작업에서 상대적으로 유리할 수 있다.
  - **셋째, 메모리 용량을 보완하는 아키텍처다.**

    - 양자화로 필요한 메모리 자체를 줄인다.
    - NVLink를 통해 분산된 메모리를 활용한다.
    - CPU 메모리와 외부 저장 계층을 사용해 HBM에 반드시 보관할 필요가 없는 데이터를 이동시킨다.
    - 소프트웨어로 데이터의 배치와 이동을 최적화한다.
  - 이 세 가지가 함께 작용하면 개별 GPU의 HBM 용량이 줄어들더라도 시스템 전체의 연산 처리량과 경제성을 개선하는 것이 가능하다.
  - 반대로 실제 작업에 필요한 활성 데이터의 양을 충분히 줄이지 못한다면 디스태킹으로 인한 성능 저하는 피하기 어렵다.

**📌 여기서 한 가지 더 생각해 볼 문제**

- - 지금까지 살펴본 기술들은 대체로 데이터를 압축하거나 다른 메모리로 이동시키는 방식이다.
  - 그러나 데이터를 이동하는 데 필요한 대역폭과 전력 자체를 줄이는 방법도 존재한다.
  - 바로 PNM과 PIM이다.

    - 데이터를 GPU로 가져온 다음 연산하는 대신 메모리 근처에서 일부 연산을 수행하면 이동해야 하는 데이터의 양을 줄일 수 있다.
    - 이것은 메모리의 물리적 용량을 증가시키지는 않지만, 제한된 메모리 대역폭을 더욱 효율적으로 활용하는 방법이 될 수 있다.
  - NVIDIA의 NVHBM은 메모리 컨트롤러를 HBM의 베이스 다이 쪽으로 이동시키는 기술이다.
  - 현재 공개된 NVHBM에 PNM 연산 엔진이 포함된 것은 아니지만, 향후 메모리 근처의 연산 기능으로 확장할 수 있을지 살펴볼 필요가 있다.
  - 특히 SK하이닉스와 Marvell이 이미 CXL 기반 PNM을 공동 개발하고 있다는 사실은 이 분야가 단순한 미래 기술이 아님을 보여준다.
  - 결국 HBM 디스태킹은 단순히 메모리를 줄이는 문제가 아니라, **메모리 용량과 대역폭의 제약을 시스템 전체에서 어떻게 해결할 것인가**라는 문제로 이어진다.
  - 현재 확인되는 직접적인 동기는 HBM 공급 제약에 가깝다.
  - 하지만 감소한 메모리 용량을 실제로 보완할 수 있느냐에 따라 해당 전략의 성공 여부가 달라질 것이다.
  - 그리고 이러한 변화는 앞으로 NVHBM, CXL, 광 메모리 패브릭, PNM/PIM이 왜 중요해지는지를 설명하는 출발점이 된다.

  - 원격 HBM에 접근할 때는 NVLink 대역폭과 지연시간의 영향을 받는다.
  - 어떤 데이터를 어느 GPU에 배치하고 어떻게 접근할지는 소프트웨어에도 영향을 받는다.
  - 따라서 NVLink는 HBM 용량을 무조건 줄이기 위한 기술이라기보다, 분산된 연산과 메모리 자원을 효율적으로 활용하기 위한 기술이다.
  - 특정 데이터의 재사용과 분산 방식이 적합하다면 로컬 HBM에 모든 데이터를 중복 보관할 필요가 줄어들 수도 있다.
  - 반대로 GPU마다 동일한 데이터가 반복적으로 필요한 작업에서는 로컬 HBM의 중요성이 여전히 높다.

**📌 기존 HBM과 무엇이 다른가?**

- - 전통적인 HBM 연결 구조에서는 GPU나 XPU의 메인 다이에 메모리 컨트롤러 및 관련 PHY 회로가 들어간다.
  - HBM 자체에는 DRAM 다이와 베이스 다이가 존재한다.
  - 메모리와 가속기 사이에서 매우 높은 대역폭을 확보하려면 넓은 물리적 인터페이스가 필요하다.
  - 이러한 인터페이스는 메인 다이의 면적과 패키징 자원을 소비한다.
  - NVHBM은 이 구조를 변경한다.
  - NVIDIA는 맞춤형 HBM 베이스 다이에 메모리 컨트롤러를 배치하고 Custom PHY를 통합한다.
  - 이를 통해 메인 다이에 필요한 메모리 인터페이스 면적과 연결 복잡성을 줄인다.

**📌 NVIDIA가 공개한 성능 목표**

|  |  |
| --- | --- |
| **항목** | **JEDEC HBM4E 대비 NVHBM** |
| 스택당 메모리 대역폭 | 최대 30% 증가 |
| PHY 및 지원 회로 면적 | 최대 67% 감소 |
| HBM 전력 | 최대 15% 감소 |
| 추가 활용 가능한 메인 다이 면적 | 최대 약 25~30% 증가 가능 |

- - 위 수치는 NVIDIA가 공개한 설계상의 최대 개선 효과다.
  - 실제 제품에서 모든 수치가 동시에 구현되거나 모든 작업의 성능이 같은 비율로 증가한다는 의미는 아니다.
  - 하지만 Custom XPU를 설계하는 기업에는 상당히 중요한 변화다.
  - 메모리 인터페이스에 사용하던 면적의 일부를 Tensor Engine, Vector Engine, SRAM, Cache 및 기타 기능에 재할당할 수 있기 때문이다.
  - 패키지 안에서 사용할 수 있는 면적과 전력에 여유가 생긴다는 것은 결국 XPU 설계의 선택지가 늘어난다는 뜻이다.

**📌 HBM 공급업체에게는 어떤 의미인가?**

- - NVHBM은 NVIDIA가 정의한 맞춤형 베이스 다이 기술이지만 실제 HBM 제조와 공급은 메모리 업체와의 협력이 필요하다.
  - NVIDIA는 주요 메모리 제조사들과 함께 NVHBM을 설계하고 검증한다고 설명한다.
  - 따라서 NVHBM의 확대가 곧바로 기존 HBM 제조사의 역할 축소를 의미하지는 않는다.
  - 오히려 맞춤형 베이스 다이의 제조, 메모리 적층, 수율 확보 및 패키징이라는 새로운 경쟁 요소가 추가된다.

**✅ 7. NVHBM은 HBM 디스펙의 해결책일까?**

- - 이 부분은 구분해서 볼 필요가 있다.
  - Rubin Ultra의 HBM 사양 변경과 NVHBM은 공개된 별개의 기술 및 제품 계획이다.
  - 따라서 NVIDIA가 HBM 적층 수를 줄이기 위해 NVHBM을 개발했다고 단정할 근거는 없다.
  - 하지만 장기적인 메모리 설계 방향에서는 공통점이 발견된다.

**📌 한정된 자원에서 효율을 극대화한다**

- - HBM의 적층 수를 줄이면 스택당 DRAM 다이 사용량을 줄일 수 있다.
  - 더 빠른 인터페이스를 사용하면 용량 증가 없이도 대역폭을 개선할 수 있다.
  - NVHBM과 같은 구조를 활용하면 메모리 인터페이스에 필요한 메인 다이 면적과 전력을 줄일 수 있다.
  - NVLink를 통해 분산된 메모리를 활용하면 모든 데이터가 반드시 하나의 GPU에 보관되어야 하는 것도 아니다.
  - 이 기술들을 적절하게 조합하면 HBM 공급량이 제한된 상황에서도 시스템 전체의 연산 효율을 개선할 수 있다.
  - 물론 용량이 줄어들면 더 큰 모델이나 긴 Context를 처리하는 데 불리해질 수 있다.
  - 원격 메모리의 성능 역시 로컬 HBM과 같지 않다.
  - 따라서 각 기술을 도입하는 과정에서는 용량, 대역폭, 지연시간, 전력 및 비용을 함께 고려해야 한다.
  - 핵심은 단순히 HBM을 줄이는 것이 아니라 **HBM을 어디에 얼마나 배치해야 가장 효율적인가**라는 문제다.

**📌** **12-Hi HBM을 8-Hi로 변경하면서 NVHBM을 함께 적용할 경우**

|  |  |  |
| --- | --- | --- |
| 항목 | 기존 | 변경 후 |
| 적층 수 | 12-Hi | 8-Hi |
| 상대 용량 | 100% | 66.7% |
| 상대 대역폭 | 100% | 최대 130% |

- - 이런 조합이 실제로 가능하다면 NVIDIA는 HBM 용량을 줄이면서도 높은 대역폭을 제공할 수 있다.
  - 그리고 바로 여기서 기술적 주도권 문제가 등장한다.

    - 기존에는 메모리 제조사들의 HBM 성능과 인터페이스 구현이 중요한 차별화 요소였다.
    - NVHBM을 사용하는 XPU에서는 NVIDIA가 맞춤형 베이스 다이와 메모리 인터페이스 아키텍처를 제공한다.
    - NVHBM의 성능과 검증 체계가 중요해질수록 XPU 설계업체가 NVIDIA의 기술을 채택할 유인이 생긴다.

**📌** **NVIDIA의 메모리 관리 플랫폼에 기회**

- - 여기서는 NVHBM보다 더 직접적인 관계가 나타난다.
  - HBM 용량이 줄어들면 필요한 데이터를 어디에 보관할 것인지가 더욱 중요해진다.
  - 특히 NVIDIA의 Dynamo는 사용 빈도가 낮은 KV Cache를 CPU 메모리, SSD, 네트워크 스토리지로 이동하고 필요할 때 재사용하도록 관리한다. CMX 역시 대규모 추론을 위한 별도의 Context 저장 계층을 제공한다.
  - 디스태킹으로 HBM 용량이 부족해질수록 이러한 기술의 중요성은 커질 수 있다.
  - 여기에서 NVIDIA의 사업적 기회는 새로운 메모리 장치를 직접 생산하는 데 그치지 않는다. 메모리를 언제, 어디에 배치하고, 어떤 경로로 이동시킬지 결정하는 소프트웨어 계층에서도 발생합니다.
  - 이 계층이 NVIDIA 플랫폼에 깊이 통합될수록 고객이 다른 플랫폼으로 이전하는 데 드는 비용도 증가할 수 있다.
  - 다만 Dynamo는 오픈소스이며 외부 스토리지와 다른 추론 엔진도 지원한다. 따라서 활용이 확대된다고 모든 부가가치를 NVIDIA가 독점하게 되는 구조는 아니다.

**✅ 8. 그렇다면 CXL은 무엇을 해결하는가?**

- - 여기서 CXL을 다시 살펴볼 필요가 있다.
  - 이전 NVIDIA 시리즈에서 NVLink와 CXL의 역할을 비교한 적이 있다.
  - 하지만 이번에는 가속기 간 연결과 외부 메모리 확장이라는 서로 다른 역할을 명확히 구분해야 한다.

**📌 CXL Type 3의 역할**

- - CXL Type 3는 외부 메모리 확장 장치를 연결하는 데 사용한다.
  - 시스템에 직접 장착한 DRAM 외에도 별도의 메모리 자원을 연결하고 확장할 수 있다.
  - CXL 스위치와 적절한 시스템 소프트웨어를 활용하면 메모리를 풀링하고 여러 호스트에 자원을 할당하는 구조도 만들 수 있다.
  - 반면 NVLink Fusion은 기본적으로 외부 기업의 CPU나 XPU를 NVLink 패브릭에 통합하기 위한 기술이다.
  - NVLink가 원격 HBM 접근을 지원한다고 해서 별도의 DRAM 메모리 풀까지 자동으로 관리하는 것은 아니다.

**📌 그럼 CXL은 너무 느린 것 아닌가?**

- - CXL은 PCIe의 물리 계층을 사용하므로 적용되는 PCIe 세대와 링크 폭에 따라 대역폭이 결정된다.

|  |  |  |  |
| --- | --- | --- | --- |
| **규격** | **전송률** | **x16 단방향 이론 대역폭** | **x16 양방향 합산** |
| CXL 2.0 / PCIe 5.0 | 32GT/s | 약 64GB/s | 약 128GB/s |
| CXL 3.x / PCIe 6.0 | 64GT/s | 약 128GB/s | 약 256GB/s |
| CXL 4.0 / PCIe 7.0 | 128GT/s | 약 256GB/s | 약 512GB/s |

- - 위 수치는 프로토콜 오버헤드 등을 고려하지 않은 대략적인 이론적 대역폭이다.
  - CXL 4.0은 2025년 11월 공개됐으며, 복수의 포트를 논리적으로 결합하는 Bundled Port도 지원한다.
  - 다만 Bundled Port는 주로 호스트와 Type 1/2 가속기 사이의 대역폭 확장을 위해 정의된 기능이므로, 모든 Type 3 메모리 풀에 동일하게 적용할 수 있는 것은 아니다.
  - NVLink 6의 3.6TB/s는 GPU에 연결된 여러 NVLink를 모두 합산한 수치다.
  - 따라서 NVLink 전체 대역폭과 CXL의 단일 x16 포트를 직접 비교해 기술 자체의 성능 차이를 단정해서는 안 된다.
  - 또한 단순 대역폭 이외에도 실제 메모리 접근 지연시간과 전체 시스템의 I/O 자원, 연결된 DRAM의 성능 및 소프트웨어가 중요하다.

**📌 NVIDIA도 CXL을 배제하지 않는다**

- - 여기서 흥미로운 사실이 있다.
  - NVIDIA의 수석 엔지니어 Derek Rohde는 CXL 4.0 발표 당시 CXL 컨소시엄의 회장 겸 재무책임자였다.
  - NVIDIA가 CXL 세계와 완전히 분리된 독자 기술만을 추진한다고 보기 어려운 이유다.
  - 실제로 Marvell은 2026년 9월 NVIDIA Vera CPU와 자사의 Structera X CXL Type 3 메모리 확장 컨트롤러 사이의 상호운용성 검증에 성공했다고 발표했다.
  - 즉 NVIDIA의 CPU를 사용하는 시스템에서도 CXL 메모리 확장이 가능하다.
  - 다만 이것이 Vera에 연결된 CXL 메모리를 모든 NVIDIA GPU가 NVLink 속도로 사용할 수 있다는 의미는 아니다.
  - 중요한 것은 NVLink와 CXL을 반드시 경쟁 관계로만 볼 필요가 없다는 점이다.

**✅ 9. Marvell의 Photonic Fabric — 메모리를 광으로 연결하다**

    - 그리고 Structera A를 이용한 Near-Memory Processing까지 추진하고 있다.

**✅ 10. 그런데 데이터를 빠르게 이동시키는 것만으로 충분할까?**

- - 여기까지 살펴본 기술에는 공통적인 문제가 있다.
  - 메모리를 아무리 빠르게 연결하더라도 데이터를 계속 이동시켜야 한다면 대역폭과 전력이 소비된다는 것이다.
  - 그렇다면 반대로 생각할 수도 있다.
  - 데이터를 GPU로 가져오는 대신 데이터가 있는 곳에서 일부 연산을 처리할 수는 없을까?
  - 여기에서 Processing-in-Memory(PIM)와 Processing-Near-Memory(PNM)가 다시 등장한다.

**📌 PIM과 PNM의 차이**

|  |  |  |
| --- | --- | --- |
| **구분** | **PIM** | **PNM** |
| 기본 개념 | 메모리 내부에서 연산 | 메모리 가까이에서 연산 |
| 연산 장치 위치 | DRAM 다이 내부 등 | 베이스 다이 또는 인접 로직 |
| 주요 목적 | 데이터 이동 최소화 | 데이터 이동 및 호스트 부담 감소 |
| 구현 과제 | 메모리 공정 및 연산 구조 | 인터페이스, 전력, 소프트웨어 |

- - 삼성전자는 이미 HBM 내부에 연산 기능을 통합하는 HBM-PIM을 발표한 바 있다.
  - 삼성은 초기 실험에서 일부 AI 작업의 성능이 약 2배 증가하고 에너지 소비가 70% 이상 감소할 수 있다고 발표했다.
  - 다만 이는 특정 실험에서 얻은 결과이며 모든 AI 작업에 동일하게 적용되는 것은 아니다.
  - PIM이 오래전부터 연구되어 왔음에도 시장의 주류가 되지 못한 이유는 단순하지 않다.
  - DRAM의 제조 공정과 연산용 로직의 최적화 방향이 다르며, 발열과 전력, 개발 비용 및 소프트웨어 호환성 문제까지 해결해야 한다.
  - 그런데 NVHBM의 등장으로 이 분야를 다시 살펴볼 이유가 생겼다.

**✅ 11. NVIDIA는 NVHBM을 통해 PNM까지 확장할 수 있을까?**

- - 이 부분부터는 현재 발표된 제품 기능과 향후 가능한 기술적 진화를 구분해서 살펴봐야 한다.

**📌 현재까지 확인된 NVHBM의 변화**

- - NVIDIA는 맞춤형 베이스 다이와 PHY를 사용한다.

  - 이를 통해 메인 다이의 면적과 전력 사용을 줄이고 대역폭을 개선한다.
  - 하지만 현재 공개된 NVHBM 자료에는 PNM 연산 엔진이 포함되어 있다는 발표는 없다.

**📌 그렇다면 향후에는?**

- - 기술적으로 생각하면 메모리 컨트롤러가 있는 베이스 다이에 데이터 처리 기능을 추가하는 것도 검토할 수 있다.
  - 예를 들면 데이터 압축과 해제, 메모리 복사, 일부 Reduction, 데이터 필터링 및 특정 메모리 집약적 연산 등이 후보가 될 수 있다.
  - 적절한 작업에서는 모든 데이터를 GPU로 전송하는 대신 메모리 근처에서 필요한 처리를 마친 뒤 결과만 전달할 수도 있다.
  - 다만 이러한 기능을 추가하면 베이스 다이의 면적과 전력, 발열, 검증 복잡성이 증가한다.
  - 무엇보다 해당 연산을 실제로 수행하기 위한 API와 소프트웨어 지원이 필요하다.

**📌 NVIDIA가 가진 또 하나의 자산은 소프트웨어다**

- - NVIDIA는 CUDA와 관련 라이브러리, 컴파일러 및 런타임을 보유하고 있다.
  - 향후 NVHBM에 실제 PNM 기능을 통합한다면 소프트웨어와 하드웨어를 함께 최적화할 수 있다는 장점이 있다.
  - 적절한 연산을 자동으로 메모리 근처에 배치할 수 있다면 기존 애플리케이션을 크게 변경하지 않고도 성능을 개선할 가능성이 있다.
  - 그러나 현재로서는 어디까지나 기술적으로 가능한 발전 방향에 대한 가설이다.
  - NVIDIA의 공식 NVHBM 로드맵에 PNM이 확정적으로 포함되었다는 뜻은 아니다.

**📌 SK하이닉스**

- - HBM 제조뿐 아니라 CXL 기반 메모리와 PNM으로 사업 영역을 확대하고 있다.

**📌 Micron**

- - DRAM과 HBM, NAND를 보유하고 있으며 데이터센터용 메모리와 스토리지 사업을 확대하고 있다.

  - 현재 진행 중인 메모리 생산능력 확대와 차세대 HBM 공급 경쟁이 중요한 과제다.

  - 여기서 중요한 것은 메모리 3사를 단순히 HBM 생산량으로만 비교하기 어려워질 수 있다는 사실이다.
  - 누가 더 많은 HBM을 생산하느냐와 누가 메모리 주변의 설계 및 시스템 통합에 더 깊이 참여하느냐는 서로 다른 경쟁이다.

**✅ 15. HBM 디스펙 이후 예상할 수 있는 변화**

**📌 첫 번째 — 용량과 대역폭의 분리**

- - 모든 세대에서 HBM의 적층 수와 용량을 동시에 높이는 것이 반드시 최적의 선택은 아닐 수 있다.
  - 높은 I/O 속도와 생산 가능한 물량을 고려한 여러 제품 구성이 등장할 가능성이 있다.

**📌 두 번째 — 분산 메모리 활용 확대**

- - NVLink와 같은 고속 인터커넥트를 통해 가속기 사이의 메모리 접근 성능을 높이는 방향이다.
  - 특히 분산 연산이 중요한 AI 작업에서는 이러한 기술의 가치가 증가할 수 있다.
  - 다만 원격 메모리를 로컬 HBM과 동일하게 사용할 수 있는 것은 아니다.

**📌 세 번째 — 외부 메모리 확장과 공유**

- - CXL을 통해 DRAM을 별도로 확장하고 여러 서버에 메모리 자원을 할당할 수 있다.
  - 가속기 사이의 고속 연결과는 다른 문제를 해결하는 영역이다.

**📌 네 번째 — 광 기반 메모리 분리**

- - 메모리 자원이 단일 서버를 넘어 여러 랙으로 분산되면 전기 연결의 거리와 전력 제약이 중요해진다.
  - Photonic Fabric과 같은 기술은 광 연결을 통해 이러한 물리적 제약을 완화하려는 접근이다.

**📌 다섯 번째 — 메모리 근처에서의 연산**

- - 데이터를 빠르게 이동시키는 것만으로는 해결하기 어려운 작업도 존재한다.
  - PNM이나 PIM을 통해 메모리 가까이에서 일부 연산을 처리하면 불필요한 데이터 이동을 줄일 수 있다.
  - SK하이닉스와 Marvell의 CMM-Ax는 이미 이러한 접근을 보여주고 있다.
  - NVIDIA가 향후 NVHBM에 유사한 기능을 통합할지는 계속 확인해야 할 부분이다.

**✅ 16. 결국 경쟁은 메모리 시스템 전체로 확대된다**

  - 특히 앞으로 검토해야 할 핵심 지표는 단순한 최대 메모리 대역폭이 아니라 실제 작업을 수행할 때의 메모리 접근 성능과 전체 시스템 비용이다.

  - 동시에 NVIDIA는 NVHBM과 NVLink Fusion을 통해 Custom XPU의 메모리 및 인터커넥트 설계 영역까지 사업 범위를 확대하고 있다.
  - Marvell은 CXL과 광 공유 메모리를 통해 외부 메모리 확장 문제를 해결하려 하고 있다.
  - SK하이닉스와 Marvell은 이미 PNM을 이용해 데이터 이동 자체를 줄이려는 기술도 개발하고 있다.
  - 이 모든 움직임을 연결하면 하나의 방향이 나타난다.

    - 지금까지는 **얼마나 빠른 HBM을 얼마나 많이 생산하는가**가 중요한 경쟁이었다.
    - 앞으로는 **얼마나 많은 메모리를 적절한 위치에 배치하고, 데이터를 얼마나 효율적으로 이동시키거나 이동 자체를 줄일 수 있는가**까지 경쟁 범위가 확대될 수 있다.
  - 결국 HBM 디스펙 이후의 변화를 이해하기 위해서는 메모리 제조사뿐 아니라 GPU, ASIC, 인터커넥트, 광반도체 및 시스템 소프트웨어 업체를 함께 살펴봐야 한다.
  - HBM이 사라지는 것이 아니다.
  - 오히려 HBM이 AI 시스템 전체에서 어떤 역할을 담당해야 하는지 다시 정의되는 과정일 수 있다.
  - **어쩌면 지금 보고 있는 것은 HBM 경쟁의 끝이 아니라 메모리 아키텍처 전쟁의 시작일지도 모른다.**
