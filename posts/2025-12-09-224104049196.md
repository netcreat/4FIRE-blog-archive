**✅ 논문 핵심**

- - 이 논문은 양자 LDPC 코드(Quantum LDPC Codes)를 위한 새로운 ‘Beam Search 기반 디코더’를 제안하며,
  - 기존 표준이던 **BP-OSD 디코더보다 더 빠르고, 더 정확하며, CPU 단일 코어에서도 실시간 운용 가능**하다는 점을 실험적으로 입증한다.
  - 특히 **이온트랩 양자컴퓨터에서 실시간(1ms 이내) 오류 보정이 가능함을 처음으로 실증 수준으로 제시**한 논문이다.

**🔹 1. 기존 문제점**

- - **기존 표준 디코더: BP-OSD**

    - ✅ 정확도는 매우 높음
    - ❌ 행렬 역산(Gaussian elimination) 때문에 **속도가 매우 느림**
    - ❌ **실시간 양자컴퓨팅에 부적합**
    - ❌ 최악의 경우(99.9퍼센타일 latency)가 치명적으로 김
  - **BP 단독 방식의 한계**

    - 양자 LDPC 구조 특성상 짧은 사이클(short cycle)이 필연적으로 존재
    - 그 결과:

      - LLR 값이 **진동**
      - **수렴 실패**
      - 디코딩 정확도 저하

**🔹 2. 제안된 해법: Beam Search + Masked BP**

- - **핵심 아이디어**

    - BP를 단일 경로로 끝까지 밀지 않고,
    - **“가장 불확실한 에러 비트부터 하나씩 고정하면서 여러 경로를 동시에 탐색”** 하는 방식이다.
  - **동작 방식 요약**

    - **초기 BP 실행**
    - **가장 신뢰도가 낮은 에러 노드 선택**
    - 해당 노드를 **0 / 1로 분기 (2개의 경로 생성)**
    - **Masked BP 실행 (고정된 노드는 BP에서 제거)**
    - 각 경로에 대해 **신뢰도 점수 계산**
    - **상위 Beam Width 개만 생존 (나머지는 제거)**
    - 반복 → 성공 시 종료

**💡그림 1 : Beam Search 디코더가 실제로 어떻게 “분기 → 평가 → 가지치기”를 반복하는지를 한 눈에 보여주는 핵심 구조도**

****

**✅LLR이란?**

**💡LLR = Log-Likelihood Ratio (로그 우도비)**

- - **LLR는 “이 비트가 0일 확률이 더 큰지, 1일 확률이 더 큰지”를 숫자 하나로 표현한 값이다.**
  - **LLR이 가장 널리 쓰이는 고전 분야**

    - 무선 통신 (5G, WiFi, LTE, 위성통신)
    - SSD / NAND Flash 저장장치
    - 위성·심해·우주 통신
    - AI/ML에서도 일부 사용
  - **LLR이 없으면 현대 통신과 저장 기술은 성립 자체가 불가능하다.**

**💡 LLR 값 해석하는 법**

|  |  |  |
| --- | --- | --- |
| **LLR 값** | **의미** | **해석** |
| **LLR > 0** | 0일 확률이 더 큼 | “이 비트는 고장 안 났을 가능성이 큼” |
| **LLR < 0** | 1일 확률이 더 큼 | “이 비트는 에러일 가능성이 큼” |
| **LLR ≈ 0** | 반반 | ✅ **“가장 불확실한 상태”** |
| |LLR| 큼 | 확신이 매우 강함 | “거의 확실함” |

**예제 1**

- - 에러 확률 p = 0.001
  - 정상일 확률 = 0.999
  - LLR=log(0.999/0.001)≈+6.9
  - ✅ **강하게 “0(정상)”이라고 믿는 상태**

**예제 2**

- - 에러 확률 p = 0.5
  - LLR=log(0.5/0.5)=0
  - ✅ **완전히 헷갈리는 상태 (가장 위험한 노드)**
  - → Beam Search가 가장 먼저 분기하는 노드

**예제 3**

- - 에러 확률 70%
  - LLR=log(0.3/0.7)≈−0.85
  - ✅ **“에러일 가능성이 더 큼”**

---

**✅ (a) 초기 단계: BP → 첫 번째 분기**

- - 그림(a)은 **디코딩이 처음 시작되는 순간**을 보여준다.

**① 기본 BP 실행 (왼쪽 BP 블록)**

- - 먼저 일반 BP(Belief Propagation)를 몇 번 반복 실행한다.
  - 이때 각 에러 노드(비트)가 얼마나 **믿을 수 있는지(LLR-log-likelihood ratio)** 계산된다.

**② 가장 불확실한 에러 노드 선택 (빨간 점)**

- - BP 결과 중에서:

    - **|LLR| 값이 가장 작은 노드 = 가장 불확실한 에러 노드**
  - 그림에서 **빨간 점으로 표시된 노드**가 바로 그 대상이다.

**③ 첫 번째 분기 (0 / 1)**

- - 이제 이 불확실한 노드 하나에 대해:

    - ✅ 위쪽 경로: **이 노드는 0이다**
    - ✅ 아래쪽 경로: **이 노드는 1이다**
    - → **이렇게 2개의 후보 세계(branch)가 만들어진다**

****

**④ Masked BP 실행**

- - 각 분기에서:

    - 방금 **0 또는 1로 고정된 노드는 BP 계산에서 제거(masking)** 된다.
    - 나머지 노드들만 다시 BP 실행 → **Masked BP**
  - ✅ 핵심 의미:

> ***“이 노드는 이미 결정했으니, 더 이상 이 노드를 가지고 흔들리지 마라.”***

---

**✅ (b) 본격적인 Beam Search 반복 구조**

- - 그림(b)는 **이 과정을 여러 단계 반복하면서 폭이 제한된 탐색을 수행하는 구조**를 보여준다.

**① 각 경로에서 다시 ‘가장 불확실한 노드’ 선택**

- - 각 Masked BP 결과마다:
  - 또 빨간 점(가장 불확실한 노드)가 선택된다.

**② 다시 0 / 1로 각각 분기**

- - 각 경로는 다시:

    - 0으로 가는 가지
    - 1로 가는 가지
    - → **경로 수가 2배로 증가**

****

**③ Masked BP 반복 실행**

- - 고정된 노드는 점점 늘어나고
  - BP는 점점 **더 좁은 자유도**로 실행된다.

**④ Pruning (가지치기) — Beam Width 유지**

- - 문제는 이대로 두면:

> ***경로 수 = 2 → 4 → 8 → 16 → 32 → 폭발***

- - 그래서 Pruning(가지치기)가 들어간다.

    - 각 경로마다 **신뢰도 점수(score)** 계산

      - 위 그림에서 총 4가지 경로에 대해 Basked BP를 다시 실행한후 남아 있는 모든 비트들의 LLR 절댓값을 전부 더함
      - 그 합이 크면 → “이 경로는 안정적”
      - 그 합이 작으면 → “이 경로는 여전히 헷갈림이 많다”
    - **상위 Beam Width개만 남기고 전부 제거**

      - **Beam Width = “매 단계에서 동시에 ‘살려두는 후보 경로의 최대 개수’”**
      - “몇 개의 평행 세계를 동시에 유지할 것인가?”를 정하는 숫자를 의미하고, 위 그림에서는 임의로 2로 정해놓음.
      - Beam Width 크기에 따른 차이

        - Beam Width값이 1이면 매우 빠른 장점이 있지만 정확도가 떨어짐
        - Beam Width값이 높을 수록 정확도는 그만큼 올라가지만 속도는 느려짐
        - **논문에서는 32를 최적의 값으로 사용됨.**
  - 📌 이 그림에서는:

    - Beam Width = **2**
    - 그래서 항상 **딱 2개의 경로만 유지**된다.

**⑤ 종료 조건**

- - 아래 중 하나가 되면 탐색 종료:

    1. 유효한 디코딩 해(He = s)를 충분히 찾았을 때

       - **H** : parity-check / detector matrix (M×N)
       - **e** : 실제로 일어난 에러 (길이 N인 0/1 벡터, 우리는 모름)
       - **s = He** : 측정한 syndrome (길이 M인 0/1 벡터, 우리는 알고 있음)
       - 여기서 디코더가 하는 일은

         - “관측된 **s**에 대해, **Hê = s** 를 만족하는 에러 벡터 **ê**를 찾아라.”
       - “유효한 해를 ‘충분히 많이’ 찾았을 때”란?

         - **num\_results = 1** :

           - 첫 번째 유효한 해(Hê = s)를 찾는 순간 **바로 종료**
         - **num\_results > 1** :

           - 유효한 해를 찾을 때마다 results에 넣고
           - |results| == num\_results 가 되면
           - → 그때 모인 후보들 중에서 **가장 좋은 것 하나만 골라서** 최종 출력
       - 예) beam63 32res

         - beam width =64
         - num\_results=32
         - → "최대 32개의 서로 다른 유효한 해를 모아 본 다음, 그 중에서 ‘가장 그럴듯한’ 에러 패턴 하나만 최종 정답으로 쓰겠다.”라는 의미임.
    2. **최대 반복 횟수 도달**

       - Beam Search는 라운드를 최대 **max\_rounds**까지 돌린다.
       - 만약 **max\_rounds까지 갔는데도**

         - 유효한 해가 하나도 없다면 → “Failure”
         - 있긴 있는데 **num\_results만큼은 안 모였다** →
         - 있는 것들 중에서 **최고 후보 하나**를 골라 반환 (논문에선 최소 weight 기준)
  - 그리고 **가장 가벼운(weight 최소) 해를 최종 정답으로 선택**한다.

    - **weight가 작을수록 “이 에러 패턴이 실제로 일어났을 법하다”** 는 의미임.

**✅****최적의 Beam Width**

**1️⃣ 정확도만 보면: 64가 더 좋다**

- - 논문 결과:

|  |  |
| --- | --- |
| **Beam Width** | **논리 오류율 개선** |
| 32 | **5.6× 감소** |
| 64 | **7.0× 감소** |
| 64 + 다중결과 | **17× 감소** |

- - - 👉 **순수 정확도만 보면 64가 이긴다.**

****

**2️⃣ 그런데 “실시간”이라는 물리적 벽이 있음**

- - 이온트랩랩/중성 원자 양자컴퓨터의 **하드 데드라인**은:

> ***“한 라운드 디코딩이 반드시 1ms 이내에 끝나야 한다”***

- - 이건 소프트웨어 목표가 아니라 **물리적 시스템 제약**이다.

**3️⃣ 32는 “99.9% 지연시간 < 1ms”를 딱 만족함**

- - 논문에서 p = 5×10-4 (이온트랩급 오류율) 기준:
  - 오류보정이 1ms를 넘으면, 다음 신드롬이 와버려서 시스템이 꼬임.

|  |  |  |
| --- | --- | --- |
| **Beam** | **평균** | **99.9% 지연** |
| 32 | **270 µs** | ✅ **940 µs** |
| 64 | **더 느림** | ❌ **1ms 초과 가능성** |

- - **Beam 32 → 최악의 경우에도 1ms 안에 들어옴**

    - **단일 CPU 코어**
    - **FPGA, ASIC 없이**
    - **소프트웨어 BP + Beam Search**
    - **실제 시뮬레이션으로 측정한 값**
  - **Beam 64 → 평균은 빠르지만 “최악의 최악”에서 1ms를 넘길 수 있음**

**✅일반 CPU 3대(32코어)**

**1️⃣ 출발점이 되는 실험 수치 (논문이 직접 측정한 값)**

- - 논문이 실제로 측정한 핵심 수치는 이 한 줄이다.

    - Beam Width = 32, p = 5×10-4에서 99.9% 디코딩 지연시간 = 940 μs (0.94 ms)
  - “최악의 경우에도 한 번의 오류보정이 1ms 안에 끝난다”는 것이 실험으로 증명된 상태를 의미함

**2️⃣ 왜 “1ms 이내”가 절대 기준이냐?**

- - 이온트랩 / 중성 원자 양자컴퓨터는:

    - **신드롬 추출 주기 자체가 약 1ms 수준**
    - 즉, 오류보정이 1ms를 넘으면, 다음 신드롬이 와버려서 시스템이 꼬인다.
  - **이 조건을 ‘안전하게’ 만족한 마지막 설정이 Beam 32.**

****

**3️⃣ 이제 “1000 논리 큐비트”는 어디서 나오느냐?**

- - 논문이 말하는 시스템 가정은:

    - 각 **논리 큐비트마다**
    - **하나의 LDPC 디코더 인스턴스가 병렬로 필요**
    - 즉: 논리 큐비트 수 ≒ 동시에 돌아가야 할 디코더 수
  - 그래서:

    - **1000 논리 큐비트 → 동시에 1000개의 디코딩 작업이 매 1ms마다 필요**

****

**4️⃣ 이제 CPU 처리량 계산이 나온다**

- - Beam 32 설정에서:

    - **1개의 CPU 코어가 1ms에 1개 디코딩을 안정적으로 처리 가능**
    - → 즉, CPU 1코어 ≒ 논리 큐비트 1개 담당
  - **그럼 CPU 32코어 1대는?**

    - 32 cores⇒32 logical qubits
  - **논리 큐비트 1000개라면?**

    - 1000÷32≈31.25
  - 즉: 32코어 CPU 약 32대면 1000 논리 큐비트 커버 가능

**5️⃣ 그런데 왜 논문은 “3대”라고 했느냐?**

- - 여기서 중요한 게 **병렬 파이프라인 구조 + 시간분할(Time-slicing)** 이다.
  - 논문이 암묵적으로 전제한 구조는:

    - 신드롬 추출은:

      - 모든 큐비트가 **완전히 동시에 1ms마다 정확히 떨어지지 않음**
    - 디코더는:

      - **완벽한 하드 리얼타임이 아니라 소프트 리얼타임 허용**
    - 그리고 중요한 점:
    - 99.9%가 0.94ms라는 건, “대부분은 훨씬 빠르게 끝난다”는 뜻이기도 함
  - **평균은 270 μs (0.27 ms)**
  - **평균 기준으로 보면 CPU 1코어가 논리 큐비트 약 3~4개를 시간분할로 감당 가능**
  - **CPU 32코어 1대는?**

    - 32×3.7≈118 logical qubits
  - 논리 큐비트 1000개면?

    - 1000÷118≈8.47
  - **CPU 32코어 기준 약 9대 수준이면 충분**

****

**6️⃣ 그럼 논문은 왜 “3대”라고 더 공격적으로 말했느냐?**

- - 논문은 여기서:

    - ✅ 평균 시간
    - ✅ 병렬 처리
    - ✅ 스케줄링 여유
    - ✅ 실제 복수 노드 동시 syndrome 겹침 빈도 감소
    - 까지 **상당히 공격적으로 최적 가정**을 해서:

> ***✅ CPU 3대(32코어 × 3 = 96코어)로도 1000 논리 큐비트 커버 가능*********

- - 이라는 “시스템 아키텍처 가능성”을 제시한 것으로 추정됨
  - 즉 이 문장은:

    - ❌ “수학적으로 3대가 딱 맞다”가 아니라
    - ✅ **“FPGA 수백 개를 쓰는 대신, 범용 서버 몇 대로도 같은 일을 할 수 있는 시대가 열렸다”는 구조적 주장에 방점을 둬야 함.**
