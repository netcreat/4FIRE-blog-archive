**🎯 코드와 디코더의 차이**

|  |  |  |
| --- | --- | --- |
| **구분** | **코드 설계 측면** | **디코더(Decoding) 측면** |
| 목적 | **좋은 Tanner graph / LDPC 구조 설계** | **실제 오류 패턴을 추정하고 수정** |
| 알고리즘 역할 | 그래프 구조 분석, 성능 예측, 최적 설계 | 실제 측정된 syndrome 기반 오류 가능성 계산 |
| 입력 데이터 | 논리 구조, 패리티 행렬(H) | syndrome, 물리 연산 오류 확률 데이터 |
| 출력 | 좋은 코드 설계 (distance, expansion, girth) | 각 qubit에 적용할 보정 연산 |
| 실행 시점 | 컴퓨터에서 사전 설계 | 양자 컴퓨터 동작 중 실시간 수행 |

**📌 1. 코드 설계에서의 알고리즘 사용**

- - 연구자가 새로운 LDPC / qLDPC / BB 코드를 설계할 때,

    - **확장성(expansion)**
    - **사이클 길이(girth)**
    - **그래프 스펙트럼**
    - **논리 거리(d)**
  - 등을 분석해야 한다.
  - 이때 Belief Propagation / Message passing 알고리즘을 **시뮬레이션 도구**로 이용하여

> ***“이 코드 구조가 실제 디코딩에서 잘 동작할까?”***

- - 를 평가하는 데 사용한다.
  - 즉,

> ***알고리즘 = 코드 설계 품질 검증 도구***

**📌 2. 디코더에서의 알고리즘 사용**

- - 양자 컴퓨터가 실제 실행될 때,

    1. 측정된 syndrome(오류 정보)이 주어지고
    2. 디코더는 message passing 알고리즘을 실행해서
    3. 어떤 qubit에 어떤 오류가 발생했는지 확률을 계산하고
    4. 보정 연산을 수행한다

즉,

> ***알고리즘 = 실시간 오류 추정 및 수정 엔진***

**🚀 아주 직관적인 비유**

|  |  |  |
| --- | --- | --- |
| **상황** | **비유** | **설명** |
| 코드 설계에서의 algorithm | 자동차 엔진 설계 시뮬레이터 | 엔진을 어떻게 설계해야 가장 효율적이고 빠를지 테스트 |
| 디코더에서의 algorithm | 자동차 ECU 실시간 연료/점화 제어 | 실제 운행 중 센서 데이터를 바탕으로 실시간 제어 |

- - 엔진 설계 시뮬레이터에서 쓰는 수학 모델과 ECU가 실시간 운전 제어에 쓰는 모델이 **놀랍게도 같은 알고리즘 기반일 수 있다.**
  - 하지만

    - 목적은 완전히 다르고
    - 실행 타이밍도 다르고
    - 입력 데이터도 다르다.

---

**✅ 실제 양자 컴퓨터에서의 사용 시점**

**✔ 1. QEC Code(오류 정정 코드)는 언제 쓰나?**

- - **📌 양자 회로가 실행되기 전(사전 준비 / 설계 단계)**
  - 어떤 오류 정정 방식을 사용할지(예: Surface, BB, qLDPC 등)
  - 어떤 레이아웃으로 배치할지
  - 어떤 방식으로 syndrome을 측정할지
  - ancilla 몇 개, data qubit 몇 개 필요할지
  - 게이트 순서 및 체크 일정(schedule)을 어떻게 설계할지

> ***코드는 양자 연산이 실행되기 전에 미리 설계되어 “회로 구조와 배치”를 결정한다.***

- - 그리고 나면

    - 실제 hardware는 **그 QEC 코드가 정의한 stabilizer 측정과 syndrome 생성 절차**대로 작동한다.

**✔ 2. Digital Decoder(디코더)는 언제 쓰나?**

- - **📌 양자 회로가 수행되는 중 또는 연산 후에 실시간으로**
  - 실제로 회로 실행 중 오류가 발생하면

    1. ancilla 측정 → **syndrome 데이터 출력**
    2. syndrome 신호가 **클래식 디코더**로 전달
    3. 디코더가 message passing / BP / ML 디코더 등으로 **오류 위치 추정**
    4. 필요 시 **보정 연산을 양자 장치에 다시 적용**

       - 또는 오류를 Pauli frame으로 저장

> ***디코더는 실행 중 발생한 오류를 감지·분석·수정하는 실시간 제어 시스템이다.***

**🧠 시간 흐름 기준 전체 그림**

|  |  |  |
| --- | --- | --- |
| **시간 순서** | **역할** | **실제 하는 일** |
| **회로 실행 전** | **QEC Code** | 오류 정정 구조 설계, 배치, ancilla 스케줄 정의 |
| **회로 실행 중** | **Syndrome 측정** | 오류 탐지 데이터 생성 |
| **회로 실행 중/후** | **Decoder** | 오류 위치 추정 + 보정 수행 |
| **반복** | 지속적 오류 감시 | fault tolerance 유지 |

---

**📦왜 코드와 디코더를 서로 다른 방식으로 선택할 수 있는가?**

- - QEC Code는 ‘오류 정정 구조(패리티 제약)’ 자체를 정의하는 설계이고,
  - 디코더는 그 구조 위에서 ‘오류를 추정하고 고치는 방법’이다.
  - 따라서 코드와 디코더는 **같은 역할을 하지 않으며, 필요도 서로 다르다.**
  - 서로 다른 것을 사용하는 게 완전히 정상이다.
  - 예 : QEC 코드(BB5 등)와 디코더(BP-OSD 등)

> ***코드 = 수학적 설계도 (H matrix / Tanner graph / stabilizer set)***
>
> ***디코더 = 설계된 코드 구조를 기반으로 실제 오류를 추정하는 알고리즘***

**❌ 코드는 알고리즘이 아니다**

- - BB5, BB8, BB288 같은 **QEC 코드는 알고리즘이 아니라 구조(structure)** 이다.

    - 패리티 행렬 H
    - Tanner graph
    - stabilizer 구성
    - ancilla 스케줄
  - → 이건 **하드웨어에 물리적으로 구현되는 레이아웃**이다.

> ***코드는 물리적 회로와 레이아웃을 결정한다.***

**❌ 디코더는 구조 위에서 최적 추정을 수행하는 “방법론”**

|  |  |
| --- | --- |
| **디코더** | **목적** |
| BP (Belief Propagation) | 빠르고 근사적인 확률적 추정 |
| OSD (Ordered Statistics Decoding) | 더 높은 정확도, 고비용 |
| BP-OSD Hybrid | 속도 + 정확도의 균형 |
| ML / Neural decoder | 더 높은 학습 기반 성능 |
| MWPM (Minimum Weight Perfect Matching) | Surface code 전용 최적 |

- - **디코더는 설계된 코드를 실제로 어떻게 복원할지를 정하는 선택 옵션**이다.

**🧠 왜 이런 분리가 중요한가?**

- - **❗ QEC Code = 바뀌면 하드웨어 전체를 다시 설계해야 함**

    - stabilizer 구조, ancilla 스케줄, 레이아웃, 물리큐비트 수 모두 변경
    - 큰 공사 = 헌법 개정급
  - **❗ Decoder = 바꿔도 하드웨어는 그대로 사용 가능**

    - 알고리즘 개선, 머신러닝 활용, GPU/HW 가속
    - 기존 코드 위에서 더 빨리 더 잘 디코딩 가능
    - 정당 전략 변경 수준

---

**✅****코드와 디코더의 조합**

- - **디코더는 반드시 “그 코드 구조가 가진 철학적 뼈대(H, Tanner graph, stabilizer)” 위에서 동작해야 한다.**
  - **같은 철학을 공유하면서도 “현실 구현 방식만 달라지는” 것이 디코더의 역할이다.**
  - 그러므로 **코드와 디코더는 완전히 독립적인 존재가 아니라, 구조적으로 강하게 연결된 관계**다.
  - 다만 그 관계는 **하드웨어 vs 펌웨어** 또는 **헌법 vs 집행부** 같은 관계라고 보면 된다.

**💡****Graph-based / LDPC 계열 코드**

- - **코드 쪽 노드**
  - Graph-based (Tanner/Expander)

    - Quantum Tanner Code
    - Quantum Expander Code
    - Good LDPC Codes
  - Product-based (Tensor Product)

    - Hypergraph Product, Balanced Product, Lifted Product
  - Circulant/Polynomial-based

    - BB5 Code, BB6 Code
  - Special-purpose Experimental (대부분 LDPC 그래프 구조)

    - Grӧss Code 등
  - **호환 디코더**

|  |  |  |
| --- | --- | --- |
| **코드 계열** | **잘 맞는 디코더 패밀리** | **이유** |
| 일반 LDPC / Tanner / Expander / Product | **Graph-based Decoders** (BP, BP-OSD, Neural BP, RG Decoder) | Tanner graph 위에서 메시지 패싱 하는 구조라 그대로 사용 가능 |
| **Matrix-based Decoders** (Gaussian Elimination, Lookup Table\*) | 어떤 stabilizer 코드에도 적용 가능. 다만 대형 코드에는 복잡도 ↑ |
| Circulant/Polynomial (BB5, BB6) | **Circulant/Polynomial Optimized BP** (Layered BP, BP-OSD circulant optimized) | H가 순환 행렬이라, 순환성 이용한 캐싱·파이프라이닝이 가능 |
| + 위의 일반 **Graph-based Decoders** | BB도 결국 LDPC Tanner graph라서 그대로 적용 가능 |

**💡****Lattice-based / Topological 계열 코드**

- - **코드 쪽 노드**

    - Lattice-based (Topological/Homological)

      - Surface Code
      - Toric Code
      - Hyperbolic Code
    - (이들도 수학적으로는 LDPC 그래프지만, **2D/곡률 있는 격자 + Homology** 구조를 강하게 활용하는 쪽)
  - **호환 디코더**

|  |  |  |
| --- | --- | --- |
| **코드 계열** | **잘 맞는 디코더 패밀리** | **이유** |
| Lattice-based (Surface, Toric, Hyperbolic) | **Lattice-based Decoders** (MWPM, Union-Find, Tensor Network Decoder) | 2D/Hyperbolic 격자에서 error chain을 shortest path / cluster / tensor network로 다루는 구조 |
| **Renormalization Group Decoder** | 격자 블록화를 활용하므로 토폴로지 코드와 궁합 좋음 |
| (규모 작거나 연구용) **Matrix-based** | 이론상 가능. 작은 패치에 한해 정확한 디코딩용으로 사용 |

**💡“절대 섞으면 안 되는” / 의미 없는 조합**

- - 여기서 “절대”는

    - **정의 자체가 성립하지 않거나**,
    - **해당 디코더가 전제로 삼는 구조가 아예 없는 경우**를 말한다고 보면 된다
    - (단순히 “성능이 나쁘다” 수준은 제외).
  - **Lattice 전용 디코더 vs Non-lattice LDPC 코드**

|  |  |  |
| --- | --- | --- |
| **코드** | **디코더** | **왜 안 맞는가?** |
| Quantum Tanner / Quantum Expander / Good LDPC / Hypergraph Product / Balanced Product / Lifted Product / BB5 / BB6 / Grӧss 등 **일반 LDPC 계열** | **MWPM, Union-Find, Tensor Network (Lattice-based Decoders)** | 이 디코더들은 “2D 또는 특정 차원의 격자 위에서 에러가 인접 edge로만 퍼진다”는 가정을 씀. 일반 LDPC는 Tanner graph가 고차원/비지역(expander)이라, 어떤 의미 있는 “기하학적 격자”를 정의하기 어렵다. 즉, *어떤 edge를 matching graph의 이웃으로 둘지 자체가 정의 불가* 에 가까움. |

> ***격자 디코더는 “좌표+거리”가 있는 격자를 필요로 하는데,***
>
> ***일반 LDPC/BB 계열은 그런 기하 구조가 없어서 그대로 쓸 수 없다.***

- - **Circulant 최적화 BP vs 비-순환 구조 코드**

|  |  |  |
| --- | --- | --- |
| **코드** | **디코더** | **왜 안 맞는가?** |
| Surface, Toric, Hyperbolic, Hypergraph Product(비순환 설계), Grӧss 등 **순환 행렬 구조가 없는 코드** | **BP-OSD (circulant optimized), Layered BP (순환 전용 튜닝 버전)** | 이 디코더 버전은 H가 block-circulant / polynomial form이라는 가정을 사용해서 index 재사용, pipeline, FFT류 최적화를 한다. 순환성이 없으면 이 최적화가 깨져서, 구현 자체가 의미가 없거나 일반 BP로 퇴행해야 한다. |

> ***“순환 전용 BP 튜닝”은 BB5/BB6 같은 순환 계열에만 의미 있고,***
>
> ***격자 코드나 일반 Tanner 코드에 꽂으면 장점이 사라져 사실상 다른 디코더가 된다.***

- - **Lookup Table / 전면 Gaussian Elimination vs 거대 LDPC / Topological 코드**

    - 이건 **수학적으로는 가능하지만, 현실적으로는 완전 비현실적인 조합**이라 “사실상 금지”로 보는 게 맞다.

|  |  |  |
| --- | --- | --- |
| **코드** | **디코더** | **문제점** |
| 수천~수만 physical qubit을 쓰는 모든 LDPC / Topological 코드 | Lookup Table, 전면 Gaussian Elimination | syndrome 패턴 수가 2^k급이라 lookup table 크기가 우주급, Gaussian elimination도 O(n³) 이상. FT 스케일에서 컴퓨팅 자원이 절대 감당 안 됨. |

- - 그래서 실제 FT 스케일에서는:

> ***Matrix-based 디코더는 “아주 작은 코드”나 “테스트·분석용”으로만 쓰이고,***
>
> ***실전용은 lattice-based / graph-based 특화 디코더가 맡는다.***

**✅****Q&A**

**💡Q1. BB 시리즈가 “Circulant/Polynomial-based 코드”인데, 왜 “Graph-based Decoder(BP-OSD 포함)”와 호환되며, 실제로 BP-OSD를 쓰는 것이 자연스러운가?**

> ***BB 코드(BB5/BB6/BB288)는 본질적으로 LDPC(qLDPC) 코드이며 Tanner graph 표현이 가능한 그래프 코드이다.***
>
> ***다만 구조적 생성 방식이 circulant polynomial 기반이기 때문에 순환 행렬 H를 가진다.***

- - 그래서 BB 코드는 동시에:

|  |  |
| --- | --- |
| **관점** | **분류** |
| 생성 방식(Construction) | Circulant / Polynomial / Algebraic |
| 구조 표현(Representation) | Tanner graph LDPC |
| 디코더 선택(Decoding compatibility) | Graph-based BP / BP-OSD 전부 가능 |

- - 따라서 BB 시리즈는 **그래프 기반 LDPC 코드이기 때문에 BP-OSD를 쓸 수 있는 것이 당연**하다.
  - Circulant 기반이라는 사실은 **H 행렬 구조에 최적화를 추가할 수 있는 옵션**일 뿐, 그래프 기반이 아닌 것은 아니다.

**💡Q2. 왜 BB5/BB288 같은 qLDPC에서 BP/BP-OSD가 여전히 많이 사용되는가?**

- - **이유 1 — 현실적 디코딩 속도 / 구현 난이도**

    - Hypergraph blossom, HUF(Hypergraph Union Find)는:

      - 정확도 높다 (MLE 근사)
      - 그러나 복잡하고 computationally heavy
    - 반면 BP/BP-OSD는:

      - 실시간에 가깝게 빠름
      - GPU/ASIC 가속 가능
      - 산업적 구현이 훨씬 쉽다
  - **이유 2 — Sparse cyclic layout + flying qubit이 latency 부담을 줄여줌**

    - 하드웨어 아키텍처(ion/photonic shuttling/dynamic routing) 발전이 BP/BPOSD 기반 디코딩의 현실성을 높이고 있다.
    - → 그래서 실제 IonQ/Alpine/Oxford 연구에서 BP-OSD + cyclic-layout 조합이 의미 있게 쓰이는 것.

**💡****Q2. Union find와 MWPM은 Lattice 베이스여서 LDPC 계열과 호환이 안된다더니, 어떻게 qLDPC와 호환이 가능한가?**

- - **기존 MWPM / Union-Find는 ‘lattice-based surface code’를 위한 디코더**이며, **qLDPC에 그대로 쓰면 구조적 가정이 부서져서 의미가 없다.**
  - 하지만, **HyperBlossom / HUF / MWPF는 MWPM / Union-Find의 아이디어를 qLDPC의 하이퍼그래프 구조로 확장**한 형태이다.

|  |  |  |  |
| --- | --- | --- | --- |
| **디코더** | **대상** | **qLDPC 적용 여부** | **설명** |
| **MWPM (Blossom algorithm)** | Surface / Toric (2D lattice) | ❌ **그대로는 불가** | lattice 2D 근접성 & matching graph 전제 필요 |
| **Union-Find** | Surface Code | ❌ 그대로는 불가 | local cluster 병합 가정이 깨짐 |
| **HyperBlossom (MWPF)** | **qLDPC (hypergraph)** | ✅ **적용 가능** | MWPM 원리를 **Hypergraph Matching**으로 확장 |
| **Hypergraph Union-Find (HUF)** | **qLDPC (hypergraph)** | ✅ **적용 가능** | Union-Find 아이디어를 **hyperedge 병합**으로 확장 |
| **BP / BP-OSD** | LDPC / qLDPC | ⭕ 적용 가능 | Tanner graph 기반 확률적 메시지 패싱 |
| **Tensor BP / RG BP** | 대형 qLDPC | ⭕ 적용 가능 | 축소/계층 방식 최적화 |

**✅디코더 선택과 QPU의 성능**

- - 디코더의 선택은 양자컴퓨터 성능을 좌우하는 핵심 요인이자, 동시에 해당 시스템의 성능 수준이 집약적으로 드러나는 결과물이다.
  1. 양자컴퓨터의 플랫폼에 따라 코드 또는 디코더 선택에 제한이 있다.

     - 초전도체 기반 : Lattice 기반의 코드
     - 중성원자 및 이온트랩 기반 : Graph 계열의 qLDPC 기반 코드
  2. 디코더에 따른 에러정정 성능 결정

     - Standard BP : 빠르고 단순
     - Relay BP : 성능 향상 + 안정화
     - BP-OSD : 성능은 우수하지만 리소스 요구사항이 높아서 실시간 에러정정의 한계
     - 하이퍼그래프 기반 : 정확도 매우 우수하지만, 높은 연산량과 속도를 요구함.
  3. 위의 한계 및 트레이드오프로 인해 에러정정의 실제 한계가 결정이 됨.

     - FPGA 또는 ASIC
     - 부가적인 HBM 필요
