**📌 Near-Memory Computing(NMC)**

- - 연산 일부를 HBM 근처에서 처리하면 GPU까지 데이터를 굳이 안 보내도 된다
  - **NMC Base/Processor/L2 Cache Dies**

    - HBM 위에 **3D stacked**된 NMC 모듈:

      - **NMC Base Die**
      - **NMC Processor Die**
      - **NMC L2 Cache Die**
    - 이 3개가 연산을 처리함
    - 즉, DRAM → Cache → Compute → GPU 로 더 가까운 위치에서 처리함
  - 기존 방식

    - HBM → GPU → GPU 연산 → 결과 저장
  - 신규 방식

    - HBM → NMC → 일부 연산 수행 → GPU로 전송(혹은 그대로 메모리 내부 소비)
    - DRAM 근처에서 데이터 전처리(offloading)를 수행
  - 산업적 의미

    - 삼성 → HBM-PIM
    - 하이닉스 → HBM-AI
    - TSMC → on-interposer compute
    - NVIDIA → HBM Near-Memory Caching 연구 중

---

**✅** **각 업체별 NMC / IMC 비교**

**📌 1. 삼성 — HBM-PIM**

- - **유형**

    - In-Memory Compute (진짜 DRAM 내부에서 연산)
  - **실체**

    - HBM logic die에 **MAC array** 삽입
    - 기존 HBM과 signaling/PHY 호환 유지
    - FPGA/GPU/CPU와 연결해서 동작 시연
  - **강점**

    - ✔ DRAM 내부에서 곧바로 연산 → 데이터 이동 거의 0
    - ✔ AI dense matmul에 최적
    - ✔ 가장 실리콘/시연/상용화에 가까움
  - **약점**

    - ✖ 범용성 낮음 (MAC 특화)
    - ✖ 캐시/제어/스케줄링 없음
    - ✖ 소프트웨어 integration 필요 (컴파일러, runtime 등)
  - **포지션**

    - AI용 특화 DRAM 제품으로 팔아먹으려는 메모리 회사 전략

**📌 2. SK하이닉스 — HBM-AI**

- - **유형**

    - HBM에 compute logic + AI dataflow 최적화
    - HBM-AI는 PIM과 비슷하지만 더 넓은 철학을 가짐:
    - PIM + NDP + Scheduling + Dataflow
  - **강점**

    - ✔ AI-friendly memory scheduling
    - ✔ HBM 내부 데이터 경로 최적화
    - ✔ Sparse/GNN 같은 irregular workload도 고려
  - **약점**

    - ✖ SK하이닉스는 compute IP가 약함 (CPU/GPU/AI 없음)
    - ✖ 로드맵과 고객 의존성 큼
  - **포지션**

    - HBM-PIM의 확장형: AI memory로서의 포지셔닝
  - 삼성은 이미 제품에 집중했고
  - SK는 system level approach를 하는 셈

**📌 3. TSMC — On-Interposer Compute**

- - **유형**

    - Near-Memory Compute, 하지만 DRAM은 건드리지 않음
    - Compute chiplets를 **CoWoS/SoIC 인터포저 위**에 배치
  - **강점**

    - ✔ DRAM 제조사와 충돌 없음 (DRAM은 DRAM대로 팔림)
    - ✔ 범용 compute 가능 (RISC-V/NPU/CUDA 등)
    - ✔ 3D/2.5D 패키징으로 수직적 확장 가능
  - **약점**

    - ✖ 데이터 이동이 삼성 PIM만큼 짧진 않음
    - ✖ TSV 내부 integration만큼 공격적이지 않음
  - **포지션**

    - 패키징 회사로서 compute를 붙여 OEM이 원하는 구조를 만들게 하는 전략
  - 즉 **TSMC는 플랫폼 제공자**

****

**📌 4. NVIDIA — HBM Near-Memory Caching**

- - **유형**

    - Cache hierarchy 확장형 compute offloading
  - 대표적으로 NVIDIA Hopper/Blackwell에서 보인 방향:

    - HBM 주변에 L2/L3 확장
    - prefetch/compute scheduling near memory
    - 일부 reduction/aggregation의 offload
    - transformer attention의 precompute 고려
  - NVIDIA의 목표는 더 명확함:

    - **HBM → GPU SM 사이의 bottleneck 제거**
  - **강점**

    - ✔ 소프트웨어 스택 완성도 압도적 (CUDA, cuDNN, Transformer engine)
    - ✔ workload 이해도 높음
    - ✔ DRAM vendor에 의존 안 함
  - **약점**

    - ✖ 패키징 복잡 (Blackwell부터 CoWoS 최대치 사용)
    - ✖ NMC 가속기 직접 집적하려면 또 전력/열이 문제
  - **포지션**

    - **메모리 가까이에 cache + scheduler + reduction logic을 붙이는 compute 확장**
  - NVIDIA는 메모리 안까지 들어가진 않음 (PIM은 안 함)

**🧩 전체 비교표**

|  |  |  |  |  |
| --- | --- | --- | --- | --- |
| **회사** | **전략** | **Compute 위치** | **범용성** | **주요 대상** |
| 삼성 | HBM-PIM | DRAM logic die 내부 | 낮음 | Dense matmul |
| SK | HBM-AI | DRAM + Dataflow | 중간 | AI memory 전체 |
| TSMC | On-Interposer | 인터포저 위 | 높음 | OEM (GPU/AI ASIC) |
| NVIDIA | Near-Memory Cache/Offload | HBM ~ GPU 사이 | 매우 높음 | Transformer workload 전체 |

**📌 철학적 차이 한 줄 정리**

- - 삼성:

    - “연산을 DRAM 안으로 넣자”
  - SK하이닉스:

    - “DRAM을 AI 친화적으로 바꾸자”
  - TSMC:

    - “패키징으로 compute를 메모리에 붙여주겠다”
  - NVIDIA:

    - “소프트웨어부터 메모리 계층까지 최적화하겠다”

**📌 누가 시장을 먹을까? (전망)**

- - 현 시점에서 가장 유력한 승자는 **NVIDIA** **방식**
  - 이유:

    - ✔ transformer workload 이해도 최강
    - ✔ 소프트웨어 생태계 압도
    - ✔ DRAM vendor에 종속 안 됨
    - ✔ 패키징으로 이미 5년 앞서 있음
    - ✔ MLPerf + HuggingFace + CUDA stack까지 통합됨

> ***NMC 같은 기능은 내가 GPU 앞단에서 할 테니 DRAM 내부나 HBM 내부에 넣지 마라***

- - 반면

    - 삼성은 **제품은 있음** → 하지만 고객이 없음
    - SK는 **전략은 좋음** → compute IP 없음
    - TSMC는 **인프라는 있음** → 하지만 고객 의존

**📌 HBM5의 NMC 기능이 갖는 의미**

- - 기술적 의미

    - 특히 트랜스포머에서 메모리 트래픽의 병목을 해소한다는 관점에서 큰 의미 있음
  - 상업적 의미

    - ✔ DRAM 벤더 입장: 매우 의미 있음
    - △ GPU 벤더 입장: 제한적
    - ✖ 시스템 통제 관점: 충돌 위험 있음
  - NVIDIA가 채택할까?

    - 메모리 내부 compute는 거의 절대 안 받아들일 가능성 큼
    - 전문 용어로 host-driven compute model
    - DRAM은 host 없이 compute execution못함

      - PIM을 다른 말로 orphan compute 라고 함.
  - 실제로 2019~2022 삼성은 HBM-PIM 데모를 수십번 했고, 성능도 잘 나왔지만,

    - NVIDIAR가 움직이지 않으니 아무 일도 안 생김.
  - IMC는 상업적으로 가능성 매우 희박함
  - NMC는 그나마 GPU의 입맛에 맞는 조건하에 약간의 가능성 있음.

**출처 : 카이스트 테라랩**

- - GPU가 HBM만 쓰는 게 아니라 CXL을 통해 GPU가 외부 확장 메모리를 접근하는 모델
  - 메모리 벤더의 이점

    - HBM이 메모리 계층의 중심
  - GPU 벤더의 이점

    - 더 이상 모든 model state를 직접 HBM에 올리지 않아도 됨

      - KV-cache → LPDDR로 빼기
      - weights → CXL.mem로 빼기
      - optimizer states (training) → SSD로 빼기
  - **Tier 1 — HBM5 (초고대역폭, 낮은 대기, 저용량)**

    - → matmul, attention inner-loop 처리
  - **Tier 2 — LPDDR (중대역폭, 중간 대기, 중용량)**

    - → KV-cache, activation, intermediate state
  - **Tier 3 — CXL.mem (고대기, 대용량)**

    - → 모델 weights, extended KV-cache, batch queue 등
  - **Tier 4 — SSD backed CXL pool (초대용량)**

    - → persistable shared parameters, swapping

**출처 : 카이스트 테라랩**

- - **DDR5 DIMM 서버용은:**

    - 전압 높음
    - RDIMM buffering 필요
    - slot form factor 큼
    - trace 길어서 latency 높음
    - 열 높음
  - **LPDDR은 모바일이어서 모든게 반대:**

    - ✔ 전력 낮음
    - ✔ 대역폭 높음
    - ✔ 밀도 좋음
    - ✔ latency 상대적으로 낮음
    - ✔ 패키징 유연
  - **NVIDIA가 SOCAMM을 추진한 이유**

    - 트래픽의 주도권을 CPU/CXL로 넘겨주고 싶지 않음
    - HBM벤더, DRAM벤더, CPU벤더, CXL 컨소시엄을 모두 견제하고 GPU 중심으로 메모리를 재편할 수 있음
    - LLM Inference 구조와 맞물림
    - 전력문제 해소
