# Cloudflare, Palo Alto, Zscaler를 한 흐름으로 이해하기

Published: 2026-03-12T19:51:27.576000+09:00

Original Naver post: https://blog.naver.com/4-fire/224214241691

---

> 투자자들이 사이버보안 대표 기업을 이야기할 때 종종 함께 언급하는 회사들이 있다.
>
> 대표적으로 **Cloudflare**, **Palo Alto Networks**, 그리고 경우에 따라 **Zscaler**다.
>
> 처음 보면 이 회사들은 같은 회사처럼 보이지 않는다.
>
> Cloudflare는 원래 CDN 회사에 가깝고, Palo Alto는 방화벽 회사로 알려져 있으며, Zscaler는 Zero Trust와 SASE 쪽에서 자주 등장한다.
>
> 즉, 출발점이 다르고 고객이 느끼는 제품의 성격도 다르다.
>
> 그런데도 이 회사들이 같은 문맥에서 언급되는 이유는 단순하다.
>
> 과거에는 서로 다른 레이어를 담당하던 회사들이었지만,
>
> 보안 산업이 **온프레미스 장비 중심 구조에서 클라우드 기반 보안 서비스 구조로 이동하면서 서로의 영역에 진입하기 시작했기 때문**이다.
>
> 따라서 이들을 이해하려면 먼저 “누가 무엇을 하던 회사였는가”보다,
>
> **어떤 레이어에서 출발했고 지금 어디까지 확장했는가**를 보는 것이 더 중요하다.

---

**✅ Cloudflare와 Palo Alto가 같이 언급되는 이유**

- - 보안이라는 큰 카테고리 안에서 두 회사는 원래 담당하던 위치가 달랐다.

**📌** **Cloudflare의 출발점**

- - Cloudflare는 원래 **CDN과 인터넷 성능 최적화 회사**였다.
  - 웹사이트 앞단에 위치해 트래픽을 분산하고, 지연시간을 낮추고, DDoS를 막고, WAF를 제공하는 식으로 성장했다.
  - 즉, 웹 트래픽이 인터넷을 통해 들어오는 **엣지(edge)** 지점에서 가시성을 확보한 회사다.
  - 이후 Cloudflare는 단순 CDN 사업자에 머물지 않고, WAF, DDoS 보호, Bot 관리, API 보안, Zero Trust, SASE까지 확장했다.
  - 그래서 지금의 Cloudflare는 “웹 가속 회사”라기보다는 **인터넷 엣지 인프라 위에 보안을 얹은 플랫폼**에 가깝다.

**📌** **Palo Alto의 출발점**

- - 반면 Palo Alto Networks는 전통적으로 **차세대 방화벽(NGFW)** 회사다.
  - 기업 내부망과 데이터센터, 지사 네트워크를 보호하는 장비에서 시작했다.
  - 이후 엔드포인트, SOC, 클라우드 보안, SASE까지 인수합병과 제품 확장을 통해 포트폴리오를 넓혔다.
  - 즉 Palo Alto는 처음부터 “보안 회사”였다.
  - Cloudflare가 인터넷 인프라에서 출발해 보안으로 올라온 회사라면, Palo Alto는 보안에서 출발해 더 넓은 플랫폼으로 확장한 회사다.

**📌** **그래서 왜 같이 비교되는가**

- - 결국 둘이 같이 언급되는 이유는,**서로 다른 출발점에서 시작했지만, 지금은** **Zero Trust와 SASE라는 중간 지점****에서 만나고 있기 때문**이다.
  - Cloudflare는 엣지 네트워크를 기반으로 기업 보안 쪽으로 올라왔고,
  - Palo Alto는 방화벽과 엔터프라이즈 보안을 기반으로 클라우드 네트워크 보안 쪽으로 확장했다.
  - 즉 예전에는

    - Cloudflare = CDN / WAF / DDoS
    - Palo Alto = 방화벽 / 내부망 보안 / SOC
  - 처럼 나뉘어 있었다면, 지금은 둘 다

    - Zero Trust
    - SASE
    - SWG
    - ZTNA
    - API 보안
    - 일부 클라우드 보안
  - 같은 영역에 발을 걸치고 있다.
  - 투자자들이 이 둘을 함께 언급하는 이유는 바로 여기에 있다.
  - **보안 산업이 이제는 개별 제품 경쟁보다 플랫폼 경쟁으로 이동하고 있기 때문**이다.

---

**✅ 실제로는 서로 다른 레이어였다**

- - 그렇다고 두 회사가 완전히 같은 시장을 보는 것은 아니다.
  - 이 부분을 분리해서 보여주면 글의 구조가 훨씬 명확해진다.
  - 보안 산업은 원래 레이어별로 나뉘어 있었다.

[![](https://mblogthumb-phinf.pstatic.net/MjAyNjAzMTJfMjQ2/MDAxNzczMzEyMjI3ODk0.Z7WUHa85TSkLWhyghvu9dT0JVIFWoynKllyMfWmjH40g.fCe0pcdJU3iWTqS9GktwpqzuZ5yNUNq3dl7zUDRAzGcg.PNG/image.png?type=w800)](#)

**📌** **네트워크 엣지 / CDN 기반 보안**

- - 이 레이어는 인터넷에서 들어오는 트래픽을 가장 앞단에서 처리한다.
  - 대표 기능은 CDN, WAF, DDoS 보호, Bot 관리, API 보안 등이다.
  - 여기서 주요 플레이어는:

    - **Cloudflare**
    - **Akamai**
    - **Fastly**
  - 이 영역의 특징은 **글로벌 PoP 네트워크**를 보유하고 있다는 점이다.
  - 보안 장비를 고객사 안에 설치하는 것이 아니라, 인터넷 트래픽이 자연스럽게 통과하는 엣지에서 보호하는 구조다.

**📌** **전통적 네트워크 보안 / 방화벽**

- - 이 레이어는 기업 내부망, 데이터센터, 지사 네트워크를 보호한다.
  - 대표 플레이어는:

    - **Palo Alto Networks**
    - **Fortinet**
    - **Cisco**
    - **Check Point**
  - 이 영역은 원래 하드웨어 중심이었고, 대기업과 공공기관, 정부 기관에서 강력한 존재감을 가졌다.

**📌** **SASE / Zero Trust**

- - 이 영역은 기존의 네트워크 보안을 클라우드화한 것이다.
  - 사용자가 어디서 접속하든, 어떤 SaaS를 쓰든, 어떤 단말을 쓰든, 클라우드에서 정책을 적용하고 트래픽을 검사하는 구조다.
  - 대표 플레이어는:

    - **Zscaler**
    - **Palo Alto Networks**
    - **Cloudflare**
    - **Fortinet**
  - 이 영역이 중요한 이유는

    - 과거의 보안 경계가 “사무실”이었는데,
    - 이제는 사용자가 집, 카페, 출장지, 모바일 환경 등 어디에 있든 보호해야 하기 때문이다.

**📌** **엔드포인트 보안**

- - 사용자 PC, 서버, 워크스테이션, 디바이스 자체를 보호하는 영역이다.
  - 대표 플레이어는:

    - **CrowdStrike**
    - **SentinelOne**
    - **Palo Alto Networks**
  - 이 영역은 랜섬웨어, 악성코드, 이상행위 탐지, XDR/EDR 중심으로 발전했다.

**📌** **클라우드 보안**

- - AWS, Azure, GCP 같은 멀티클라우드 환경에서 워크로드와 설정을 보호하는 영역이다.
  - 대표 플레이어는:

    - **Palo Alto Networks**
    - **Wiz**
    - **Orca Security**
    - **Aqua Security**

****

**📌** **IAM / 접근제어**

- - 누가 무엇에 접근할 수 있는지를 관리하는 영역이다.
  - 대표 플레이어는:

    - **Okta**
    - **Microsoft**
    - **Ping Identity**

---

**✅ 그런데 왜 경계가 흐려졌는가**

- - 이제 중요한 포인트는, 이 레이어 구조가 예전처럼 깔끔하게 나뉘어 있지 않다는 점이다.
  - 보안 산업은 지금 **“레이어 전쟁”에서 “플랫폼 전쟁”으로 이동하는 중**이다.
  - 예전에는 한 회사가 한 영역에서 강하면 됐다.
  - 하지만 지금은 고객이 보안 제품을 여러 개 따로 사서 이어붙이는 방식보다, 가능하면 **하나의 플랫폼에서 통합 관리**하기를 원한다.
  - 그래서 각 회사들은 자신들의 원래 영역을 넘어 서로의 영역으로 들어가기 시작했다.

    - Palo Alto는 방화벽 회사를 넘어 엔드포인트, SASE, 클라우드 보안, SOC까지 확장했다.
    - Cloudflare는 CDN/WAF에서 시작해 Zero Trust, SASE, API 보안, 네트워크 보안 영역으로 올라왔다.
    - Cisco는 네트워크 장비에서 보안으로 확장 중이다.
    - Microsoft는 ID, 엔드포인트, 클라우드 보안을 묶고 있다.
    - Zscaler는 Zero Trust와 SASE를 중심으로 확장하고 있다.
  - 즉 지금은 “이 회사는 정확히 어느 영역 회사인가?”라는 질문 자체가 점점 어려워지고 있다.
  - 왜냐하면 **모두가 서로의 경계를 침범하고 있기 때문**이다.

---

**✅ SASE는 왜 중요해졌는가**

- - 이제 여기서 SASE를 설명하면 자연스럽다.

**📌** **SASE란 무엇인가**

- - SASE는 **Secure Access Service Edge**의 약자다.
  - 쉽게 말하면, 기존에 회사 건물 안에 설치하던 네트워크 장비와 보안 장비를 **클라우드 서비스 형태로 통합한 모델**이다.
  - 예전 기업 구조는 이랬다.

    - 직원은 사무실에서 일한다
    - 서버는 회사 데이터센터 안에 있다
    - 그러므로 회사 건물 경계에 방화벽을 세우면 된다
  - 하지만 지금은 구조가 완전히 달라졌다.

    - 직원은 재택근무, 출장, 원격근무를 한다
    - 데이터는 AWS, Azure, SaaS로 흩어져 있다
    - 기업 시스템 접근 경로가 사무실 하나로 고정되지 않는다
  - 이 상황에서는 과거처럼 “회사 건물 앞에 방화벽 한 대”로 해결할 수 없다.
  - 그래서 보안을 **사용자 중심, 클라우드 중심**으로 재구성한 개념이 SASE다.

**📌** **SASE를 구성하는 요소**

- - SASE는 하나의 제품이 아니라 여러 기능의 결합이다.

    - **SD-WAN**: 네트워크 연결 최적화
    - **SWG**: 웹 트래픽 필터링
    - **CASB**: SaaS 사용 통제
    - **ZTNA**: 사용자와 앱 간 접근 제어
    - **FWaaS**: 클라우드 기반 방화벽
  - 즉 SASE는 “보안 클라우드”이면서 동시에 “네트워크 클라우드”다.

---

**✅ 같은 SASE라도 Cloudflare와 Zscaler는 다르다**

- - 이제 SASE가 왜 중요한지를 설명했으면,
  - 같은 SASE로 묶여도 Cloudflare와 Zscaler는 철학이 다르다는 점을 풀면 된다.

**📌** **Cloudflare의 출발점: 인터넷 인프라**

- - Cloudflare는 원래 전 세계에 분산된 PoP를 가진 CDN 회사였다.
  - 즉 이미 인터넷 트래픽이 통과하는 위치를 확보하고 있었다.
  - 그래서 Cloudflare가 SASE를 한다는 것은, **기존 엣지 네트워크 위에 보안 서비스를 얹는 방식**에 가깝다.
  - 구조는 대체로 다음과 같다.

    - 사용자 → 가장 가까운 Cloudflare 엣지 → 검사 → SaaS/서버
  - 이 방식의 강점은:

    - Anycast 기반으로 빠른 라우팅
    - 레이턴시가 낮음
    - 웹/API 트래픽에 강함
    - 개발자 친화적
    - Edge compute와 연결 가능
  - 즉 Cloudflare는 **네트워크가 먼저 있고, 보안이 그 위에 올라간 구조**다.

**📌** **Zscaler의 출발점: 보안 정책 엔진**

- - 반면 Zscaler는 처음부터 Zero Trust와 기업 보안 정책 적용에 초점을 둔 회사다.
  - 사용자 디바이스에 에이전트를 설치하고,
  - 모든 트래픽을 Zscaler의 보안 클라우드로 보내 검사한 뒤 목적지로 전달한다.
  - 구조는 대체로 다음과 같다.

    - 사용자 PC → Zscaler 클라우드 → 정책 검사 → 목적지
  - 이 방식의 강점은:

    - 정책 적용이 매우 강력함
    - DLP가 깊음
    - CASB가 깊음
    - 대기업 보안팀이 선호
    - 사용자 단에서 통제 가능
  - 즉 Zscaler는 **보안 정책이 먼저이고, 네트워크는 그 정책을 집행하는 수단**이다.

**📌** **그래서 같은 SASE라도 철학이 다르다**

- - Cloudflare는

    - “네트워크 엣지 기반 SASE”라고 볼 수 있고,
  - Zscaler는

    - “보안 정책 중심 SASE”라고 보는 것이 맞다.
  - 둘 다 클라우드 기반 보안이라는 점에서는 비슷하지만,

    - Cloudflare는 인터넷 인프라에서 출발했고,
    - Zscaler는 보안 정책 엔진에서 출발했다는 차이가 있다.

---

**✅ “둘 다 TLS인데 뭐가 다르냐”는 질문의 핵심**

- - 사용자 입장에서는 둘 다 암호화된 터널처럼 보일 수 있다.
  - 실제로 둘 다 TLS 기반 연결을 활용한다.
  - 하지만 차이는 **암호화 그 자체가 아니라, 어디에서 통제를 시작하느냐**에 있다.

[![](https://mblogthumb-phinf.pstatic.net/MjAyNjAzMTJfMzIg/MDAxNzczMzEyNDM5MDA1.39TrzeoMwj5tfS7SNjVIb6jVWny-1ZvcFEA-mg_vTfkg.pVwFOpVwGuSHroEQBX_59Y3-dWgVG-SViWPoNicOB_4g.PNG/image.png?type=w800)](#)

**📌** **Cloudflare**

- - Cloudflare는 대체로 서비스 앞단 또는 엣지에서 TLS 종단을 잡는다.
  - 즉 사용자의 브라우저가 Cloudflare PoP와 HTTPS 연결을 맺고,
  - Cloudflare가 그 지점에서 트래픽을 검사한다.
  - 이 구조는 **서비스 보호 중심**이다.

**📌** **Zscaler**

- - Zscaler는 에이전트를 통해 사용자 디바이스에서 출발하는 트래픽을 자사 보안 클라우드로 강제로 보내고, 거기서 검사한다.
  - 이 구조는 **사용자 통제 중심**이다.
  - 따라서 둘 다 TLS 기반이라도,

    - Cloudflare는 **네트워크 엣지 종단**
    - Zscaler는 **사용자 단 강제 터널**
  - 이라는 차이가 있다.
  - 즉 암호화 방식이 같다고 해서 보안 아키텍처가 같은 것은 아니다.

---

**✅ Cloudflare는 PoP까지 오는 구간이 무방비인가**

- - 이 질문은 Cloudflare 구조를 이해할 때 매우 중요하다.
  - Cloudflare는 사용자가 가장 가까운 PoP로 접속하고, 거기서 트래픽이 검사된다.
  - 그러면 자연스럽게 이런 의문이 나온다.

    - “그럼 사용자에서 Cloudflare PoP까지 가는 인터넷 구간은 무방비 아닌가?”
    - 정확히 말하면 **완전한 무방비는 아니다.**
  - 다만 보호 방식이 다르다.

**📌** **TLS로 암호화된다**

- - 사용자와 Cloudflare 사이의 연결은 대부분 HTTPS/TLS다.
  - 즉 중간 ISP나 네트워크 사업자가 내용을 평문으로 보기는 어렵다.

**📌** **DDoS는 Anycast 구조로 분산된다**

- - Cloudflare는 Anycast 기반 네트워크이기 때문에, 공격 트래픽이 특정 지점으로 집중되지 않고 여러 PoP로 분산된다.
  - 따라서 엣지 이전 구간이 완전히 비어 있는 것은 아니다

.

**📌** **인터넷 코어와 가까운 위치를 가진다**

- - Cloudflare는 수많은 ISP와 직접 피어링하고 있어, 일반 기업보다 인터넷 코어에 훨씬 가까운 위치에서 동작한다.

**📌** **다만 이론적 리스크는 남아 있다**

- - 물론 BGP 하이재킹, 국가 단위 검열, MITM 같은 위험이 이론적으로는 가능하다.
  - 그래서 RPKI, 인증서 검증, HSTS 같은 보조 장치가 중요하다.
  - 이 점에서 Zscaler는 디바이스에서부터 보안 클라우드로 강제 터널을 만들기 때문에
  - **출발점 통제 측면에서는 더 strict한 모델**로 보일 수 있다.

---

**✅ 그래서 보안 측면에서는 Zscaler가 더 강한가**

- - 대체로 정책 통제와 DLP, 검사 깊이만 보면 Zscaler 쪽이 더 strict한 구조라고 볼 수 있다.
  - 그런데 여기서 중요한 것은, 보안은 항상 “더 강하면 더 좋은 것”이 아니라는 점이다.
  - 엄격함에는 비용이 따른다.

**📌** **Zscaler식 strict 모델의 단점**

1. 1. **성능 오버헤드**

      - 모든 트래픽을 Zscaler 클라우드로 보내고,
      - TLS 복호화/재암호화, DLP 검사, 정책 평가를 하면
      - 레이턴시와 처리 비용이 올라갈 수 있다.
   2. **TLS Break and Inspect 문제**

      - 강한 보안을 위해 HTTPS를 풀어서 검사해야 하는 경우,
      - 앱 충돌, 인증서 핀닝 문제, 특정 SaaS 오작동 같은 운영 이슈가 생길 수 있다.
   3. **에이전트 의존성**

      - Zscaler는 디바이스 에이전트 기반 통제가 핵심이기 때문에
      - BYOD, IoT, 서버, 컨테이너 환경에서 적용이 복잡해질 수 있다.
   4. **비용 구조**

      - 사용자 단위 과금과 기능별 추가 라이선스가 붙기 쉬워
      - 대기업에는 맞아도 SMB나 스타트업에는 부담이 될 수 있다.
   5. **개발자 친화성 부족**

      - Cloudflare는 Workers, API Gateway, CDN, Edge compute와 자연스럽게 연결되지만,
      - Zscaler는 보안팀 중심 제품이다.
      - 개발자 플랫폼 성격은 상대적으로 약하다.

---

**✅ 그렇다면 왜 Cloudflare를 선택하는가**

- - Cloudflare가 선택되는 이유는 단순히 “보안이 덜 강해서 더 편하다”가 아니다.
  - 오히려 **네트워크, 성능, 운영 편의성, 개발자 친화성, 가격 구조**까지 포함한 전체 시스템 관점에서 더 적합한 경우가 있기 때문이다.
  - Cloudflare가 유리한 경우는 보통 다음과 같다.

    - SaaS 사용 비중이 큰 기업
    - 글로벌 트래픽이 많은 기업
    - 레이턴시에 민감한 서비스
    - API 호출이 많고 웹 기반 서비스가 중요한 기업
    - 개발팀과 네트워크팀의 이해관계를 함께 만족시켜야 하는 기업
    - CDN, WAF, Zero Trust를 하나의 플랫폼으로 묶고 싶은 기업
  - 즉 Zscaler는 “보안팀이 좋아하는 구조”에 가깝고,
  - Cloudflare는 “네트워크팀과 개발팀까지 포함해 전체 운영 측면에서 설득력 있는 구조”에 더 가깝다.
  - 그래서 현실 시장은 단순히

    - Zscaler = 강함
    - Cloudflare = 약함
  - 이 아니라,

    - Zscaler = 통제 중심
    - Cloudflare = 성능과 확장성 중심의 균형형
  - 으로 보는 편이 정확하다.

---

**✅ 개인 사용자도 쓸 수 있는가**

**📌** **Cloudflare**

- - Cloudflare는 개인 사용자가 쓸 수 있는 제품이 있다.
  - 대표적으로:

    - **1.1.1.1 DNS**
    - **WARP**
  - 이들은 개인이 설치해서 빠른 DNS, 프라이버시 보호, 공용 Wi-Fi 보안 강화 같은 용도로 사용할 수 있다.
  - 물론 이것이 기업용 Zero Trust 정책 엔진과 동일한 것은 아니지만, Cloudflare가 **인터넷 인프라 회사**이기 때문에 개인 시장에도 자연스럽게 제품을 확장할 수 있다는 점을 보여준다.

**📌** **Zscaler**

- - 반면 Zscaler는 기본적으로 기업용이다.
  - 개인이 직접 계정을 만들어 독립적으로 쓰는 서비스가 아니라, 회사 IT 조직이 정책을 설계하고 사용자를 관리하는 구조다.
  - 이 차이는 두 회사의 본질을 그대로 보여준다.

    - Cloudflare = 인터넷 네트워크 회사가 보안으로 확장
    - Zscaler = 기업 보안 정책 회사

**✅ PQC 관점에서는 왜 Cloudflare가 더 널리 깔릴 수 있는가**

- - 이제 마지막으로 PQC(Post-Quantum Cryptography)까지 연결할 수 있다.
  - 이건 단순 보안 제품 비교를 넘어, 누가 미래 암호화 전환에서 더 빠르게 확산될 수 있는가의 문제다.
  - PQC는 기본적으로 TLS 레이어 전환과 밀접하다.
  - 즉 공개 인터넷에서 브라우저와 서버가 협상하는 암호 체계를 양자내성 알고리즘으로 바꾸는 문제다.

**📌** **Cloudflare가 유리한 이유**

- - Cloudflare는 이미 수많은 웹사이트의 TLS를 엣지에서 종단한다.
  - 즉 브라우저와 Cloudflare 엣지 사이의 핸드셰이크를 업그레이드하면 대규모 웹사이트 집합에 빠르게 PQC를 적용할 수 있다.
  - 쉽게 말하면:

    - **브라우저 ↔ Cloudflare 엣지**
  - 이 경계만 바꾸면 수백만 사이트에 효과가 전달될 수 있다.
  - 그래서 Cloudflare는 PQC의 **대중적 확산**에 유리하다.
  - 아래는 Cloudflare는 자사의 **Cloudflare One** 플랫폼이 이제 **제로 트러스트와 WAN 서비스를 포함한 전체 SASE 스택 전반에서 포스트 퀀텀 암호화(PQC)를 지원**한다고 발표했다는 내용의 자체 블로그이니 참고하자.

**📌** **Zscaler의 경우**

- - Zscaler는 기업 단위 정책 통제 회사다.
  - PQC를 적용하려면

    - 클라이언트 에이전트
    - Zscaler 클라우드
    - 검사 엔진
    - 내부 앱
    - 정책 시스템
  - 전체 호환성을 검증해야 한다.
  - 즉 배포 범위는 좁지만 통제는 더 깊다.
  - 그래서 PQC에서도 구조는 비슷하다.

    - **Cloudflare**: 인터넷 전체에 빠르게 널리 배포하기 유리
    - **Zscaler**: 기업 내부 정책으로 강제 적용하기 유리
  - 즉 Cloudflare는 **인프라 레벨 확산**,
  - Zscaler는 **정책 레벨 통제**에 강점이 있다.

- - Cloudflare, Palo Alto, Zscaler는 겉으로 보기에는 서로 다른 회사처럼 보이지만, 실제로는 보안 산업이 이동하고 있는 방향을 가장 잘 보여주는 사례들이다.
  - 과거 보안 산업은

    - CDN
    - 방화벽
    - 엔드포인트
    - IAM
    - 클라우드 보안
  - 처럼 레이어별로 뚜렷하게 분리되어 있었다.
  - 하지만 지금은

    - 사용자 위치가 고정되지 않고
    - 데이터가 클라우드로 이동했으며
    - SaaS와 API가 핵심이 되고
    - 기업이 통합 플랫폼을 원하면서
  - 각 회사가 서로의 영역으로 들어가는 **플랫폼 전쟁**이 벌어지고 있다.
  - 이 과정에서:

    - **Cloudflare**는 네트워크 엣지에서 출발해 보안으로 올라오는 회사
    - **Palo Alto**는 전통 보안에서 출발해 클라우드 플랫폼으로 확장하는 회사
    - **Zscaler**는 보안 정책 중심으로 SASE를 구현하는 회사
  - 라고 볼 수 있다.
  - 그리고 같은 SASE, 같은 TLS, 같은 Zero Trust라는 단어를 써도 실제로는 **출발점, 통제 지점, 고객군, 운영 철학이 전부 다르다.**
  - 결국 핵심은 이것이다.

    - **Cloudflare는 인터넷 인프라를 장악하면서 보안으로 확장하는 회사이고,**
    - **Palo Alto와 Zscaler는 보안 통제를 중심으로 플랫폼을 넓혀가는 회사들이다.**
  - 즉 이 회사들을 비교할 때는 누가 더 “보안이 강하냐”만 보면 안 되고,

    - 어디에서 트래픽을 장악하는가
    - 누가 정책을 강제하는가
    - 누가 더 넓게 배포할 수 있는가
    - 누가 더 낮은 마찰로 확산될 수 있는가
  - 를 함께 봐야 한다.
