# 논리 큐비트 800개를 향한 코드 설계: Walking Cat과 신규 qLDPC 연구를 함께 읽기

**✅ 1. 실시간 디코더 논쟁에서 시작된 질문**

[![](https://mblogthumb-phinf.pstatic.net/MjAyNjEwMDFfMSAg/MDAxNzkwODM1ODIxOTM1._7ldbh2H01_RMfDoUwrhH1FMjt86XEt-rhQcLz1ZM84g.UX19JCkWS6WMl5-8kH68Wa1T_xgo3JN5MF7n45wCk3Yg.PNG/image.png?type=w800)](#)

- - 최근 Michaela Eichinger와 IonQ의 QEC 연구 책임자 Nicolas Delfosse가 주고받은 의견은 양자 오류 정정 성과를 어떻게 읽어야 하는지 보여준다.
  - Michaela의 문제 제기는 다음과 같다.

    - 실제 양자 하드웨어와 디코더를 연결한 실시간 QEC는 이미 선행 연구가 있다.
    - IonQ의 이번 연구는 **시뮬레이션으로 생성한 데이터를 실제 CPU에서 디코딩한 성과**다.
    - 따라서 독자가 발표를 보고 “IonQ가 수백 개 논리큐비트를 실제로 구동하며 실시간 오류정정을 했다”고 이해하면, 연구가 입증한 범위를 넘어선다.
    - 연구 자체는 훌륭하지만, ‘최초’와 ‘종단 간’이라는 표현은 범위를 분명히 해야 한다.
  - Michaela는 연구 자체의 가치를 인정하면서, **실제 양자 하드웨어에서 수행한 실시간 오류 정정**과 **시뮬레이션 워크로드를 처리한 디코더 실험**의 차이를 강조했다.
  - Nicolas는 양자 워크로드가 시뮬레이션이라는 점을 인정하면서, 연구의 기여가 수백 개 논리 큐비트 규모의 전체 디코딩 파이프라인을 실시간으로 처리할 수 있는지 검증한 데 있다고 설명했다.
  - IonQ의 디코더 연구는 최대 408개 논리 큐비트의 워크로드를 대상으로, MacBook Pro의 M4 Max CPU에서 12개 코어를 사용해 처리 시간을 측정했다. 신드롬 추출 주기는 워크로드에 따라 1ms 또는 5ms를 가정했다.

    - [Real-time decoder for a MegaQuOp quantum computer using a single CPU](https://arxiv.org/html/2608.25027v1)
  - 한편 2021년 Honeywell·현재 Quantinuum 계열의 연구는 실제 이온 장치에서 하나의 논리 큐비트에 반복적인 신드롬 측정과 실시간 디코딩을 수행했다.

    - [Realization of real-time fault-tolerant quantum error correction](https://arxiv.org/html/2107.07505v1)
    - 따라서 **‘실시간 QEC 자체가 처음’이라는 해석은 성립하지 않는다.** 다만 이것만으로 IonQ가 주장하는 ‘대규모 범용 응용의 전체 디코딩’이라는 한정된 신규성까지 반박되는 것은 아니다.
  - 본문에는 **최대 408개 논리큐비트를 시뮬레이션한 벤치마크**라고 명시돼 있다. 동시에 제목과 도입부는 ‘업계 최초의 종단 간 실시간 디코더’, ‘양자 시스템을 최고 속도로 계속 작동시킨다’는 표현을 앞세운다.

    - 내 판단으로는 **본문이 시뮬레이션을 숨겼다고 보기는 어렵지만, 앞부분만 읽으면 실제 QPU 통합 성과로 다소 오해할 여지가 있다.**

|  |  |  |
| --- | --- | --- |
| **구분** | **Michaela가 강조한 기준** | **Nicolas가 강조한 기준** |
| 실증의 범위 | 실제 QPU와 연결된 오류 정정 | 대규모 애플리케이션의 디코딩 처리 능력 |
| 발표 표현 | ‘최초’와 ‘종단 간’의 범위를 정확하게 명시 | 연구가 해결한 확장성 문제를 충분히 평가 |
| 공통된 인식 | 시뮬레이션 성과는 유용하지만 하드웨어 통합은 별도의 과제 | 시뮬레이션 성과는 유용하지만 하드웨어 통합은 별도의 과제 |

- - 이 대화를 통해 볼 수 있는 것은 **코드 설계, 디코더, 실제 하드웨어의 성과를 각각 평가해야 한다**는 점이다.
  - Nicolas가 이후 공유하며 높이 평가한 신규 qLDPC 논문도 이 관점에서 읽을 필요가 있다.

**✅ 2. Nicolas가 주목한 신규 연구는 무엇인가**

- - 논문은 **Design Principles for Ultra-High-Rate Quantum Codes**, arXiv:2609.30069이다. Jong Yeon Lee, Koki Okada, Nishad Maskara, Kenta Kasai, Hengyun Zhou의 공동 연구다.

    - [Design Principles for Ultra-High-Rate Quantum Codes](https://arxiv.org/html/2609.30069v1)
  - Nicolas는 코드 구성부터 디코더와 아키텍처까지 발전이 빠르게 진행되고 있으며, 각각의 개선이 누적된다는 관점에서 이 연구를 소개했다.
  - 연구진은 인코딩률, 코드 거리, 검사 무게, 코드 크기 사이의 절충 관계를 체계적으로 탐색한다.
  - 주요 접근은 **pair-partition 기반 코드 구성**, **symplectic halving을 이용한 non-CSS 코드 구성**, **대칭성을 활용한 낮은 무게의 논리 연산자 기저 탐색**이다.
  - 아래 세 코드는 논문의 초록에 명시된 대표 결과다. 모두 non-CSS이며 검사 무게는 10이다.

- - 인코딩률과 데이터 큐비트 비용은 n,k를 이용해 계산한 값이다. 논문 Table II에는 인코딩률이 각각 0.233, 0.221, 0.215로 제시된다.
  - 이 연구는 코드 구성과 시뮬레이션을 다룬다. 이 결과를 특정 회사의 하드웨어 구현이나 채택 발표로 연결할 근거는 제시되지 않았다.

**✅ 3. 코드의 숫자와 검사 무게는 서로 다른 정보를 담는다**

- - 양자 코드의 [[n,k,d]]에서 **n은 데이터 큐비트 수**, **k는 논리 큐비트 수**, **d는 코드 거리**다.
  - 코드 거리는 신드롬으로 드러나지 않으면서 논리 상태를 바꾸는 비자명한 논리 연산자의 최소 무게다.
  - 이상적인 오류 정정 조건에서 임의의 데이터 큐비트 오류를 보장해 정정할 수 있는 개수는 t=(d-1)/2다. 따라서 d=11이면 5개, d=15이면 7개, d=20이면 9개다.

- - 검사 무게 w는 검사 하나가 비자명하게 작용하는 데이터 큐비트의 개수다. 연산자에 X,Z,Y가 붙은 위치를 세며, Y도 큐비트 하나로 센다.
  - Q70의 검사 무게가 7이라는 것은 **70개 데이터 큐비트 중 검사 하나가 7개를 확인한다**는 뜻이다.
  - 검사 하나는 신드롬 비트 하나를 제공한다. 여러 검사의 결과를 함께 보고 디코더가 오류를 추정한다.
  - 실제 회로에서는 측정과 게이트에도 오류가 발생한다. 따라서 코드 거리 d와 회로 수준 거리 dcirc를 구분해야 한다.

**✅ 4. Walking Cat의 세 코드와 비교하면 무엇이 달라졌는가**

- - Walking Cat에서 사용한 세 코드는 Q54, Q70, Q102다. 각각 GB8, BB7, GB8 계열의 CSS 코드다.
  - 읽는 방법은 다음과 같다.

    - **거리가 같으면:** 인코딩률이 높은 코드의 값이 크다.
    - **인코딩률이 같으면:** 거리가 두 배일 때 값은 네 배이다.
    - **두 요소가 모두 달라지면:** 인코딩률과 거리를 각각 확인해야 한다.

|  |  |  |  |  |
| --- | --- | --- | --- | --- |
| **대표 코드** | **인코딩률 (k/n)** | **kd^2/n** | **검사 무게** | **구조** |
| Q54 [[54,2,10]] | 3.70% | 3.70 | 8 | CSS |
| Q70 [[70,6,9]] | 8.57% | 6.94 | 7 | CSS |
| Q102 [[102,22,9]] | 21.57% | 17.47 | 8 | CSS |
| 신규 [[90,21,11]] | 23.33% | 28.23 | 10 | non-CSS |
| 신규 [[140,31,15]] | 22.14% | 49.82 | 10 | non-CSS |
| 신규 [[200,43,20]] | 21.50% | 86.00 | 10 | non-CSS |

- - 대표 신규 코드들의 인코딩률은 Q102와 비슷하다. **눈에 띄는 개선은 더 큰 코드 거리를 함께 확보했다는 점**이다.
  - 특히 [[90,21,11]]은 Q102보다 적은 데이터 큐비트로 비슷한 수의 논리 큐비트를 담으면서 거리 11을 확보한다.
  - [[200,43,20]]은 Q102와 거의 같은 인코딩률에서 훨씬 큰 거리 20을 확보한다.

    - 지표가 크게 상승한 이유는 주로 **거리 20을 확보했기 때문이다.**
    - **지표 86이 17.47보다 약 4.92배 크다고 해서, 논리 오류율이나 계산 속도가 4.92배 개선됐다는 뜻은 아니다.**

**✅ 5. CSS와 non-CSS는 구현 방식에도 영향을 준다**

- - CSS 코드는 안정자 생성자를 X 전용 검사와 Z 전용 검사로 나눌 수 있다. Z 검사는 X 오류 성분을, X 검사는 Z 오류 성분을 확인한다.
  - non-CSS 코드는 이 분리가 성립하지 않는 일반적인 안정자 코드다. 검사는 서로 다른 큐비트에 X와 Z를 섞어 적용할 수 있으며 Y도 포함할 수 있다.

|  |  |  |
| --- | --- | --- |
| **비교 항목** | **CSS** | **non-CSS** |
| 오류 성분 처리 | X·Z 성분을 나눠 디코딩하는 구성이 가능 | 혼합된 검사 구조에 맞춘 처리가 필요 |
| 코드 설계 | X·Z 분리 조건 아래에서 구성 | 일반 안정자의 설계 자유도를 활용 |
| 논리 연산 | 동일 코드 블록 사이의 transversal CNOT 등을 활용하기 좋다 | 코드에 맞는 논리 연산과 측정 방법을 설계해야 한다 |

- - CSS 여부만으로 성능 우열을 정할 수는 없다. 오류율과 인코딩률뿐 아니라 초기화, 읽기, 게이트, 디코딩까지 함께 평가해야 한다.
  - 신규 논문의 non-CSS 메모리 시뮬레이션은 초기 상태 준비와 최종 읽기를 이상적으로 취급하고 대기 오류를 제외한다. 논리 연산을 위한 surgery 비용과 아키텍처 비교는 후속 과제로 남긴다.
  - 시뮬레이션 결과를 읽을 때는 어떤 동작이 잡음 모델에 포함됐는지도 확인해야 한다.

**✅ 6. Walking Cat의 ℓ,m,A,B를 읽는 방법**

[![](https://mblogthumb-phinf.pstatic.net/MjAyNjEwMDFfMjE4/MDAxNzkwODM3Mzk4MDY4.akhPq9przRUNXKB9ceVW7wSrE384EwfI3TDyMLV6-v8g.cZ7oMqcPzYPd-7KT8-CP9hIpcVGCqYrq1ru0c-I82qog.PNG/image.png?type=w800)](#)

[**Fault-Tolerant Quantum Computing with Trapped Ions: The Walking Cat Architecture**](https://arxiv.org/html/2604.19481v1)

**📌 ℓ,m은 순환 길이다**

- - BB 코드의 ℓ은 x 방향, m은 y 방향의 순환 길이다. Q70에서는 ℓ=7,m=5다.
  - x 방향으로 7칸, y 방향으로 5칸 이동하면 각각 출발점으로 돌아온다. 이를 x7=I,y5=I로 쓴다.
  - 출발점을 (0,0)으로 잡으면 이동 결과는 다음과 같다.

|  |  |  |
| --- | --- | --- |
| **이동 칸 수** | **x 방향 이동 후 좌표** | **y 방향 이동 후 좌표** |
| 0칸 | (0,0) | (0,0) |
| 1칸 | (1,0) | (0,1) |
| 2칸 | (2,0) | (0,2) |
| 3칸 | (3,0) | (0,3) |
| 4칸 | (4,0) | (0,4) |
| 5칸 | (5,0) | (0,0) - 처음으로 복귀 |
| 6칸 | (6,0) | (0,1) |
| 7칸 | (0,0) - 처음으로 복귀 | (0,2) |

- - 한 데이터 그룹에는 ℓm=7×5=35개 큐비트가 있다. Q70은 이러한 그룹을 두 개 사용하므로 n=2ℓ m=70이다.
  - 소문자 x,y는 순환 이동 행렬이다. 대문자 Pauli 연산자 X,Z와 구분해서 읽어야 한다.

**📌 A,B는 검사에 연결할 위치를 정한다**

- - Q70의 정의는 **A=y****2****+x****2****+x****3****+x****4**, **B=y+x+x****3******다.
  - 각 항은 같은 출발점에서 선택하는 별도의 위치다. 항을 차례대로 따라가는 이동 경로로 읽지 않는다.

|  |  |  |  |
| --- | --- | --- | --- |
| **행렬** | **연결되는 데이터 그룹** | **출발점 \((0,0)\)에서 선택하는 위치** | **연결 수** |
| A | 첫 번째 그룹 | (0,2),(2,0),(3,0),(4,0) | 4개 |
| B | 두 번째 그룹 | (0,1),(1,0),(3,0) | 3개 |

- - 두 그룹의 (3,0)은 서로 다른 큐비트다. 따라서 한 검사의 무게는 4+3=7이다.

**📌 이전 논문의 코드 구성표는 이렇게 읽는다**

|  |  |  |  |  |
| --- | --- | --- | --- | --- |
| **코드** | **계열·검사 무게** | **ℓ,m** | **A** | **B** |
| Q102 | GB8 | 51,1 | x^22+x^26+x^37+x^50 | x^19+x^28+x^29+x^35 |
| Q70 | BB7 | 7,5 | y^2+x^2+x^3+x^4 | y+x+x^3 |
| Q54 | GB8 | 27,1 | x^8+x^13+x^15+x^16 | x^7+x^8+x^10+x^15 |

- - GB는 m=1인 경우다. 표의 별표는 Walking Cat에서 사용한 코드를 표시한다.
  - 원문의 Family는 코드 계열, w는 검사 무게, n,k,d는 코드 매개변수, kd2/n은 인코딩률과 거리를 함께 보는 지표다.

**✅ 7. 신규 논문의 J,L,P는 무엇을 정하는가**

[![](https://mblogthumb-phinf.pstatic.net/MjAyNjEwMDFfNzIg/MDAxNzkwODM4MzEyNDU4.NFOaIiDww13MFh7P0k1hcNyy7k8Vcog-MqYwTrovBSIg.s5CFy6WdzcrbFGcu4Qy1tijddf-Z1BAfx2dKTvw8BJ0g.PNG/image.png?type=w800)](#)

[**Design Principles for Ultra-High-Rate Quantum Codes**](https://arxiv.org/html/2609.30069v1)

- - 이번 CPM-PP 구성은 **P× P 순환 이동 행렬들을 J행·L열로 배치**해 CSS 부모 코드의 검사 행렬을 만든다.

|  |  |  |
| --- | --- | --- |
| **변수** | **정하는 것** | **CSS 부모 코드에서의 의미** |

- - 따라서 CSS 부모의 검사 행렬 크기는 JP× LP다. 검사 행을 늘려도 데이터 큐비트가 복제되지는 않으므로 J를 데이터 큐비트 수에 곱하지 않는다.
  - L,P가 고정되면 J는 n의 계산식에 직접 들어가지 않는다. 대신 검사 연결 수와 독립적인 제약을 바꾸며 k,d에 영향을 준다.
  - 이 구성의 설계 인코딩률은 Rdes=1-2J/L이다. 검사 사이의 종속성에 따라 실제 인코딩률은 달라질 수 있다.

**📌** **CSS 부모 코드란?**

**✅ 8. 왜 Walking Cat은 2ℓ m, 신규 코드는 LP/2인가**

- - 공통된 계산 기준은 **데이터 큐비트 수 = 데이터 그룹 수 × 그룹당 큐비트 수**다.
  - ℓm과 P는 그룹 내부 크기를 정하는 역할이 비슷하다. 두 논문의 변수를 동일시하는 **일반적인 등식 ℓm=P는 없다**.

|  |  |  |  |
| --- | --- | --- | --- |
| **코드 구성** | **데이터 그룹 수** | **그룹당 큐비트 수** | **데이터 큐비트 수** |
| Walking Cat의 GB·BB 코드 | 2 | ℓm | 2ℓm |
| 신규 CPM-PP의 CSS 부모 | L | P | LP |
| halving 후 non-CSS 코드 | L/2 | P | LP/2 |

- - Walking Cat의 2는 A,B에 대응하는 두 데이터 그룹에서 나온다.
  - 신규 코드의 L은 CSS 부모의 데이터 그룹 수다. Halving은 데이터 큐비트 수와 논리 큐비트 수를 모두 절반으로 줄이며 **인코딩률 k/n을 유지한다**.

|  |  |  |
| --- | --- | --- |
| **신규 non-CSS 코드** | **J,L,P** | **데이터 큐비트 계산** |
| [[90,21,11] | 4,10,18 | 10×18/2=90 |
| [[140,31,15] | 4,10,28 | 10×28/2=140 |
| [[200,43,20] | 4,10,40 | 10×40/2=200 |

- - 예를 들어 [[90,21,11])의 CSS 부모는 **10그룹 × 18개 = 180개**다. Halving 후에는 **5그룹 × 18개 = 90개**가 된다.
  - 여기에 2P를 적용하면 데이터 그룹을 두 개로 가정하게 된다. 실제 이 구성의 halving 후 그룹 수는 다섯 개다.
  - 신규 논문의 non-CSS 수식 H=(A| B)에서 A,B는 **같은 큐비트들의 X 성분과 Z 성분**을 기록한다.
