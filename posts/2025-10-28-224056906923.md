**✅****Riverlane의 주요 비지니스**

- - 영국 케임브리지에 본사를 둔 Riverlane은 주로 **양자 오류 정정(Quantum Error Correction, QEC)** 기술 개발에 집중하는 기업으로, 양자컴퓨터가 실용화 단계로 나아가기 위해 반드시 해결해야 할 오류 문제를 기술적·산업적 관점에서 풀고 있다. 다음은 사업·제품·솔루션을 정리한 내용이다.

**💡****사업 목적 및 핵심 역량**

- - 미션: “양자컴퓨터를 지금보다 훨씬 더 빨리 유용하게 만든다(Make quantum computing useful far sooner).”
  - 핵심 문제: 현재 양자컴퓨터는 물리 큐비트가 매우 불안정해서 **연산 오류가 빠르게 누적**되며, 이 상태로는 실용적 수준의 양자 알고리즘을 돌리기 어렵다. Riverlane은 이 문제를 해결하기 위해 QEC 기술을 연구·개발한다.
  - 기술 영역:

    - QEC 디코더 알고리즘 및 하드웨어 구현
    - 오류정정 코드 설계
    - 여러 큐비트 플랫폼(초전도, 이온, 광자 등)에 적용 가능한 인터페이스 및 솔루션
    - QEC 학습·개발 툴 (소프트웨어 개발 키트, SDK) 등

**💡****주요 제품·솔루션**

Riverlane이 제공하는 주요 제품/솔루션은 다음과 같다.

**💡****솔루션 적용 및 협업 사례**

- - Riverlane은 여러 양자컴퓨터 제조사, 정부기관, HPC 센터와 협업 중이다.
  - 예시: Pasqal(중성 원자 플랫폼)과의 파트너십 — Pasqal의 하드웨어에 Riverlane의 QEC 스택을 통합하여 결함허용(fault-tolerant) 양자컴퓨터 구현을 목표로 함.
  - 재원 조달: 2024년 8월, 약 7천5백만 달러(£75M) 규모의 시리즈 C 펀딩 확보.

**💡****향후 로드맵 및 미래 전략**

- - Deltaflow 로드맵: 예컨대 최대 250개의 물리큐비트까지 실시간 QEC가 가능한 “Deltaflow 2” 단계 등.
  - 장기적으로는 수백만~수십억 개 물리큐비트 단위의 오류정정이 가능한 생태계 구축을 목표로 함.
  - 소프트웨어/하드웨어 통합 전략: SDK, 학습 플랫폼부터 하드웨어 칩까지 전체 생태계 구축

**💡****왜 중요한가**

- - 오류정정은 양자컴퓨터가 실용적 응용(예: 화학 시뮬레이션, 신약 개발, 소재 설계 등)을 하기 위해 반드시 넘어야 할 허들이다. Riverlane의 솔루션은 이 허들을 타깃으로 한다.
  - 다양한 하드웨어 플랫폼을 지원함으로써 특정 기술에 종속되지 않는 **플랫폼 독립성**을 강조한다.

**✅기존 양자컴퓨터 제조사와 Riverlane 방식 비교**

기존 각각의 양자컴퓨터 제조사의 방식과 Riverlane의 방식을 비교해보자.

**💡****기존(IBM·Google 등) 양자 제어 구조**

- - 사용자는 Qiskit·Cirq 같은 **상위 인터페이스에서 회로를 정의**한다.
  - 그 회로는 **Pulse Scheduler → Control Software → FPGA/하드웨어**로 내려가며, 실질적인 펄스(전압, 마이크로파, 위상)는 **FPGA/DAC**가 생성한다.
  - 하지만 이 FPGA 계층은 **OS나 사용자가 직접 접근할 수 없는 폐쇄된 펌웨어 레벨**이며, 각 하드웨어 제조사(IBM, Google, IonQ 등)가 개별적으로 개발한다.
  - 이 구조는 **API 호출마다 수백 µs~ms 지연**이 생기며, 하드웨어별로 전혀 다른 명령 구조를 가지므로 **이식성이 없다**.

> 기존 방식: “소프트웨어가 큐비트를 직접 제어하지 못하고, 제조사별 펌웨어가 중간에서 신호를 처리하는 구조.”

**💡** **Riverlane Deltaflow의 방식**

- - 리버레인의 접근은 완전히 다르다:
  - Deltaflow는 **HAL(Hardware Abstraction Layer)** 를 통해 서로 다른 하드웨어(이온·초전도·실리콘·광자)를 **단일 인터페이스로 제어**한다.
  - 이 OS는 **FPGA 내부에서 실행되는 제어 루프를 직접 프로그래밍**한다.

    - 즉, 명령이 중간 소프트웨어를 거치지 않고 **바로 FPGA 타이밍 블록으로 전송**된다.
  - 이렇게 하면 **큐비트 제어·피드백 지연이 µs → ns 수준**으로 줄어든다.

> Riverlane의 Deltaflow는 **운영체제 수준에서 FPGA를 직접 제어**함으로써 소프트웨어가 곧 하드웨어 제어권을 가지는 구조로 진화했다.
>
> 즉, 제조사 전용 펌웨어가 담당하던 FPGA 계층을 **직접 관리하도록 개방함으로써**, 연구자·개발자도 하드웨어 제어 루프를 재정의하고, 다양한 하드웨어에서 동일한 코드로 실험을 재현할 수 있게 만든 것이다.
>
> 이것이 바로 Riverlane이 말하는 “**양자 제어의 민주화 (Democratization of Quantum Control)**”다.

**✅QPU를 폐쇄적으로 운영하는 이유**

그럼, 제조사가 큐비트를 오픈하여 사용자가 직접 제어하게 해주면?

**1️⃣ 기술적 이유 — “제어권이 곧 안정성이다”**

|  |  |  |
| --- | --- | --- |
| **항목** | **제조사 입장** | **설명** |
| **하드웨어 안정성** | 매우 민감한 큐비트는 **수 ns 타이밍, μV 단위 전압**에도 영향을 받음 | 잘못된 사용자 코드가 FPGA 타이밍 루프를 건드리면 즉시 decoherence 발생 |
| **피드백 루프** | 제조사들은 하드웨어 레벨에서 **보정·칼리브레이션 루프**를 자동 실행 중 | 이 루프를 외부 사용자가 건드리면 안정성이 무너짐 |
| **펌웨어 동기화** | FPGA·AWG·DAC 간 동기화는 내부 클록·PLL 구조로 통합되어 있음 | 사용자 개입 시 위상 동기 오차 발생 가능 |
| **보안·격리 문제** | FPGA가 직접 펄스를 쏘므로 악성 코드나 과전압도 가능 | 실험 장비 손상 위험 때문에 완전 개방 불가 |

- - 제조사 입장에서는 “FPGA 제어”는 단순한 계산이 아니라 **양자 하드웨어의 생명선**이다.
  - 그래서 **폐쇄적 제어 펌웨어 구조**를 유지하는 것이 안정성 확보에 유리하다.

**2️⃣ 상업적 이유 — “제품은 서비스 모델로 팔린다”**

|  |  |  |
| --- | --- | --- |
| **항목** | **제조사 입장** | **설명** |
| **클라우드 서비스 모델** | IBM, IonQ, Quantinuum, Google은 “클라우드 접속형 QPU 서비스”를 판매 | 고객이 FPGA를 제어하게 되면 서비스 모델 붕괴 |
| **IP 보호** | 제어 펌웨어·보정 루틴은 핵심 기술(IP) | 외부 접근 허용 시 회로 구조나 타이밍 노하우 노출 위험 |
| **고객 지원 부담** | 각 사용자가 하드웨어 레벨을 건드리면 문제 발생 시 지원 불가 | 고객별 세팅을 맞춰줘야 하므로 운영비 급증 |
| **시장 분화 전략** | “하드웨어+소프트웨어 통합”이 브랜드 차별화 수단 | 통제권 개방 시 브랜드 간 차별성 상실 |

- - 즉, 제조사는 **서비스 품질과 IP 보호**를 위해 저수준 제어권을 고객에게 넘기지 않는다.

**3️⃣ Riverlane의 위치 — “하드웨어를 대신 관리해주는 표준계층”**

- - Riverlane은 제조사 대신 그 제어 계층을 **표준화된 운영체제 형태로 관리**한다.

    - 제조사는 여전히 하드웨어 내부 타이밍·안정화 루프를 유지
    - Riverlane은 그 위에 **표준 HAL (Hardware Abstraction Layer)** 을 얹어
    - FPGA의 사용자 영역(User Region)만 제어 가능하게 분리
  - 즉, **완전 개방(사용자가 직접 FPGA를 제어)** 은 아니고,
  - **제조사-리버레인-사용자**의 3단계 구조로 **안정성과 개방성의 균형**을 맞춘 것이다.

> 주변에서 게임기나 휴대폰을 보다 더 효율적으로 사용하고 싶어서 이른바 "탈옥"을 시도하다가 전혀 작동이 안되는 "벽돌"현상을 호소하는 경우가 간혹 발생한다.
>
> 사용자가 임의로 변경하는 경우, 디바이스의 안정성에 중대한 결함이 발생할 수 있을 경우라면, 제조사는 개인 유저의 접근을 차단하게 된다.
>
> 하지만, 양자컴퓨터를 사용하는 유저라면 일반 유저는 아니겠고, 적당한 선에서 FPGA의 기능을 접근할 수 있도록 개방하여 다양한 기능과 성능 향상을 제공해 주는 대신 시스템의 안정성도 해치지 않는 유일한 해법이라 할 수 있겠다.

**✅QPU의 제어**

**1️⃣ QPU 제어의 기본 구조 (플랫폼 공통 개념)**

- - 모든 QPU는 아래와 같은 **4단 제어 스택**을 갖는다:

|  |  |  |
| --- | --- | --- |
| **계층** | **역할** | **대표 구성** |
| **① 사용자 계층** | 회로 실행 명령, 타이밍 스케줄 | OS, API, Qiskit, Δflow.OS |
| **② 제어기 (Controller)** | 시퀀스 관리, 신호 스케줄, 동기화 | 실시간 서버 + 타이밍 펌웨어 |
| **③ 전자 제어 하드웨어** | 펄스 생성·측정 | FPGA, DDS, AWG, DAC, ADC |
| **④ QPU** | 실제 큐비트 물리 구현 | 초전도 Josephson, 트랩드 이온, 실리콘, 광자 |

**2️⃣ 제어 하드웨어의 구성요소별 역할**

|  |  |  |
| --- | --- | --- |
| **장비** | **기능** | **설명** |
| **AWG (Arbitrary Waveform Generator)** | 아날로그 펄스 생성 | 초전도 큐비트 제어에 사용. 마이크로파 펄스의 진폭·위상 제어 |
| **DDS (Direct Digital Synthesizer)** | 정밀 주파수·위상 발생기 | 트랩드 이온에서 레이저 주파수 또는 마이크로파 톤 제어 |
| **DAC (Digital-to-Analog Converter)** | 디지털 파형을 아날로그 신호로 변환 | FPGA 내부에서 파형 데이터를 DAC으로 보냄 |
| **ADC (Analog-to-Digital Converter)** | 측정된 큐비트 신호(형광, 반사파 등)를 디지털화 | 측정 결과를 FPGA로 전달 |
| **FPGA** | 실시간 타이밍·피드백 | ns~μs 단위로 모든 신호를 동기화하고 제어 루프 관리 |

- - 즉, FPGA가 **“두뇌”**, AWG/DDS/DAC이 **“손발”**, QPU가 “몸”이라 보면 된다.

**3️⃣ 플랫폼별 제어 방식의 차이**

|  |  |  |  |
| --- | --- | --- | --- |
| **플랫폼** | **제어 신호** | **제어 장비** | **특징** |
| **초전도 (IBM, Google, Quantinuum 일부)** | 마이크로파 펄스, flux bias | AWG + DAC + FPGA | FPGA가 수 ns 정밀 타이밍으로 펄스 시퀀스 제어 |
| **이온 트랩 (IonQ, Oxford Ionics)** | 레이저 빔, 마이크로파, RF 전위 | DDS + FPGA + DAC | FPGA가 광 제어기(DDS)를 통해 레이저 주파수/위상 동기화 |
| **실리콘 스핀 (Intel, Diraq 등)** | GHz 전류/전압 펄스 | DAC + AWG + FPGA | FPGA가 gate 전압 제어 신호 실시간 조정 |
| **광자 (PsiQuantum, Xanadu)** | 위상 변조, 펄스 셰이핑 | EOM driver + FPGA + photonic control ASIC | FPGA가 optical switch 제어 및 타이밍 동기 |

**4️⃣ 구체적 예시: IBM과 Oxford Ionics 비교**

|  |  |  |
| --- | --- | --- |
| **구분** | **IBM (초전도)** | **Oxford Ionics (이온 트랩)** |
| **제어 핵심** | FPGA 기반 “QCC (Quantum Control Core)” | FPGA + DDS 기반 “Microwave Control Stack” |
| **신호 종류** | Flux bias, Microwave drive | RF trap, Microwave/Raman control |
| **피드백 루프** | FPGA → ADC → FPGA → DAC | FPGA → DDS → Laser driver |
| **실시간성** | ns~μs | μs~ms (레이저 시스템 포함) |
| **운영체제** | IBM Qiskit Pulse (폐쇄형) | Riverlane Δflow.OS (HAL 기반 개방형) |

**5️⃣핵심 정리**

- - **QPU는 “FPGA + 아날로그 신호 장치(AWG/DDS/DAC/ADC)”로 제어된다.**
  - FPGA는 실시간 제어의 중심 두뇌로서 다음을 담당하고,

    - 타이밍 동기화
    - 펄스 스케줄링
    - 피드백 판단
  - AWG/DDS는 FPGA가 보낸 디지털 명령을 아날로그 파형으로 변환해 **실제 큐비트(초전도, 이온 등)에 작용하는 물리 신호**를 만들어낸다.
  - IBM, IonQ, Oxford Ionics, Quantinuum, Google 모두 이런 구조를 유지하되, **“FPGA를 사용자가 직접 접근할 수 있느냐**” 에서만 차이를 보인다.

**6️⃣ 각 시스템별 비교**

|  |  |  |  |  |
| --- | --- | --- | --- | --- |
| **구분** | **제어 신호** | **핵심 제어 장비** | **실시간성** | **OS/제어 방식** |
| **IBM (초전도)** | 마이크로파, Flux bias | FPGA + AWG + ADC | ns~μs | Qiskit Pulse / 폐쇄형 |
| **Oxford Ionics (이온)** | 레이저, RF, 마이크로파 | FPGA + DDS + AOM | μs~ms | EQC/ 폐쇄형 |
| **PsiQuantum (광자)** | 광 위상, 스위치 | FPGA + EOM + Photonic ASIC | ns | FPGA + Photonic Driver ASIC |

**✅****제조사가 HAL(****Hardware Abstraction Layer) 제공, 가능한가?**

**1️⃣ HAL이 필요한 이유**

- - FPGA를 직접 노출하면 다음과 같은 문제가 있기 때문에,

    - 타이밍 안정성,
    - 장비 손상 위험,
    - 멀티유저 충돌
  - HAL은 이런 위험을 막으면서도, 사용자에게 **“FPGA에 직접 제어 신호를 보낸 느낌”** 을 줄 수 있는 안전한 인터페이스다.

**2️⃣ HAL이 하는 일**

- - HAL은 다음 세 가지를 한다:

|  |  |  |
| --- | --- | --- |
| **계층** | **기능** | **역할** |
| **(1) 명령 변환 (Command Translation)** | 사용자가 작성한 고급 제어 명령(예: apply\_pulse(channel=3, phase=90°))을 FPGA 레지스터 명령으로 변환 | API → FPGA bitstream 변환기 |
| **(2) 시간 스케줄링 (Timing Scheduler)** | FPGA 내부의 clock domain 에 안전하게 매핑 | ns 단위 지연·클럭 불일치 방지 |
| **(3) 권한 필터링 (Access Sandbox)** | 접근 가능한 레지스터·버퍼 영역만 허용 | 하드웨어 보호, 사용자 격리 |

- - 즉 HAL은 FPGA를 직접 만지지 않아도 **FPGA의 모든 기능을 안전하게 이용할 수 있는 창구** 역할을 한다.

**3️⃣ Riverlane Deltaflow 예시**

- - Riverlane의 Deltaflow는 FPGA가 수행하는 시간·게이트 제어를 HAL로 추상화했다.

    - 사용자는 Python API로 apply\_gate("X", qubit=2) 를 호출
    - HAL이 이를 FPGA의 timing + pulse + DDS 명령으로 변환
    - FPGA는 ns 단위로 동작하면서 실제 펄스를 출력
  - → FPGA 접근 없이도 동일한 실시간 제어 결과를 얻는다.

**4️⃣ 실제 구현이 “매우 어려운” 이유**

- - 문제는 **양자컴퓨터용 HAL** 이 일반 산업용 HAL보다 훨씬 복잡하다는 점이다.
  - FPGA에 단순히 명령을 전달하는 수준이 아니라, **ns~μs 단위의 동기화·스케줄링·보호를 동시에 수행**해야 하기 때문이다.

|  |  |  |
| --- | --- | --- |
| **구분** | **설명** | **결과** |
| **① 타이밍 결정성(Determinism)** | HAL이 FPGA 내부 클럭에 정확히 맞춰 타이밍을 제어해야 함. 일반 OS 커널 수준의 지터(10~100ns)도 치명적 | 실시간 RTOS 수준의 펌웨어 필요 |
| **② 자원 매핑(Resource mapping)** | FPGA 내부에 수천 개의 DSP, LUT, BRAM이 있음. 각 기능을 HAL이 자동 배분·스케줄링해야 함 | 동적 자원 관리가 어려움 |
| **③ 피드백 루프 안전성(Safety)** | 측정 결과가 μs 단위로 FPGA에 피드백될 때, 사용자 코드가 잘못된 루프를 만들면 하드웨어가 과열/과전류 발생 | HAL이 보호 로직 삽입 필요 |

- - 즉, HAL은 단순한 추상화 계층이 아니라, **하드웨어 보안, 타이밍 커널, 실시간 스케줄러** 를 전부 포함한 “미니 OS” 수준이 된다.

**5️⃣결론**

- - HAL을 제공하면, 사용자는 FPGA를 직접 만지지 않아도 실시간 제어·피드백 루프를 안전하게 구현할 수 있다.
  - 즉, IonQ 같은 시스템도 HAL을 올리기만 하면 외부 사용자에게 제어 권한을 열 수 있다.
  - HAL은 원리적으로 “FPGA에 안전한 문을 하나 여는 일”이다.
  - 하지만 그 문은 **μs 단위 실시간 보장 + 안전성 + 자원 관리**까지 책임져야 하므로, 단순 드라이버가 아니라 **운영체제급 복잡성**을 가진다.

> HAL을 만들 수 있다.
>
> 하지만 **“만들 수 있는 것”과 “안전하게, 산업 수준으로 제공할 수 있는 것”은 전혀 다르다.**
>
> 즉, HAL은 단순한 필터링 레이어가 아니라 **하드웨어 제어 + 실시간 OS + 보안 커널을 통합한 엔진**이다.
>
> 그래서 지금도 Riverlane, IBM, Quantinuum 같은 곳이 수년 단위로 개발하는 것이다.
>
> 이것이 Quantum Machines의 OPX가 각광을 받고, Nvidia의 선택을 받아 DGX Quantum에 내장된 이유이기도 하다.

**✅****결론**

- - 지난 9월 Analyst Day에서 **IonQ**는 자사의 **양자 운영체제(Quantum Operating System, QOS)** 비전을 공식적으로 언급했다.
  - 이는 단순한 제어 소프트웨어가 아니라, 하드웨어·펌웨어·미들웨어를 포괄하는 통합적 플랫폼으로서의 운영체제를 의미한다. 이미 **Microsoft**를 비롯해 **NVIDIA** 등 주요 기업들이 유사한 방향으로 양자 운영체제 개발을 추진 중이다.
  - 향후 양자컴퓨팅 시장의 주도권은 **FPGA를 얼마나 효율적으로 활용하고 제어할 수 있는가**에 달려 있다고 해도 과언이 아니다.

    - 양자컴퓨팅이 직면한 가장 큰 기술적 도전은 두 가지 — **연산 능력(Quantum Performance)** 과 **확장성(Scalability)** — 이다.
    - 연산 능력은 양자 오류 정정(QEC) 기술의 정교함에 의해 결정되고, 확장성은 **광자 기반 원격 얽힘(Photonic Entanglement)** 을 통한 QPU 간 연결성 확보에 달려 있다.
    - 그리고 이 두 영역 모두의 기반에는 **FPGA를 통한 실시간 제어 및 통신 동기화**가 존재한다.
  - 결국, FPGA의 안정적인 접근과 제어권을 사용자 또는 상위 소프트웨어 계층에 제공하는 것은, 일종의 “Mini OS”를 구축하는 것과 같다.
  - 즉, 복합적인 **양자 운영체제(QOS)** 는 하위 계층의 하드웨어(FPGA, QPU 등)를 정밀하게 제어하고, 상위 계층의 알고리즘 및 응용 프로그램이 이를 표준화된 인터페이스를 통해 활용할 수 있도록 하는 **전체 생태계의 핵심 제어 허브** 역할을 수행하게 된다.
  - QOS가 진화를 거듭할 수록 양자컴퓨터는 고전컴퓨터로부터의 독립을 꿈꿀 수 있게 된다.

    - 이것이 QOS를 준비해야 하는 이유인 것이다.

> 가야할 길이 너무 멀다. 혹시 이중 일부를 이미 준비한 기업은 없을까 모색할 법도 하다.
