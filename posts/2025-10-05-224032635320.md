먼저 비트코인이 동작하는 네트워크에서 사용되는 암호화 기법을 살펴보자.

서명에는 ECDSA를 사용했었는데, Schnorr(BIP340)을 사용하고, 해시에는 SHA-256, RIPEMD-160을 조합해서 사용한다.

먼저 서명과 해시가 무엇인지 살펴보자.

**💡****서명 (디지털 서명)**

- - 디지털 서명은 서명자의 개인키로 메시지를 암호화해서 만든 고유한 암호화된 값이다.
  - ECDSA 같은 알고리즘을 사용해서, 메시지 해시값을 개인키로 서명해 생성하며, 이 서명은 공개키로 검증 가능하다.
  - 서명의 목적은 메시지가 서명자에 의해 작성되었고, 도중에 변경되지 않았음을 보증하는 것이다.
  - 비트코인에서 ECDSA 서명은 거래 내역이 진짜 소유자에 의해 승인되었는지 확인하는 데 사용된다.

**💡****해시 (단방향 해시 함수)**

- - 해시는 임의 길이 데이터를 고정된 크기의 짧은 값(해시값)으로 변환하는 함수이다.
  - 이 과정은 단방향이며, 해시값으로부터 원본 데이터를 복원하는 것은 불가능하다.
  - SHA-256 같은 해시는 데이터 무결성을 검사하거나, 디지털 서명 시 메시지의 요약(메시지 다이제스트)을 만드는 데 사용된다.
  - 비트코인 네트워크는 블록체인 무결성 유지, 작업 증명(채굴)에 SHA-256 해시를 사용한다.

> 비트코인에서는 디지털 서명을 이용하여, 메시지가 서명자에 의해 작성되었고, 도중에 변경되지 않았음을 보증한다. 하지만, 메시지 크기가 클 경우, 전체 메시지를 그대로 서명하면 계산량이 비효율적으로 커지기 때문에, 임의의 크기의 메시지를 해시값으로 압축한 값을 이용하게 된다.
>
> 즉, 서명 과정에서 개인키로 해시값에 서명하고, 검증 과정에서 공개키로 서명을 확인하는 방식을 사용한다.

**💡****서명과 공개키**

- - 위에서 말하는 서명은 우리가 지겹게 써왔던 공인인증서(또는 공동인증서)에서 사용하던 방식이다.
  - 아래는 공인 인증서의 일부인데, 그 중 SubjectPublicKey필드값이 공개키 정보에 해당한다.

TBSCertificate ::= SEQUENCE {
...
subject Name,
subjectPublicKeyInfo SubjectPublicKeyInfo,
...
}
SubjectPublicKeyInfo ::= SEQUENCE {
algorithm AlgorithmIdentifier,
subjectPublicKey BIT STRING
}

- - 개인키는 인터넷 뱅킹시 항상 입력하던 비밀번호를 가리킨다. 지금까지는 공동인증서의 비밀번호(개인키)만 잘 보관하고 있으면 큰 문제가 생기지 않았고, 위와 같이 공개키 또한 노출이 되어도 문제가 되지 않았다.

**💡****해시**

- - 해시의 사전적 의미

    - 다진 고기, 음식
    - 잡동사니, 쓰레기
    - 우물정자 - 해시태그가 여기서 나온 말.
    - (속어)마리화나
    - 특정 함수를 이용하여 아무리 큰 값을 입력하더라도 고정된 길이의 데이터 값을 출력하는데, 이때의 출력값을 해시라고 함.
  - 역상 저항성

    - 동일한 값을 입력하면 해시값은 항상 동일하지만, 이 해시값을 이용하여 입력값을 알아낼 수 없다.

> 한번 다진 고기를 다시 원래 형태의 고기로 만들 수 없는 이치임.

- - 역변환이 불가능한 대신, Alice가 고기를 보내면서 다진 고기를 추가로 보내면, 이 고기를 받은 Bob은 고기를 다져서 Alice가 보낸 다진 고기와 같은지 다른지 비교한다.
  - 만일 Alice가 투뿔 한우를 보냈는데, 중간에서 누가 한돈으로 교체했다면, Bob은 그것을 받아서 일부를 다져보는데, 당연히 한돈일테니, 다진 한우와 다른 것을 알게되고, 누군가(누군지는 알 수 없음) 양아치 짓을 했는지 알 수 있게 된다.

**✅****암호화 기술**

**💡****비대칭 암호 (Asymmetric Cryptography)**

- - **RSA**: 소인수분해의 어려움에 기반. 이메일, HTTPS 인증서 등에서 오래 사용됨.
  - **ECC (Elliptic Curve Cryptography)**: 타원곡선 기반. RSA보다 짧은 키로 같은 보안 강도.
  - **ECDSA**: 디지털 서명에 사용 (비트코인, 이더리움 등 블록체인).
  - **EdDSA (Ed25519)**: 빠르고 안전한 서명 알고리즘, SSH·TLS 등에서 점점 더 많이 쓰임.
  - **Diffie–Hellman / ECDH**: 안전한 키 교환 방식.

**💡****대칭키 암호 (Symmetric Cryptography)**

- - **AES (Advanced Encryption Standard)**: 현재 가장 널리 사용되는 블록 암호. (AES-128/192/256)
  - **ChaCha20**: 모바일·저전력 환경에서 자주 사용되는 스트림 암호.
  - **3DES**: 예전 표준이지만 지금은 보안성·성능 한계로 점차 퇴출됨.

**💡****해시 함수 (Hash Functions)**

- - **SHA-2 (SHA-256, SHA-512 등)**: 블록체인, 디지털 서명, 무결성 검증에 광범위하게 사용.
  - **SHA-3 (Keccak)**: 차세대 해시 표준.
  - **BLAKE2 / BLAKE3**: 빠르고 안전한 해시 함수로 최근 많이 채택됨.
  - **MD5, SHA-1**: 예전에 널리 쓰였지만 보안 취약점 때문에 더 이상 권장되지 않음.

**💡****기타 (메시지 인증, 키 파생 등)**

- - **HMAC (Hash-based Message Authentication Code)**: 메시지 무결성 검증.
  - **PBKDF2, bcrypt, scrypt, Argon2**: 비밀번호 안전 저장용 키 파생 함수.
  - **TLS/SSL 프로토콜**: 실제 인터넷 보안 통신에서 RSA, ECC, AES, 해시 등을 조합해 사용.

**✅RSA와 ECC 차이**

**💡****RSA vs ECC (타원곡선 암호)**

- - **수학적 기초**

    - RSA: 큰 정수의 **소인수분해(factorization)** 문제에 기반.
    - ECC(예: ECDSA, Schnorr): 타원곡선 위의 **이산대수 문제(ECDLP)** 에 기반.
  - **키 크기(동일한 보안 수준에서)**

    - RSA: 매우 큰 키 필요 (예: 2048-bits RSA ≒ 112–128비트 보안 수준).
    - ECC: 같은 보안 수준에서 훨씬 작은 키(예: secp256k1 같은 곡선은 256-bit 키로 충분).
  - **서명·연산 효율**

    - ECC가 일반적으로 **더 작은 공개키·서명 크기**, **빠른 서명·검증**을 제공해 자원 제약 환경(모바일, 블록체인)에 유리.
  - **구조적 차이(실사용 영향)**

    - RSA는 공개키(모듈러스와 지수)가 크고 서명/암호화 방식도 다름.
    - 비트코인/암호화폐는 RSA가 아니라 **타원곡선 기반 서명(ECDSA 또는 Schnorr)** 을 사용함 — 그래서 ECC 특성이 직접적으로 영향.
  - **사용용도**

    - RSA는 공개키로 데이터를 암호화하면, 개인키로 암호문을 복호화하여 원본 데이터를 복원 가능
    - ECDSA는 서명자의 서명이 진짜인지 검증하기 위한 용도로 사용. 복호화 하는 기능 없음.

**💡****양자컴퓨터(Shor) 관점**

- - **둘 다 취약**: Shor의 알고리즘은 정수 소인수분해(RSA)와 이산대수(ECC 둘 다)를 다항시간에 풀 수 있도록 설계되어 있다. 즉 **RSA도 ECC도 이론적으로 깨진다**.
  - **실전 차이**: 키 크기나 구조 때문에 공격에 필요한 양자 자원(큐비트 수, 게이트 수 등) 추정치는 달라지지만, 본질적 위험은 동일: *공개키가 알려져 있고 충분한 양자자원이 있다면 개인키 복원이 가능*.

**💡****해시와 대칭암호는 다르게 영향을 받음**

- - RSA/ECC 같은 비대칭(공개키) 암호는 Shor로 **치명적**.
  - 대칭키(예: AES)와 해시(SHA-256)는 Grover 알고리즘으로 **제곱근 가속**을 당하므로, 키 길이만 늘리면(예: AES-256) 어느 정도 방어 가능.

    - 키공간이 2K라면

      - 고전 방식으로 암호를 구하려고 할때 시도 회수가 2K라면,
      - 양자 방식(Grover 알고리즘)으로 구하려면 2K/2로 줄어든다는 의미.
    - AES-128 → 실질 안전도 ≈ 64비트. (현대 보안 기준 대비 약함)
    - AES-256 → 실질 안전도 ≈ 128비트. (여전히 강력)
    - 키 길이가 늘어날 수록 방어 가능성이 더욱 높지만, 양자컴퓨터의 컴퓨팅 능력이 향상되거나 새로운 알고리즘이 등장할 경우 안심할 수 없는 상황
  - 블록체인에서는 서명(비대칭)의 위험이 더 직접적이다.

**✅****네트워크별 핵심 암호 기술 (간단 정리)**

**💡****비트코인 (Bitcoin)**

- - **서명**: 타원곡선 secp256k1 기반의 **ECDSA**(과거) / **Schnorr****(BIP340)**(Taproot 도입 이후). 주요 구현은 libsecp256k1.
  - **해시**: 블록 해시/머클루트 등에 **SHA-256**(두 번 적용) + 주소 생성에 **RIPEMD-160**을 조합.

**💡****이더리움 (Ethereum)**

- - **서명**: 계정 서명에 **secp256k1** **/** **ECDSA** (v,r,s 형태, 공개키 복구 방식 사용).
  - **해시**: 트랜잭션·컨트랙트·주소 생성 등에 **Keccak-256**(일반적으로 ‘Ethereum의 SHA-3’로 불리는 Keccak 계열)을 사용.

**💡****라이트코인 / 도지코인 / 비트코인캐시 계열**

- - **서명/해시**: 비트코인과 구조가 유사 — 대부분 **secp256k1 + SHA-256**(혹은 채굴 알고리즘 차이로 scrypt/other PoW 사용) 등. (네트워크별로 PoW 해시 함수가 다름)

**💡****솔라나 (Solana)**

- - **서명**: **Ed25519 (EdDSA)** 를 기본 서명체계로 사용 (고성능/저비용 서명/검증). 온체인에서 Ed25519 검증을 위한 네이티브/프리컴파일 지원도 존재.
  - **해시:** SHA-256 등도 병용.

****

**💡****기타 주요체인(요약)**

- - **Algorand, Stellar, Tezos 등**: 주로 **Ed25519 / EdDSA** 또는 선택적으로 **secp256k1 / P-256** 등을 지원.
  - **Ripple (XRP)**: 과거엔 secp256k1를 많이 썼고, 최근엔 Ed25519 등 옵션을 제공.
  - **스마트컨트랙트 플랫폼의 토큰(ERC-20 등)**: 기본적으로 이더리움의 암호화 스택을 따라감(= Keccak-256 + secp256k1 서명 모델).

**💡****기능별 정리 (서명 / 해시 / 특수기법)**

- - **디지털 서명**: secp256k1(ECDSA / Schnorr), Ed25519(EdDSA) — 대부분의 계정·트랜잭션 인증에 사용.
  - **해시 함수**: SHA-256, Keccak-256(이더리움), BLAKE2 등 — 블록체인 무결성·주소·채굴(POW)에 사용.
  - **영지식(Zero-Konwledge Prrof, ZKP)·프라이버시**: zk-SNARKs (Groth16 등), Ring Signatures, Bulletproofs, Pedersen Commitments — 프라이버시 코인·프라이버시 레이어에서 사용.
  - **합의(채굴) 해시(예시)**: Bitcoin: SHA-256d, Litecoin: Scrypt(예전), Zcash: Equihash(예전) — *합의용 해시*는 네트워크마다 다름.

> 대부분의 블록체인에서는 비대칭 암호키와 해시를 사용한다.

**💡****핵심 요약**

- - **취약 포인트 —** **서명****(타원곡선 ECDSA / Schnorr)**

    - 비트코인의 거래인증에 쓰이는 타원곡선 서명법(ECDSA / Schnorr)은 이론적으로 쇼어(Shor)의 알고리즘으로 개인키를 공략당할 수 있다. 즉 **공개키가 알려진 경우**(주소를 재사용했거나 이미 공개키가 블록체인에 드러난 경우) 개인키를 양자컴퓨터가 찾아내면 도난당할 수 있다.
  - **해시(SHA-256 등)는 훨씬 더 안전하다**

    - 해시함수(블록 해시·채굴 관련)는 그다지 취약하지 않다. 양자컴퓨터의 그로버 알고리즘은 가속을 제공하지만, 고전적 공격 대비 *근본적 파괴*가 아닌 **제곱근 속도 향상**만 준다 — 현실적 관점에서 즉시 깨질 수준은 아니다.
  - **누가 먼저 위험한가(타깃)**

    - 공개키가 이미 블록체인에 드러난 지갑(주소 재사용 또는 이전에 서명해 공개한 경우)이 가장 위험. 여러 연구·분석은 ‘레거시 지갑(재사용 주소 등)’의 상당량이 위험하다고 본다.
    - 반대로 **아직 공개키를 드러내지 않은(새로 생성한) 미사용 주소**는 당장은 안전하다.
  - 많은 블록체인/지갑 개발자·거래소는 **하이브리드 PQ 전환 전략**(기존 + PQ 알고리즘 병행), 키 회전, 주소 재사용 금지 등을 권장하고 있음.

- - 위 논문은 IonQ의 SVP인 Martin Roetteler 박사가 2017년 Microsoft에서 활동할 당시 분석한 내용이다.

      - Roetteler 등(2017)의 회로 분석은 타원곡선 이산대수(예: n-bit prime field)에 대해 **9n+2⌈log2n⌉+10** 개의 논리적 큐비트 상한식을 제시한다. 이 공식을 n=256에 대입하면 **약** **2.3k logical qubits** 수준이 나온다 — 그래서 타원곡선 계열은 ‘수천 논리큐비트’로 자주 표기됩

    - **실행시간(속도)**: 가정에 따라 수분~수시간~수일까지 다양하게 나오며, ‘하루 이내’ 또는 ‘수분~수시간’ 같은 시나리오도 최적화 가정 하에 제시된다. ECDLP(타원곡선 로그)는 같은 보안 등급의 RSA보다 보통 자원 요구가 **더 낮은 편**(즉, 상대적으로 깨기 쉬움)으로 평가된다.

**✅****한줄 결론**

**충분한 ‘논리적’(error-corrected) 큐비트가 확보되면 ECDSA/EdDSA 같은 타원곡선 서명으로 보호된 개인키는 복원될 수 있다**. 그렇기 때문에 **(1) 단기적 실무조치**와 **(2) 장기적 프로토콜/표준 전환(포스트-양자 암호, PQC)** 을 병행하는 게 안전하다.

**✅****대안(요약 — 무엇이 있고 장단점은?)**

**💡****1) 긴급·실무 조치(오늘~몇 달) — 개인/거래소 모두**

- - **주소 재사용 금지 & 이미 공개키가 노출된 주소의 자금 이동**
  - (이더리움의 경우) 한 번 서명해서 보낸 주소는 공개키가 복원 가능 → 가능한 한 즉시 새 주소로 옮기는 것을 권장. (비트코인도 P2PKH→스펜드 시 공개키 노출)
  - **대형 홀더/거래소**: 큰 잔액·레거시 주소(오래된 주소/사토시 시대 자금)는 우선순위로 이동·보호. 다중 서명(M-of-N)·콜드 스토리지 강화 권장.

**💡****2) 중간(1–3년) — 하이브리드/혼합 도입**

- - **하이브리드 서명/키교환(클래식 + PQC)**
  - 트랜잭션 또는 인증에 **기존 알고리즘과 PQ 알고리즘을 동시에 사용**하여 둘 다 깨야 성공하는 구조로 만듦(권장 ‘과도기’ 전략). NCSC 등도 하이브리드 접근을 단계적 전환 수단으로 권장.
  - **멀티시그(Multisig)·Threshold 서명에서 알고리즘 다양화**
  - 예: M-of-N 중 일부 키를 PQ 알고리즘으로 바꿔 공격 난이도를 높임. (거래소/커스터디에 유효)

**💡****3) 장기(3+년) — 표준 전환 및 프로토콜 업그레이드**

- - **PQC 표준 채택**: NIST가 선정한 알고리즘들 — **CRYSTALS-Kyber (KEM), CRYSTALS-Dilithium / Falcon / SPHINCS+ (서명)** 등을 도입. 각각 장단점(키/서명 크기, 검증비용, 구현 난이도)이 있으므로 서비스 요구에 맞춰 선택해야 함.

    - **Dilithium**: 균형형(크기·속도).
    - **Falcon**: 서명 크기가 짧아 블록체인 친화적(단, 구현·특허·정밀성 고려).
    - **SPHINCS+**: 해시기반(매우 안전·투명) — 그러나 서명 크기가 크다(온체인 비용 문제).
  - **프로토콜 레벨 마이그레이션 (BIP/하드포크/소프트포크)**

    - 체인 자체의 규격을 바꿔 PQ 서명을 지원하거나 하이브리드 트랜잭션 타입을 추가(비트코인/Ethereum 모두 논의중). 이건 커뮤니티 합의·테스트·시뮬레이션이 필요.

**💡****4) 대안적(특수) 방법**

- - **해시 기반 서명(Lamport + Merkle tree, SPHINCS 계열)**: 원리상 양자저항성이 강함(Shor 영향 없음). 단점: 키·서명 크기와 상태관리(일부는 일회용)가 문제. SPHINCS+는 stateless로 현실적 선택지.
  - **데이터 장기보호**: 장기 기밀(“store now, decrypt later”) 대비 → 데이터를 AES-256 등으로 암호화하고 이 대칭키를 PQ KEM(예: Kyber)로 감싸 보관(키 관리·갱신 정책 필요).

**✅****구체적 권장 체크리스트 (우선순위별 — 개인 / 서비스 운영자)**

**💡****개인(지갑 사용자)**

1. 1. **지금 당장**: 이미 ‘보낸 적 있는’(트랜잭션을 만든) 주소에 큰 금액을 넣지 말고, 가능하면 새(미사용) 주소로 빠르게 옮긴다. (공개키 노출 위험).
   2. **중기**: 거래소에 맡긴 자금(특히 레거시 주소가 많은 거래소)은 거래소의 PQ 계획과 키 관리 정책을 확인. 큰 금액은 콜드 월렛에 분산 보관.
   3. **백업**: 개인 시드·프라이빗키 백업은 AES-256 등으로 강력히 암호화(장기 저장 대비), 복구 키는 오프라인·다지점 저장.

**💡****기관·거래소·지갑 제공자**

1. 1. **당장**: 크립토 인벤토리 파악 — 어떤 지갑·주소가 공개키를 노출했는지 목록화.
   2. **단기**: 핵심 자금(고액) → PQ 준비가 끝날 때까지 안전한 새로운 주소(비재사용)로 선제 이동, 멀티시그 정책 강화.
   3. **중기**: **하이브리드 서명**(클래식 + PQ) 시험 도입, PQ 라이브러리(검증된 구현) 통합 테스트.
   4. **장기**: 프로토콜 변경(soft/hard fork)·고객 커뮤니케이션·법적·운영적 준비 포함한 PQ 마이그레이션 로드맵 수립(예: NCSC 권고 타임라인 참고).

**✅****왜 “하이브리드(클래식+PQC)”가 현실적 해법인가?**

- - **이유**: PQ 표준·라이브러리가 성숙해도, 생태계 전반(지갑·노드·하드웨어·규제)이 동시에 바뀌긴 어렵다. 하이브리드는 **기존 호환성 유지 + 미래 방어**를 동시에 제공함. NCSC 등도 하이브리드 단계를 권장한다.

**💡****구현상 고려사항(블록체인 특유의 제약)**

- - **서명 크기(가스·수수료 문제)**: SPHINCS+ 서명은 큰 편 → 온체인 비용 상승. Falcon은 작지만 구현·IP 이슈·수치 안정성 고려 필요. Dilithium은 균형형. 선택은 체인 특성(블록 사이즈, 가스 모델)에 따라 달라짐.
  - **상호운용성**: 소프트포크/하드포크 없이도 일부 체인은 트랜잭션 안에 ‘추가 메타데이터’(예: OP\_RETURN)에 PQ서명을 넣는 실험을 할 수 있지만, 이는 법적·실무적 검토 필요.
