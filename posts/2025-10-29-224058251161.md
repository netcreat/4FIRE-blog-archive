> 앞서 NVQLink에 대해서 알아봤었는데, 과연 GPU가 리얼타임으로 QPU를 컨트롤 할 수 있을지가 초미의 관심사다. 그래서 이번 포스팅에서는 이 부분을 집중 분석해 보겠다.

---

**✅****GPU의 특성**

**1️⃣ GPU의 기본 개념**

- - **GPU (Graphics Processing Unit)** = 다수의 연산 코어를 병렬로 배치한 대규모 병렬 연산기.
  - 원래 그래픽 렌더링용으로 설계됐지만, 지금은 과학 계산, AI, 양자 시뮬레이션, 딥러닝 등 범용 고성능 연산에 쓰입니다.

**2️⃣ GPU의 핵심 특성**

|  |  |  |
| --- | --- | --- |
| **분류** | **특성** | **설명** |
| **1. 병렬성 (Massive Parallelism)** | ✔ | 수천~수만 개의 연산 코어가 동시에 연산. 대규모 벡터/행렬 계산에 압도적. |
| **2. 스루풋 (High Throughput)** | ✔ | 초당 수백 TFLOPS의 처리량. CPU 대비 수백 배. |
| **3. 결정성 부족 (Non-deterministic Timing)** | ⚠️ | 내부 스케줄링이 동적이라 실행 타이밍이 일정하지 않음. 실시간 제어엔 부적합. |
| **4. 지연 (Latency)** | ⚠️ | 단일 연산은 느림(수 µs~ms). 하지만 대량 병렬 연산엔 최적화. |
| **5. 메모리 병목** | ⚠️ | 연산은 빠르지만 VRAM I/O가 지연 요인이 됨. |
| **6. 동시성 (Concurrency)** | ✔ | 수천 스레드가 동시에 실행되지만 순서 보장은 안 됨. |
| **7. 결정적 결과** | ✔ | 비결정적은 “타이밍”이지 “결과”는 항상 동일. 같은 입력 → 같은 출력. |

**3️⃣ GPU의 내부 동작 모델 (CUDA 기준)**

1. 1. **CPU가 명령을 생성**

      - CUDA API 호출(cudaLaunchKernel)
      - GPU 메모리에 데이터를 올림
   2. **GPU가 커널 실행**

      - SM 단위로 수천 워프를 병렬 실행
      - Warp scheduler가 동적으로 스레드를 배분
   3. **결과 반환**

      - GPU 메모리 → CPU 메모리로 전송
   - 이 과정은 매우 빠르지만, CPU ↔ GPU 전송이나 커널 스케줄링 시점은 **운영체제와 하드웨어 상태에 따라 변동**된다.
   - 그래서 실시간성(real-time determinism)이 없다.

**4️⃣ GPU의 장점 vs 단점**

|  |  |  |
| --- | --- | --- |
| **구분** | **장점** | **단점** |
| **장점** | • 엄청난 병렬 처리 성능• AI/양자 시뮬레이션에 최적• 높은 전력 효율 대비 성능 | • 실시간 제어 불가 (비결정성)• 단일 스레드 연산 느림• OS 스케줄러 의존• 전력 소모 큼 |
| **결정적 루프** | ✖ 불가능 | 지연이 일정하지 않음 |
| **통합 연산 (AI+Quantum)** | ✔ NVQLink가 이 역할 수행 | GPU가 대규모 보정/디코딩/학습 처리 담당 |

**5️⃣ GPU의 특성이 NVQLink와 결합할 때의 의미**

|  |  |
| --- | --- |
| **GPU 특성** | **NVQLink에서의 활용** |
| **병렬성** | 수천 큐비트의 신드롬 데이터를 동시에 디코딩 가능 (AI 기반 QEC). |
| **대역폭** | RTH DMA를 통해 µs 단위로 대량 데이터 전송 가능. |
| **비결정성 보완** | RTH FPGA가 타이밍 결정성을 보정, GPU는 연산만 담당. |
| **AI 통합성** | QPU 피드백 + AI 모델 최적화(예: RL 기반 error mitigation). |

**6️⃣ GPU와 FPGA/QPU의 역할 대비**

|  |  |  |  |
| --- | --- | --- | --- |
| **계층** | **구성요소** | **역할** | **시간 스케일** |
| **물리 제어** | FPGA 제어기 | 펄스 / 측정 / 실시간 보정 | ns–µs |
| **연산 피드백** | GPU (NVQLink) | 오류 디코딩, AI 학습, 하이브리드 계산 | µs–ms |
| **시스템 관리** | CPU | 스케줄링, 리소스 분배 | ms–s |

GPU는 **“느린 게 아니라 비결정적이라 직접 제어엔 부적합하지만”**, **QEC·AI 연산 등 ‘대규모 병렬 계산’에는 무적**이다.

그래서 Nvidia는 **FPGA와 RTH**를 붙여 그 약점을 보완한 것이다.

---

**✅****RTH란?**

**1️⃣ RTH (Real-Time Host)의 정체**

|  |  |
| --- | --- |
| **구분** | **내용** |
| **형태** | 하드웨어 + 펌웨어 하이브리드 모듈 (FPGA 또는 ASIC 형태) |
| **역할** | GPU와 QPU 사이에 존재하는 **실시간 통신 브리지**, NVQLink 패브릭의 “제어 코어” |
| **물리적 위치** | NVSwitch Fabric 보드 또는 DGX Quantum/NVQLink 서버 내 FPGA 슬롯 형태로 탑재 |
| **주요 기능** | ① DMA 엔진 (Zero-Copy 전송)  ② 타임스탬프 / 클럭 동기화 (PTP-like Precision Timing)  ③ Command Queue / Event Loop 버퍼링  ④ μs 단위 피드백 스케줄링 / 인터럽트 관리 |

- - 요약하면 → **GPU = 두뇌**, **RTH = 신경 중계소**, **QPU Control = 근육 신경**
  - GPU는 AI 연산을 병렬로 처리하고, RTH가 그 결과를 μs 결정성으로 전달·수행 하게 만든다.

> **DMA (Direct Memory Access)** =
>
> **“직접 메모리 접근”** 기술이다.
>
> 즉, **CPU를 거치지 않고** 장치가 메모리와 직접 데이터를 주고받게 해주는 방식이다.

**2️⃣ RTH 가 GPU 피드백을 가속하는 방식**

|  |  |  |
| --- | --- | --- |
| **단계** | **기존 GPU 루프 (느림)** | **NVQLink + RTH 루프 (개선)** |
| **1. QPU 측정** | 제어기 → CPU → GPU 로 전달 (드라이버 개입) | 제어기 → RTH DMA → GPU 직접 메모리로 바로 전송 |
| **2. GPU 연산** | OS 큐잉 → 스케줄링 → 커널 실행 | CUDA-Q RT 커널 직접 호출 (지연 1 µs 이내) |
| **3. 보정 명령 전달** | CPU 스택 복귀 → 제어기 송신 | RTH → Control HW 직접 신호 전송 (지연 0.5 µs 이내) |
| **총 왕복 지연** | 10–100 µs | 2–5 µs |

- - 즉, GPU는 느리것이 아니고, “GPU가 CPU 드라이버 경로를 거치느라 느린 것”인데, RTH가 이 경로를 하드웨어 DMA 루프로 우회시켜 지연을 줄이는 것이다.
  - RTH가 중간에 CPU 커널 개입을 완전히 제거하고 **FPGA급 결정성 루프를 하드웨어 수준에서 보장**하는 것이다.

    - 전통 구조: QPU → Control HW → **CPU (OS)** → GPU → CPU → QPU
    - NVQLink: QPU → Control HW → RTH ↔ GPU ↔ RTH → Control HW → QPU

**3️⃣ RTH 실체**

- - **RTH (Real-Time Host)** 는 단순 프로토콜이 아닌 하드웨어 컴포넌트다.
  - FPGA·ASIC 기반 DMA / 타임싱크 엔진으로 GPU와 QPU 사이를 직접 연결한다.
  - GPU가 결정성 제어를 못 하는 한계를 RTH가 보완하여 **μs 레벨 피드백 루프**를 가능하게 만든다.
  - 결과적으로 GPU는 “고속 AI 보정 연산 두뇌”, RTH는 “하드리얼타임 중계기”, FPGA 제어기는 “신경 말단” 역할을 담당한다.

---

**✅RTH는 연구 개발이 완료되었나?**

> 결론부터 말하면, **RTH(Real-Time Host)** 는 아직 **공개 상용화된 독립 제품은 아니다.**
>
> 다만 **엔비디아 내부에서** **DGX Quantum** **→ NVQLink로 진화하는 과정에서 이미** ***프로토타입 수준*****으로 존재하고**,
>
> 2025년 GTC DC에서 공식 발표된 NVQLink에는 **“하드웨어 포함형 구성요소”** 로 언급돼 있다.

**1️⃣ DGX Quantum → NVQLink 로의 연속선**

|  |  |  |  |
| --- | --- | --- | --- |
| **세대** | **시기** | **주요 특징** | **RTH 관련** |
| **DGX Quantum (2023)** | QM + NVIDIA 1세대 | μs 지연 컨트롤 루프, FPGA 중계 기술 탑재 | 초기형 RTH (“OPX Bridge”) |
| **NVQLink (2025)** | 17 + 5 협력사 통합 | GPU–QPU 통합 패브릭 표준화, RT API 공개 | 개선형 RTH 하드웨어 내장 (제조사별 커스터마이즈 가능) |
| **DGX Quantum 2 (예정 2026)** | DOE 랩 테스트 후 공급 | 다중 GPU ↔ 다중 QPU 루프 지원 | 완전한 RTH ASIC 버전 통합 예정 |

**2️⃣ 왜 “프로토콜 아닌 하드웨어”로 가나?**

- - GPU는 OS 스택 지연이 있어 μs 피드백에 직접 참여 불가.
  - NVQLink는 이를 보완하기 위해 **RT Host** 모듈을 FPGA/ASIC 형태로 탑재해

    - GPU 명령 큐 → 제어기 → QPU 로 가도록 만듦.
  - 그래서 RTH는 **실시간 패브릭의 하드웨어 노드** 이며, 나중에는 각 제조사(QM, Qblox, Keysight)가 **자체 RTH 호환 모듈**을 만들게 될 가능성이 크다.

---

**✅근데, 결정성이라는게 뭔데?******

**1️⃣ 결정성(determinism)이란**

- - **같은 입력과 조건에서 항상 동일한 시간·결과로 동작하는 것.**

    - 예: FPGA는 게이트 레벨에서 클럭이 완전히 고정되어 있어서 매 사이클마다 정확히 같은 시간에 신호가 나온다.

      - → **Deterministic (결정적)**
    - 반면 GPU나 CPU는 운영체제, 캐시, 스레드 스케줄링, 버스 점유 등에 따라 실행 시점이 매번 약간씩 달라진다.

      - → **Non-deterministic (비결정적)**

****

**2️⃣ GPU가 비결정적인 이유**

|  |  |
| --- | --- |
| **원인** | **설명** |
| **멀티스레드 스케줄링** | GPU는 수천 개의 스레드를 동시에 돌리며 내부에서 실행 순서를 동적으로 조정함.  어느 워프(warp)가 먼저 처리될지 예측 불가. |
| **캐시/메모리 지연** | L1·L2·VRAM 접근 시점이 상황마다 달라짐 → 메모리 충돌(cache miss) 시 지연 발생. |
| **OS 개입** | CUDA 커널 실행은 OS 커널을 통해 트리거되므로, 인터럽트나 시스템 부하에 따라 밀릴 수 있음. |
| **동시성 자원 공유** | 여러 커널이나 프로세스가 GPU를 공유하면 리소스 점유 타이밍이 달라짐. |

- - → 그래서 **연산 속도 자체는 빠르지만, “이 명령이 정확히 2.00 µs 후에 실행된다”를 보장할 수 없다.**

****

**3️⃣ 반면 FPGA는 결정적**

- - FPGA는 하드웨어 게이트가 클럭 동기화로 직접 연결되어 있어, 모든 신호가 동일한 클럭 사이클에 반복적으로 발생한다.

    - 예: “이 펄스는 20 ns마다 발생하고, 200 ns 후에 항상 측정 신호를 보낸다.”

      - → 완전히 예측 가능.
    - 따라서 QPU 제어·에러 보정 루프에는 **결정적 타이밍이 필수**라 FPGA가 쓰이는 것이다.

**4️⃣ 그래서 NVIDIA가 RTH를 만든 이유**

- - GPU는 비결정적이므로 직접 QPU 제어 루프를 맡기 어렵다.
  - 그 대신 **RTH(Real-Time Host)** 가 FPGA / ASIC급 하드웨어로 GPU와 QPU 사이에서
  - 타이밍을 “고정”시켜주는 중계 역할을 한다.

    - GPU → RTH : 병렬 연산 결과 전달
    - RTH → QPU Control HW : 정확히 μs 단위로 신호 스케줄
    - 결과: GPU의 비결정성(비예측성)을 **결정성 있는 하드웨어 계층으로 보정**

> DGX Quantum은 RTH 개념의 프로토타입이었고, 그 QM FPGA 브리지 구조가 확장·표준화되어 NVQLink의 핵심 모듈(RTH) 로 진화했다.
>
> 따라서 DGX 라인은 NVQLink 생태계의 “직계 전신(ancestor)”이다.

**5️⃣NVQLink 구조 (GPU 통합형 릴레이 방식)**

|  |  |
| --- | --- |
| **계층** | **역할** |
| **Control FPGA** | 펄스 / 측정 / 로우레벨 피드백 실행 (여전히 실시간 제어 담당) |
| **RTH (Real-Time Host)** | GPU–FPGA 사이의 **하드웨어 브리지**, DMA · 타이밍 동기화 담당 |
| **GPU (CUDA-Q Runtime)** | 오류 디코딩, AI 보정, 논리 큐비트 피드백 연산, 하이브리드 루프 계산 |
| **CPU Host** | 실험 전체 오케스트레이션, 리소스 관리 |
| **특징** | FPGA는 빠른 IO 담당, GPU는 고연산 피드백 / AI 보정 담당 |
| **지연** | 왕복 2 ~ 5 µs (하드웨어 DMA + GPU 디코딩 포함) |

**6️⃣ 동작 흐름 요약**

1. 1. **QPU가 측정 신호를 보냄**

      - → Control FPGA가 수 ns 단위로 수집
   2. **FPGA가 측정 결과를 RTH로 DMA 전송**

      - → CPU 개입 없음
   3. **RTH가 GPU 메모리로 직접 매핑**

      - → GPUDirect 메커니즘으로 µs 내 도착
   4. **GPU가 QEC 디코딩 또는 AI 보정 연산 수행**

      - → 수백~수천 큐비트 규모 QEC 가능
   5. **GPU 결과를 RTH → FPGA 로 돌려보냄**

      - → FPGA가 펄스 보정 명령을 즉시 QPU에 반영

**💡****NVQLink 간단 스펙**

- - **GB200 Grace-Blackwell Superchip** = RTH + GPU + ARM CPU를 한 칩에 통합

    - → NVQLink의 “Real-Time Host”는 더 이상 외장 FPGA 가 아니라 칩셋 레벨 통합 모듈입니다.
    - → 그래서 DMA 전송과 타이밍 싱크가 직접 온보드 에서 일어남.
  - **400 Gb/s / <4 µs** 성능 = NVQLink Fabric 이 FPGA-GPU 간 데이터 전송을 사실상 ‘메모리 내부 복사’ 수준으로 가깝게 만듦.
  - 이로써 QPU 제어기가 보낸 신드롬(syndrome) 데이터를 GPU 가 즉시 받아 디코딩하거나, AI 기반 오류 보정을 실시간으로 수행 가능

> 블로그 초기에 FPGA를 다루면서, 일정 성능 이상의 QPU라면 성능을 고려해서 HBM이 탑재된 FPGA가 필요할 것이라고 밝힌 바 있는데, 괴물이 등장했다.
>
> FPGA+GPU+CPU+HBM
