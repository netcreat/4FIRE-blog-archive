**✅ 1. 네트워크 스위치는 무엇을 관찰할 수 있을까?**

**📌 VEN은 네트워크의 눈과 귀 역할을 한다**

- - Elisity에 등록된 VEN은 기존 스위치의 네이티브 기능을 이용해 단말 정보를 발견하고 네트워크 통신을 관찰한다.
  - 여기서 수집하는 정보는 크게 **Endpoint Discovery**와 **Flow Telemetry**로 구분할 수 있다.
  - Endpoint Discovery는 어떤 장비가 네트워크에 연결되어 있는지 식별하는 기능이다.
  - Flow Telemetry는 발견된 장비가 누구와 어떤 통신을 하고 있는지 분석하기 위한 정보다.
  - 두 기능은 서로 관련되어 있지만 반드시 동일한 방법으로 수집되는 것은 아니다.

|  |  |  |
| --- | --- | --- |
| **데이터 구분** | **주요 정보** | **분석 목적** |
| 장치 식별 | MAC 주소, IP 주소 | 어떤 장비인가? |
| 장치 위치 | 스위치, 포트, VLAN, 사이트 | 어디에 연결되어 있는가? |
| 장치 특성 | 제조사 OUI, CDP/LLDP, DHCP 정보 | 어떤 종류의 장비인가? |
| 통신 상대 | Source/Destination IP | 누구와 통신하는가? |
| 통신 프로토콜 | TCP, UDP, ICMP 등 | 어떤 방식으로 통신하는가? |
| 서비스 포트 | Source/Destination Port | 어떤 서비스를 사용하는가? |
| 트래픽 통계 | Bytes, Packets, 통신 방향 | 얼마나 많은 데이터를 교환하는가? |
| 통신 시점 | 최초·마지막 관찰 시각 | 언제 통신했는가? |
| 정책 결과 | Allow, Deny, 정책 상태 | 어떤 정책이 적용되었는가? |

- - 이 가운데 MAC 주소나 VLAN 등은 Endpoint Discovery와 장비 식별 과정에서 확보된다.
  - 반면 출발지·목적지 IP, 포트, 프로토콜, Bytes, Packets 등은 Flow Telemetry의 대표적인 정보다.
  - Elisity의 공식 Traffic Analytics는 이러한 정보를 장비(Device), Policy Group, Distribution Zone 단위로 정리하여 보여준다.
  - 다만 스위치 모델과 제조사에 따라 제공되는 데이터 필드와 수집 범위가 다를 수 있다.

**📌 모든 네트워크 인터페이스에서 무조건 데이터를 수집하는 것은 아니다**

- - Elisity는 VEN에 등록된 스위치의 인터페이스 역할을 평가해 Endpoint Discovery와 Flow Telemetry를 활성화하거나 비활성화할 수 있다.
  - 일반적으로 사용자 단말이 연결된 UNI(User Network Interface)는 정보 수집 대상이 된다.
  - 반면 업링크, 관리 인터페이스, 다른 네트워크 장비와 연결된 NNI(Network-to-Network Interface) 등은 중복 수집을 방지하기 위해 자동 제외될 수 있다.
  - 관리자가 필요한 인터페이스에 대해 수동으로 설정을 변경하는 것도 가능하다.
  - 따라서 Elisity가 스위치에 연결되었다는 사실만으로 해당 네트워크의 모든 트래픽을 빠짐없이 관찰할 수 있다고 가정해서는 안 된다.

**✅ 2. NetFlow/IPFIX로 무엇을 알 수 있을까?**

**📌 패킷의 내용이 아니라 통신의 특징을 수집한다**

- - 네트워크 텔레메트리에서 가장 중요한 기술 중 하나가 NetFlow/IPFIX다.
  - NetFlow는 Cisco에서 발전시킨 Flow 정보 수집 기술이고, IPFIX는 관련 정보를 표준화된 형식으로 내보내기 위한 프로토콜이다.
  - 예를 들어 직원 PC가 내부 서버에 HTTPS로 접속했다면 Flow 정보는 다음과 같이 표현될 수 있다.

|  |  |
| --- | --- |
| **항목** | **예시 데이터** |
| Source IP | 10.10.10.25 |
| Destination IP | 10.20.30.50 |
| Source Port | 52341 |
| Destination Port | 443 |
| Protocol | TCP |
| Sent Bytes | 15.2 MB |
| Received Bytes | 128.6 MB |
| First Observed | 09:10:25 |
| Last Observed | 09:14:32 |
| Service | HTTPS |
| Policy Action | Allow |

- - 위 데이터는 이해를 돕기 위한 가상의 Flow 기록이다.
  - 이 정보만으로도 어느 장비가 어느 서버에 접속했고, 어떤 서비스를 사용했으며, 어느 방향으로 얼마나 많은 데이터를 교환했는지 파악할 수 있다.
  - 그러나 실제 HTTPS 통신 안에서 어떤 문서를 열었고 어떤 명령이 실행되었는지까지 알 수 있는 것은 아니다.
  - **NetFlow/IPFIX는 기본적으로 패킷의 Payload 전체를 분석하는 DPI(Deep Packet Inspection) 기술이 아니기 때문**이다.

**📌 NetFlow, DPI, EDR은 관찰하는 영역이 다르다**

|  |  |  |  |
| --- | --- | --- | --- |
| **비교 항목** | **NetFlow / IPFIX** | **DPI / IDS·IPS** | **EDR** |
| 분석 위치 | 네트워크 장비 | 네트워크 검사 지점 | PC·서버 내부 |
| IP·포트 정보 | 가능 | 가능 | 관련 연결 정보 확인 가능 |
| 트래픽량·통신 관계 | 핵심 기능 | 가능 | 엔드포인트 관점에서 가능 |
| 패킷 Payload 분석 | 일반적으로 불가 | 핵심 기능 | 네트워크 패킷 검사와는 다른 방식 |
| 악성코드 시그니처 탐지 | 기본 기능 아님 | 지원 가능 | 지원 |
| 프로세스 이름 확인 | 일반적으로 불가 | 제한적 | 가능 |
| 파일·프로세스 행위 분석 | 불가 | 제한적 | 핵심 기능 |
| 암호화된 통신의 실제 내용 | 알 수 없음 | 별도 복호화 등 필요 | 호스트 내부 가시성에 따라 분석 가능 |

- - 예를 들어 TCP 445 포트로 여러 서버에 접근하는 Flow를 관찰했다면 SMB 통신이 발생하고 있다는 사실은 알 수 있다.
  - 하지만 그 안에서 정상적인 파일 복사가 이루어지는지, 악성코드가 랜섬웨어를 전파하고 있는지는 Flow 정보만으로 확정하기 어렵다.
  - 이러한 구분을 이해해야 Elisity의 실제 분석 능력을 정확하게 평가할 수 있다.

**📌 추가적인 애플리케이션 식별도 가능하다**

- - 지원되는 Cisco Catalyst 9000 환경에서는 AVC(Application Visibility and Control)와 NBAR(Network-Based Application Recognition)을 연동해 추가적인 애플리케이션 정보를 Flow에 포함할 수 있다.
  - 예를 들어 일반적인 IP·Port 기반 정보보다 구체적인 애플리케이션 또는 서비스 분류를 제공할 수 있다.
  - 하지만 이 기능을 이용한다고 해서 모든 암호화된 세션의 내용을 분석할 수 있는 것은 아니다.
  - 또한 Elisity 공식 문서는 AVC용 설정이 일부 Catalyst 3000 시리즈와 호환되지 않는다고 설명한다.
  - 따라서 애플리케이션 분석 능력 역시 스위치 모델에 따라 달라진다.

**✅ 3. 수집된 데이터는 어디서 분석되는가?**

**📌 VE와 CCC는 서로 다른 역할을 한다**

- - VEN이 수집한 Endpoint Discovery 및 Flow 정보를 VE로 전달하면, VE는 이를 처리하고 CCC와 교환한다.
  - CCC는 IdentityGraph, Traffic Analytics, Policy Engine, Elisity Intelligence 등을 통해 장비와 통신 관계를 관리한다.
  - 단순화하면 아래와 같은 구조다.

|  |  |  |
| --- | --- | --- |
| **단계** | **구성요소** | **주요 처리 내용** |
| ① 데이터 발견 | VEN | 장비 연결정보 및 Flow 수집 |
| ② 수집·전달 | VE | 텔레메트리 처리, 중앙 관리 시스템과 교환 |
| ③ 장비 식별 | IdentityGraph | 다양한 출처의 정보를 결합해 장비의 신원 파악 |
| ④ 통신 분석 | Traffic Analytics | 장비·그룹별 통신 관계 및 통계 분석 |
| ⑤ AI 분석 | Elisity Intelligence | 미분류 장비 분류, 정책 그룹 및 Allow/Deny 추천 |
| ⑥ 정책 관리 | CCC Policy Engine | 관리자 정책 설정 및 집행 조율 |

- - 여기서 중요한 것은 VE가 모든 AI 분석을 수행하는 서버는 아니라는 사실이다.
  - 공식 문서에서 설명하는 Elisity Intelligence는 CCC에 통합된 AI 기능이다.
  - 따라서 로컬 VE를 배포해도 AI 기반 장비 분류와 정책 추천의 중심은 클라우드 CCC에 있다.
  - 앞선 2편에서 로컬 VE와 클라우드 VE의 차이를 분석했던 이유도 여기에 있다.

**✅ 4. IdentityGraph는 장비의 정체를 어떻게 파악할까?**

**📌 MAC 주소만으로 장비를 정확하게 구분할 수 있을까?**

- - 병원 네트워크에 IP 주소가 10.20.30.50인 새로운 장비가 발견되었다고 가정해 보자.
  - 스위치는 해당 장비의 MAC 주소, IP 주소, 연결 포트, VLAN 등을 확인할 수 있다.
  - MAC 주소의 OUI를 조회하면 제조사에 관한 단서를 얻을 수도 있다.
  - 하지만 이것만으로 해당 장비가 CT Scanner인지, MRI인지, 환자 모니터인지 정확히 구분하기는 어렵다.
  - 동일한 제조사의 여러 장비가 같은 네트워크 인터페이스 제조사의 칩을 사용할 수 있고, MAC 주소가 변경되거나 위조될 가능성도 있기 때문이다.
  - 따라서 Elisity는 네트워크에서 수집한 정보를 외부 자산관리·보안 시스템과 결합한다.

**📌 IdentityGraph의 정보 통합 구조**

|  |  |  |
| --- | --- | --- |
| **정보 출처** | **제공할 수 있는 정보** | **분석에 활용하는 목적** |
| Elisity Native | MAC, VLAN, VEN 위치, 장비 특성 | 네트워크 기반 기본 식별 |
| Microsoft Active Directory | 사용자, 컴퓨터, 로그인 정보 | 사용자·장비 관계 확인 |
| ServiceNow CMDB | 자산 종류, 모델, 소유·관리 정보 | 공식 등록 자산 여부 확인 |
| CrowdStrike | 엔드포인트 및 보안 상태 | 관리형 장비 여부와 위험 정보 확인 |
| Armis | IoT/OT/IoMT 장비 특성 및 위험 정보 | 비관리형 장비 식별 보강 |
| Claroty | 산업·의료장비 식별 및 보안 정보 | OT/IoMT 식별 보강 |
| Tenable | 취약점 및 자산 보안 정보 | 위험 속성 보강 |
| DHCP / DNS 등 | IP 할당 및 호스트명 | 장비 식별정보 보강 |

- - 공식 자료에 따르면 IdentityGraph는 네이티브 텔레메트리와 25개 이상의 외부 정보 출처를 통합하는 AI 분석 기반을 제공한다.
  - 중요한 것은 단순히 정보를 많이 수집하는 것이 아니라 **같은 장비에 대한 서로 다른 출처의 정보를 하나의 신원 정보로 결합한다는 점**이다.

**📌 실제 장비 식별 사례**

- - 가상의 CT Scanner가 네트워크에 연결되었다고 가정하자.
  - 각 정보 출처에서 다음과 같은 결과를 얻을 수 있다.

|  |  |
| --- | --- |
| **정보 출처** | **발견된 정보** |
| 스위치 텔레메트리 | MAC, IP, VLAN 120 |
| MAC OUI | 의료장비 관련 제조사 |
| Flow Analytics | PACS 서버, DNS, NTP와 통신 |
| ServiceNow CMDB | CT Scanner |
| Armis | Medical Imaging Device |
| Active Directory | 해당 장비 정보 없음 |
| CrowdStrike | 등록 정보 없음 |

- - IdentityGraph는 이러한 정보를 결합해 장비 유형과 정책 적용에 사용할 속성을 정리한다.
  - 이 경우 CMDB와 IoT 보안 시스템이 일치하는 정보를 제공한다면 장비를 Medical Device로 분류할 근거가 강해진다.
  - 다만 위 정보만으로 CT Scanner라는 세부 모델명까지 항상 자동으로 확정된다는 뜻은 아니다.
  - 특히 Active Directory나 CrowdStrike에 등록되어 있지 않다는 사실만으로 악성 장비라고 판정해서는 안 된다.
  - 의료장비, 프린터, IP 카메라처럼 애초에 도메인이나 EDR에 등록되지 않는 장비도 많기 때문이다.

**✅ 5. IdentityGraph의 Consistency Score는 무엇인가?**

**📌 서로 다른 정보 출처가 얼마나 일치하는지 평가한다**

- - IdentityGraph의 흥미로운 기능 중 하나가 Consistency Score다.
  - 이 점수는 장비 유형에 대한 여러 정보 출처의 분류가 얼마나 일치하는지를 나타낸다.
  - 예를 들어 ServiceNow, Armis, Claroty가 모두 해당 장비를 Medical Device로 분류한다면 서로 상충하는 분류를 제공하는 경우보다 일관성이 높다.

|  |  |  |  |
| --- | --- | --- | --- |
| **ServiceNow** | **Armis** | **Claroty** | **해석** |
| Medical Device | Medical Device | Medical Device | 장비 범주에 대한 높은 일치도 |
| Medical Device | Medical Device | Unknown | 일부 출처에서만 확인 |
| Medical Device | Workstation | Medical Device | 출처 사이에 분류 충돌 존재 |
| Unknown | Unknown | Unknown | 장비 분류 근거 부족 |

- - Consistency Score는 단순한 악성 장비 위험 점수가 아니다.
  - 여러 출처의 장비 분류가 얼마나 일치하는지를 보여주는 지표다.
  - 또한 여러 시스템이 동일한 잘못된 정보를 제공할 가능성도 있으므로 점수가 높다고 해서 장비의 신원이 절대적으로 보장되는 것은 아니다.

**📌 정보가 충돌하면 어떤 것을 신뢰할까?**

- - Elisity는 **Core Effective Attributes**라는 통합된 장비 속성을 관리한다.
  - 외부 시스템의 정보가 서로 다를 경우 고객이 설정한 정보 출처의 우선순위에 따라 사용할 속성을 결정할 수 있다.
  - 예를 들어 공식 자산 종류는 ServiceNow를, 장비의 운영체제 정보는 전문 IoT 플랫폼을 우선하도록 구성하는 식이다.
  - 이처럼 정보 출처별 신뢰 우선순위를 관리하는 것이 중요하다.
  - 특히 병원이나 산업 현장에서는 장비의 신원을 잘못 판단하면 정상적인 업무 통신이 차단될 위험이 있기 때문이다.

**✅ 6. Elisity Native Identity — 외부 보안 시스템 없이도 무엇을 알 수 있을까?**

**📌 Elisity 자체 식별 엔진의 역할**

- - 모든 기업이 CMDB나 EDR, IoT 보안 제품을 완벽하게 구축하고 있는 것은 아니다.
  - 따라서 Elisity는 외부 보안 솔루션에 의존하지 않고 네트워크에서 직접 추출할 수 있는 장비 식별 기능도 제공한다.
  - 대표적으로 제조사 정보, 장비 유형, 네트워크 위치, 통신 패턴 등을 이용한다.

|  |  |
| --- | --- |
| **Native Attribute** | **정보 출처 및 역할** |
| Vendor | MAC OUI 기반 제조사 식별 |
| Device Type | MAC, CDP/LLDP 등으로 장비 유형 추정 |
| Device Genre | IT, OT, IoT, IoMT 등의 범주로 분류 |
| Hostname / FQDN | DHCP, Reverse DNS 및 기타 정보 기반 |
| VLAN | 장비가 연결된 논리적 네트워크 |
| VEN Association | 장비가 발견된 스위치 및 집행 지점 |
| Subnet | 장비의 IP 네트워크 대역 |
| Randomized MAC | 무작위 MAC 주소 사용 여부 |
| EDR Detected | 알려진 EDR 서비스와의 통신 관찰 |

**📌 EDR Detected는 특히 주목할 기능이다**

- - Elisity는 장비가 CrowdStrike나 Microsoft Defender 등 알려진 EDR 서비스와 통신하는지를 관찰해 EDR Detected 속성을 부여할 수 있다.
  - 이 기능은 해당 EDR 제품이 CCC에 직접 연동되어 있지 않더라도 일부 동작할 수 있다.
  - 공식 문서는 EDR 통신 확인을 주기적으로 수행한다고 설명한다.
  - 다만 EDR 서버와 통신했다는 사실만으로 EDR 에이전트가 정상적으로 설치되었거나 실제 위협으로부터 보호되고 있다고 보장할 수는 없다.
  - 즉, **EDR Detected는 EDR의 정상 작동을 증명하는 보안 인증이 아니라, 네트워크에서 관찰한 간접적인 단서**다.
  - 실제 감염 상태와 위협 탐지 결과는 EDR 시스템과 직접 연동해 확인하는 편이 더 정확하다.

**✅ 7. Traffic Analytics는 어떤 분석을 수행할까?**

**📌 장비와 장비 사이의 통신 관계를 시각화한다**

- - CCC의 Traffic Analytics는 수집된 Flow를 단순한 로그 목록으로만 보여주지 않는다.
  - 장비와 장비, Policy Group과 Policy Group, Distribution Zone 사이의 통신 관계를 시각화할 수 있다.
  - 공식 문서에는 Traffic Vectors와 Traffic Records라는 두 가지 주요 조회 방식이 설명되어 있다.

|  |  |
| --- | --- |
| **분석 기능** | **주요 역할** |
| Traffic Vectors | 통신 상대와 방향을 Sankey 형태로 시각화 |
| Traffic Records | 개별 통신 관계와 정책 정보를 표로 확인 |
| Policy Group View | 그룹 사이의 통신 관계 분석 |
| Device View | 특정 장비가 통신한 상대 분석 |
| Distribution Zone View | 네트워크 구역 간 통신 관계 파악 |
| Top Talkers | 트래픽량이 많은 통신 관계 식별 |
| Usage Hours | 장비의 시간대별 통신 활동 확인 |
| Policy Action Filter | 허용·차단된 통신 필터링 |
| Policy Status Filter | Active, Simulation, No Policy 상태 분석 |

**📌 가상의 병원 네트워크를 분석해 보자**

- - 한 CT Scanner가 평소 PACS 서버에 의료 영상을 전송한다고 가정하자.
  - 해당 장비의 Traffic Analytics에서 다음과 같은 통신 관계를 확인했다고 해보자.

|  |  |  |  |
| --- | --- | --- | --- |
| **목적지** | **포트** | **관찰된 통신** | **추가 검토** |
| PACS Server | TCP 104 | 의료 영상 전송 | 정상 업무 경로 후보 |
| DNS Server | UDP 53 | 이름 확인 | 필수 서비스 여부 확인 |
| NTP Server | UDP 123 | 시간 동기화 | 필수 서비스 여부 확인 |
| 외부 미확인 IP | TCP 443 | HTTPS 통신 | 목적지 및 용도 확인 |
| Domain Controller | TCP 445 | SMB 통신 | 업무상 필요 여부 확인 |
| 직원 PC | TCP 3389 | RDP 연결 시도 | 승인된 유지보수인지 확인 |

- - 여기서 TCP 104, UDP 53, UDP 123처럼 예상할 수 있는 업무 통신 외에 새로운 통신 경로가 관찰되었다고 가정해 보자.
  - 보안 관리자는 그 통신이 필요한 것인지 확인할 수 있다.
  - 예를 들어 제조사 유지보수를 위해 RDP 접속이 필요한 의료장비도 있을 수 있으므로, 처음 발견한 통신이라고 무조건 차단하는 것은 위험하다.
  - 반대로 승인되지 않은 SMB 또는 RDP 통신이라면 해당 경로를 차단하는 보안 정책의 근거가 될 수 있다.
  - 이처럼 Elisity는 **통신 관계의 가시성을 보안 정책 수립에 활용하는 구조**다.

**📌 Usage Hours로 무엇을 알 수 있을까?**

- - Elisity의 Usage Hours는 장비의 시간대별 통신 활동과 Policy Group 소속 변화를 확인할 수 있는 기능이다.
  - 예를 들어 평소 업무 시간에만 사용되는 장비가 새벽 시간에 활동했다면 추가 조사가 필요한 상황일 수 있다.
  - 다만 야간 백업, 자동 업데이트, 정기 점검 역시 새벽에 발생할 수 있다.
  - 따라서 시간대별 활동의 변화는 분석 단서이지 그 자체가 침입 판정은 아니다.

**✅ 8. 그렇다면 Elisity는 어떤 침입을 감별할 수 있을까?**

**📌 이상징후 관찰과 공격 탐지는 구분해야 한다**

- - 여기서 가장 중요한 기술적 구분이 필요하다.
  - 네트워크 Flow에는 공격을 의심할 만한 흔적이 남을 수 있다.
  - 그러나 그런 흔적을 볼 수 있다는 것과 해당 공격을 자동으로 식별해 악성이라고 판정한다는 것은 전혀 다른 문제다.
  - Elisity의 공식 자료에서 확인되는 핵심 분석 기능은 장비 식별, 통신 관계 가시성, 정책 위반 확인, AI 장비 분류 및 정책 추천이다.
  - 따라서 모든 네트워크 공격 유형을 자동 탐지하는 NDR 엔진과 동일한 기능을 제공한다고 가정해서는 안 된다.

|  |  |  |
| --- | --- | --- |
| **공격 유형** | **Flow·IdentityGraph로 관찰 가능한 정보** | **직접 판정의 한계** |
| 미인가 장비 연결 | 새로운 MAC/IP, 미등록 장비, 위치 정보 | 미등록이 곧 악성이라는 뜻은 아님 |
| Port Scan | 여러 목적지 포트로의 반복 접근 기록 | 전용 스캔 탐지 엔진과 동일하지 않음 |
| Lateral Movement | 기존에 없던 내부 서버 접속 관계 | 정상적인 관리 통신과 구분 필요 |
| 랜섬웨어 확산 | 다수 서버·SMB 경로로의 접근 | 랜섬웨어 종류나 감염 자체는 별도 분석 필요 |
| Command & Control | 미확인 외부 IP와의 통신, 트래픽량 | 정밀한 주기 분석과 악성 판정은 전문 도구 필요 |
| Data Exfiltration | 외부 목적지로의 높은 송신량 | 데이터 내용과 유출 의도는 알 수 없음 |
| 계정 탈취 | 평소와 다른 자원에 대한 접근 정보 | 인증 로그·IAM·EDR 등의 정보 필요 |
| 악성 파일 다운로드 | 외부 서버와의 통신 기록 | 파일 자체의 악성 여부 판단 불가 |
| 취약점 악용 | 특정 서비스에 대한 네트워크 접속 | 실제 Exploit 성공 여부는 확인 불가 |

- - 예를 들어 C2 통신의 대표적인 특징 중 하나는 외부 서버와 반복적으로 통신하는 Beaconing 패턴이다.
  - 그러나 정밀한 Beaconing 탐지에는 통신 발생 간격, 패킷 특성, 목적지 평판 등을 분석할 수 있어야 한다.
  - 단순히 외부 IP와 TCP 443 통신이 발생했다는 사실만으로 C2라고 판단할 수는 없다.
  - Elisity의 Traffic Analytics에서 관련 통신을 조사할 수는 있지만, 이를 자체적으로 완전한 C2 탐지 엔진으로 제공한다고 확인된 것은 아니다.

**📌 Elisity의 역할은 탐지보다 정책 판단에 가깝다**

- - 따라서 Elisity가 잘할 수 있는 일과 전문 보안 제품이 수행해야 할 일을 나눠 생각할 필요가 있다.
  - 감염 여부가 확정되지 않았어도 어떤 장비가 원래 접근하면 안 되는 서버에 통신하려는지 파악할 수 있다.
  - 또한 EDR이나 OT 보안 제품이 해당 장비의 위험 상태를 전달하면 그 정보를 정책 그룹 분류에 활용할 수 있다.
  - 다만 알려지지 않은 랜섬웨어의 파일 암호화 행위나 프로세스 내부 동작 자체를 NetFlow만으로 분석하지는 못한다.
  - 따라서 Elisity와 EDR/NDR은 경쟁 관계라기보다 서로 다른 보안 계층을 담당하는 관계로 이해하는 것이 적절하다.

**✅ 9. Elisity Intelligence — AI는 실제로 무엇을 하는가?**

**📌 AI가 보안 정책을 스스로 결정하고 차단할까?**

- - Elisity는 AI 기능을 Elisity Intelligence라는 이름으로 제공한다.
  - 공식 기술자료에 따르면 핵심 기능은 크게 세 가지로 구성된다.

    - **AI Device Classification, AI-Powered Insights, Elisity Assistant**다.
  - 여기서 가장 중요한 사실은 AI가 모든 보안 정책을 관리자 승인 없이 자동으로 적용하는 구조가 아니라는 점이다.

|  |  |  |
| --- | --- | --- |
| **AI 기능** | **주요 역할** | **실제 결과** |
| AI Device Classification | 미분류 장비의 유형 추론 | 장비 분류 추천 |
| AI-Powered Insights | Policy Group·Allow/Deny 정책 분석 | 정책 및 개선 사항 추천 |
| Elisity Assistant | 자연어 기반 네트워크 정보 조회 | 분석 결과·설명·관리 정보 제공 |

**📌 ① AI Device Classification — 알 수 없는 장비의 정체를 추론한다**

- - IdentityGraph에 Unknown 또는 Unclassified 장비가 나타났다고 가정해 보자.
  - AI는 MAC 주소와 유사 장비의 특징, 관찰된 네트워크 통신, 외부 IP 소유 정보 등을 참고할 수 있다.
  - AD, CMDB, EDR 등의 정보가 추가로 들어올 시간을 허용한 뒤 여러 단서를 결합해 장비 유형을 추천하는 방식이다.
  - 예를 들어 미분류 장비를 Printer, Medical Device, Workstation 등의 범주로 제안할 수 있다.
  - 관리자는 추천 결과와 근거를 확인하고 승인하거나 거절할 수 있다.
  - 승인된 장비 분류는 IdentityGraph에 반영되며, 이미 설정된 Policy Group 조건에 따라 해당 장비가 재분류될 수 있다.

**📌 ② AI-Powered Insights — 정책을 추천한다**

- - 이 기능은 수집된 장비와 통신 관계 정보를 바탕으로 정책 운영을 개선하는 데 초점을 둔다.
  - 공식 문서에는 Dynamic Policy Group 추천, Static Policy Group 추천, Allow/Deny 정책 추천, Traffic Review 기능이 설명되어 있다.

|  |  |
| --- | --- |
| **AI 추천 기능** | **실제 활용 예시** |
| Dynamic Policy Group | 미분류 의료장비를 위한 새로운 동적 그룹 추천 |
| Static Policy Group | DHCP/DNS, Guest Wi-Fi 등의 알려진 서브넷 그룹 추천 |
| Policy Suggestions | 장비 그룹 간 Allow/Deny 정책 추천 |
| Traffic Review | 시뮬레이션 중인 정책의 실제 통신 영향 검토 |
| Enforcement Score | 정책 집행 수준에 대한 지표와 예상 개선 효과 제시 |

- - 여기서 정책 추천은 실제 차단 정책과 구분해야 한다.
  - Elisity의 공식 자료는 AI가 제안한 정책을 기본적으로 Simulation Mode로 생성한다고 설명한다.
  - 관리자는 실제 통신에 미칠 영향을 검토한 뒤 Active 상태로 전환할 수 있다.
  - 즉, AI가 정책 생성을 돕지만 실제 보안 정책 활성화에는 관리자의 판단이 개입한다.

**📌 ③ Elisity Assistant — 보안 관리자를 위한 AI 분석 도우미**

- - Elisity는 CCC 26.2에서 자연어 기반 Elisity Assistant를 소개했다.
  - 네트워크 관리자라면 다음과 같은 질문을 할 수 있다.

|  |  |
| --- | --- |
| **질문 예시** | **기대하는 분석** |
| 현재 몇 개의 장비가 네트워크에 연결되어 있는가? | 장비 수량 및 상태 요약 |
| 미분류 장비는 몇 대인가? | IdentityGraph 정보 조회 |
| 최근 새로운 네트워크 활동이 있었는가? | 관찰된 이벤트와 통신 요약 |
| 어떤 정책 위반이 발생했는가? | 정책 및 관련 이벤트 조회 |
| 특정 장비가 어떤 서버와 통신했는가? | Traffic Analytics 기반 정보 조회 |
| 어떤 정책을 추가해야 하는가? | 정책 설정 안내 및 추천 정보 제공 |

- - 자연어 질의가 가능하다는 것은 운영 편의성 측면에서 의미가 있다.
  - 하지만 AI Assistant가 정책 위반을 설명할 수 있다는 사실과 새로운 악성코드를 독립적으로 발견한다는 주장은 구분해야 한다.
  - 공식 자료에서 강조하는 AI의 역할은 **정보 검색·장비 분류·정책 추천과 운영 지원**이다.

**✅ 10. Elisity의 AI가 사용하는 기술과 데이터 보안**

**📌 모든 AI 기능이 하나의 LLM으로 동작하는 것은 아니다**

- - Elisity의 AI 기능은 머신러닝 기반 장비 분류, 정책 추천 엔진, 자연어 기반 Assistant로 나뉜다.
  - 장비 식별에서는 네트워크 텔레메트리와 장비의 특성을 분석하는 기술이 중요하다.
  - 반면 자연어로 질문하고 답변하는 Assistant에서는 LLM이 활용된다.
  - 따라서 제품에 LLM이 도입되었다는 사실만으로 모든 장비 식별과 정책 결정이 생성형 AI에 의해 수행된다고 이해하면 안 된다.

**📌 고객 네트워크 정보는 어떻게 보호할까?**

- - Elisity의 AI 기술자료에는 고객별 Single-Tenant CCC 아키텍처와 AWS Bedrock 기반 Private LLM 활용 방식이 설명되어 있다.
  - 또한 고객 데이터를 AI 모델의 학습이나 파인튜닝에 사용하지 않는다고 명시하고 있다.

|  |  |
| --- | --- |
| **보안 항목** | **공식 자료에서 설명하는 방식** |
| CCC 격리 | 고객별 Single-Tenant 인스턴스 |
| LLM 인프라 | AWS Bedrock 기반 Private LLM |
| 고객 데이터 학습 | 고객 데이터로 모델 학습·파인튜닝하지 않는다고 명시 |
| 접근 권한 | CCC의 RBAC 정책 적용 |
| AI 정책 변경 | 관리자 승인 필요 |
| 감사 기록 | 장비 분류 변경, 정책 및 관리 작업 등의 기록 |
| 전송 보안 | 제어 경로에 TLS 적용 |

- - 이는 제조사가 설명하는 제품의 보안 설계 및 데이터 처리 정책이다.
  - 실제 고객 데이터의 저장 위치, 로그 보존 기간, 데이터 레지던시, 계약상 처리 조건 등은 별도의 보안 심사에서 확인할 필요가 있다.
  - 특히 의료기관과 공공기관에서는 네트워크 메타데이터 자체도 민감한 인프라 정보일 수 있으므로, Payload를 전송하지 않는다는 사실만으로 모든 데이터 보안 문제가 해결되는 것은 아니다.

**✅ 11. 실제 도입 환경에서 무엇을 검증해야 할까?**

**📌 기능 목록보다 실제 데이터의 품질이 중요하다**

- - 지금까지의 내용을 보면 Elisity는 상당히 다양한 장비 식별 및 네트워크 가시성 기능을 제공한다.
  - 하지만 좋은 분석 시스템을 구축하기 위해서는 수집되는 데이터가 충분하고 정확해야 한다.
  - 특히 기존 스위치의 지원 범위와 텔레메트리 수집 방식에 따라 분석의 결과가 달라질 수 있다.

|  |  |
| --- | --- |
| **검증 항목** | **실제 확인해야 할 내용** |
| 장비 발견률 | 전체 단말 중 몇 %를 식별할 수 있는가? |
| 장비 분류 정확도 | PC, 서버, IoT, 의료장비를 얼마나 정확히 구분하는가? |
| 정보 출처 충돌 | CMDB와 IoT 보안 제품의 정보가 다를 때 어떻게 처리하는가? |
| Flow Coverage | 모든 필요한 통신 경로가 수집되는가? |
| Telemetry 처리량 | VEN당 Flow 발생량과 VE·CCC 처리 능력 |
| 실시간성 | 신규 장비 및 통신 관계가 CCC에 반영되기까지 걸리는 시간 |
| 분석 정밀도 | 포트·프로토콜·서비스 정보를 얼마나 세밀하게 구분하는가? |
| AI 추천 정확도 | 추천된 장비 분류와 정책의 오탐·누락 비율 |
| 외부 EDR 연동 | 위험 상태 변경이 IdentityGraph에 반영되는 시간 |
| 데이터 보안 | 전송·저장·보존·접근 통제 방식 |

**📌 특히 AI 장비 분류의 정확도가 중요하다**

- - 네트워크에 연결된 장비를 잘못 분류하면 부적절한 정책이 적용될 수 있다.
  - 예를 들어 CT Scanner를 일반 직원 PC로 분류하면 의료 영상 전송에 필요한 통신이 차단될 수 있다.
  - 반대로 미확인 장비를 신뢰할 수 있는 서버로 잘못 분류하면 필요 이상의 접근 권한을 부여할 위험이 있다.
  - 따라서 AI의 장비 분류 정확도는 단순한 편의성 문제가 아니라 실제 네트워크의 가용성과 보안에 직접적인 영향을 줄 수 있다.
  - **특히 의료·OT 환경에서는 AI가 얼마나 똑똑한가보다, 잘못된 판단을 얼마나 안전하게 검증하고 수정할 수 있는지가 더 중요할 수 있다.**

---

**✅ 결론 — Elisity의 AI는 공격보다 네트워크의 정체성과 통신 관계를 이해하는 데 집중한다**

- - Elisity는 기존 스위치가 수집하는 텔레메트리를 이용해 어떤 장비가 네트워크에 연결되어 있고, 누구와 어떤 서비스를 이용해 통신하는지 파악한다.
  - IdentityGraph는 이러한 정보에 AD, CMDB, EDR, IoT/OT 보안 제품의 정보를 결합해 장비의 신원과 보안 상태를 더욱 풍부하게 만든다.
  - Elisity Intelligence는 미분류 장비의 유형을 추천하고, 통신 관계를 바탕으로 보안 정책의 개선 방향을 제안한다.
  - 그러나 이 과정이 모든 종류의 공격을 직접 탐지하거나 악성코드를 판별한다는 의미는 아니다.
  - 패킷 내부의 악성 행위나 호스트의 프로세스 활동을 분석하는 데에는 여전히 IDS/IPS, NDR, EDR 등의 전문 기술이 필요하다.
  - Elisity가 제공하는 실질적인 가치는 **이러한 네트워크·신원·보안 정보를 통합해 각 장비가 어떤 자원에 접근할 수 있는지 결정할 수 있도록 만드는 데 있다.**
  - 결국 핵심은 장비에 대해 얼마나 많은 정보를 수집하는가가 아니라, 그 정보가 얼마나 정확하고 실제 접근 통제에 얼마나 유용한가다.
  - 그렇다면 이러한 장비 식별과 통신 분석 결과는 실제로 어떻게 보안 정책으로 바뀔까?
  - 공격자가 정상 계정을 탈취했거나 PC가 랜섬웨어에 감염되었다면, 기존에 허용되었던 통신 권한을 어느 수준까지 제한할 수 있을까?
  - 또한 이러한 정책 변경은 얼마나 빠르게 이루어질까?

> ***다음 4편에서는 「랜섬웨어에 감염되어도 확산하지 못한다 — Elisity의 동적 마이크로세그멘테이션」을 통해 실제 Allow/Deny 정책, Dynamic Policy Group, EDR 연동, 자동 격리와 그 한계까지 살펴보기로 한다.***

**✅ 용어 정리 (Glossary)**

|  |  |
| --- | --- |
| **용어** | **의미** |
| **Endpoint Discovery** | 네트워크에 연결된 장비의 식별 정보와 연결 위치를 발견하는 기능 |
| **Flow Telemetry** | 장비 사이의 통신 관계·프로토콜·트래픽량 등을 수집하는 기능 |
| **NetFlow** | Cisco에서 발전시킨 네트워크 통신 흐름 정보 수집 기술 |
| **IPFIX** | IP Flow Information Export. 네트워크 Flow 정보 내보내기를 위한 표준 프로토콜 |
| **DPI** | Deep Packet Inspection. 패킷 내부 내용까지 검사하는 기술 |
| **NBAR** | Network-Based Application Recognition. Cisco의 애플리케이션 분류 기술 |
| **AVC** | Application Visibility and Control. 네트워크 애플리케이션 가시성 및 제어 기술 |
| **MAC OUI** | MAC 주소의 제조사 식별에 활용되는 접두부 |
| **CDP / LLDP** | 인접 네트워크 장비에 관한 정보를 교환하는 프로토콜 |
| **IdentityGraph** | 여러 시스템의 장비 식별 정보와 보안 상태를 결합하는 Elisity의 신원 관리 엔진 |
| **Core Effective Attributes** | 여러 데이터 출처에서 우선순위에 따라 통합한 대표 장비 속성 |
| **Consistency Score** | 서로 다른 출처의 장비 범주 분류가 얼마나 일치하는지 나타내는 지표 |
| **Traffic Vectors** | 장비·정책 그룹 사이의 통신 흐름을 시각화하는 기능 |
| **Sankey Diagram** | 흐름의 방향과 규모를 연결선의 형태와 너비로 표현하는 시각화 방식 |
| **Top Talkers** | 선택된 기준에서 트래픽량이 많은 통신 주체 또는 관계 |
| **Policy Group** | 공통 신원·속성·보안 조건을 가진 장비를 묶는 논리적 그룹 |
| **Simulation Mode** | 정책을 실제 차단에 적용하기 전에 영향을 검토하는 모드 |
| **EDR Detected** | 장비가 알려진 EDR 서비스와 통신하는지 관찰한 Elisity Native 속성 |
| **Elisity Intelligence** | AI 기반 장비 분류·정책 추천·자연어 분석 기능 |
| **Elisity Assistant** | CCC 내부 정보를 자연어로 조회하고 설명하는 AI 도우미 |
| **C2 (Command & Control)** | 공격자가 감염된 장비에 원격 명령을 전달하거나 정보를 교환하는 통신 체계 |
| **Beaconing** | 감염된 장비가 외부 서버 등에 반복적으로 접속하는 통신 패턴 |
| **Data Exfiltration** | 허가되지 않은 방식으로 내부 데이터를 외부로 유출하는 행위 |
| **RBAC** | Role-Based Access Control. 역할에 따라 권한을 부여하는 접근제어 방식 |
| **Single-Tenant** | 고객별로 분리된 전용 서비스 환경을 제공하는 아키텍처 |
