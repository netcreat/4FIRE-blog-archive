# NVIDIA, Slurm에 QPU를 편입하다 — 그 이면에 담긴 두 가지 의미

Published: 2026-11-20T09:28:01+11:00

Original Naver post: https://blog.naver.com/4-fire/224484048655?fromRss=true&trackingCode=rss

---

**✅ HRES·QRMI·QDMI 구조와 양자 슈퍼컴퓨팅의 실제 의미**

- - 2026년 11월 SC26에서 NVIDIA는 슈퍼컴퓨터의 대표적인 작업 스케줄러 **Slurm**에 양자처리장치(QPU)를 정식 공유 자원으로 통합하는 구조를 발표했다. 기술적 핵심은 Slurm 26.11의 **HRES(Hierarchical Resources) 플러그인 인터페이스**다.
  - IonQ의 채드 사카크(Chad Sakac)는 이 소식에 “마법은 아니지만 필수적이다(Not magic but essential)”라며, 대규모 시스템에서는 오케스트레이션과 같은 기반 인프라가 중요하다고 평가했다.

    - "I’m super excited about this. Not magic but essential. Experience is that fundamental plumbing (orchestration) is fundamental, particularly in HPC or anything that demand scaling."
  - 이번 변화는 QPU의 큐비트 수나 게이트 충실도가 개선됐다는 발표가 아니다. **양자컴퓨터를 HPC 센터가 배정·감시·예약·회수할 수 있는 표준적인 운영 자원으로 만드는 기술**이다. NVIDIA는 지난 5년간 슈퍼컴퓨팅 센터의 QPU 도입이 약 7배로 증가했으며, 약 30개 센터가 50대 이상의 QPU 배치를 진행 중이라고 밝혔다. [[NVIDIA 발표]](https://blogs.nvidia.com/blog/slurm-quantum-computing-supercomputing/)

**✅ 1. NVIDIA의 플랫폼 전략: SchedMD 인수와 개방형 생태계**

- - NVIDIA는 2025년 12월 15일 Slurm의 주요 개발사인 **SchedMD 인수**를 발표했다. 동시에 Slurm을 오픈소스·공급사 중립적으로 유지하겠다고 약속했다. [[NVIDIA 공식 발표]](https://blogs.nvidia.com/blog/nvidia-acquires-schedmd/)
  - 이를 NVIDIA의 CUDA-Q, GPU 시스템, NVQLink 등과 함께 보면 하드웨어 공급을 넘어 양자·고전 하이브리드 컴퓨팅의 실행·관리 소프트웨어 계층까지 영향력을 확장하려는 전략으로 해석할 수 있다. 다만 이는 **전략적 추론**이지, 모든 QPU가 NVIDIA 하드웨어에 종속된다는 확정적 사실은 아니다.
  - 오픈소스·공급사 중립성 약속은 중요하지만, 생태계가 특정 기업의 개발 우선순위와 지원 체계에 얼마나 의존하게 되는지는 계속 관찰할 필요가 있다.

**✅ 2. Slurm은 무엇을 관리하며, QPU는 왜 예외였나?**

- - Slurm은 여러 연구자와 애플리케이션이 공유하는 슈퍼컴퓨터에서 작업 대기열, 우선순위, 계산 노드, CPU/GPU 자원, 실행 시간 등을 관리하는 오픈소스 워크로드 매니저다.
  - 예를 들어 연구자가 CPU 노드 4개와 GPU를 30분 동안 요청하면 Slurm이 자원 및 정책에 따라 작업을 배치한다. 반면 QPU는 네트워크를 통해 여러 계산 노드에서 접근하는 **클러스터 공유 가속기**인 경우가 많아, 기존의 GPU 자원 모델에 잘 들어맞지 않았다.
  - 물리적으로 QPU를 데이터센터에 설치하는 것만으로는 해결되지 않는다. 사용자 인증, 사이트별 정책, 사용량 기록, 장비 교정 상태, QPU 세션 또는 예약, 실패 시 복구까지 운영체계와 연결해야 한다.

**📌 기존 GRES와 License+SPANK 구조의 한계**

|  |  |  |
| --- | --- | --- |
| **기존 방법** | **구조** | **문제** |
| GRES(Generic Resources) | GPU처럼 특정 계산 노드에 연결된 자원으로 관리 | QPU가 하나의 노드에 묶이므로 다른 노드가 접근하기 어려움. 지정 노드가 장애를 일으키면 QPU 접근도 막힐 수 있음. |
| License + SPANK | 클러스터 전체 공유 수량은 License로 관리하고, SPANK 플러그인으로 QPU 옵션과 노드 초기화 처리 | QPU 대기 중에도 계산 노드를 선점할 수 있고, 자원 예약과 장비 옵션이 별도 플래그로 분리될 수 있음. |
| 사이트 맞춤형 통합 | 센터와 공급사마다 별도 연동 코드를 작성 | 업그레이드마다 호환성을 확인해야 하고, QPU 제조사가 고객별 통합을 반복해야 함. |

**✅ 3. HRES의 핵심: QPU를 노드와 분리된 공유 자원으로 모델링**

- - HRES는 Slurm 25.05에 베타 기능으로 도입된 자원 모델이다. License처럼 자원이 특정 노드에 소속되지 않지만, **어떤 노드 그룹에서 해당 공유 자원에 접근할 수 있는지**를 Layer로 표현한다.
  - Slurm 26.11에서 추가된 것은 이 HRES를 외부 QPU 미들웨어와 연결하는 플러그인 인터페이스다. 첫 구현인 hres/lua를 이용하면 QPU 공급사나 커뮤니티가 Lua 플러그인을 작성하고, 고객은 자신의 환경에 맞는 설정 파일을 사용하면 된다.
  - 하나의 Layer는 이름, 사용 가능한 노드 목록, 자원 수량(count)을 갖는다. QPU 1대에 대한 단순 모델이라면 접근 가능한 노드를 묶고 count: 1을 지정할 수 있다. 단, 이 값은 **동시 허용 작업 수에 대한 스케줄링 설정**이지 QPU의 물리 큐비트 수나 연산 성능이 아니다.

**📌 관리자 설정: resources.yaml 예시**

- - **NVIDIA 기술문서의 예시 구조에 따른 HRES 관리자 설정(설명용 주소)**

- resource: qpu
mode: MODE\_1
plugin:
type: hres/lua
config:
- name: path
value: /etc/slurm/hres\_qpu.lua
- name: endpoint
value: https://qpu-gateway.example.org
maintenance\_cycle: 30
layers:
- layer\_name: qpu1
nodes: ["node[0001-0123]"]
count: 1

- - resource: qpu는 작업 요청에 사용할 자원 이름이고, plugin.type: hres/lua는 호출할 플러그인 종류를 지정한다.
  - nodes: ["node[0001-0123]"]는 1번부터 123번까지의 계산 노드가 이 Layer를 이용할 수 있음을 뜻한다. 모든 노드가 반드시 QPU와 직접 전용 케이블로 연결돼 있다는 뜻은 아니며, 실제 접근은 네트워크와 미들웨어 구성에 달려 있다.
  - maintenance\_cycle: 30은 QPU 상태를 30초 주기로 확인하도록 설정한 예시이며, 30초가 고정된 의무 값은 아니다.
  - **운영 책임 분리:** resources.yaml에는 사이트별 엔드포인트·노드·정책을 기록하고, 플러그인에는 장비 연동 로직을 둔다. 이렇게 해야 공급사가 플러그인을 재사용하면서도 HPC 관리자는 자신의 운영 정책을 유지할 수 있다.

**📌 Lua란?**

- - Python이나 JavaScript처럼 코드를 작성하는 데 사용하지만, 특히 다른 소프트웨어 안에 내장해 기능을 확장하는 스크립트 언어(Embedded Scripting Language)로 많이 사용된다.
  - 이번 NVIDIA의 Slurm HRES에서 Lua가 등장하는 이유는 **Slurm과 QPU 제조사의 자원 관리 시스템을 연결하는 플러그인의 동작을 Lua 스크립트로 정의할 수 있기 때문**이다.

|  |  |
| --- | --- |
| **구성요소** | **역할** |
| Slurm | HPC 작업과 CPU·GPU·QPU 자원을 배정하는 스케줄러 |
| HRES | QPU 같은 외부 자원을 Slurm에서 관리하기 위한 기능 |
| **Lua** | HRES가 외부 자원을 어떻게 확인·예약·반환할지 정의하는 스크립트 언어 |
| QRMI / QDMI | 실제 QPU 관리 시스템과 연결되는 인터페이스 |

- - 따라서 중요한 구조는 다음과 같다.

    - **Slurm → Lua 콜백 → QRMI/QDMI → QPU 제조사의 관리 시스템**
  - 여기서 한 가지 더 중요한 점이 있다.

    - **QPU 제조사가 Slurm 자체를 수정하지 않아도 Lua 플러그인과 미들웨어 연동을 구현해 자신의 QPU를 Slurm에서 관리할 수 있다는 것**이다.
  - 이것이 NVIDIA가 이번에 선택한 방식의 장점이다.

**✅ 4. 실제 아키텍처: Slurm이 QPU를 직접 제어하는 것은 아니다**

- - NVIDIA 기술문서에서 가장 중요한 경계는 **Slurm/HRES 플러그인과 실제 QPU 사이에 별도의 QPU Access Middleware가 존재한다**는 점이다.

[![](https://mblogthumb-phinf.pstatic.net/MjAyNjExMTlfMTk5/MDAxNzk1MDk3NzY2NjY5.TA68QfJJX6iqxRQcf7ub3G0q5wbLLSUxK5Ue8rGfitkg.2wTqECzI3iJMQud03RxYGpespk4o1j1XEAbF7wxlLzIg.PNG/image.png?type=w800)](#)

- - Slurm 컨트롤러(slurmctld)는 QPU가 사용 가능한지 확인하고 계산 노드와 자원을 배정한다. HRES Lua 플러그인은 미들웨어 API를 호출하며, QPU 제조사별 장비 세부 제어와 실제 양자 작업 실행은 미들웨어·공급사 런타임이 담당한다.
  - 따라서 Slurm 통합은 **스케줄링·접근·예약·작업 생명주기 관리**를 표준화하는 것이지, 초저지연 피드백 제어나 오류 정정 알고리즘을 Slurm에 구현하는 것이 아니다.

**📌 작업이 시작되고 종료될 때의 데이터 흐름**

[![](https://mblogthumb-phinf.pstatic.net/MjAyNjExMTlfOSAg/MDAxNzk1MDk2OTk5NTIz.ZeCsWeO6xALd0aXu1GnvNdJq8y84M9ZIrJl-B4Uy92Yg.Czw-GRtKtFAT-Kex1tPnX_I4_LIfLqZ3EN9Q4y6Hyr8g.PNG/image.png?type=w800)](#)

- - ① QPU 상태 확인 → ② QPU 작업 승인 여부 판정 → ③ 필요하면 별도 스레드에서 QPU 예약 → ④ 접근 가능한 CPU/GPU 노드에서 하이브리드 작업 실행 → ⑤ 종료 시 세션과 자원 반납 순으로 이해하면 된다.
  - 특히 ②와 ③의 구분이 중요하다. **QPU를 예약하기 위해 기다리는 동안 계산 노드까지 먼저 배정해 낭비하지 않도록** 작업 시작 전 판정과 비동기 예약을 구분했다.

**✅ 5. HRES/Lua 콜백: 내부적으로 어떤 일이 벌어지나?**

- - NVIDIA는 hres/lua에서 동작하는 주요 콜백을 공개했다. 콜백은 Slurm 컨트롤러, 계산 노드, 개별 태스크의 서로 다른 단계에서 호출된다. 아래 표는 기술문서의 명칭과 역할을 유지하면서 한국어로 정리한 것이다.

|  |  |  |
| --- | --- | --- |
| **콜백** | **실행 위치·시점** | **QPU 통합에서의 역할** |
| hres\_create\_context | slurmctld, 설정 읽을 때 | 미들웨어 연결 정보·상태 초기화 |
| hres\_maintenance | slurmctld, 주기적 | QPU 상태 조회, Layer 사용 가능/중지 갱신 |
| hres\_controller\_job\_prerun | slurmctld, 노드 할당 전·job lock 내부 | 캐시된 장비 상태로 빠르게 승인/대기 결정 |
| hres\_controller\_job\_async\_prerun (선택) | slurmctld, 별도 스레드 | 느린 QPU 예약·세션 확보 및 실행 노드용 payload 생성 |
| hres\_controller\_job\_revoke | slurmctld, prerun 뒤 작업 시작 실패 시 | 확보한 예약의 취소/반납 |
| hres\_node\_job\_prolog | 해당 작업의 각 노드, Prolog 이전 | 접근 서비스 시작·작업별 파일 준비 |
| hres\_node\_task\_prolog | 각 태스크, root 권한·실행 전 | 태스크별 권한 필요한 초기화 |
| hres\_node\_user\_task\_prolog | 각 태스크, 사용자 권한·실행 직전 | 사용자 문맥의 환경 설정 |
| hres\_node\_task\_epilog | 개별 태스크 종료 후 | 태스크 단위 정리 |
| hres\_node\_job\_epilog | 각 작업 노드, Epilog 이후 | 서비스 종료 및 작업별 파일 제거 |
| hres\_controller\_job\_epilog | slurmctld, 노드 정리 후 자원 반환 전 | QPU 예약 해제·세션 반환 |
| hres\_destroy\_context | slurmctld, 설정 재읽기 이전 | 연결 종료 및 플러그인 상태 해제 |

**📌 기술적 설계 포인트 세 가지**

- - **1) 컨트롤러의 잠금을 오래 붙잡지 않아야 한다.** hres\_controller\_job\_prerun은 job lock 상태에서 실행되므로, 느린 네트워크 호출이나 외부 QPU 예약을 직접 수행하는 것은 부적절하다. 이를 위해 async\_prerun이 별도 스레드에서 실행될 수 있게 설계됐다.
  - **2) 상태 확인과 자원 배정을 연결한다.** hres\_maintenance는 QPU가 교정·장애 등으로 이용 불가능해졌을 때 disable\_layer를 설정해 해당 Layer의 새 배정을 중단하거나, 복구 후 해제할 수 있다.
  - **3) 외부 서비스 장애를 계산 노드 장애로 오인하지 않는다.** 외부 미들웨어가 응답하지 않으면 ESLURM\_HRES\_REMOTE\_FAIL을 반환할 수 있다. 이 경우 prerun 실패 시 작업을 대기 상태로 두고, 노드 prolog/epilog 실패가 곧바로 노드 drain으로 이어지지 않도록 구분한다.

**📌 설명용 Lua 콜백의 최소 구조**

- - **NVIDIA 기술문서의 함수 구조를 따른 축약 예시. middleware\_\* 함수는 실제 제공되지 않는 자리표시자이며, 운영에 필요한 다른 콜백도 생략돼 있음**

function hres\_maintenance(ctx, layers)
local ready = middleware\_status(ctx.config.endpoint)
for \_, layer in ipairs(layers) do
layer.disable\_layer = not ready
end
return slurm.SUCCESS
end
function hres\_controller\_job\_prerun(ctx, job, prep)
if not middleware\_can\_admit(ctx, prep.plugin\_args) then
return slurm.ESLURM\_HRES\_REMOTE\_FAIL
end
return slurm.SUCCESS
end
function hres\_controller\_job\_epilog(ctx, job, prep)
middleware\_release(ctx.config.endpoint, prep.payload)
return slurm.SUCCESS
end

**✅ 6. 사용자 입장에서는 무엇이 바뀌는가?**

- - 관리자가 QPU 연동을 구성했다면 연구자는 기존의 sbatch 작업 스크립트 안에서 QPU 자원을 요청할 수 있다. QPU 전용 포털에서 별도로 예약한 뒤 HPC 작업과 수동으로 연결하는 절차를 줄일 수 있다.
  - 아래는 Slurm 26.11 HRES 지원 환경의 예시다. 실제 운영에서는 센터의 Partition, QPU 자원 이름, 공급사 SDK 및 권한 설정에 맞게 수정해야 한다.
  - **4개 계산 노드와 QPU 자원 1개를 요청하는 배치 작업**

#!/bin/bash
#SBATCH --job-name=hybrid-qpu-job
#SBATCH --nodes=4
#SBATCH --time=00:30:00
#SBATCH --resources=qpu:1
srun ./my\_hybrid\_app

- - QPU별 옵션도 --resources='qpu:1[shot=1000]'처럼 하나의 자원 요청 인자에 실을 수 있다. 여기서 shot=1000은 플러그인으로 그대로 전달되는 사용자 옵션의 예시이며, Slurm 자체가 샷 수를 해석하거나 모든 공급사가 이 옵션을 동일하게 지원하는 것은 아니다.
  - **중요한 보안 주의사항:** NVIDIA 기술문서는 관리자 설정, 사용자 인자, 플러그인 payload가 실행 노드와 작업 사용자에게 노출될 수 있으므로 **API 키·비밀번호 등 비밀 정보를 넣지 말라**고 명시한다. 실제 인증정보는 별도의 적절한 자격증명 관리 체계로 다뤄야 한다.

**✅ 7. QRMI와 QDMI는 어떻게 다른가?**

- - Slurm은 QPU 공급자별 API를 하나하나 구현하지 않는다. 대신 미들웨어가 장치 정보를 다루고, HRES 플러그인이 해당 미들웨어와 Slurm을 연결한다. NVIDIA 기술문서가 소개한 대표 구현이 **QRMI**와 **QDMI**이다.

|  |  |  |
| --- | --- | --- |
| **구분** | **QRMI** | **QDMI** |
| 정식 명칭 | Quantum Resource Management Interface | Quantum Device Management Interface |
| 개발 주체 | IBM 중심의 Qiskit 커뮤니티 | 독일 Munich Quantum Software Stack(MQSS) |
| 주요 참여 기관 | IBM, RPI, STFC Hartree Centre, Pasqal 등 | TUM, LRZ 등 |
| 공개 연혁 | 2025년 주요 프로젝트 공개 | 2024년 학술 발표 |
| 주요 목적 | QPU 자원 예약·할당·해제·상태 관리 | QPU 장치 정보·기능·실행 인터페이스 표준화 |
| 공식 국제표준 | 확인되지 않음 | 확인되지 않음 |
| Slurm 종속성 | 없음 | 없음 |
| 오픈소스 | 예 | 예 |

- - 두 인터페이스를 단순히 서로 대체 가능한 하나의 표준으로 취급하면 안 된다. 이번 HRES 구현에서 가장 큰 차이는 **실제 QPU 사용권을 작업 시작 전에 획득하는가, 아니면 공급사의 내부 대기열로 넘기는가**다.

|  |  |  |
| --- | --- | --- |
| **구분** | **QRMI 기반 HRES 플러그인** | **QDMI 기반 HRES 예시** |
| 초점 | QPU 자원 접근·사용권 확보 | QPU 장치 정보·상태 및 작업 제출 |
| 식별 | QRMI 구성에 정의된 자원 이름 | QDMI Device ID |
| 상태 확인 | QPU 가용성 확인 | 장치 상태 확인. 예시에서는 idle 또는 busy 상태를 허용 |
| 작업 시작 전 | 사용자 자격증명으로 예약 또는 세션 확보 | HRES 작업 허용 여부 판단. 별도 예약 없음 |
| 실제 실행 대기 | 백엔드가 지원하는 예약/세션 범위에 의존 | QPU 공급사의 내부 큐가 실제 실행 순서를 관리 |
| 작업 종료 | 할당된 예약 또는 세션 해제 | 공급자 측 작업 처리 정책에 따름 |
| 호환성 | 기존 QRMI SPANK 환경변수 이름을 유지해 기존 애플리케이션 연속성 고려 | MQSC Orchestrator를 통해 공급자별 QDMI 연동 |

**📌 QRMI 방식: 작업마다 QPU 접근을 확보**

- - QRMI 구현은 작업 시작 전에 사용자의 자격증명을 이용해 QPU에 대한 예약 또는 세션을 획득한다. 시간이 걸리는 작업이므로 별도 스레드를 이용해 Slurm 컨트롤러의 핵심 경로를 불필요하게 막지 않도록 설계했다.
  - 작업이 끝나면 확보했던 QPU 사용권을 해제한다. 기존 QRMI SPANK 플러그인과 동일한 환경변수를 제공하므로 기존 응용 프로그램의 변경 부담을 줄이는 것도 목표다.

**📌 QDMI 방식: 실제 연산 대기는 공급사에서 관리**

- - 공개된 QDMI 예시는 장치가 idle 또는 busy로 보고되면 Slurm에서 작업을 허용할 수 있지만, 그 시점에 QPU 자체를 배타적으로 예약하지 않는다.
  - 따라서 Slurm 작업이 허용되더라도 QPU 연산은 공급사 내부 큐에 다시 대기할 수 있다. **Slurm 작업 시작 시각과 실제 QPU 연산 시작 시각을 동일하다고 간주하면 안 된다.**
  - 이 차이는 자원 사용률 분석에도 중요하다. Slurm의 계산 노드 점유 시간, 공급사 QPU 대기 시간, 실제 quantum execution time을 분리해야 전체 워크플로 비용과 지연시간을 정확하게 비교할 수 있다.

**✅ 8. Slurm·CUDA-Q·NVQLink는 서로 대체재가 아니다**

- - 동일한 NVIDIA 양자-HPC 플랫폼에 등장하더라도 이 기술들은 서로 다른 계층에 속한다. HRES는 HPC 센터의 **누가 언제 어떤 계산 자원에 접근하는가**를 관리한다.
  - CUDA-Q는 양자·고전 혼합 애플리케이션을 개발하고 실행하는 소프트웨어 프레임워크다. NVQLink는 GPU와 QPU 제어 시스템 사이의 저지연 통합을 겨냥한 기술로, HRES의 작업 예약 기능과는 목적이 다르다.

|  |  |  |
| --- | --- | --- |
| **구성 요소** | **담당 계층** | **주요 문제** |
| Slurm / HRES | 워크로드·공유 자원 관리 | 작업 배치, 접근 권한, 자원 가용성, 예약/해제 |
| QRMI / QDMI | 미들웨어 연계 인터페이스 | 장비 상태·세션·작업 요청 연동 |
| CUDA-Q | 하이브리드 실행 소프트웨어 | CPU/GPU/QPU를 이용한 응용 프로그램 개발·실행 |
| NVQLink | 저지연 시스템 통합 | GPU와 QPU 제어 사이의 빠른 데이터 교환 지원 |
| QPU 자체 런타임 | 양자 하드웨어 제어 | 큐비트 조작, 장비 교정, 실제 양자 연산 |

- - 따라서 Slurm HRES만 설치했다고 실시간 양자 오류 정정 피드백, GPU-QPU 초저지연 통신, 공급자 간 양자회로 이식성까지 자동으로 확보되는 것은 아니다.
  - 또한 GPU와 QPU의 대규모 동시 운영을 위한 비용, 회선 지연, 장비 교정, 작업 실패 복구, 공급자 큐 정책은 여전히 개별적으로 검증해야 한다.

**✅ 9. 현재 확인되는 참여 기업과 도입 단계**

- - NVIDIA는 첫 HRES 통합에 참여한 양자 생태계로 **Alice & Bob, IBM, IQM, MQSC, Pasqal, Quantinuum**을 소개했다. 이 명단은 모든 공급사가 동일한 수준으로 상용 운영 중이라는 의미는 아니다.
  - IBM과 Pasqal은 QRMI 기반 통합과 관련 개발을 공개했고, MQSC는 QDMI와 Slurm HRES를 결합한 오케스트레이터를 소개했다. IQM은 관련 통합을 지원하되 실제 클러스터 환경에서 검증을 진행 중이라고 발표했다.

|  |  |  |
| --- | --- | --- |
| **주체** | **공개된 관련 기술·프로젝트** | **해석상 주의점** |
| IBM / QRMI 커뮤니티 | QRMI와 Slurm HRES 연결, 기존 SPANK 기반 연동 경험 | 공통 인터페이스 개발과 모든 사이트 상용 운영은 서로 다른 단계 |
| Pasqal | QRMI를 이용한 Pasqal QPU 접근과 HPC 하이브리드 워크플로 | 도입 사이트·작업 유형별 성능은 별도 검증 필요 |
| MQSC | HRES + QDMI + 컴파일/실행 오케스트레이터 | QPU 내부 대기열까지 Slurm이 통제하는 구조는 아님 |
| IQM | Slurm HRES 통합 지원 및 테스트 | 검증 단계와 상용 서비스 가용성을 구분해야 함 |
| Alice & Bob / Quantinuum | NVIDIA의 참여 생태계 명단에 포함 | 동일한 구현 방식·운영 수준이라고 추정할 수 없음 |

**✅ 10. IonQ와의 연결: 긍정적이지만 확정된 내용은 제한적**

- - IonQ는 2026년 9월 발표에서 **Superion 256을 2027년 NVIDIA Accelerated Quantum Research Center(NVAQC)에 설치할 예정**이라고 밝혔다. 계획대로 진행되면 해당 QPU는 NVIDIA GB200 NVL72와 NVQLink로 연결되고, CUDA-Q를 이용한 하이브리드 작업에 활용될 예정이다. [[IonQ 공식 발표]](https://www.ionq.com/news/ionq-to-advance-quantum-supercomputing-by-bringing-first-qpu-to-nvidia-accelerated-quantum-research-center)
  - 이는 NVIDIA의 GPU-QPU 하이브리드 환경에 IonQ 하드웨어가 참여한다는 확정된 협력 계획이다. 그러나 **Slurm HRES 플러그인을 IonQ가 이미 완성했거나 이번 초기 참여 명단에 포함됐다고 발표된 것은 아니다.**
  - IonQ 공식 GitHub에는 QRMI 프로젝트를 포크한 저장소([ionq/qrmi](https://github.com/ionq/qrmi))가 공개돼 있다. QRMI 관련 기술에 대한 관심을 보여주는 정황일 수 있지만, 포크 자체는 HRES 상용 연동을 완료했다는 증거가 아니다.

- - 투자자 관점에서 앞으로 확인해야 할 지표는 단순한 “플랫폼 지원” 발표보다 구체적이다. Slurm을 통한 QPU 작업 성공률, 사용자별 대기시간, QPU 사용률, 실제 작업 완료까지 걸리는 시간(Time-to-Solution), 총비용(Cost-to-Solution), 설치 이후 운영 안정성을 확인할 필요가 있다.
  - 특히 NVAQC 설치는 2027년 계획이므로, 이번 2026년 11월 발표만으로 IonQ의 Superion 256이 이미 Slurm HRES 환경에서 검증됐다고 해석해서는 안 된다.

**✅ 11. QPU 스케줄러도 NVIDIA로 통일되는가? — 상위 오케스트레이션과 하위 런타임의 경계**

- - 이미 IBM·IonQ·Quantinuum 등 주요 QPU 제조사는 자체 작업 큐, 우선순위 정책, 사용 세션 및 장비 제어 시스템을 운영한다. 별도로 qBraid 같은 업체는 여러 공급사의 QPU에 공통으로 접근하는 서비스를 제공한다. 따라서 이번 Slurm 확대는 기존 시장에 새로운 관리 계층이 들어오는 사건이다.
  - **확인된 사실:** Slurm 26.11의 HRES는 QPU를 HPC 클러스터 차원의 공유 자원으로 표현하고, QRMI·QDMI 등 외부 인터페이스에 연결한다. 이는 제조사의 내부 실행 큐나 양자 하드웨어 제어를 Slurm이 직접 대체한다는 뜻이 아니다. [[NVIDIA 기술 문서]](https://developer.nvidia.com/blog/integrating-qpus-into-supercomputing-centers-using-slurm-hres-plugins)
  - **산업적 해석:** 고객이 보는 공통 작업 제출·자원 할당 계층은 Slurm으로 수렴할 수 있지만, 공급사별 QPU 실행·세션·교정·오류 관리 계층은 계속 필요하다. 즉 스케줄러 전체의 통일이라기보다 **스케줄링 책임의 계층화**에 가깝다.

**📌 왜 QPU 자체 스케줄러는 사라지지 않는가?**

- - QPU는 GPU와 달리 교정 상태와 장비별 특성에 따라 실행 가능 시점이 바뀔 수 있다. 제조사 런타임은 사용자가 요청한 회로를 실제 물리 하드웨어에 맞춰 실행하는 제약을 처리해야 한다.
  - **QRMI 방식**은 Slurm 작업이 고전 자원을 소비하기 전에 QPU 사용권 확보를 시도할 수 있다. 반면 NVIDIA 문서의 **QDMI 기반 예시**에서는 Slurm이 작업을 허용하더라도 실제 QPU 실행 순서는 공급사 내부 대기열이 결정할 수 있다.
  - 따라서 네트워크로 비유하면 상위 멀티벤더 오케스트레이터와 제조사별 장비 운영 소프트웨어가 공존하는 구조다. 다만 QPU 내부의 초저지연 제어까지 일반 NMS와 동일하게 취급해서는 안 된다.

  - **IonQ의 Quantum OS**도 같은 맥락이다. Slurm이 연구센터의 QPU 접근을 관리하더라도 IonQ 내부의 Fair Share·Sessions는 QPU 작업을 실행하는 과정에서 계속 역할을 할 수 있다. 반대로 고객 접점 일부가 HPC 통합 시스템으로 이동하는 경쟁 압력도 존재한다.

**✅ 13. NVIDIA의 플랫폼 주도권과 경쟁: 표준화가 곧 독점은 아니다**

- - NVIDIA는 2025년 12월 Slurm 주요 개발사 SchedMD를 인수했다. 따라서 양자컴퓨터 HPC 배포가 늘어날 때 **기존 HPC 스케줄러의 발전 방향에 영향력을 행사할 수 있는 위치**에 있다는 것은 사실이다. 다만 NVIDIA는 Slurm을 오픈소스·공급사 중립적으로 유지하겠다고 공식 발표했다. [[NVIDIA SchedMD 인수]](https://blogs.nvidia.com/blog/nvidia-acquires-schedmd/)

    - 자원 배정에는 **Slurm/HRES**,
    - 양자·고전 프로그램에는 **CUDA-Q**,
    - 저지연 GPU–QPU 연결에는 **NVQLink**,
    - 고전 계산에는 **GPU**라는 서로 다른 계층이 존재한다.
  - 상호 보완 효과가 있을 수 있지만, HRES를 사용하려면 반드시 CUDA-Q·NVQLink·NVIDIA GPU를 함께 구매해야 하는 것은 아니다.
  - **경쟁 사례:** AMD는 SC26에서 IBM 양자 하드웨어와 AMD CPU·GPU를 연결하는 개방형 소프트웨어 스택을 제시했다. 여기에는 Slurm용 어댑터와 QRMI·QDMI 위의 공통 연결 계층도 포함된다. 즉 **Slurm 채택 확대와 NVIDIA GPU 종속은 동의어가 아니다.** [[AMD 공식 기술 발표]](https://www.amd.com/en/developer/resources/technical-articles/2026/an-open-software-stack-to-connect-quantum-computers-and-supercom.html)
  - **해석:** NVIDIA가 차지할 수 있는 전략적 이점은 QPU 제조를 직접 지배하는 것보다, 양자컴퓨터가 연결되는 HPC 운영·개발 환경에서 널리 쓰이는 핵심 소프트웨어의 개발 주도권과 고객 관계에 있다. 그러나 실제 시장 점유율이나 종속 효과는 향후 도입 사례로 검증해야 한다.

**📌 향후 확인할 다섯 가지 관찰 지표**

- - **① 제조사 채택률:** QPU 제조사가 Slurm HRES 또는 QRMI/QDMI 플러그인을 실제 상용 장비에 얼마나 도입하는가.
  - **② 이중 스케줄링의 비효율:** Slurm 예약과 제조사 내부 대기열 사이의 대기시간·예약 실패·재시도 문제가 얼마나 개선되는가.
  - **③ 독립 소프트웨어 사업자의 역할:** qBraid 같은 서비스가 단순 작업 제출을 넘어 개발·과금·운영 기능으로 얼마나 차별화하는가.
  - **④ 성능 자동화 수요:** Q-CTRL 등 교정·오류 억제 기술이 대규모 QPU 도입에서 필요한 운영 소프트웨어로 성장하는가.
  - **⑤ 플랫폼 독립성:** NVIDIA GPU뿐 아니라 AMD GPU, IBM·IonQ·Quantinuum 등의 QPU에서도 공통 작업 관리가 실제로 검증되는가.

**✅ 15. 결론: 양자컴퓨터 상용화에 필요한 운영 인프라의 한 단계**

- - 이번 NVIDIA 발표의 핵심은 Slurm에 단순히 “QPU”라는 장치 이름을 추가한 것이 아니다. **노드에 종속되지 않는 공유 자원 모델, 외부 장비의 건강 상태를 반영하는 스케줄링, 느린 예약 작업의 비동기 처리, 작업 종료·실패 시 자원 반환**을 하나의 확장 가능한 운영 구조로 묶었다는 점이다.
  - QRMI와 QDMI가 서로 다른 QPU 접근 방식을 지원하고, Slurm이 이를 플러그인으로 연결하면서 HPC 센터는 공급사별 작업 제출과 운영 절차를 통합할 가능성을 확보했다. 이는 HPC 엔지니어링과 양자컴퓨팅이 접점을 넓혀 가는 변화다.
  - 다만 2026년 11월 20일 현재 Slurm 26.11은 발표·배포 준비 단계의 기술이며, 실제 각 센터의 배치·안정화 수준은 다를 수 있다. QPU의 과학적 유용성이나 투자 수익성까지 입증한 발표는 아니다.
  - **최종 판단:** 이번 발표는 양자컴퓨터의 연산 성능보다 **배포 반복성, 운영 확장성, HPC 접근성**을 높이는 인프라 진전이다. 양자 하드웨어 경쟁과 별개로, 대규모 상용 운영의 전제조건을 만드는 움직임으로 평가할 수 있다.
  - 산업 구조 측면에서는 상위 HPC 작업 배정과 QPU 제조사의 내부 런타임이 분리되고 있다. 장기적으로 고객이 이용하는 공통 관리 계층의 영향력은 커질 수 있지만, 실제 연산·교정·오류 관리 기능은 여전히 개별 공급사의 기술력에 달려 있다.
  - **투자·산업 관찰 포인트:** NVIDIA의 Slurm 생태계 확대를 QPU 소프트웨어 시장의 즉각적인 통일이나 특정 하드웨어 독점으로 해석해서는 안 된다. 업체별 HRES 채택, 상위·하위 대기열 통합, CUDA-Q 및 경쟁 플랫폼과의 상호운용성, 독립 사업자의 차별화가 핵심이다.
