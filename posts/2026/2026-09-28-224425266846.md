    - 당시 나는 이를 단순한 파트너 로고 모음이라기보다, 장기적으로는 양자컴퓨터가 기존 CPU·GPU·네트워크 인프라와 연결되는 구조를 염두에 둔 것일 가능성을 생각해봤다.
  - 특히 Nexus Photonics를 공부하면서 다음과 같은 가설을 제시했다.

    - NVIDIA가 NVQLink를 통해 GPU와 여러 종류의 QPU를 연결하는 인터페이스를 선점하려 한다면,
    - IonQ는 Nexus Photonics를 통해 **광학 계층 자체를 Merchant Supplier 형태로 확장하려는 것은 아닐까?**
  - 물론 이것은 아직 어디까지나 가설이다.
  - 그런데 Nexus의 기술을 조금 더 살펴보다가 재미있는 숫자를 하나 발견했다.

**📌 100GHz 이상의 광변조기**

- - Nexus는 100GHz 이상의 고속 광변조기 기술을 보유하고 있다.
  - 처음에는 이 숫자를 양자 네트워킹 성능과 직접 연결해서 생각하기 쉬웠다.
  - 하지만 자세히 보면 이야기가 조금 달라진다.
  - 양자 네트워킹과 고전적 광통신에서 요구하는 “속도”는 같은 의미가 아니다.

---

**✅ 양자 네트워킹에서 중요한 것은 고대역폭이 아니다**

- - 고전 네트워킹에서는 800Gbps, 1.6Tbps 등의 대역폭이 높은 전송 성능이 핵심이다.
  - 반면, IonQ가 추진하고 있는 광자 기반 양자 네트워킹의 핵심은 많은 데이터를 보내는 것이 아니다.
  - 핵심은 **서로 떨어져 있는 QPU 사이에 높은 충실도의 얽힘을 얼마나 빠르게 생성할 수 있느냐**다.
  - 현재 논의되는 수치는 대략 다음과 같다.

    - Remote entanglement: 약 **1,000회/s**
    - 장기 목표: 약 **10,000회/s**
  - Chris Monroe 교수의 설명을 보면 10,000/s라는 숫자가 왜 중요한지도 이해할 수 있다.

**📌 Local gate와 Remote entanglement의 시간축**

- - 같은 ion trap 안에서 두 이온을 얽히게 하는 local entangling gate는 대략 **10~200μs** 정도의 시간축에서 동작한다.
  - 반면 remote entanglement가 1,000/s라면 평균적으로 약 **1ms마다 하나의 entanglement resource**를 생성하는 셈이다.
  - 이것을 10,000/s까지 높이면 평균 간격은 약 **100μs**가 된다.
  - 즉,

|  |  |
| --- | --- |
| **구분** | **대략적인 시간** |
| Local trapped-ion entangling gate | 10~200μs |
| Remote entanglement @ 1,000/s | 약 1ms |
| Remote entanglement @ 10,000/s | 약 100μs |

- - 10,000/s에 도달하면 remote entanglement의 시간축이 local two-qubit gate와 같은 영역으로 들어오기 시작한다.
  - 여러 QPU를 하나의 더 큰 컴퓨터처럼 사용할 때 **QPU 사이 연결이 QPU 내부 연산보다 지나치게 느린 병목이 되는 것을 줄이려는 것**이다.

---

**✅ 그렇다면 100GHz가 필요한가?**

- - 여기서 처음 생긴 의문은 이것이었다.
  - 양자컴퓨터 내부 연산도 수십~수백 μs이고, remote entanglement 목표도 10kHz 수준이라면,

**📌 “왜 굳이 100GHz짜리 광변조기가 필요한가?”**

- - 결론부터 말하면,

    - **10,000/s의 remote entanglement를 만들기 위해 반드시 100GHz가 필요한 것은 아니다.**
  - 양자 얽힘 생성률을 높이는 데 중요한 것은 오히려 다음과 같은 요소들이다.

    - 광자 생성 효율
    - 광자 수집 효율
    - 광섬유 결합 효율
    - photon indistinguishability
    - 검출 효율
    - 광손실
    - 병렬화
    - 양자메모리
  - 광변조기가 100GHz로 동작한다고 해서 remote entanglement가 자동으로 100GHz로 올라가는 것은 아니다.
  - 평균 얽힘 생성 간격과 개별 광자 펄스를 제어하는 시간축 역시 서로 다른 문제다.

---

**✅ 여기에서 1.6T 라는 또 다른 숫자가 등장한다**

- - 광통신 업계에서는 **1.6T**라는 숫자를 자주 볼 수 있다.
  - 여기서 1.6T는 1.6THz가 아니다.

**📌 1.6Tbps**

- - 초당 1.6조 비트의 고전적 데이터를 전송한다는 의미다.
  - 따라서 이것은 광변조기의 대역폭인 GHz와 바로 같은 단위로 비교할 수 없다.
  - 관계를 단순화하면 다음과 같다.
  - 데이터 전송률은 대략

    - **Baud × 한 심볼에 담는 비트 수 × 병렬 채널 수**
  - 로 생각할 수 있다.

**📌 예를 들어 PAM4를 사용하면**

- - PAM4는 하나의 symbol에 2bit를 담는다.
  - 8개의 광채널을 사용하고 각각 약 100Gbaud로 동작한다고 단순화하면,

    - **100Gbaud × 2bit × 8 lane = 1.6Tbps**
  - 즉 1.6Tbps는 단일 광변조기가 1.6THz로 동작해야 한다는 의미가 아니다.
  - 여러 고속 광채널과 PAM4 같은 변조 기술을 병렬로 사용하는 구조다.

---

**✅ 그렇다면 Nexus의 100GHz+ 광변조기는 생각보다 상당히 빠른 것 아닌가?**

- - 바로 여기서 이야기가 재미있어진다.
  - 100GHz analog bandwidth와 100Gbaud는 동일한 숫자가 아니다.
  - 실제 필요한 변조기 bandwidth는 pulse shaping, driver, DSP, 허용되는 signal degradation 등에 따라 달라진다.
  - 따라서 단순히

    - **100GHz modulator = 100Gbaud**
  - 라고 등치시킬 수는 없다.
  - 그러나 **100GHz 이상의 광변조기 기술을 확보하고 있다는 것은 200Gbps/lane급 고속 광통신 소자를 구현하기 위한 상당히 유리한 출발점**으로 볼 수 있다.
  - 즉 Nexus의 100GHz 기술은 IonQ가 10kHz remote entanglement를 달성하기 위해서라기보다, 장기적으로 **고전적 고속 광통신 시장까지 기술을 확장할 수 있는 가능성**에서 더 흥미롭게 볼 수 있다.

---

**✅ 그렇다면 bps와 Hz는 어떻게 연결해서 봐야 할까?**

- - 여기서 한 가지 헷갈리기 쉬운 부분이 있다.
  - 1.6T는 **1.6Tbps**, 즉 초당 1.6조 비트의 데이터 전송속도이고,
  - Nexus가 말하는 100GHz는 **광변조기의 아날로그 대역폭**이다.
  - 둘은 단위부터 다르기 때문에 직접적으로

    - **100GHz = 100Gbps**
  - 라고 볼 수는 없다.

**📌 중간에 Baud라는 개념이 들어간다**

- - 데이터 전송속도를 단순화하면 다음처럼 볼 수 있다.

    - **bps = Baud × bits per symbol × 병렬 lane 수**
  - 여기서 각각의 의미는 다음과 같다.

|  |  |
| --- | --- |
| **구분** | **의미** |
| bps | 초당 실제 전송하는 bit 수 |
| Baud | 초당 전송하는 symbol 수 |
| bits/symbol | 하나의 symbol에 담는 bit 수 |
| Lane | 동시에 사용하는 병렬 광채널 수 |

- - 즉 같은 Baud라도 하나의 symbol에 몇 bit를 담느냐에 따라 실제 데이터 전송량은 달라진다.

---

**✅ 가장 단순한 방식 — NRZ**

- - NRZ는 하나의 symbol에 1bit를 담는다.
  - 따라서 관계가 가장 단순하다.

    - **1 symbol = 1 bit**
  - 예를 들어 8개의 lane으로 1.6Tbps를 만들려면,

    - **1.6Tbps ÷ 8 = 200Gbps/lane**
  - NRZ는 1 symbol = 1bit이므로,

    - **200Gbps/lane = 200Gbaud/lane**
  - 이론적으로는 8개의 lane이 각각 200Gbaud로 동작해야 한다.

|  |  |  |  |
| --- | --- | --- | --- |
| **변조 방식** | **bits/symbol** | **Lane** | **필요한 symbol rate** |
| NRZ | 1 | 8 | 200Gbaud/lane |

- - 문제는 lane당 200Gbaud는 아날로그 회로와 광소자에 상당히 높은 부담을 준다는 것이다.

---

**✅ 그래서 PAM4를 사용한다**

- - 오늘날 고속 데이터센터 광통신에서 많이 사용하는 방식이 **PAM4**다.
  - PAM4는 한 번의 symbol에서 4개의 amplitude level을 사용한다.
  - 4개의 상태는 정보량으로 보면

    - **log****2****4** **= 2bit**

      - **00**
      - **01**
      - **10**
      - **11**
  - 즉, **1 symbol = 2bit** 가 된다.

**📌 8 lane PAM4로 1.6T를 만든다면**

- - 전체 데이터는 1.6Tbps
  - 8개 lane을 사용하면,

    - **1.6Tbps ÷ 8 = 200Gbps/lane**
  - PAM4는 symbol 하나당 2bit를 담으므로,

    - **200Gbps ÷ 2 = 100Gbaud**
  - 따라서 이론적으로는,

    - **100Gbaud × 2bit × 8 lane = 1.6Tbps**
  - 가 된다.

|  |  |  |  |  |
| --- | --- | --- | --- | --- |
| **변조 방식** | **bits/symbol** | **Lane** | **Symbol rate** | **총 데이터율** |
| NRZ | 1 | 8 | 200Gbaud | 1.6Tbps |
| PAM4 | 2 | 8 | 100Gbaud | 1.6Tbps |
| PAM4 | 2 | 16 | 50Gbaud | 1.6Tbps |

- - 결국 1.6T를 만들기 위해 반드시 하나의 장치가 1.6THz로 움직여야 하는 것은 아니다.
  - **더 많은 bit를 한 symbol에 담고, 여러 lane을 병렬화하면 된다.**

---

**✅ 더 높은 변조 방식은 어떨까?**

- - 이론적으로는 하나의 symbol에 더 많은 bit를 담을 수도 있다.

**📌 16QAM**

- - 16개의 서로 다른 상태를 사용하므로,

    - **log****2****16** **= 4bit/symbol**
  - 이론적으로 8 lane으로 1.6Tbps를 만든다면,

    - **1.6Tbps ÷ 8 ÷ 4 = 50Gbaud**
  - 즉 symbol rate를 더 낮출 수 있다.

|  |  |  |  |  |
| --- | --- | --- | --- | --- |
| **변조 방식** | **bits/symbol** | **Lane** | **Symbol rate** | **총 데이터율** |
| NRZ | 1 | 8 | 200Gbaud | 1.6Tbps |
| PAM4 | 2 | 8 | 100Gbaud | 1.6Tbps |
| 16QAM | 4 | 8 | 50Gbaud | 1.6Tbps |

- - 하지만 여기서 중요한 것은 **bits/symbol을 높이면 무조건 좋은 것은 아니라는 점**이다.
  - symbol 안에 더 많은 정보를 욱여넣을수록 서로 다른 상태를 구분하기가 어려워진다.
  - 그만큼 요구되는 조건도 까다로워진다.

    - 더 높은 SNR
    - 더 정밀한 선형성
    - 더 복잡한 DSP
    - 더 높은 위상 안정성
    - 더 복잡한 수신 구조
  - 특히 16QAM 같은 방식은 일반적인 short-reach PAM4 데이터센터 링크와는 다른 coherent optical architecture에서 주로 사용된다.

---

**✅ 1.6T 구현을 더 현실적으로 보면**

- - 실제 시스템에서는 단순한 이론 계산보다 조금 더 복잡하다.
  - 예를 들어 nominal 200Gbps/lane이라도 실제 line rate에는 FEC와 protocol overhead가 포함된다.
  - 그래서 실제 symbol rate는 단순 계산한 100Gbaud보다 약간 높아질 수 있다.
  - 현재 1.6T Ethernet 계열에서는 **약 106Gbaud급 PAM4**가 자주 언급되는 이유도 이 때문이다.
  - 따라서 실제 구조는 대략 다음과 같이 볼 수 있다.

|  |
| --- |
| **약 100~106Gbaud**  **↓**  **PAM4**  **↓**  **약 200Gbps/lane**  **↓**  **8 optical lanes**  **↓**  **약 1.6Tbps** |

- - 여기서 Nexus의 100GHz+ modulator가 실제로 중요한 질문은 이것이다.

**📌 “이 modulator가 100Gbaud급 PAM4 환경에서 충분히 깨끗한 eye diagram과 낮은 BER을 만들 수 있는가?”**

- - 결국 평가해야 할 것은 단순 bandwidth 숫자 하나가 아니다.

    - insertion loss
    - modulation efficiency
    - drive voltage
    - extinction ratio
    - linearity
    - thermal stability
    - power consumption
    - BER
    - manufacturing yield
  - 가 함께 검증되어야 한다.
  - 보다 더 자세한 내용은 이전 포스트에서 다뤘으니 참고하자.

**✅ 그런데 광변조기 하나만으로 1.6T가 되는 것은 아니다**

- - 여기서 또 하나의 중요한 구분이 필요하다.
  - 고속 광변조기를 보유했다고 해서 바로 1.6T optical transceiver가 완성되는 것은 아니다.

  - 하지만 고속 DSP, SerDes, FEC 등 전자 계층까지 Nexus가 직접 모두 개발할 필요는 없다.
  - 이 부분에서 **Broadcom이라는 이름이 다시 등장한다.**

  - 충분한 bandwidth, drive voltage, linearity, insertion loss 등의 조건을 만족하는 외부 optical engine과 결합하는 것이 기술적으로 가능하다.

**✅ 그런데 양자 네트워킹과 1.6T를 섞어서는 안 된다**

|  |  |  |
| --- | --- | --- |
|  | **Quantum networking** | **Classical optical networking** |
| 목적 | Entanglement 생성·분배 | 대량 데이터 전송 |

| IonQ 목표 | 10,000 remote entanglements/s | 해당 없음 |
| 중요 요소 | fidelity, loss, photon collection, interference | bandwidth, BER, power, latency |
| Nexus 100GHz 의미 | 빠른 photon control 등에 활용 가능 | 고속 광통신으로 확장 가능한 핵심 자산 |
| 1.6T 필요성 | 필수 아님 | 매우 중요 |

- - Nexus가 IonQ의 QPU들을 연결하는 데 1.6Tbps가 필요해서 100GHz modulator를 개발한 것이라고 보는 것은 지나친 해석이다.
  - IonQ의 remote entanglement 목표는 10,000/s이고, 그 이유 역시 local trapped-ion gate의 10~200μs time scale과 맞추려는 데 있다.
  - 양자 네트워킹에서 핵심은 bandwidth보다 **얽힘의 품질과 생성 효율**이다.

**✅ 결론 — Nexus의 해자는 1.6T 자체가 아닐 수도 있다**

- - 처음에는 이런 생각이 들었다.

    - **“Nexus는 양자 쪽에는 해자가 있는데, 아직 고속 광통신 쪽에서는 한계가 있는 것 아닌가? 이 부분까지 올라오면 Lumentum이나 Coherent 같은 기존 광통신 업체들과도 경쟁하게 되는 것 아닐까?”**
  - 그런데 조금 더 들여다보니, 이 문제는 단순히 1.6T를 할 수 있느냐 없느냐로 볼 사안은 아닌 것 같다.

    - Nexus가 양자 네트워킹에서 성공하기 위해 **1.6T급 데이터 전송 성능이 반드시 필요한 것은 아니다.**
  - IonQ가 지금 중요하게 보는 목표도 1.6Tbps 데이터 전송이 아니라 **10,000/s remote entanglement**이기 때문이다.
  - 즉 양자 네트워킹에서의 핵심 경쟁력은 고속 데이터 전송 그 자체보다,

    - 낮은 광손실,
    - 높은 photon collection efficiency,
    - 높은 entanglement fidelity,
    - 정밀한 optical control,
    - 그리고 여러 QPU를 실제 연산 가능한 수준으로 연결하는 능력에 있다.
  - 반면 Nexus가 가진 **100GHz+ 광변조기 기술은 완전히 다른 확장 가능성**을 보여준다.
  - 만약 앞으로,

    - Broadcom 같은 고전 네트워크 업체가 양자 생태계에 진입할 수 있는 광학적 접점이 필요해지거나,
    - 양자 네트워킹의 remote entanglement 요구 속도 역시 현재 목표인 초당 10,000회를 훨씬 넘어서는 단계로 올라가고,
    - 고전 네트워크와 양자 네트워크 사이의 연결 요구가 본격적으로 커지며,
    - 동시에 Nexus의 기술이 실제 **200G/lane 이상의 고속 데이터 통신 환경에서도 검증된다면,**
  - Nexus의 역할은 단순한 양자 네트워킹용 광학 부품 공급업체에서 끝나지 않을 수 있다.
  - 양자 네트워킹을 넘어 **고속 광통신 시장까지 확장할 수 있는 선택지**가 생기기 때문이다.
  - 그리고 그 과정에서 Nexus가 DSP·SerDes·FEC·Ethernet interface까지 처음부터 모두 자체 개발할 필요도 없다.
  - Broadcom 같은 업체들은 이미 그 영역에서 필요한 기술과 제품 스택을 갖추고 있다.
  - 따라서 중요한 질문은

    - **“Nexus가 1.6T를 혼자 만들 수 있느냐?”**가 아니라,
    - **“Nexus의 optical layer가 Broadcom 같은 기존 네트워크 생태계와 결합할 수 있느냐?”**에 더 가까울지도 모른다.

**📌 내가 보는 가장 흥미로운 가설은 이것이다**

- - **IonQ가 Nexus를 인수한 이유가 단순히 자신의 QPU를 광자로 연결하기 위해서만은 아닐 수도 있다.**

    - Nexus가 양자 네트워킹의 optical layer를 담당하고,
    - SkyWater가 이를 반복 생산 가능한 semiconductor platform으로 만들며,
    - Broadcom·AMD·ARM 같은 기존 computing ecosystem과 연결된다면,
  - IonQ는 장기적으로 **Quantum과 Classical 양쪽에 걸쳐 광학 기술을 공급하는 Pick-and-Shovel 구조**를 만들 수도 있다.
  - 이 구조에서는 Nexus가 반드시 완제품 광트랜시버 업체가 될 필요도 없다.
  - 오히려 핵심 optical engine, modulator, laser, detector, PIC 같은 기반 기술을 제공하면서,
  - Broadcom 같은 업체가 DSP·SerDes·Ethernet switching을 담당하는 형태가 더 자연스러울 수도 있다.
  - NVIDIA가 NVQLink를 통해 \*\*“GPU와 QPU를 연결하는 인터페이스”\*\*를 장악하려 한다면,
  - IonQ가 Nexus를 통해 노릴 수 있는 것은 그보다 한 단계 아래에서 실제 광자가 이동하고 신호가 변환되는 **physical optical layer**일 수도 있다.
  - 다시 말해,

    - NVIDIA가 **컴퓨팅 시스템 간 연결 규격**을 잡으려 한다면,
    - IonQ는 Nexus와 SkyWater를 통해 **그 연결을 실제로 구현하는 광학적 기반**을 잡으려는 그림도 생각해볼 수 있다.
  - 아직은 어디까지나 가설이다.
  - 현재 공개된 정보만으로 Broadcom·Nexus·SkyWater가 1.6T 광통신 제품을 공동 개발한다고 말할 수는 없다.
  - 다만 Broadcom이 이미 가지고 있는 1.6T급 DSP·SerDes·Ethernet 기술과 Nexus의 100GHz+ 광학 기술을 함께 놓고 보면,
  - 지난번 슬라이드에서 보았던 **Broadcom·AMD·ARM·Nexus라는 조합이 이전과는 조금 다르게 보이기 시작한다.**
  - 어쩌면 핵심은 1.6T 자체가 아니라,

    - **양자 네트워크와 고전 네트워크가 결국 하나의 시스템 안에서 만나는 순간,**
    - **그 접점을 누가 가장 먼저 장악하느냐**
    - 에 있을지도 모른다.
