# QSPM의 진짜 기술적 경쟁력은 탐지 센서가 아니라 배포 구조에 있는가?

Published: 2026-11-01T18:32:20+11:00

Original Naver post: https://blog.naver.com/4-fire/224461209664?fromRss=true&trackingCode=rss

---

**✅ PQC 탐지, CBOM, DPI, ERSPAN, Elisity 컨테이너 심층 분석**

- - **핵심 질문:** 양자내성암호(PQC) 전환이 필요한 기업 자산을 찾으려면 네트워크 패킷을 수집해야 한다. Palo Alto Networks와 Zscaler는 자사 플랫폼을 통과하는 트래픽을 볼 수 있고, Forescout는 별도의 센서와 패킷 수집을 활용한다. 그렇다면 IonQ가 인수하기로 발표한 Elisity는 기존 스위치와 Virtual Edge(VE), ERSPAN만으로 탐지의 음영지역을 줄이면서 새로운 물리 하드웨어를 최소화할 수 있을까?
  - **이번 글의 분석 범위:** PQC 탐지 원리, TLS·SSH·VPN에서 실제로 식별할 수 있는 정보, SPAN/RSPAN/ERSPAN, Forescout·Palo Alto·Zscaler의 관측 범위, Elisity의 VEN·VE 구조, Cisco IOx App Hosting의 실제 선례, 멀티벤더 확장과 개발 난이도, 운영비용·검증 조건까지 순서대로 다룬다.
  - **가장 중요한 구분:** 제조사 문서로 확인된 **상용 기능**과 IonQ·Elisity가 앞으로 구현할 수 있는 **기술적 제안**을 혼동하지 않는다. 이 글에서 설명하는 Elisity의 내장형 QSPM DPI 센서는 아직 출시·성능이 검증된 제품으로 취급하지 않는다.
  - **기준일:** 2026년 11월 1일. 공식 공개문서와 지금까지의 기술 토론을 기초로 작성한 분석이며, 실제 고객망에서 측정한 벤치마크는 아니다.

**✅ 1. QSPM과 PQC 탐지, CBOM은 각각 무엇인가?**

**📌 PQC 탐지는 암호를 직접 깨는 기술이 아니다**

- - **PQC(Post-Quantum Cryptography)**는 장래의 충분히 강력한 양자컴퓨터에도 견디도록 설계한 암호기술을 가리킨다. 대표적인 표준으로 ML-KEM(키 설정), ML-DSA·SLH-DSA(전자서명)가 있다.
  - **Cryptographic Discovery**는 기업의 서버·네트워크 장비·애플리케이션·인증서·보안 모듈이 현재 어떤 암호 알고리즘을 사용하거나 지원하는지 발견하는 과정이다.
  - **QSPM(Quantum Security Posture Management)**은 이렇게 발견한 암호자산을 양자 취약성, 중요도, 업무 영향, 전환 상태와 연결해 지속적으로 관리하려는 플랫폼 개념이다. 제조사마다 제품 범위가 다르며 QSPM이라는 명칭만으로 특정 탐지 기능을 보장하지 않는다.
  - **CBOM(Cryptography Bill of Materials)**은 제품·서비스 안에 어떤 암호 알고리즘, 라이브러리, 인증서, 키 관리 의존성이 존재하는지 기록한 암호자산 명세다. **네트워크에서 관찰한 TLS 연결 목록만으로 완전한 CBOM이 만들어지는 것은 아니다.**
  - **마이크로세그멘테이션**은 허용되지 않은 통신을 제한하는 접근통제 기술이다. RSA·ECDHE 통신을 제한할 수는 있어도 그 암호 알고리즘 자체를 ML-KEM으로 자동 교체하지는 못한다.

| --- | --- | --- | --- |
| **구분** | **핵심 질문** | **필요 데이터** | **산출물** |
| 네트워크 자산 발견 | 이 IP/MAC는 어떤 장비인가? | ARP·SNMP·DHCP·CMDB·Flow | 장비 인벤토리 |
| 암호 사용 발견 | 실제 통신에 어떤 알고리즘이 쓰였는가? | TLS·SSH·IKE 패킷, 방화벽·프록시 로그 | 관측된 암호 사용 |
| 암호 지원능력 확인 | 업데이트하면 PQC를 사용할 수 있는가? | OS·라이브러리·펌웨어·벤더 지원정보 | Quantum-ready 후보 |
| CBOM 구축 | 어느 앱·인증서·코드·키에 무엇이 연결돼 있는가? | 네트워크 + 호스트·코드·PKI·HSM | 암호자산·종속관계 목록 |
| QSPM | 어디부터 바꾸고 무엇이 아직 위험한가? | CBOM + 위험정보 + 업무 중요도 | 우선순위·변경·검증·감사 |
| 정책 집행 | 전환 전 불필요한 접근을 막을 수 있는가? | IdentityGraph·정책·스위치 ACL | 위험 완화·접근 제한 |

**📌 사용 가능(Ready)과 실제 안전(Safe)은 다르다**

- - **지원(Offered/Capable):** 클라이언트나 라이브러리가 X25519MLKEM768을 제공할 수 있다. 이 사실만으로 현재 연결이 PQC를 사용한다는 뜻은 아니다.
  - **실제 협상(Negotiated):** 서버와 클라이언트가 특정 세션에서 어떤 키 설정 알고리즘을 선택했는지의 증거다. 제안한 알고리즘과 실제 선택된 알고리즘을 별도로 기록해야 한다.
  - **부분 전환:** TLS 키 설정은 하이브리드 PQC로 바뀌었어도 서버 인증서의 서명 알고리즘은 RSA 또는 ECDSA일 수 있다. 키 설정과 인증서 서명은 별도 평가 대상이다.
  - **미관측(Unknown):** 한 번도 통신을 본 적 없는 장비를 PQC 안전이라고도 취약이라고도 단정하면 안 된다. 탐지 범위와 신뢰도를 함께 표시해야 한다.

**📌** **PQC가 필요한 장비는 어떻게 찾아낼까?**

- - 핵심은 생각보다 간단하다.
  - 보안시스템이 장비를 찾아다니면서 "너는 양자컴퓨터에 안전하니?"라고 직접 질문하는 것이 아니다.
  - 대신 현재 사용 중인 암호기술을 조사한 뒤 양자 취약성이 있는지 판단한다.
  - 이때 실제로는 서로 다른 네 가지 방법을 조합한다.

    - ① 패킷 감시 — Passive Discovery

      - 통신을 옆에서 관찰해 TLS·SSH 등의 암호 협상정보를 분석한다. SPAN·TAP·ERSPAN을 사용하는 방식이다.
    - ② 기존 보안장비의 로그 수집

      - 방화벽이나 보안 프록시가 이미 관찰한 TLS·VPN 정보를 가져온다. 별도 SPAN이 필요하지 않을 수 있다.
    - ③ 서버·장비에 직접 질문 — Active Discovery

      - 스캐너가 TLS·SSH 연결을 시도하거나 장비 관리 API로 설정과 소프트웨어 버전을 확인한다.
    - ④ 내부 소프트웨어 조사 — Configuration/Code Analysis

      - 서버의 암호 라이브러리, 인증서, 소스코드, HSM 설정 등을 조사한다. 네트워크 패킷만으로는 보이지 않는 정보를 찾는다.
  - 이 네 가지는 경쟁업체의 제품명이 아니라 실제로 암호자산을 발견하는 기술적 방법이다.

**✅ 2. DPI는 무엇을 분석하는가? TLS 1.3 사례로 이해하기**

**📌 NetFlow와 DPI가 보는 정보는 다르다**

- - **NetFlow·IPFIX**는 출발지·목적지 IP, 포트, 프로토콜, 바이트 수, 연결 시각 등 흐름 메타데이터를 제공한다. 일반적인 Flow 레코드만으로 TLS 키 교환이 ECDHE인지 ML-KEM인지 구분할 수 없다.
  - **DPI(Deep Packet Inspection)**는 패킷의 상위 프로토콜 구조를 해석한다. TLS ClientHello와 ServerHello, SSH 키 교환 메시지, IKE 협상정보 같은 실제 프로토콜 필드를 분석하는 방식이다.
  - **핵심:** TLS 1.3에서 키 교환 그룹을 알아내기 위해 반드시 HTTPS 애플리케이션 데이터를 복호화할 필요는 없다. 공개되는 초기 핸드셰이크의 관련 필드를 분석할 수 있기 때문이다.
  - **다만:** TLS 1.3 인증서 메시지 등 핸드셰이크 일부는 암호화된다. 패시브 센서가 보았다는 이유만으로 모든 인증서 서명·호스트 내부 키 사용까지 알 수 있는 것은 아니다.

|  |  |  |  |
| --- | --- | --- | --- |
| **순서** | **통신 메시지** | **센서가 알 수 있는 정보** | **예시 판단** |
| ① | ClientHello | 클라이언트가 제안한 지원 그룹과 key\_share | X25519와 X25519MLKEM768 제안 |
| ② | ServerHello | 실제로 선택된 키 교환 그룹 | X25519 선택 → 이 세션의 키 설정은 고전 방식 |
| ③ | 서버 인증·애플리케이션 통신 | TLS 1.3에서는 상당 부분 암호화돼 별도 정보 필요 | 키 교환만으로 서명 안전성까지 판정 불가 |
| ④ | CBOM·QSPM 기록 | 원본 자산과 증거 시각, 관측 지점, 신뢰도 연결 | 서버 A: TLS Key Exchange = Classical |

**📌 실제 찾아야 할 TLS·SSH·VPN 정보**

- - **TLS:** 버전, 지원·실제 협상 키 교환 그룹, 가능한 경우 인증서의 공개키·서명 알고리즘, 서비스·서버·클라이언트 역할.
  - **SSH:** KEX 알고리즘, 호스트키·서명 알고리즘, 암호화·MAC 알고리즘. 접속 정책과 실제 지원 알고리즘의 차이도 중요하다.
  - **IKE/IPsec:** VPN 종단 장비가 협상한 키 설정·인증 관련 정보. WAN에 보이는 IPsec 터널의 바깥쪽 정보와 터널 내부 애플리케이션의 TLS 사용을 구분해야 한다.
  - **QUIC/HTTP/3:** UDP/443을 사용하는 QUIC에도 TLS 1.3 핸드셰이크가 포함되지만, TCP 기반 TLS 파서만으로 같은 수준의 분석을 할 수는 없다. 별도의 QUIC 프로토콜 처리가 필요하다.
  - **예시 표준:** IETF RFC 10024는 X25519MLKEM768, SecP256r1MLKEM768, SecP384r1MLKEM1024 세 가지 하이브리드 TLS 1.3 키 설정 그룹을 정의한다. 알고리즘의 식별 자체는 표준화된 코드 포인트를 인식하는 문제이기도 하다.

**✅ 3. 실제 암호자산 발견은 네 가지 방법을 조합해야 한다**

|  |  |  |  |  |
| --- | --- | --- | --- | --- |
| **방법** | **데이터 수집 경로** | **물리 센서 필수?** | **장점** | **고유한 한계** |
| 패시브 DPI | SPAN/TAP/ERSPAN → 패킷 분석기 | 아니오: VM·내장 컨테이너 가능 | 실제 사용된 프로토콜을 관찰 | 센서가 못 본 세션은 누락 |
| 인라인 장비 로그 | NGFW·프록시·VPN 종단의 텔레메트리 | 기존 장비 재활용 가능 | 기존 장비와 고객 운영체계 활용 | 장비를 거치지 않는 경로는 누락 |
| Active Scan | 서버·장비에 TLS/SSH 연결 시도, 인증 관리 인터페이스 조회 | 일반 VM이면 가능 | SPAN 없이 지원 능력·설정 확인 | 실제 모든 연결·코드 사용을 알 수 없음 |
| 구성·코드·API 분석 | OS·PKI·HSM·EDR·CMDB·소스·빌드 자료 | 대개 물리 센서 불필요 | 저장·내부 호출 등 패킷 밖 영역 보완 | 접근권·벤더 API·에이전트 등 필요 |

- - **가장 흔한 오해:** "PQC 탐지에는 반드시 하드웨어 센서가 있어야 한다"는 설명은 지나친 일반화다. **실제 통신을 수동으로 분석하려면 관측 지점과 패킷 처리 자원**이 필요하지만, 그것이 반드시 새로운 물리 어플라이언스일 필요는 없다.
  - **또 다른 오해:** "SPAN만 하면 모든 암호자산을 발견한다" 역시 틀리다. 소스코드 서명, 저장 데이터 암호화, 장비 내부의 암호 라이브러리·HSM 키는 패킷이 전혀 없을 수도 있다.
  - **현실적인 목표:** 트래픽·설정·자산·코드의 서로 다른 증거를 결합해 관측률, 확인 범위, 미확인 영역까지 함께 보여주는 것이다.

**✅ 4. 왜 WAN 한 곳만 SPAN하면 전사 PQC 탐지가 안 되는가?**

- - **WAN 구간에서 잘 보이는 것:** 그 구간을 실제 통과하는 인터넷·전용회선·Site-to-Site 통신이다. WAN이 IPsec이면 내부 TLS 트래픽이 터널로 가려질 수 있다.
  - **병원 내부 동일 VLAN:** 의료기기와 PACS 서버가 액세스·집선망 내부에서만 통신하면 인터넷 방화벽의 로그나 WAN SPAN에는 나타나지 않는다.
  - **데이터센터 East-West:** ToR 스위치 내부 또는 Leaf 간 처리되는 서버 통신은 인터넷 NGFW를 통과하지 않을 수 있다.
  - **동일 하이퍼바이저/컨테이너 호스트:** vSwitch·가상 브리지·Pod 사이에서 종단되는 트래픽은 물리 스위치에 도착하지 않을 수 있다. 물리 스위치 ERSPAN만으로는 볼 수 없다.
  - **장기간 휴면 장비:** 비상복구용 서버나 간헐적으로 작동하는 의료기기에는 관측할 TLS 세션이 없을 수 있다. Active Scan과 설정 조회가 필요하다.
  - **보안이 강화된 터널:** IPsec·MACsec 등의 외부에서 원시 패킷만 수집하면 내부 프로토콜은 가려질 수 있으므로 복호화 이후 지점이나 해당 터널 종단의 메타데이터가 필요하다.

|  |  |  |
| --- | --- | --- |
| **트래픽 사례** | **WAN SPAN만 설치** | **추가로 필요한 관측 위치/방법** |
| 사용자 → 인터넷 SaaS | 경유하면 일부 볼 수 있음 | ZIA/NGFW 로그, TLS 프록시 양측 협상 확인 |
| CT → 같은 병원의 PACS | 경로가 WAN 밖이면 누락 | 액세스·집선 스위치, 현장 VM 또는 능동 검사 |
| 서버 A → 데이터센터 DB | WAN을 안 지나면 누락 | 서버 ToR/Leaf, 내부 방화벽, 애플리케이션 설정 |
| VM ↔ 같은 ESXi의 VM | 물리망 미경유 시 누락 | vSwitch/하이퍼바이저·호스트 텔레메트리 |
| 병원 A ↔ 병원 B IPsec | 터널 바깥쪽만 보일 수 있음 | VPN 종단 메타데이터 또는 복호화 후 관측 |
| HSM 내부에서 서명 | 대부분 판단 불가 | HSM 관리 API·키 인벤토리·애플리케이션 분석 |

**✅ 5. Forescout — 네트워크 센서 중심의 PQC 위험 발견**

**📌 eyeSentry에서 eyeFocus까지 이어지는 경로**

- - **상용제품 확인:** Forescout eyeSentry는 네트워크 에지에서 Active·Passive Sensor를 제공하고, eyeSentry 26.2.3 문서는 TLS·SSH 핸드셰이크의 key share·암호화·키 교환 알고리즘을 파싱하는 PQC DPI 개선사항을 명시한다.
  - **패시브 경로:** 스위치의 SPAN·TAP·ERSPAN 등으로 복제한 패킷을 eyeSentry의 관측 인터페이스에 전달하고, DPI 엔진이 암호 필드를 추출한다.
  - **능동 경로:** Active Sensor는 SNMP, WMI/WinRM, OT 프로토콜 등으로 장비 정체와 상태를 보완한다. 모든 자산 식별 기능에 SPAN이 필수인 것은 아니다.
  - **중앙 분석:** eyeFocus의 PQC Exposure Assessment는 위험 자산의 수, 관측된 Post-Quantum Capable 사용, 프로토콜 취약점, 준비도 추세를 대시보드로 묶는다.
  - **하드웨어에 관한 주의:** 2026년 eyeSentry 공식 안내에는 지원되는 4130·6120·6140·6160 물리 어플라이언스가 구체적으로 열거돼 있다. 따라서 "Forescout는 무조건 VM만 있으면 된다"고 표현해서는 안 된다. 제품·센서 배포 모델마다 지원범위를 구분해야 한다.

|  |  |  |  |
| --- | --- | --- | --- |
| **구성요소** | **역할** | **추가 관측범위** | **남는 문제** |

| eyeFocus PQC Dashboard | 자산별 위험·양자보안 지표 집계 | 위험관리·추세·보고 | 센서 입력의 완전성에 의존 |

**📌 Forescout의 실제 한계와 장점**

- - **장점:** 특정 벤더 방화벽을 통과하지 않는 내부 트래픽에도 별도 센서를 배치할 수 있고, OT·IoMT 자산 식별 기술 및 Active Sensor로 장비 정보를 보완한다.
  - **한계:** 패킷 미러링이 없는 경로, 동작하지 않는 장비, 로컬 VM 내부 통신, 암호화된 터널 내부, 소스코드의 암호 호출은 별도의 수단이 없으면 누락될 수 있다.
  - **판단:** Forescout가 "모든 포트를 SPAN해야 작동하는 플랫폼"이라는 해석은 맞지 않는다. 반면 **패킷 DPI가 필요한 암호 협상 발견 범위는 센서 관측 지점의 제약을 받는다.**

**✅ 6. Palo Alto Networks — NGFW를 분산형 암호정보 센서로 활용**

**📌 방화벽이 이미 보는 패킷을 재활용한다**

- - **수집 구조:** NGFW·Prisma Access에서 SSL/TLS·SSH·VPN 텔레메트리를 만들고 Strata Logging Service로 모은 뒤 Quantum-Safe Security 애플리케이션에서 분석한다.
  - **동적 CBOM:** 키 교환, 알고리즘, 인증서, 애플리케이션, 단말·장비의 OS·암호 라이브러리 버전 등을 연결해 암호 의존성을 관리한다. 방화벽 정보 외에 지원되는 타사 API 커넥터도 활용한다.
  - **SPAN이 필요하지 않은 이유:** 방화벽이 해당 패킷의 인라인 처리 지점이기 때문이다. 일반적으로 별도 미러링 포트를 구축할 필요 없이 방화벽 로그에서 암호정보를 얻을 수 있다.
  - **가시성의 경계:** 방화벽을 통과하지 않는 동일 VLAN·데이터센터 East-West·호스트 내부 통신의 모든 암호 사용이 자동으로 발견되는 것은 아니다.
  - **별도 유료 조건:** Quantum-Safe Security 라이선스, 관리형 NGFW/Prisma Access, 장비 텔레메트리 등 공식 제품요건이 있다. "이미 NGFW가 있으면 아무 비용도 없이 가능"하다는 뜻은 아니다.

**📌 Palo Alto의 특별한 차이 — Cipher Translation**

- - **QSPM 탐지 이후 조치:** PAN-OS 12.1 이상의 NGFW가 TLS 프록시가 되어 일부 구형 클라이언트나 서버의 외부 구간을 하이브리드 PQC 방식으로 보호하는 Cipher Translation 기능이 문서화돼 있다.
  - **Forward Proxy:** 레거시 클라이언트 → NGFW 구간은 기존 TLS로 남을 수 있고, NGFW → 외부 서버 구간에 PQC를 적용할 수 있다.
  - **Inbound Proxy:** 외부 클라이언트 → NGFW 구간은 PQC를 적용하면서 NGFW → 기존 내부 서버 구간은 Classical TLS로 유지할 수 있다.
  - **주의:** 이는 프록시 양쪽에 서로 다른 보안경계가 생기는 구조다. 원래 서버의 암호 라이브러리와 내부 모든 통신을 PQC로 직접 교체했다는 뜻이 아니다.
  - **근거:** [Quantum-Safe Security 공식 설명](https://docs.paloaltonetworks.com/strata-cloud-manager/navigation/insights-scm/quantum-safe-security) · [운영·라이선스 요건](https://docs.paloaltonetworks.com/network-security/quantum-security/administration/quantum-safe-security) · [지원 커넥터](https://docs.paloaltonetworks.com/network-security/quantum-security/administration/quantum-safe-security/connect-third-party-data-sources/supported-connectors)

**✅ 7. Zscaler — 인터넷·SaaS TLS 관측에는 유리하지만 내부망 전체를 뜻하지 않는다**

**📌 ZIA와 ZPA를 구분해야 한다**

- - **ZIA의 주된 관측 대상:** 사용자·지점·서버에서 Zscaler Internet Access의 Public Service Edge를 경유하는 인터넷·SaaS 접속이다. 공식 PQC Visibility Report 메뉴 자체가 Internet & SaaS / Web Activity 아래에 있다.
  - **ZPA의 존재:** Zscaler Private Access는 사설 애플리케이션 접근을 중계한다. 다만 **ZIA PQC Visibility Report와 동일한 암호 알고리즘 인벤토리를 ZPA가 제공한다는 근거는 별도로 확인하지 못했다.**
  - **클라우드 프록시의 강점:** 원래 기업에 ZIA 경유 구조가 있다면 각 액세스 스위치에 새로운 SPAN을 설정하지 않아도 해당 웹 트랜잭션의 PQC 사용 통계를 얻을 수 있다.
  - **근본적 한계:** PACS→DB, VM→VM, 내부 Site-to-Site 통신이 ZIA를 거치지 않으면 ZIA의 PQC 보고서에서는 보이지 않는다.

**📌 제안한 알고리즘과 실제 협상된 알고리즘을 혼동하면 안 된다**

- - **Client→Zscaler:** 클라이언트가 제안한 PQC/Hybrid 키 설정과 실제 협상 알고리즘을 기록할 수 있다.
  - **Zscaler→외부 서버:** 프록시가 서버와 별도로 협상하는 TLS 키 교환·서명 알고리즘 정보가 남는다.
  - **주의할 통계:** 공식 리포트의 일부 "PQC" 분류는 **클라이언트가 PQC 또는 Hybrid를 제안했는가**를 기준으로 한다. 실제로 서버 구간까지 PQC로 협상된 비율과 동일하지 않다.
  - **결론:** ZIA는 기업 웹 트래픽에서 상당히 유용한 관측 지점이지만, ZIA 로그만으로 전사 CBOM이 완성됐다고 말해서는 안 된다.
  - **근거:** [ZIA PQC Visibility Report](https://help.zscaler.com/zia/viewing-post-quantum-cryptography-visibility-report) · [ZIA 웹 로그의 실제 PQC 필드](https://help.zscaler.com/legacy-zia/nss-feed-output-format-web-logs)

**✅ 9. SPAN·RSPAN·ERSPAN은 어떻게 다르며, 멀티벤더에서 통할까?**

**📌 세 종류의 미러링을 분리하면 이해가 쉽다**

|  |  |  |  |
| --- | --- | --- | --- |
| **구분** | **SPAN** | **RSPAN** | **ERSPAN** |
| 패킷 복사본 전달 | 같은 장비의 물리 포트 | L2로 연결된 전용 VLAN | IP 라우팅망 위의 GRE 캡슐화 |
| L3 라우팅망 통과 | 일반적으로 불가능 | 일반적으로 불가능 | 가능 |
| 분석기 위치 | 스위치 근처의 캡처 포트 | RSPAN VLAN이 닿는 L2 구간 | 원격 VM/서버 또는 지원되는 내장 앱 |
| 추가 부담 | 로컬 포트·미러링 자원 | 전용 VLAN·L2 트래픽 | 추가 GRE 헤더·WAN/스위치 대역폭 |
| QSPM 활용 | 로컬 DPI 센서 | 같은 L2 영역 센서 | 분산 스위치 → 지역/중앙 분석기 |

- - **ERSPAN(Encapsulated Remote SPAN)**은 원본 패킷의 복사본을 IP/GRE 패킷 안에 넣어 다른 네트워크의 분석기까지 전달한다. 원래 업무 트래픽을 중단하거나 경로를 바꾸는 기능은 아니다.
  - **ERSPAN 자체는 암호화가 아니다.** GRE로 전송되는 복사 패킷에는 민감한 내부 패킷 내용이 포함될 수 있다. 고객망 전체에 무차별로 미러링을 보내면 프라이버시·보안·성능 위험이 발생한다.
  - **멀티벤더 호환:** Cisco뿐 아니라 Arista EOS, 일부 Juniper·HPE Aruba CX 장비와 NVIDIA Cumulus Linux에도 ERSPAN 또는 GRE 기반 원격 미러링이 존재한다. 그러나 모델·ASIC·펌웨어·캡슐화 Type·수신 측 디캡슐레이션 지원이 서로 다르다.
  - **특히 Arista:** 공식 EOS 설명에 ACL을 적용한 ingress filtered mirroring과 GRE 터널 목적지가 명시된다. 다만 모든 플랫폼과 방향에서 동일한 필터가 지원되는 것은 아니다.
  - **Juniper:** ACX7000의 ERSPAN 문서에는 미러링 대상이 논리 인터페이스로 지정돼도 실제 물리 인터페이스 전체가 복제되는 제약 등 모델별 예외가 소개돼 있다.
  - **HPE Aruba:** AOS-CX는 원격 미러링용 destination tunnel을 지원하지만 일부 관리 포트·터널 중첩·ASIC 조합에 제한이 있다.

|  |  |  |
| --- | --- | --- |
| **제조사·제품군** | **공식 문서로 확인된 기능** | **검증할 항목** |
| Cisco Catalyst / IE | ERSPAN, 일부 IOx App Hosting과 내장 센서 | ERSPAN 버전·IOx 자원·AppGigabitEthernet·SSD |
| Arista EOS | GRE 터널 목적지와 일부 ACL 미러링 | ASIC·EOS 버전·세션 수·RX/TX 필터 |

**📌 ERSPAN이 있으면 WAN 부담도 사라질까?**

- - **아니다.** ERSPAN은 패킷을 전달하는 방법일 뿐, TLS 핸드셰이크만 자동으로 뽑아내는 기술은 아니다. 선택적 소스 포트·VLAN·ACL 필터링이 없다면 대량의 일반 페이로드도 함께 복사될 수 있다.
  - **미러링 트래픽이 누락될 수 있는 이유:** 목적지 대역폭 제한, 스위치 미러링 리소스, 큐 혼잡, MTU, 필터 방향 제한, 패킷 손실, 캡슐화 비호환성 등이 있다.
  - **보다 나은 방향:** 로컬 컨테이너에서 패킷의 프로토콜 필드를 해석하고, 원본 패킷 전체가 아니라 **암호 협상 메타데이터만 중앙 플랫폼에 전달**한다면 원격 ERSPAN의 대역폭과 개인정보 유출 위험을 줄일 수 있다.
  - **현장 선택:** 모든 것을 중앙 데이터센터에 모으는 한 가지 방식보다 사이트별 로컬 컨테이너·지역 VM·기존 NGFW 로그·Active Scan을 조합하는 것이 합리적이다.

**✅ 10. Elisity의 VEN과 VE는 같지 않다 — 이 구분이 가장 중요하다**

**📌 VEN은 패킷을 처리하는 새 어플라이언스가 아니다**

- - **VEN(Virtual Edge Node):** Elisity에 온보딩된 기존 스위치의 정책 집행 지점을 뜻한다. 스위치의 기존 ASIC·ACL·보안 기능을 통해 통신을 허용하거나 제한한다.
  - **VE(Virtual Edge):** 클라우드 정책 플랫폼과 현장 네트워크 사이의 제어·연동 기능을 수행한다. 하이퍼바이저에서 컨테이너/VM 방식으로, 일부 지원 Cisco 스위치에서는 App Hosting 컨테이너 방식으로 배포할 수 있다.
  - **현재 제품 원칙:** Elisity는 자사 VEN이 데이터를 별도의 패킷 처리 경로로 끌어들이지 않는다고 설명한다. 기존 데이터플레인은 스위치에 그대로 남는다.
  - **중요한 한계:** VEN이 NetFlow·장비 신원정보를 수집한다고 해서 TLS ClientHello·ServerHello의 키 설정 그룹까지 읽고 있다는 뜻은 아니다. **PQC DPI에는 추가 패킷 파서 또는 다른 데이터 소스**가 필요하다.
  - **따라서 구상해야 할 것은:** VEN을 그대로 DPI 엔진으로 변환하는 일이라기보다 **VE와 같은 기존 제어 플랫폼에 내장형 DPI 컨테이너 또는 외부 센서 결과를 연결하는 일**이다.

**✅ 11. Eilisity를 통한 PQC 탐지 기능 구현 아키텍처**

**📌 Cisco Cyber Vision은 이미 유사한 접근을 사용한다**

- - **공식 구축 절차 확인:** Cisco Cyber Vision은 일부 Catalyst 9300/9400의 IOx App Hosting 환경에 센서 애플리케이션을 실행하고, 스위치에서 ERSPAN으로 복제한 패킷을 AppGigabitEthernet을 통해 내부 센서로 전달하는 구성을 문서화했다.
  - **즉, 이론적인 주장만은 아니다.** "기존 스위치에서 패킷을 복사해 스위치 안의 컨테이너가 분석한다"는 데이터 경로 자체는 구현 선례가 존재한다.
  - **하지만 소유주체가 다르다.** Cisco Cyber Vision 센서가 지원하는 것과 Elisity VE에 PQC DPI를 추가할 수 있다는 것은 별개 문제다. 기술적 유사성은 충분하지만 제품 간 공동 배포·자원 공유·인증 여부는 공개자료로 확인되지 않는다.
  - **또한 IOx가 일반 목적 서버와 동급의 패킷 처리 용량을 제공한다는 뜻도 아니다.** CPU·메모리·저장장치·내부 애플리케이션 인터페이스가 분석 규모를 제한할 수 있다.
  - **근거:** [Cisco Cyber Vision: ERSPAN → IOx 센서 구성](https://www.cisco.com/c/en/us/td/docs/security/cyber_vision/publications/Switches/Release-4-2-0/b_Cisco_Cyber_Vision_Sensor_Application_for_Cisco_Switches_Installation_Guide/m_initial-configuration_switches.html) · [Cisco 산업망 Cyber Vision 구성 예시](https://www.cisco.com/c/en/us/td/docs/solutions/Verticals/Industrial_Automation/Manufacturing_AI/dual-fabric-vplc.html)

**📌 제안 아키텍처 A — 스위치 내부에 소형 PQC 파서를 배치**

|  |  |  |
| --- | --- | --- |
| **처리 단계** | **기존 네트워크에서 실행되는 작업** | **중앙 플랫폼으로 보내는 데이터** |
| 1. 정상 패킷 전달 | 기존 스위치 ASIC이 업무 트래픽을 계속 전달 | 업무 패킷 자체는 중앙으로 보내지 않음 |
| 2. 선택적 미러링 | 관심 포트·VLAN·트래픽을 IOx 쪽으로 복사 | 로컬 미러링 복사본 |
| 3. 내장형 DPI 컨테이너 | TLS/SSH의 핸드셰이크·알고리즘 필드만 분석 | IP, 포트, 알고리즘, 관측시각, 증거 등 |
| 4. VE·IdentityGraph 통합 | 장비의 역할·자산 ID와 암호 위험을 연결 | 정규화된 위험정보·CBOM 일부 |
| 5. 중앙 QSPM | 위험도·전환현황·정책 우선순위 계산 | 개인정보를 최소화한 암호 메타데이터 |

- - **가능한 효과:** 고객망의 모든 원본 패킷을 WAN이나 데이터센터에 보내지 않고, 현장에서 암호 협상 메타데이터만 추출해 전송할 수 있다면 데이터 이동량을 크게 줄일 여지가 있다.
  - **새 물리 하드웨어 절감:** 해당 장비가 필요한 CPU·메모리·스토리지·라이선스를 이미 갖추고 있다면 별도 센서 서버 구매를 피할 가능성이 있다.
  - **잠재적 단점:** 기존 Elisity VE와 추가 DPI 컨테이너를 동시에 실행하려면 자원 충돌·애플리케이션 격리·고가용성·업그레이드·장애 동작·보안패치 체계를 검증해야 한다.
  - **주의:** App Hosting이 없는 스위치를 컨테이너 호스트로 만들기 위해 새로운 물리 스위치로 교체한다면 처음 목표였던 저비용 배포의 장점이 사라질 수 있다.

**📌** **제안 아키텍처 B — 로컬 컨테이너가 불가능하면 ERSPAN과 지역 VM**

- - **외부 VM도 새로운 물리 센서와는 다르다**

    - **문제 상황:** Arista 스위치나 Cisco의 일부 VEN 지원 모델에서 ERSPAN은 가능하지만 스위치 내부에서 Elisity VE 또는 DPI 컨테이너를 실행할 수 없는 경우를 생각해 보자.
    - **대안:** 네트워크 지역 또는 데이터센터에 이미 존재하는 가상화 서버에서 소형 DPI 분석 VM/컨테이너를 실행하고, 스위치들이 선택적으로 ERSPAN 패킷을 보내도록 한다.
    - **장점:** 전용 물리 어플라이언스를 현장마다 신규 설치할 필요가 없고, 여러 스위치의 패킷을 지역별 VM 하나로 모아 운영할 수 있다.
    - **한계:** 기존 가상화 자원을 재사용하더라도 CPU·메모리·가상 NIC·스토리지·ERSPAN 전송 대역폭과 운영 비용은 발생한다. 모든 트래픽을 한 VM으로 보내면 성능과 가시성 모두 나빠질 수 있다.
    - **구현상 주의:** ERSPAN Type II/III, GRE 프로토콜 값, VTEP/VRF, MTU, 미러링 방향을 수신 분석기가 정확히 해석해야 한다. 패킷 필터·스트림 재조립이 부족하면 TLS 세션 시작을 놓칠 수 있다.
  - **아키텍처 A와 B가 해결하지 못하는 마지막 음영지역**

    - **동일 ESXi 호스트 내 VM↔VM:** 물리 ToR에서 복사할 패킷이 없다. vSwitch·게스트 OS·서비스 메시의 메타데이터를 추가로 수집해야 한다.
    - **PKI·HSM·코드 서명:** 암호정보는 장비 내부에서만 사용될 수 있다. 인증서 관리·HSM·코드 저장소·빌드 파이프라인과 연동해야 한다.
    - **휴면·비정기 장비:** Passive DPI만으로는 충분한 관측 시점을 기다려야 한다. 안전한 범위의 Active Scan과 벤더별 설정 조회가 필요하다.
    - **암호화 터널 안의 서비스:** ERSPAN으로 보낸 패킷에도 보통 원래 IPsec/TLS 암호화는 유지된다. 그 내부의 알고리즘을 반드시 볼 수 있다는 뜻은 아니다.
    - **결론:** 컨테이너와 ERSPAN으로 **물리 센서 배치의 공백**은 상당 부분 줄일 수 있으나 **암호자산 탐지의 모든 음영지역**을 해결하는 만능 수단은 아니다.

**📌** **제안 아키텍처 C — 하드웨어를 추가하지 않는 데이터 융합 방식**

|  |  |  |  |
| --- | --- | --- | --- |
| **우선순위** | **정보원** | **주요 수집 내용** | **대부분의 경우 필요한 것** |
| 1 | Elisity IdentityGraph·기존 NetFlow | 자산·업무·통신 관계 | 기존 CCC·VE·VEN 배포 |
| 2 | NGFW·프록시·VPN API | 이미 관찰된 TLS·SSH·IKE 협상 | 기존 장비의 API·로그·라이선스 |
| 3 | Active TLS/SSH Scan | 지원 알고리즘·인증서·서비스 구성 | 일반 관리 VM, 스캔 정책 |
| 4 | 스위치 내장 DPI 컨테이너 | 실제 관찰된 내부 TLS·SSH 협상 | 지원 모델·App Hosting·미러링 |
| 5 | ERSPAN → 지역 DPI VM | 내장 컨테이너 미지원 영역 | 기존 VM 및 네트워크 여유자원 |
| 6 | PKI·HSM·SBOM·코드·EDR·CMDB | 숨은 암호 의존성과 실제 소유자 | API 권한·분석도구·운영조직 |
| 7 | 필요 시 물리 TAP/센서 | 그외 관측 불가능한 중요 구간 | 신규 장비는 최후의 선택 |

- - **이 구조의 핵심:** 가능한 한 기존 고객이 이미 구매한 스위치, 보안장비, 가상화 인프라, 인증서 관리 체계를 재사용한다.
  - **기술적 전략:** 소프트웨어를 하나의 데이터 수집 방식에 묶지 않고 패킷·로그·설정·코드 자료를 **IdentityGraph의 동일 자산 ID**에 연결한다.
  - **정보의 품질 관리:** 자료마다 "실제로 관찰함 / 설정을 확인함 / 지원 가능성만 추정함 / 아직 미확인"의 증거 수준을 반드시 별도로 기록한다.
  - **정책 집행:** QSPM이 위험도를 높게 평가하더라도 자동으로 광범위한 차단을 시행하기보다, 업무 중요도와 통신 종속관계를 확인하고 시뮬레이션·승인을 거쳐 제한적으로 집행하는 편이 안전하다.
  - **전환의 한계:** IdentityGraph와 DPE가 접근을 차단해도 실제 암호 교체는 PKI·애플리케이션·서버·네트워크 장비의 별도 작업을 요구한다.

**📌 여기서 비용과 가시성을 동시에 측정해야 한다**

- - **물리 장비 수:** 신규 어플라이언스 수만 세면 안 된다. SSD, CPU/메모리 증설, 추가 스위치, 라이선스, 가상화 비용, WAN 전송량도 포함해야 한다.
  - **관측률:** 전체 자산 중 암호 사용이 실제 관찰된 자산 비율뿐 아니라 **중요 애플리케이션·통신 경로 중 확인되지 않은 비율**도 별도로 계산해야 한다.
  - **정확도:** PQC 지원 여부와 실제 사용 여부를 혼동했거나 TLS 1.3 인증서 서명을 잘못 판정한 사례를 측정해야 한다.
  - **안전성:** SPAN 변경이 업무 트래픽을 방해하지 않는지, 패킷 분석 앱 과부하가 스위치 제어 기능에 영향을 주지 않는지, 센서 장애 시 업무 패킷 전달이 유지되는지 검증해야 한다.

**✅ 13. 이 방식이 실제로 어려운 이유 — 패킷 파서보다 기업망 제품화가 어렵다**

**📌 개발 난이도는 최소 네 단계로 나누어야 한다**

|  |  |  |  |  |
| --- | --- | --- | --- | --- |
| **단계** | **필요한 개발** | **상대 난이도** | **독자적 가치** | **현재 Elisity와 연결할 때** |
| ① TLS·SSH 파서 PoC | 알고리즘 코드 인식, 핸드셰이크 재조립 | 낮음~중간 | 기본 암호 발견 | 별도 모듈로 추가할 수 있음 |
| ② 자산별 암호 위험·CBOM | 여러 출처 정규화, 자산 매핑, 증거 관리 | 중간~높음 | 운영자에게 유용한 지속적 인벤토리 | IdentityGraph 기반 활용 가능 |
| ③ 분산 센서의 현장 운영 | IOx/VM·ERSPAN, HA, 업그레이드, 패킷 손실 | 높음 | 새 물리장비 최소화와 확장성 | VE/VEN·지원 스위치 재사용이 관건 |
| ④ 전사적 QSPM 전환관리 | PKI/HSM·코드·클라우드·전환 검증·감사 | 매우 높음 | 지속적 보안 운영 서비스 | 외부 파트너·독자 IP 통합 필요 |

- - **1단계가 상대적으로 쉬운 이유:** TLS·SSH의 메시지 구조와 하이브리드 키 설정 그룹은 표준화돼 있다. 오픈소스 프로토콜 분석기·TLS 스캔 라이브러리도 활용할 수 있다.
  - **3단계부터 난도가 올라가는 이유:** 센서의 정확도 외에도 고객망 수백 개의 이기종 스위치, 수만 대 자산, 서로 다른 IOS/EOS, 관리망 ACL, MTU, 방화벽 정책, 장애복구를 다뤄야 하기 때문이다.
  - **App Hosting 확장이 별도의 제품 개발인 이유:** VEN 지원 모델을 늘리는 것과 VE 컨테이너를 실행할 수 있는 모델을 늘리는 것은 별도 과제다. 여기에 원시 패킷을 내부 애플리케이션에 전달하는 기능까지 검증해야 한다.
  - **자체 개발과 연동의 선택:** 암호 발견 기능을 외부 제품에서 API로 가져오면 출시를 앞당길 수 있지만 독자 IP와 원가·라이선스 협상의 유연성은 제한될 수 있다. 직접 개발하면 통제력이 커지는 대신 운영 부담이 늘어난다.

**📌 개발기간에 대한 조건부 추정**

|  |  |  |
| --- | --- | --- |
| **목표** | **기술적 추정 기간** | **필요 전제** |
| TLS/SSH 탐지 PoC | 약 1~3개월 | 숙련 인력, 기존 파서 재사용, 소수 프로토콜 |
| 기존 로그 + IdentityGraph QSPM 대시보드 | 약 3~6개월 | 데이터 API 접근권, 기존 자산 그래프 활용 |
| 로컬 IOx·ERSPAN/VM 센서의 베타 운영 | 약 9~18개월 | 선정한 스위치 모델, 보안·성능 테스트 |
| 대규모 기업용 멀티벤더 배포 | 약 12~24개월 이상 | 지원 매트릭스, 원격 운영·장애복구·다수 고객 PoC |
| 코드·PKI·HSM을 포함한 광범위한 QSPM | 2~4년 이상도 가능 | 전문 인력·파트너·고객별 통합 범위 |

- - **위 기간은 공식 일정이나 산업 평균이 아니다.** 이미 확보한 코드·인력·외부 제품·고객망 조건에 따라 크게 변할 수 있는 예시적 엔지니어링 추정이다. 일부 과제는 병렬로 진행할 수 있다.
  - **IonQ의 현재 위치:** 회사는 2026년 9월 QSPM을 고객에게 제공한다고 설명했지만, 실제 암호탐지 엔진이 자체 개발인지, 외부 연동인지, VEN·IOx 내장형인지 공개자료만으로 확인되지 않는다.
  - **인수의 의미:** IonQ·Elisity의 과제는 단순한 표준 프로토콜 파서 자체보다, 자산 그래프·정책 집행·멀티벤더 현장 배포를 얼마나 자연스럽게 통합하느냐에 있을 가능성이 크다.

**✅ 15. NIST 전환 일정과 QSPM 사업의 지속성**

- - **수요의 배경:** NIST는 2026년 10월 27일 IR 8547 최종본을 발표해 양자 취약 공개키 암호에서 PQC로 옮기기 위한 전환 방향을 정리했다.
  - **미국 연방 중요 시스템:** 키 설정은 2030년, 디지털 서명은 2031년의 앞당겨진 전환 목표가 제시되며, 2035년은 광범위한 연방 전환의 주요 목표다. 일반 민간기업의 모든 RSA/ECC 사용을 같은 날짜에 일률적으로 금지한다고 해석해서는 안 된다.
  - **첫 번째 수요:** 아직 어디에 어떤 암호가 사용되는지 모르는 기업은 암호자산의 초기 발견·우선순위·PQC 전환 프로젝트를 구매할 수 있다.
  - **두 번째 수요:** 앱·인증서·장비·코드가 계속 바뀌므로 CBOM을 최신 상태로 유지하고 새로 발생한 Classical 암호 사용을 추적하는 **Crypto-Agility** 관리가 장기 운영 서비스로 이어질 가능성이 있다.
  - **그러나:** 규제 전환 수요가 일회성 프로젝트로 끝나거나 기존 대형 보안 플랫폼에 기능이 흡수된다면 독립적인 QSPM 제품의 가격 경쟁력이 약화될 수도 있다.
  - **따라서 IonQ의 인수 논리는:** 일회성 대시보드를 추가하는 것보다, 기존 Elisity 고객에게 지속적인 암호 사용 발견·자산위험 분석·정책 통합 서비스를 낮은 추가 배포비용으로 제공하는 데 있다.
  - **공식 근거:** [NIST IR 8547 최종 발표](https://www.nist.gov/news-events/news/2026/10/nist-report-provides-guidelines-transition-post-quantum-cryptography) · [NIST IR 8547 원문 안내](https://csrc.nist.gov/pubs/ir/8547/final)

**✅ 16. IonQ는 실제로 무엇을 개발하고 있는가? — 핵심 엔지니어 채용으로 역추적한 QSPM 전략**

- - 지금까지 Forescout, Palo Alto Networks, Zscaler의 PQC 탐지 기술을 비교하고, Elisity가 기존 스위치의 App Hosting과 ERSPAN을 활용해 추가 하드웨어와 탐지 사각지대를 줄일 가능성을 분석했다.
  - 그런데 여기서 한 가지 중요한 질문이 남는다.
  - **IonQ는 이러한 기업용 보안 플랫폼을 실제로 개발할 수 있는 조직과 인력을 갖추고 있을까?**
  - 이를 확인하기 위해 IonQ의 Quantum Platform – Network & Security 조직에 이미 합류한 엔지니어와 현재 공개된 기술 채용공고를 살펴봤다.
  - 그 결과, 단순히 PQC 관련 연구인력을 확보하는 수준을 넘어 **대규모 네트워크 발견, 실시간 텔레메트리, 보안정책 분석, 클라우드 SaaS, Agentic AI, 서비스 운영 자동화**를 담당하는 엔지니어링 조직이 형성되고 있다는 사실을 확인했다.

    - IonQ는 IdentityGraph에 암호자산과 암호 위험정보를 추가할 계획을 공식 발표했다.
  - 이러한 요소를 결합하면 다음과 같은 개발 방향을 생각해 볼 수 있다.
  - **App Hosting을 지원하는 스위치에는 가능한 범위에서 로컬 탐지 소프트웨어를 실행하고, 지원하지 않는 구간은 선택적으로 ERSPAN을 사용해 지역 VM 분석기로 전달하며, 나머지 공백은 장비 API·PKI·HSM·Active Scan으로 보완하는 방식이다.**
  - 이 구조가 실제로 구현된다면, 모든 네트워크 구간에 새로운 물리 센서를 설치하는 방식보다 추가 하드웨어를 줄일 가능성이 있다.
  - 또한 고객사에 이미 설치된 스위치와 기존 Elisity 관리체계를 활용하므로 배포·정책관리·운영 측면에서도 이점이 생길 수 있다.
  - 그러나 아직 확인되지 않은 기술적 문제는 분명하다.

|  |  |
| --- | --- |
| **검증해야 할 핵심 기능** | **현재 공개자료상 확인 여부** |
| 대규모 네트워크 텔레메트리 수집 플랫폼 개발 | 확인 |
| 보안정책·위험평가 엔진 개발 | 확인 |
| SaaS 기반 QSPM 품질 검증 직무 | 확인 |
| IdentityGraph 암호자산 정보 통합 로드맵 | 공식 발표로 확인 |
| 자체 TLS·SSH PQC DPI 엔진 | 미확인 |
| CBOM 생성 방식과 데이터 출처 | 미확인 |
| Elisity VEN·VE와 QSPM 수집기 통합 | 미확인 |
| 스위치 App Hosting 기반 PQC 탐지 컨테이너 | 미확인 |

| 실제 고객 환경의 암호자산 탐지율·사각지대 감소 | 미확인 |

- - 특히 **gNMI·SNMP 텔레메트리는 그 자체로 TLS·SSH 암호 협상 내용을 제공하는 DPI가 아니다.**
  - 또한 Kubernetes 기반 Cloud Container 개발 경험과 Cisco IOS-XE의 IOx App Hosting 센서 개발 경험도 동일하지 않다.
  - 따라서 이번 채용 분석은 QSPM 플랫폼의 기반 기술을 확보하고 있다는 근거는 되지만, 우리가 가정한 스위치 내장 PQC 탐지 방식의 실현을 입증하지는 못한다.

**📌 종합 판단 — 이제 개발 주체보다 기술 통합 여부가 중요하다**

- - 이번 인력과 채용공고 조사는 IonQ의 QSPM 전략을 해석하는 데 의미 있는 변화를 가져왔다.
  - 처음에는 IonQ가 암호탐지 소프트웨어를 자체 개발할 수 있을지, Elisity 인수 후 다른 회사의 기술을 도입해야 하는지가 주요 관심사였다.
  - 그러나 현재 공개된 인력을 보면 **IonQ는 이미 네트워크 장비 관리, 분산 데이터 처리, 클라우드 SaaS, 보안정책 분석, AI 운영 자동화 분야의 전문 엔지니어링 조직을 구성하고 있다.**
  - 더욱 중요한 것은 Elisity의 IdentityGraph에 암호자산과 암호 위험정보를 통합하겠다는 공식 로드맵이다.
  - 이제 질문의 핵심은 누가 PQC 탐지 엔진을 만드는가보다 **그 탐지 결과를 기존 네트워크 관리·정책 집행 플랫폼에 얼마나 효율적으로 연결할 수 있는가**로 이동한다.
  - 그 과정에서 우리가 앞서 검토한 App Hosting, ERSPAN, 기존 VM, 장비 API 등을 활용한 하드웨어 최소화 전략은 기술적으로 검토할 가치가 있다.
  - 다만 진정한 경쟁력을 판단하려면 새로운 하드웨어가 얼마나 적게 필요한지만 볼 것이 아니라, **실제 암호자산 탐지 범위, 놓치는 트래픽의 비율, 수집 정확도, 스위치 성능 영향, 고객별 배포비용, 운영 안정성**까지 검증해야 한다.
  - **현재 확인된 가장 중요한 사실은 IonQ가 기업용 네트워크 보안 SaaS를 개발할 인력과 아키텍처 역량을 적극적으로 확보하고 있으며, Elisity의 기존 IdentityGraph에 암호자산 위험정보를 추가하는 방향을 공식화했다는 점이다.**
  - **아직 검증해야 할 가장 중요한 가설은 이 기술들이 기존 네트워크 인프라를 최대한 재활용하면서 PQC 탐지 사각지대와 구축비용을 동시에 줄이는 하나의 통합 플랫폼으로 발전할 수 있는가이다.**
  - 이것이 향후 IonQ의 QSPM 기술 경쟁력을 평가할 때 추적해야 할 핵심이다.

**✅ 17. 종합 판단 — 정말 획기적이려면 무엇이 입증돼야 할까?**

**📌 긍정적 가설:** **수집 위치의 장벽을 낮추면 사업의 성격이 달라질 수 있다**

- - **기존 경쟁구도:** Forescout는 센서를 배치해야 하는 구간에 유연하게 들어갈 수 있지만 수집 인프라가 필요하다. Palo Alto와 Zscaler는 기존 보안장비를 지나는 트래픽을 효율적으로 분석하지만 그 밖의 통신은 별도 방법이 필요하다.
  - **Elisity가 활용할 자산:** 이미 관리하는 멀티벤더 스위치와 자산·정책 그래프다. Cisco 일부 모델은 VE 컨테이너를 호스팅할 수 있고, 스위치 내부 IOx 센서로 ERSPAN을 전달하는 Cisco Cyber Vision 선례도 있다.
  - **기술적 제안:** App Hosting이 가능한 모델에는 경량 암호 파서, 지원하지 않는 모델에는 선택적 ERSPAN→지역 VM, 패킷 밖 영역에는 Active Scan·API를 결합한다.
  - **기대효과:** 대규모 별도 물리 센서 구매를 줄이면서 암호 사용의 실제 관측 범위를 확대할 수 있다면, 기존 Elisity의 "새로운 하드웨어 설치 최소화"라는 장점을 QSPM까지 확장할 여지가 생긴다.
  - **그러나 혁신성은 아직 가설이다:** 이 아키텍처가 경쟁사보다 더 낮은 TCO, 높은 탐지 커버리지, 더 적은 운영 장애를 보인다는 동일 조건의 고객 PoC는 공개적으로 확인되지 않는다.

**📌 특히 세 가지 질문을 다시 확인해야 한다**

- - **① 실제로 얼마나 많은 VEN이 내장형 분석을 실행할 수 있는가?**

    - VEN 지원 범위와 App Hosting/DPI 실행 가능 범위는 다르다. 고객이 이미 보유한 스위치 중 몇 %에서 실제 구현되는지가 관건이다.
  - **② 패킷 전체가 아닌 암호정보만 수집할 수 있는가?**

    - 스위치 내장형 분석에서 TLS·SSH의 필요한 필드를 안정적으로 추출하고 중앙에는 메타데이터만 전송해야 대역폭·프라이버시·운영비용상 이점이 커진다.
  - **③ 남아 있는 음영지역을 얼마나 명시적으로 관리할 수 있는가?**

    - 전혀 보지 못한 자산을 "안전"으로 표시하지 않고 미관측 상태로 기록하며, Active Scan·PKI·HSM·코드 도구로 보완할 수 있어야 한다.
  - **최종 결론:** IonQ가 QSPM을 어느 자회사에서 개발하는지는 투자·기술 평가의 핵심이 아닐 수 있다. 보다 중요한 것은 **기존 Elisity 네트워크 인프라를 이용해 추가 하드웨어 비용을 얼마나 줄이고, 관측할 수 없던 기업 내부 암호 사용을 얼마나 더 발견할 수 있는가**다.
  - **현재 확인된 사실:** Elisity의 VE/VEN, 일부 Catalyst의 App Hosting, Cisco Cyber Vision의 내장 센서, 여러 벤더의 원격 미러링, 경쟁사의 PQC 탐지 기능은 각각 실재한다.
  - **아직 확인되지 않은 사실:** Elisity가 위 요소들을 결합한 독자적인 QSPM DPI 센서를 상용화했는지, 해당 센서가 어느 스위치에서 어떤 처리량으로 동작하는지, 그리고 경쟁업체보다 나은 비용·탐지율을 보이는지는 확인되지 않았다.
  - **만약 입증된다면:** Elisity의 가치는 단순히 "PQC 탐지 기능을 추가한 마이크로세그멘테이션 업체"가 아니라, 기존 스위치 설치 기반을 활용해 **기업 전체의 양자 취약 암호를 지속적으로 발견·관리·완화하는 플랫폼**으로 재평가할 여지가 있다.
  - **따라서 다음에 확인할 증거는:** 기능 발표 문구가 아니라 실제 지원 스위치 목록, IOx/ERSPAN 센서 배포 방식, 정확한 암호 탐지 범위, 추가 라이선스 비용, 고객별 센서 수, 미관측률, 정책 집행까지의 검증 결과다.

**✅ 용어 정리 — 핵심 네트워크·보안 개념**

|  |  |
| --- | --- |
| **용어** | **의미** |
| PQC | 양자내성 공개키 암호기술의 통칭 |
| QSPM | 기업 암호자산의 양자 취약성을 발견·평가·전환 관리하는 플랫폼 개념 |
| CBOM | Cryptography Bill of Materials. 암호 알고리즘·라이브러리·키·인증서·의존성 명세 |
| DPI | Deep Packet Inspection. 패킷 내부 프로토콜 필드까지 해석하는 기술 |
| Passive Discovery | 실제 네트워크 통신을 관찰해 정보를 얻는 방식 |
| Active Scan | 대상 장비에 직접 연결·질의해 설정이나 지원 기능을 확인하는 방식 |
| SPAN | 스위치가 선택한 포트·VLAN의 패킷 복사본을 로컬 수신 지점으로 전송 |
| RSPAN | L2 전용 VLAN을 통해 다른 스위치까지 미러링 패킷 전송 |
| ERSPAN | IP/GRE 캡슐화로 원격 분석기까지 미러링 패킷 전송 |
| VE / VEN | Elisity의 제어·연동 구성요소(VE)와 기존 스위치 기반 정책 집행 지점(VEN) |
| IOx / App Hosting | 지원 Cisco 스위치 안에서 컨테이너 애플리케이션을 실행하는 기능 |
| HNDL | Harvest Now, Decrypt Later. 현재 수집한 암호 데이터를 미래에 복호화하려는 위협 |
| Crypto-Agility | 암호 알고리즘·라이브러리·키·정책을 지속적으로 교체·전환할 수 있는 역량 |
| Quantum Ready | PQC를 사용할 수 있는 기술적 준비 상태(제품별 정의에 주의) |
| Quantum Safe | 실제 통신·서비스에서 충분한 양자내성 보호가 적용된 상태(범위별 검증 필요) |
