# Q54, Q70, Q102 — IonQ는 왜 하나의 양자 오류정정 코드 대신 세 개를 만들었을까?

Published: 2026-08-30T13:52:26.015000+09:00

Original Naver post: https://blog.naver.com/4-fire/224394947524

---

**✅ Walking Cat을 보다 보면 이상한 이름들이 계속 등장한다**

- - Walking Cat Architecture를 보다 보면 Q54, Q70, Q102라는 이름이 반복해서 등장한다.
  - 처음에는 이 숫자가 각각 Memory, Magic Factory, Cat Factory를 뜻하는 것처럼 보일 수 있다.
  - 하지만 실제로는 전혀 다르다.
  - Q54, Q70, Q102는 모두 qLDPC quantum error-correcting code의 특정 인스턴스다.
  - 반면:
  - Memory

    - MEK Factory
    - CH2 Factory
    - Cat Factory
  - 는 각각 그 양자컴퓨터 안에서 수행해야 하는 기능이다.
  - 즉 가장 먼저 다음 둘을 분리해야 한다.

**📌 Code와 Factory는 다른 층이다**

- - Q54 / Q70 / Q102

    - 논리큐비트를 어떻게 physical qubit에 encoding하고 보호할 것인가를 정하는 코드
  - Memory / MEK / CH2 / Cat Factory

    - 그 보호된 qubit을 어떤 목적으로 사용할 것인가를 정하는 기능
  - 비유하면 Q54, Q70, Q102는 서로 다른 종류의 공장 건물이고, Memory·MEK·CH2는 그 건물 안에 어떤 생산라인을 설치할 것인가에 가깝다.

---

**✅ [70,6,9]라는 숫자부터 이해해보자**

**📌 Q70 = [70,6,9]**

- - 70개의 physical data qubit을 이용해서
  - 6개의 logical qubit을 만들고
  - code distance는 9인 구조다.
  - 같은 방식으로:

|  |  |  |  |  |
| --- | --- | --- | --- | --- |
| **Code** | **Physical qubits** | **Logical qubits** | **Distance** | **대략적인 성격** |
| Q54 | 54 | 2 | 10 | H 연산 특화 |
| Q70 | 70 | 6 | 9 | 빠른 logical operation |
| Q102 | 102 | 22 | 9 | 높은 logical density |

- - 즉 숫자가 커질수록 무조건 좋은 코드라는 뜻이 아니다.
  - 각각 무엇에 최적화했는지가 다르다.

**📌 비유**

- - 자동차도 스포츠카, SUV, 트럭이 모두 자동차지만 목적이 다르다.
  - Q54, Q70, Q102도 모두 logical qubit을 보호하는 qLDPC code지만:

    - Q54는 특수 작업에 강하고
    - Q70은 빠르고 유연하며
    - Q102는 많은 logical qubit을 싣는 데 강하다.

---

**✅ Q70 — Walking Cat의 스포츠카**

**📌 Q70의 가장 중요한 특징은 Fast Clifford다**

- - Q70은 [70,6,9] BB7 code다.
  - 70개의 physical qubit으로 6개의 logical qubit을 encoding한다.
  - 숫자만 보면 Q102보다 logical density가 낮다.
  - 하지만 대신 굉장히 중요한 장점이 있다.
  - Q70은 6개의 logical qubit에 대한 Clifford operation을 매우 자유롭게 Clifford-frame tracking으로 처리할 수 있다.
  - Walking Cat에서는 실제 physical logical gate를 모두 수행하지 않고 상당 부분을 software상의 frame update로 넘길 수 있기 때문에 이것이 매우 큰 장점이 된다.

**📌 비유**

- - 일반 자동차는 방향을 바꾸려면 실제 핸들을 돌려야 한다.
  - Q70은 가능한 많은 작업을 실제 자동차를 움직이지 않고 내비게이션의 좌표계만 바꿔 처리하는 것과 비슷하다.
  - 그래서 실제 quantum hardware가 해야 할 일을 크게 줄일 수 있다.

---

**✅ 그래서 Q70은 Memory와 Magic Factory를 모두 맡을 수 있다**

**📌 Q70을 Memory로 쓰면**

- - 70 physical qubits → 6 logical qubits → 계산용 logical data를 저장한다.

**📌 그런데 같은 Q70을 MEK Factory로 쓰면**

- - 같은 6개의 logical qubit 공간에서 MEK magic-state distillation protocol을 실행할 수 있다.
  - 그 결과 T gate에 사용할 두 개의 고품질 logical H state를 얻는다.
  - 즉 같은 Q70 block을 상황에 따라 Memory 또는 Magic Factory로 사용할 수 있다.

**📌 비유**

- - 평소에는 승객을 나르는 버스인데,
  - 필요할 때 내부 좌석을 접고 화물차로 바꿀 수 있는 차량이라고 생각하면 된다.
  - 같은 hardware를 계산 상황에 맞게 Memory와 Magic Factory 사이에서 재배치할 가능성이 생긴다.
  - Walking Cat이 이를 Single-Code Architecture라고 부르는 이유도 여기에 있다.

---

**✅ MEK — Q70을 위해 만들어진 프로토콜은 아니다**

**📌 MEK는 IonQ가 만든 것이 아니다**

- - MEK는 Meier, Eastin, Knill의 이름을 딴 기존 magic-state distillation protocol이다.
  - 기본적인 아이디어는 여러 개의 noisy H state를 받아 더 적은 수의 훨씬 깨끗한 H state를 만드는 것이다.
  - 대표적으로:

|  |
| --- |
| **10 noisy H states**  **↓**  **MEK**  **↓**  **2 higher-fidelity H states** |

- - 구조다.

**📌 IonQ가 새롭게 한 것은 MEK + Q70 조합이다**

- - MEK 자체는 기존 기술이다.
  - 하지만 MEK에는 여러 Clifford operation이 필요하다.
  - Q70은 바로 이 Clifford operation을 매우 싸게 처리하는 데 특화되어 있다.
  - 따라서:

|  |
| --- |
| **MEK protocol**  **+**  **Q70의 Fast Clifford 특성**  **↓**  **Walking Cat의 MEK Factory** |

- - 라는 상당히 자연스러운 조합이 만들어진다.

---

**✅ 그럼 MEK는 반드시 Q70에서만 돌아가는가?**

**📌 아니다**

- - MEK는 protocol이고 Q70은 그 protocol을 실행하는 code다.
  - 따라서 **MEK ≠ Q70**이다.
  - 필요한 logical qubit 수와 Clifford operation을 지원하는 다른 code에서도 MEK를 구현할 수 있다.
  - 다만:

    - logical gate 비용
    - logical measurement 비용
    - error rate
    - decoding overhead
  - 등을 고려하면 Walking Cat에서는 Q70이 매우 좋은 선택이었던 것이다.

**📌 비유**

- - MEK는 요리법이고 Q70은 주방이다.
  - 같은 요리를 다른 주방에서도 만들 수 있다.
  - 하지만 그 요리에 필요한 장비가 가장 잘 갖춰진 주방이 Q70이었던 것이다.

---

**✅ Q54 — logical density는 낮지만 H 하나만큼은 특별하다**

**📌 Q54 = [54,2,10]**

- - 54개의 physical qubit을 사용하면서 logical qubit은 2개밖에 만들지 못한다.
  - Encoding rate만 보면 상당히 낮다.
  - Memory 용도로만 보면:

    - Q70은 70 → 6
    - Q102는 102 → 22
    - Q54는 54 → 2
  - 이므로 매력적이지 않다.
  - 그런데 Q54에는 다른 코드가 쉽게 제공하지 못하는 매우 특별한 성질이 있다.

**📌 Strongly Transversal H**

- - Q54에서는 physical qubit 전체에 H gate를 transversal하게 적용하면:

    - H⊗54
  - logical level에서:

    - H̄ ⊗ H̄
  - 로 동작한다.

**📌 비유**

- - Q54는 승객을 두 명밖에 태우지 못하는 자동차다.
  - 그래서 택시로는 형편없다.
  - 그런데 특수 장비를 실으면 다른 차로는 할 수 없는 일을 아주 쉽게 할 수 있다.
  - 즉 Q54는 승객 수가 아니라 특수 기능 때문에 선택된 차량이다.

---

**✅ 그리고 바로 이 특징이 CH2와 완벽하게 맞는다**

**📌 CH2는 무엇을 하는가**

- - CH2는 두 개의 logical H magic state를 준비하고 이 둘을 함께 검증하는 Walking Cat의 magic-state protocol이다.
  - 대략:

|  |
| --- |
| **두 개의 logical H state 준비**  **↓**  **H̄ ⊗ H̄ 측정**  **↓**  **두 state를 동시에 검증**  **↓**  **두 개의 고품질 H state 출력** |

- - 구조다.

**📌 그런데 Q54는 H̄ ⊗ H̄를 아주 자연스럽게 제공한다**

- - Q54 자체가 두 logical qubit을 encoding하고
  - physical H⊗54가 logical H̄⊗H̄와 연결되기 때문에
  - CH2가 원하는 연산과 Q54의 transversal property가 절묘하게 맞아떨어진다.
  - 그래서:

|  |
| --- |
| **Q54**  **+**  **Strongly transversal H**  **+**  **2 logical qubits**  **↓**  **CH2 Factory** |

- - 라는 조합이 만들어진다.

---

**✅ 그렇다고 CH2 = Q54인 것도 아니다**

**📌 CH2도 protocol이다**

- - CH2 protocol과 CH2-in-Q54 implementation은 구분해야 한다.
  - 논문이 설명하는 조건을 만족하는 다른 [n,2,d] code가 있고 strongly transversal H를 제공한다면 이론적으로 CH2를 다른 code에서도 구현할 수 있다.

**📌 하지만 Q54가 상당히 매력적인 이유**

- - CH2 verification에서는 큰 cat state가 필요하다.
  - Code 크기가 커지면 cat state 역시 커질 수 있다.
  - 예를 들어:

    - Q54 → 54-qubit cat
    - 가상의 Q100 → 100-qubit cat
  - 이라면 code가 커질수록 verification 부담도 커진다.
  - Q54는:

    - 비교적 작은 n
    - distance 10
    - strongly transversal H
  - 를 동시에 가진다.

**📌 비유**

- - CH2라는 작업에는 특정 모양의 공구가 필요하다.
  - 다른 공구로도 가공할 수는 있지만 매우 복잡해진다.
  - Q54는 애초에 그 작업에 꼭 맞는 전용 공구를 가진 작업대에 가깝다.

---

**✅ Q102 — Walking Cat의 창고**

**📌 Q102 = [102,22,9]**

- - Q102의 가장 큰 장점은 단순하다.
  - 102 physical qubits → 22 logical qubits
  - Encoding rate는 약 21.6%다.
  - 비교하면:

    - Q54 ≈ 3.7%
    - Q70 ≈ 8.6%
    - Q102 ≈ 21.6%
  - logical information을 많이 저장하는 데 압도적으로 유리하다.

**📌 비유**

- - Q70이 스포츠카라면 Q102는 대형 물류창고다.
  - 순간적인 기동성보다 같은 공간에 얼마나 많은 정보를 넣을 수 있는지가 중요하다.

---

**✅ 하지만 Q102는 Q70만큼 자유롭게 움직이지 못한다**

**📌 Density에는 대가가 있다**

- - Q70은 logical width 6 범위에서 Clifford operation을 매우 자유롭게 frame-track할 수 있다.
  - 반면 Q102의 22 logical qubit을 모두 같은 방식으로 자유롭게 다루면 logical Pauli representative의 physical weight가 너무 커질 수 있다.
  - 그래서 Walking Cat에서는 Q102의 직접적인 logical interaction width를 제한한다.
  - 결과적으로 Q102는 높은 density대신 상대적으로 제한된 logical connectivity/operation flexibility를 가진다.

**📌 결국**

- - Q70 = Fast
  - Q102 = Dense
  - 라는 trade-off가 생긴다.

---

**✅ 세 코드의 역할이 이제 보인다**

|  |  |  |  |
| --- | --- | --- | --- |
|  | **Q54** | **Q70** | **Q102** |
| Code | [54,2,10] | [70,6,9] | [102,22,9] |
| Family | GB8 | BB7 | GB8 |
| Logical qubits | 2 | 6 | 22 |
| Encoding rate | 약 3.7% | 약 8.6% | 약 21.6% |
| 가장 큰 강점 | Transversal H | Fast Clifford | High Density |
| Memory | 가능하지만 비효율적 | 핵심 용도 | 핵심 용도 |
| MEK Factory | 기본 구성 X | 적합 | 기본 구성 X |
| CH2 Factory | 매우 적합 | 기본 구성 X | 기본 구성 X |
| Walking Cat 역할 | Magic specialist | Fast architecture | Dense architecture |

---

**✅ 그런데 Cat Factory는 이 표에 같이 넣으면 오히려 헷갈린다**

**📌 Cat Factory는 Q54/Q70/Q102 같은 logical code block이 아니다**

- - Cat Factory는 logical data를 장기간 저장하는 곳이 아니다.
  - Magic state를 만드는 곳도 아니다.
  - 그 역할은 logical Pauli measurement에 사용할 physical cat state를 만드는 것이다.
  - 만들어진 cat state는:

|  |
| --- |
| **Cat Factory**  **↓**  **Q70 Memory**  **또는**  **Q102 Memory**  **또는**  **Q54 CH2 Factory**  **↓**  **Cat-Based Measurement** |

- - 에 사용된다.

**📌 비유**

- - Q54/Q70/Q102가 자동차라면 Cat Factory는 자동차가 아니다.
  - 차량을 검사하기 위한 이동식 진단장비를 생산하는 공장에 가깝다.

---

**✅ Cat State의 크기도 대상 코드에 따라 달라진다**

- - Cat Factory가 항상 같은 크기의 cat state를 만드는 것도 아니다.
  - 측정하려는 logical operator의 physical weight에 맞춰 필요한 크기가 달라진다.
  - Walking Cat에서 제시된 최대값의 예는 다음과 같다.

|  |
| --- |
| **Q54 일반 operation → 16**  **Q70 → 18**  **Q102 → 30**  **MEK/Q70 → 18**  **CH2/Q54 → 특별히 54** |

**📌 특히 CH2가 재미있다**

- - CH2는 H⊗54에 해당하는 검증 때문에 54-qubit cat state가 필요하다.
  - 즉 Q54 자체는 작은 code지만, 그 특수한 H verification 때문에 굉장히 큰 measurement probe를 요구한다.

---

**✅ 그래서 Walking Cat은 하나의 공장이 아니라 산업단지에 가깝다**

**📌 전체를 공장 비유로 연결해보자**

- - Q102 Memory

    - 대형 창고
    - 많은 logical qubit 저장
  - Q70 Memory

    - 고속 생산라인
    - logical operation을 빠르게 처리
  - Q70 MEK Factory

    - 기존 MEK 공정을 빠른 Q70 설비에 올린 magic-state 정제소
  - Q54 CH2 Factory

    - transversal H라는 특수 장비를 사용하는 전용 magic-state 공장
  - Cat Factory

    - 각 생산라인에서 사용할 measurement probe를 만드는 센서 공장
  - 그리고 이 모든 공장이 함께 만들어내는 최종 목적이 **Universal Fault-Tolerant Quantum Computation**이다.

---

**✅ 그런데 왜 Magic Factory가 그렇게 중요한가**

**📌 Clifford gate만으로는 Universal QC가 안 된다**

- - Clifford 연산만 사용하면 superposition과 entanglement도 만들 수 있다.
  - 하지만 state가 stabilizer 영역에 머물기 때문에 범용 양자계산에는 부족하다.
  - T 같은 non-Clifford resource가 이 영역 밖으로 나가게 해준다.

**📌 그래서 T gate가 비싸다**

- - Walking Cat에서는 Clifford operation 상당 부분을 software frame tracking으로 싸게 처리할 수 있다.
  - 그러나 T gate는 그렇게 처리할 수 없다.
  - T가 필요하면:

|  |
| --- |
| **Magic State 준비**  **↓**  **검증**  **↓**  **Q70 data와 logical measurement**  **↓**  **Outcome Decoder**  **↓**  **measurement-conditioned frame update**  **↓**  **T 구현** |

- - 이 필요하다.

**📌 즉 Magic Factory는 부속품이 아니다**

- - Magic Factory가 충분한 속도로 H state를 공급하지 못하면 T gate를 기다리느라 계산이 멈춘다.
  - 따라서 대규모 FTQC에서 magic-state throughput은 실제 computation throughput과 직접 연결된다.

---

**✅ MEK와 CH2는 같은 목적에 접근하는 서로 다른 길이다**

**📌 MEK**

- - 기존에 존재하던 distillation protocol
  - 많은 noisy magic state를 투입
  - 더 깨끗한 magic state 두 개 출력
  - Q70의 빠른 Clifford 특성과 잘 맞는다.

**📌 CH2**

- - Walking Cat에서 제안한 새로운 접근
  - 두 개의 logical H state를 준비
  - H̄⊗H̄를 직접 검증
  - Q54의 strongly transversal H와 잘 맞는다.

**📌 비유**

- - MEK는 원재료를 많이 넣고 반복 정제해서 순도를 올리는 정유공장에 가깝다.
  - CH2는 처음부터 특수 생산라인에서 제품을 만들고 강력한 품질검사를 거쳐 출하하는 공장에 가깝다.
  - 목적은 모두 고품질 magic state 생산이지만 생산 방식이 다르다.

---

**✅ IonQ가 정말 새롭게 만든 것은 무엇인가**

**📌 qLDPC라는 개념 자체는 IonQ 기술이 아니다**

- - Generalized Bicycle
  - Bivariate Bicycle
  - Hypergraph Product
  - 같은 code family는 기존 quantum coding 연구에서 발전해왔다.

**📌 하지만 Q54/Q70/Q102라는 구체적인 operating point는 Walking Cat에서 제시됐다**

- - Walking Cat 논문에서는:

    - Q54 = [54,2,10]
    - Q70 = [70,6,9]
    - Q102 = [102,22,9]
  - 를 이 architecture에 적합한 새로운 구체적 code instance로 제시한다.

**📌 프로토콜도 출처가 다르다**

- - MEK

    - 기존 학계의 protocol
  - MEK-in-Q70

    - Walking Cat식 implementation
  - CH2

    - Walking Cat에서 제안한 protocol
  - CH2-in-Q54

    - 그 protocol과 Q54의 특성을 결합한 실제 factory architecture

---

**✅ 이것은 앞으로도 Q54/Q70/Q102만 쓰겠다는 뜻이 아니다**

**📌 오히려 반대에 가깝다**

- - Walking Cat의 three-ring framework는 특정 하나의 code에 완전히 고정된 구조가 아니다.
  - GB, BB, cyclic-HGP 계열의 다른 compatible code를 넣을 수 있다.
  - 따라서 Q54/Q70/Q102는 최종적인 세 개의 고정 코드라기보다 **현재 발견된 매우 좋은 세 개의 operating point**로 보는 편이 적절하다.

**📌 비유**

- - 자동차 플랫폼을 먼저 만들고:

    - 스포츠 모델
    - 장거리 모델
    - 화물 모델
  - 을 올리는 것과 비슷하다.
  - 앞으로 더 좋은 code가 발견되면 새로운 모델을 추가할 수 있다.

---

**✅ 다른 회사도 Q54, Q70, Q102를 사용할 수 있을까**

**📌 수학적으로는 가능하다**

- - qLDPC code는 IonQ trapped-ion hardware에만 존재할 수 있는 수학이 아니다.
  - 공개된 code를 다른 연구진이:

    - simulation
    - decoder 연구
    - 다른 architecture에 적용
  - 하는 것은 기술적으로 가능하다.

**📌 하지만 상업적 이용은 다른 문제다**

- - 논문에 공개됐다는 사실과 상업적 사용권은 같은 이야기가 아니다.
  - Walking Cat의:

    - architecture
    - physical implementation
    - control
    - transport
    - factory 구성
  - 등에 별도의 지식재산권이 걸릴 수 있다.
  - 따라서:

    - 수학적으로 구현 가능
    - 상업적으로 자유롭게 사용 가능
  - 은 구분해서 볼 필요가 있다.

---

**✅ 결국 Walking Cat의 진짜 흥미로운 점은 “전문화”에 있다**

**📌 하나의 만능 code가 모든 일을 하는 구조가 아니다**

- - Q54는 H에 강하다.
  - Q70은 Clifford에 강하다.
  - Q102는 density에 강하다.
  - Cat Factory는 측정에 필요한 ancilla를 전문적으로 공급한다.
  - 그리고 필요한 계산에 따라 이들을 조합한다.

**📌 여기서 보이는 설계 철학**

- - 양자컴퓨터를 확장하는 방법이 반드시:

    - 더 큰 code 하나
    - 더 많은 physical qubit 하나
  - 만을 의미하지 않는다.
  - 오히려:

    - Memory에는 density가 좋은 code
    - 빠른 계산에는 Clifford가 좋은 code
    - Magic State 생산에는 transversal property가 좋은 code
    - measurement에는 전용 Cat Factory
  - 를 배치하는 식으로 역할을 전문화할 수 있다.

---

**✅ 개인적으로 Walking Cat에서 가장 흥미로운 부분**

- - 처음 Q54, Q70, Q102를 보면 단순히 숫자가 다른 qLDPC code 세 개처럼 보인다.
  - 하지만 각 코드를 어디에 배치했는지를 보면 IonQ가 FTQC를 바라보는 방식이 보인다.
  - Q102에 모든 것을 시키지 않는다.
  - Q70이 더 작다고 Q102의 하위 버전으로 취급하지 않는다.
  - Q54의 encoding rate가 낮다고 버리지도 않는다.
  - 각 코드가 가진 수학적 특징을 찾아 가장 잘하는 일을 맡긴다.

**📌 결국 이런 구조다**

- - Q102:

    - 많이 저장해라.
  - Q70:

    - 빨리 움직여라.
  - Q54:

    - H를 잘 처리해라.
  - Cat Factory:

    - 필요한 measurement probe를 계속 공급해라.
  - Magic Factory:

    - Universal QC를 가능하게 하는 비싼 non-Clifford resource를 끊임없이 공급해라.
  - 이렇게 보면 Walking Cat은 단순한 오류정정 코드 논문이라기보다, 서로 다른 qLDPC code와 factory를 역할별로 배치하는 **FTQC용 heterogeneous architecture**에 훨씬 가깝다.

---

**✅ 그리고 이 방향이 중요한 이유**

- - 오늘날 CPU 하나만 봐도:

    - CPU core
    - GPU
    - NPU
    - cache
    - memory controller
  - 가 모두 다른 역할을 맡는다.
  - 모든 작업을 하나의 범용 core에 몰아주는 것이 아니라, 각 작업에 가장 적합한 hardware를 붙이는 방식이다.
  - Walking Cat 역시 비슷한 방향으로 볼 수 있다.

    - 하나의 만능 logical block이 아니라
    - specialized logical blocks + specialized resource factories를 연결한다.
  - 그래서 Q54, Q70, Q102라는 숫자보다 더 중요한 것은:

> ***Walking Cat이 logical qubit을 하나의 균일한 자원으로 보지 않고, 계산·저장·Magic State 생산·measurement라는 서로 다른 업무에 맞춰 코드 자체를 전문화하고 있다는 점이다.***

- - 어쩌면 대규모 FTQC의 경쟁은 단순히 “누가 더 많은 logical qubit을 만들었는가”보다, **서로 다른 logical resource를 얼마나 효율적으로 배치하고 연결하는가**의 경쟁으로 넘어갈지도 모른다.

**📌 (b) Decoder가 늦으면 Stretch가 생긴다**

[![](https://mblogthumb-phinf.pstatic.net/MjAyNjA4MzBfMTA4/MDAxNzg4MDYzNzg4OTYw.qh1aMa-420L2eGUtCvClBgaj0xenMnoGTuKAs8LiNa8g.aj9Npxp_zZs6hAjnnn9a9waaY-C7QIgyYGReGU8By-kg.PNG/image.png?type=w800)](#)

- - Error Decoder는 5 SEC를 보지만 3 SEC마다 결과를 확정해야 한다.
  - decoding이 이 시간 예산보다 오래 걸리면 backlog가 생긴다.
  - backlog가 남아 있는 동안 logical operation은 진행하지 못하고, QEC를 유지하기 위한 stall SEC만 계속 실행한다.
  - 이 추가 지연 비율을 Stretch라고 한다.
  - 비유하면 주문 처리 속도보다 주문이 더 빨리 들어와 일이 밀리는 것과 같다.

**📌 (c) Error Decoder와 Outcome Decoder의 역할 분담**

[![](https://mblogthumb-phinf.pstatic.net/MjAyNjA4MzBfNTYg/MDAxNzg4MDYzODEyNTUz.rX7eNSOsjJMhz1ub_fronk-viX7mBYPVV15szXvUAUUg.bYUF7IggJ0KIm9gQ1JTQY5NvP4704x9pIcVZIG1FUhgg.PNG/image.png?type=w800)](#)

- - Error Decoder는 계산 전체 동안 계속 syndrome을 분석하며 Pauli frame을 유지한다.

    - 5 SEC window
    - 3 SEC commit
    - 정확도 우선
  - Outcome Decoder는 logical measurement가 발생할 때만 작동한다.

    - 2 SEC window
    - 1 SEC commit
    - 속도 우선
  - Cat measurement의 raw result ci 를 syndrome 정보와 함께 분석해 correction di 를 구하고, ci⊕di로 corrected logical outcome을 얻는다.
  - Viterbi는 이런 결과들을 반복해서 보고 충분히 확신이 생기면 measurement를 종료한다.
  - 비유하면 Error Decoder는 전체 사건을 조사하는 형사이고, Outcome Decoder는 지금 당장 교차로에서 진행 여부를 판단해야 하는 교통경찰이다.

**📌 (d) Physical error가 많을수록 Stretch도 커진다**

[![](https://mblogthumb-phinf.pstatic.net/MjAyNjA4MzBfMjYz/MDAxNzg4MDYzODI4NjMz.WOpH-ZhP9pw63RGIaf_7quSObpWdB_HlZwe3j_AfkR0g.g2xf0AoTVI96ow9ycEsUp4QAKILjOT3950khWPHTLAsg.PNG/image.png?type=w800)](#)

- - CNOT error rate가 증가할수록 syndrome이 많아지고 decoder가 처리해야 할 후보도 늘어난다.
  - 그 결과 backlog와 Stretch가 증가한다.
  - pCNOT=10−4에서는 Stretch가 대체로 매우 낮지만, 5×10−4에서는 MIPT와 Heisenberg n64가 약 10% 수준까지 증가한다.
  - Heisenberg n266이 408 logical qubit인데도 Stretch가 낮은 이유는 SEC 시간이 5 ms로, 102-logical-qubit case의 1 ms보다 decoder에게 5배 많은 시간이 주어졌기 때문이다.
  - 비유하면 더 큰 시험인데도 시험시간을 5배 더 주면 오히려 시간 부족이 덜할 수 있는 것과 같다.
