- - Elisity는 장비의 정체를 파악하고, 각 장비가 어떤 서버와 어떤 프로토콜로 통신하는지 분석하며, 이를 기반으로 접근제어 정책을 수립한다.
  - 그렇다면 이러한 정보는 실제 보안 사고에서 어떤 역할을 할까?
  - 가령 한 직원의 PC가 랜섬웨어에 감염되었다고 가정해 보자.
  - 공격자는 해당 PC에서 파일서버, 데이터베이스, 도메인 컨트롤러를 탐색하고 접근 권한을 확대하려 할 수 있다.
  - 기존 보안 시스템은 이러한 공격을 탐지하고 차단하려고 한다.
  - 그러나 Elisity는 여기에 다른 접근을 추가한다.

    - **공격을 발견하지 못했더라도, 감염된 PC가 원래 접근할 수 없었던 서버에는 도달하지 못하도록 사전에 통신 경로를 제한하는 것이다.**
  - 그리고 EDR과 같은 전문 보안 시스템에서 감염 사실을 확인했다면, 기존에 허용되었던 접근 권한마저 축소하는 동적 격리 정책을 구현할 수 있다.
  - 이번 글에서는 Elisity의 Policy Group, Security Profile, Policy Matrix, EDR 연동과 자동 격리 메커니즘을 살펴보고, 실제로 얼마나 빠르고 정확하게 대응할 수 있는지 분석하기로 한다.

**✅ 1. 랜섬웨어의 위험은 최초 감염에서 끝나지 않는다**

**📌 최초 감염과 내부 확산은 다른 단계다**

- - 랜섬웨어 공격은 일반적으로 피싱, 탈취된 계정, 취약한 원격 접속 서비스, 소프트웨어 취약점 등을 통해 시작될 수 있다.
  - 하지만 최초 감염된 장비 한 대만 공격하는 것으로 끝나지 않는 경우도 많다.
  - 공격자가 내부 시스템을 탐색하고 다른 장비로 이동하면서 피해 범위를 확대할 수 있기 때문이다.
  - 이처럼 공격자가 최초 침입 지점에서 다른 시스템으로 이동하는 행위를 Lateral Movement라고 한다.

|  |  |  |
| --- | --- | --- |
| **공격 단계** | **공격자의 목적** | **주요 보안 수단** |
| Initial Access | 최초 침입 경로 확보 | NGFW, 이메일 보안, MFA, 취약점 관리 |
| Execution | 악성코드 실행 | EDR, 애플리케이션 통제 |
| Discovery | 내부 장비·계정·서비스 탐색 | EDR, NDR, 로깅 및 모니터링 |
| Lateral Movement | 다른 PC·서버로 이동 | Microsegmentation, EDR, IAM |
| Privilege Escalation | 높은 권한 획득 | PAM, IAM, EDR |
| Data Exfiltration | 중요 데이터 탈취 | DLP, NGFW, NDR |
| Impact | 파일 암호화·서비스 중단 | EDR, 백업, 복구, 접근 격리 |

- - 이 가운데 Elisity가 주로 관여하는 영역은 Lateral Movement의 억제와 네트워크 접근 범위의 제한이다.
  - 악성코드의 실행 자체를 탐지하거나 파일을 복구하는 전문 제품은 아니다.
  - 대신 공격자가 장비에 침입하더라도 그 장비가 접근할 수 있는 네트워크 자원을 사전에 줄여 놓는 방식이다.

**📌 탐지하지 못해도 차단할 수 있다는 의미**

- - 예를 들어 한 직원 PC가 감염되었지만 EDR에서는 아직 감염을 발견하지 못했다고 가정해 보자.
  - 공격자가 사내 파일서버에 TCP 445로 접근하려고 시도한다.
  - 그런데 해당 PC가 속한 Policy Group에서 파일서버로의 SMB 통신을 허용하지 않았다면 네트워크에서 접근을 차단할 수 있다.
  - 이때 Elisity는 패킷이 랜섬웨어인지 확인할 필요가 없다.
  - 출발지 장비와 목적지 서버 사이의 통신이 허용된 것인지만 판단하면 되기 때문이다.
  - 바로 이 점이 탐지 중심 보안과 접근제어 중심 보안의 차이다.

**✅ 2. Elisity는 보안 정책을 어떻게 구성할까?**

**📌 Policy Group과 Security Profile이 핵심이다**

- - Elisity의 정책은 기본적으로 Policy Group과 Security Profile을 결합해 만든다.
  - Policy Group은 공통된 신원이나 장비 속성을 가진 자산을 묶는 논리적인 그룹이다.
  - Security Profile은 이러한 그룹 사이에 어떤 프로토콜과 서비스를 허용하거나 차단할 것인지 정의하는 규칙이다.
  - 정책은 CCC에서 관리되고 VE를 거쳐 지원되는 VEN에 배포된다.

|  |  |  |
| --- | --- | --- |
| **구성요소** | **역할** | **예시** |
| IdentityGraph | 장비의 신원·보안 상태 관리 | 직원 PC, 의료장비, 관리 서버 |
| Policy Group | 공통 조건의 장비 그룹화 | Staff-PC, Medical-Device |
| Security Profile | 프로토콜·포트별 허용·차단 | TCP 443 허용, TCP 445 차단 |
| Policy | 출발지·목적지 그룹 사이의 규칙 | Staff-PC → Finance-DB 차단 |
| Policy Matrix | 그룹 사이의 정책 관계 표시 | Allow, Deny, Custom |
| Policy Set | 사이트·업무 환경별 정책 집합 | Hospital-A, Hospital-B |
| VEN | 실제 패킷에 정책 집행 | 스위치 ACL·그룹 기반 제어 |

**📌 Static Policy Group과 Dynamic Policy Group**

- - Static Policy Group은 IP 주소나 서브넷을 기준으로 장비를 분류한다.
  - 예를 들어 10.20.30.0/24를 특정 서버 그룹으로 정의하는 방식이다.
  - Dynamic Policy Group은 장비의 신원과 속성에 따라 자동으로 소속을 결정한다.
  - 예를 들어 의료장비로 분류된 장비, 특정 AD 부서의 사용자, EDR 상태가 정상인 PC 등을 조건으로 사용할 수 있다.

|  |  |  |
| --- | --- | --- |
| **항목** | **Static Policy Group** | **Dynamic Policy Group** |
| 분류 기준 | IP 주소, 서브넷 | 신원·장비 종류·보안 속성 |
| 관리 방식 | 주소 기반 | 속성 기반 자동 분류 |
| IP 변경 영향 | 정책 관리에 영향 가능 | 신원 기반 조건을 유지할 수 있음 |
| 주요 용도 | 서버 서브넷, 고정 주소 자원 | PC, IoT, 의료장비, 위험 장비 |
| 동적 격리 활용 | 주소 기반 변경 필요 가능 | 위험 상태에 따른 자동 재분류 가능 |

- - 여기서 Dynamic이라는 표현은 AI가 보안 정책을 계속 새롭게 만들어 낸다는 의미가 아니다.
  - **관리자가 미리 정의한 조건에 따라 장비의 Policy Group 소속이 동적으로 달라질 수 있다는 의미**다.
  - 이 차이가 실제 자동 격리 구조를 이해하는 데 매우 중요하다.

**✅ 3. 가장 중요한 사실 — Elisity는 기본적으로 Default Allow다**

**📌 정책을 만들지 않았다고 통신이 차단되는 것은 아니다**

- - 이 부분은 반드시 짚고 넘어갈 필요가 있다.
  - Elisity의 공식 Policy Matrix 문서에는 별도 정책이 존재하지 않는 두 Policy Group 사이의 통신이 기본적으로 허용된다고 명시되어 있다.
  - 즉, Elisity를 설치했다고 해서 처음부터 모든 장비가 최소 권한으로 통제되는 것은 아니다.
  - 관리자가 실제 차단 정책을 정의하고 Active 상태로 적용해야 접근이 제한된다.
  - 따라서 제로트러스트 솔루션을 도입했다는 사실과 제로트러스트 정책이 완성되었다는 사실은 구분해야 한다.

**📌 Policy Matrix의 세 가지 기본 정책**

|  |  |  |
| --- | --- | --- |
| **정책 유형** | **의미** | **적용 예시** |
| Allow All | 두 그룹 사이의 모든 IP 통신 허용 | 제한 없는 특정 업무 통신 |
| Deny All | 두 그룹 사이의 모든 IP 통신 차단 | 직원 PC → 의료장비 관리망 |
| Custom Policy | 특정 서비스만 허용 또는 차단 | CT Scanner → PACS TCP 104 허용 |

- - Custom Policy에서는 Security Profile에 포함된 L3/L4 규칙과 Final Policy Action을 함께 사용한다.
  - 예를 들어 PACS 서버로 TCP 104를 허용하고 Final Policy Action을 Deny로 설정하면, 해당 정책에 명시되지 않은 나머지 통신을 차단하도록 설계할 수 있다.
  - **Security Profile 설정 예시**

|  |  |  |
| --- | --- | --- |
| **순서** | **조건** | **동작** |
| Rule 1 | TCP Destination Port 104 | Allow |
| Rule 2 | 승인된 관리 서비스 | Allow |
| Final Policy Action | 그 밖의 IP 통신 | Deny |

- - 이렇게 하면 업무에 필요한 서비스를 명시적으로 허용하고 나머지 통신은 차단하는 최소 권한 정책을 구성할 수 있다.
  - 단, 모든 VEN이 동일한 Layer 4 수준의 집행 기능을 제공하는 것은 아니다.

**📌 Default Allow와 Default Security Profile은 다르다**

- - Elisity에는 새 Policy Group을 만들 때 기본 Security Profile을 자동으로 상속하도록 하는 기능도 있다.
  - 예를 들어 의료장비나 격리 그룹에 대해 기본 Deny 프로파일을 지정할 수 있다.
  - 다만 이 상속 기능은 새롭게 생성되는 정책 관계에 적용되며 기존의 모든 정책을 소급해서 변경하는 것은 아니다.
  - 또한 상속으로 생성된 정책은 즉시 Active 상태로 적용될 수 있다.
  - 따라서 운영자가 상속 규칙을 잘못 설정하면 정상 업무가 영향을 받을 수 있다.
  - Default Allow라는 플랫폼 기본 동작을 이해한 뒤, 중요한 그룹에 대해 명시적인 차단 정책과 상속 규칙을 설계해야 한다.

**✅ 4. 실제 병원 네트워크에 적용해 보자**

**📌 여섯 개의 Policy Group을 정의한다**

- - 한 병원에 직원 PC, 의료장비, PACS 서버, 일반 업무 서버, 서버 관리 시스템, 보안 복구 서버가 있다고 가정해 보자.
  - 모든 장비를 하나의 신뢰 영역으로 취급하는 대신 업무 목적과 보안 상태에 따라 분류한다.

|  |  |  |
| --- | --- | --- |
| **Policy Group** | **포함되는 장비** | **주요 접근 권한** |
| Staff-Healthy | 보안 상태가 정상인 직원 PC | 승인된 업무 서비스 |
| Medical-Devices | CT, MRI, 환자 모니터 등 | 지정된 의료 시스템 |
| PACS-Servers | 의료 영상 저장·관리 서버 | 승인된 의료 영상 통신 |
| Admin-Servers | 도메인 컨트롤러, 관리 서버 | 승인된 관리자 및 필수 인프라 통신 |
| Remediation | 보안 복구·관리 시스템 | 감염 장비 복구에 필요한 통신 |
| Quarantine | 감염되거나 정책상 위험한 장비 | 복구 목적의 제한된 접근 |

**📌 Policy Matrix로 접근 권한을 제한한다**

- - 다음 표는 실제 보안 정책 구성을 이해하기 위한 예시다.

|  |  |  |  |
| --- | --- | --- | --- |
| **출발지** | **목적지** | **허용 서비스** | **정책** |
| Staff-Healthy | 업무 서버 | 승인된 HTTPS | Custom Allow |
| Staff-Healthy | PACS-Servers | 승인된 업무 앱 경로 | Custom Allow |
| Staff-Healthy | Admin-Servers | 일반 관리 서비스 | Deny |
| Staff-Healthy | Medical-Devices | 직접 접근 | Deny |
| Medical-Devices | PACS-Servers | TCP 104 등 승인된 서비스 | Custom Allow |
| Medical-Devices | Admin-Servers | 불필요한 관리 접근 | Deny |
| Quarantine | Remediation | 승인된 복구 서비스 | Custom Allow |
| Quarantine | 일반 내부 업무망 | 모든 일반 접근 | Deny |
| Quarantine | 의료장비 네트워크 | 모든 일반 접근 | Deny |
| Quarantine | 중요 DB 및 관리망 | 모든 일반 접근 | Deny |

- - 중요한 점은 정상적인 Staff-Healthy 그룹도 모든 시스템에 접근할 수 있는 것은 아니라는 사실이다.
  - 공격자가 직원의 PC를 탈취했더라도 해당 PC가 원래 접근할 수 없던 의료장비나 관리 서버에는 도달하지 못하도록 제한한다.
  - 즉, **감염 사실을 발견하기 전에 이미 첫 번째 방어가 작동하고 있는 구조**다.

---

**✅ 5. 랜섬웨어 감염 전후의 네트워크 접근은 어떻게 바뀔까?**

**📌 첫 번째 방어 — 사전에 설정한 최소 권한**

- - 정상 상태의 직원 PC는 업무 서버와 필요한 애플리케이션에 접근할 수 있다.
  - 그러나 PACS의 관리 인터페이스, 서버 관리망, 의료장비 제어 시스템 등에는 불필요한 접근을 허용하지 않는다.
  - 공격자가 PC를 탈취하더라도 이 기존 정책이 적용된 상태라면 승인되지 않은 경로를 통한 내부 이동은 차단할 수 있다.
  - 이 단계에서는 감염 탐지나 새로운 정책 변경이 필요하지 않다.

**📌 두 번째 방어 — 감염 판정 후 접근 권한 축소**

- - 이번에는 EDR이 해당 PC의 감염을 확인했다고 가정해 보자.
  - EDR에서 제공하는 보안 상태가 IdentityGraph에 반영되고, Dynamic Policy Group의 조건에 일치하면 장비가 Quarantine 그룹으로 재분류될 수 있다.
  - 이후 해당 장비에는 Quarantine 그룹에 미리 정의된 네트워크 정책이 적용된다.
  - 이전까지 접근할 수 있었던 일반 업무 서버도 차단하고, 필요에 따라 보안 복구 서비스만 허용하는 식이다.

**📌 감염 전후의 접근 권한 비교**

|  |  |  |
| --- | --- | --- |
| **통신 대상** | **감염 전** | **감염 판정 후 격리 정책 적용** |
| 일반 업무 서버 | Allow | Deny |
| PACS 업무 애플리케이션 | 조건부 Allow | Deny |
| 의료장비 관리망 | Deny | Deny |
| 도메인 관리 인터페이스 | Deny | Deny |
| 승인된 보안 복구 서버 | Allow 또는 조건부 | Allow |
| 승인되지 않은 인터넷 서비스 | 기존 정책에 따름 | Deny |

- - 두 번째 방어는 원래 허용된 통신까지 제한한다는 점에서 첫 번째 방어와 다르다.
  - 따라서 동적 격리에는 외부 시스템이 제공한 감염 정보의 정확성과 정책 적용 속도가 중요하다.
  - 또한 모든 서비스가 중단되는 완전한 격리와, 치료·복구에 필요한 서비스만 남기는 제한적 격리는 서로 다른 운영 전략이다.

---

**✅ 6. EDR과 Elisity는 어떻게 연동할까?**

**📌 EDR은 위협을 탐지하고 Elisity는 접근 권한을 조정한다**

- - Elisity는 CrowdStrike, SentinelOne과 같은 EDR 제품과 연동할 수 있다.
  - EDR은 장비 내부의 악성 프로세스와 파일, 보안 상태를 확인한다.
  - Elisity는 EDR이 제공하는 장비 정보와 보안 속성을 IdentityGraph에 통합한다.
  - 이렇게 통합된 속성을 Dynamic Policy Group의 조건으로 사용할 수 있다.

|  |  |
| --- | --- |
| **구성요소** | **주요 역할** |
| EDR Agent | 악성코드·프로세스·보안 상태 분석 |
| EDR Management Platform | 감염·위험 정보 관리 |
| Elisity Connector | API를 이용한 속성 조회 및 통합 |
| IdentityGraph | 장비 신원과 보안 상태의 통합 관리 |
| Dynamic Policy Group | 정의된 조건에 따른 장비 재분류 |
| Policy Engine | 해당 그룹에 적용할 정책 결정 |
| Virtual Edge | 필요한 VEN에 정책 설정 전달 |
| VEN | 실제 네트워크 접근제어 집행 |

**📌 SentinelOne과의 연동 예시**

- - Elisity는 SentinelOne의 엔드포인트 상태를 IdentityGraph에 반영하는 통합을 제공한다.
  - SentinelOne 측에서 제공하는 감염 상태, 에이전트 버전, 방화벽 상태, 디스크 암호화 상태, 관리 콘솔 연결 상태 등을 정책 조건으로 활용할 수 있다고 설명한다.
  - 예를 들어 SentinelOne 에이전트가 정상이고 감염되지 않은 PC에만 중요 업무 애플리케이션 접근을 허용하는 정책을 구성할 수 있다.
  - 반대로 감염 상태가 확인되었거나 필요한 보안 조건을 충족하지 못하는 장비는 제한된 Policy Group으로 이동시키는 정책을 설계할 수 있다.
  - 이때 EDR 자체의 호스트 격리 기능과 Elisity의 네트워크 마이크로세그멘테이션 정책은 별도로 작동하는 보안 계층이다.

**📌 CrowdStrike와의 연동은 어떻게 다를까?**

- - CrowdStrike 연동에서는 Hostname, OS, 장비 모델, Tags, Host Groups, Overall ZTNA Score 등의 속성을 가져올 수 있다.
  - 이러한 정보는 장비의 신뢰 상태와 그룹 분류에 활용할 수 있다.
  - 다만 모든 EDR 커넥터가 동일한 감염 상태 필드와 동일한 자동 격리 동작을 제공하는 것은 아니다.
  - 특정 위협 탐지 이벤트가 실제로 어떤 속성에 매핑되고, 그 값이 얼마나 빠르게 갱신되는지를 제품별로 확인해야 한다.

**📌 자동 격리와 AI 정책 추천은 다른 기능이다**

- - 사전에 구성한 Dynamic Policy Group은 장비의 조건이 달라졌을 때 그룹 분류와 적용 정책을 자동으로 변경할 수 있다.
  - 반면 Elisity Intelligence가 새롭게 제안하는 Allow/Deny 정책은 기본적으로 Simulation Mode로 생성되며, 관리자 검토와 활성화가 필요하다.
  - 따라서 Elisity의 AI가 네트워크 트래픽을 보다가 랜섬웨어를 발견하면 임의의 새로운 정책을 만들어 즉시 차단한다고 이해해서는 안 된다.
  - **자동 격리의 핵심은 사전에 승인한 정책이 장비의 신원 또는 보안 상태 변화에 따라 동적으로 적용되는 데 있다.**

**✅ 7. 실제 자동 격리는 얼마나 빠를까?**

**📌 탐지 속도와 격리 속도는 다르다**

- - EDR이 감염을 발견한 시점과 VEN에서 네트워크 차단 정책이 실제로 적용되는 시점은 같지 않다.
  - 그 사이에는 EDR 상태 갱신, 커넥터의 정보 조회, IdentityGraph 업데이트, 정책 그룹 평가, VE의 정책 전달 및 VEN의 설정 적용 과정이 존재할 수 있다.
  - 따라서 자동화된 정책 집행을 지원한다는 것만으로 수초 이내 격리가 보장된다고 판단해서는 안 된다.

**📌 공식 문서에서 확인되는 커넥터 갱신 주기**

|  |  |  |
| --- | --- | --- |
| **항목** | **SentinelOne 연동** | **CrowdStrike 연동** |
| 정보 획득 | 관리 API 조회 | 관리 API 조회 |
| 기본 속성 갱신 주기 | 24시간 | 24시간 |
| 수동 Refresh | 지원 | 지원 |
| 주기 변경 | Global Timer 1~168시간 설정 가능 | 고급 타이머 설정 가능 |
| IdentityGraph 활용 | 보안 상태·장비 속성 | 장비 속성·ZTNA Score 등 |
| 실제 격리 소요 시간 | 별도 검증 필요 | 별도 검증 필요 |

- - SentinelOne의 공식 Elisity Connector 문서에는 Global Timer의 기본값이 24시간이라고 명시되어 있다.
  - CrowdStrike의 Classification Details 문서에도 기본적으로 24시간마다 속성을 새로 조회한다고 설명되어 있다.
  - 따라서 커넥터가 단순히 주기적인 API 조회에 의존한다면, EDR이 감염을 탐지한 직후 그 결과가 네트워크 정책에 반영되지 않을 수 있다.
  - 제품이나 통합 방식에서 별도의 이벤트 기반 갱신 경로가 제공된다면 결과가 달라질 수 있지만, 이를 개별적으로 확인해야 한다.
  - 결국 중요한 것은 EDR의 탐지 속도가 아니라 **탐지 결과가 VEN의 정책 집행으로 이어지는 전체 시간**이다.

**📌 PoC에서 측정해야 할 시간**

|  |  |
| --- | --- |
| **단계** | **측정 항목** |
| T1 | 공격 발생 → EDR 탐지 |
| T2 | EDR 탐지 → IdentityGraph 속성 갱신 |
| T3 | 속성 갱신 → Dynamic Policy Group 변경 |
| T4 | 그룹 변경 → VE의 정책 전달 |
| T5 | 정책 전달 → VEN의 실제 차단 적용 |

- - 전체 대응 시간은 이 단계들에 걸린 시간을 합산하여 측정해야 한다.
  - 특히 T2는 커넥터의 Polling Interval 및 이벤트 전달 구조에 따라 큰 차이가 발생할 수 있다.
  - T4와 T5 역시 VE와 VEN 사이의 통신 상태, 스위치 플랫폼, 정책 규모와 하드웨어 자원에 따라 달라질 수 있다.
  - 이를 확인하지 않은 채 실시간 자동 격리를 보장한다고 주장하는 것은 적절하지 않다.

**✅ 8. 정책을 실제로 적용하기 전에 어떻게 검증할까?**

**📌 Simulation Mode — 차단하지 않고 영향을 먼저 확인한다**

- - 의료장비나 산업제어망에 보안 정책을 적용할 때는 정상적인 서비스가 차단되지 않도록 신중하게 검증해야 한다.
  - 예를 들어 의료장비가 평소 통신하던 서버를 잘못 차단하면 영상 전송이나 장비 유지보수에 문제가 생길 수 있다.
  - 이를 방지하기 위해 Elisity는 정책을 Simulation Mode로 저장할 수 있다.
  - Simulation Mode에서는 실제 트래픽을 차단하지 않고, 구성한 정책이 활성화되었다면 어떤 통신이 영향을 받았을지 검토할 수 있다.
  - 관리자는 Traffic Analytics와 Policy Matrix를 확인한 뒤 정책을 Active 상태로 전환할 수 있다.

|  |  |  |
| --- | --- | --- |
| **항목** | **Simulation Mode** | **Active Mode** |
| 정책 생성 | 가능 | 가능 |
| 정책 영향 분석 | 가능 | 가능 |
| 실제 패킷 차단 | 하지 않음 | 정책에 따라 집행 |
| 트래픽 관찰 | 지원 | 지원 |
| 정상 업무 영향 | 정책 자체의 차단 영향 없음 | 잘못된 정책이면 업무 중단 가능 |
| 주요 용도 | 사전 검증 및 최적화 | 실제 보안 통제 |

**📌 실제 정책 배포 순서**

- - ① 먼저 Traffic Analytics로 정상적인 업무 통신 관계를 관찰한다.
  - ② 장비를 적절한 Policy Group으로 분류한다.
  - ③ 중요한 서비스에 필요한 Allow 규칙을 정의한다.
  - ④ 차단하려는 경로의 Deny 규칙을 Simulation Mode에 설정한다.
  - ⑤ 업무 시간뿐 아니라 야간 배치, 백업, 의료장비 점검 등 다양한 운영 시간대의 트래픽을 확인한다.
  - ⑥ 검증이 끝난 정책만 단계적으로 Active 상태로 전환한다.
  - ⑦ 적용 후 허용·차단 로그와 실제 업무 영향을 지속적으로 확인한다.

**📌 AI도 정책 적용 전 검토 과정에 참여한다**

- - Elisity Intelligence의 Policy Suggestions는 그룹 간 Allow/Deny 정책을 추천한다.
  - 공식 자료에는 추천된 정책을 Simulation Mode에 생성하고 Traffic Review로 영향을 검토하는 흐름이 설명되어 있다.
  - AI는 정책의 후보를 찾아주는 역할을 할 수 있지만 실제 정책 적용의 책임은 운영자에게 남는다.
  - 특히 고가용성이 중요한 의료·OT 네트워크에서는 이러한 사전 검증이 필수적이다.

**✅ 9. 모든 스위치에서 똑같이 격리할 수 있을까?**

**📌 실제 집행 성능은 VEN에 따라 달라진다**

- - Elisity는 기존 스위치를 정책 집행 지점으로 활용하기 때문에 제조사별 하드웨어와 소프트웨어 기능의 차이를 피할 수 없다.
  - 예를 들어 Cisco Catalyst는 TrustSec 관련 기능을 이용할 수 있지만, Juniper나 Aruba는 다른 네이티브 정책 집행 방식을 사용한다.
  - 이러한 차이에 따라 정책의 세분화 수준도 달라질 수 있다.

|  |  |  |
| --- | --- | --- |
| **제조사·플랫폼** | **정책 집행 방식** | **주요 확인 사항** |
| Cisco Catalyst | TrustSec·SGT·ACL 등 | 모델, 라이선스, SGT/ACL 자원 |
| Arista EOS | MSS 기반 그룹 제어 | MSS 그룹 수, TCAM, 설정 반영 영향 |
| Juniper EX 직접 연동 | GBP 및 L3 기반 정책 | 해당 플랫폼의 L4 정책 미지원 |
| HPE Aruba CX | L3 기반 정책 | 현재 통합에서 L4 정책 미지원 |

- - 예를 들어 정책에서 TCP 445만 차단하려 한다면 스위치가 해당 Layer 4 정책을 지원해야 한다.
  - 일부 플랫폼에서 Layer 3 수준의 Allow/Deny만 지원한다면 출발지와 목적지 IP 또는 그룹 사이의 전체 통신을 차단하는 식으로 적용 범위가 넓어질 수 있다.
  - 따라서 CCC에서 정책을 정의할 수 있다는 사실과 해당 정책을 특정 VEN이 동일한 정밀도로 집행할 수 있다는 것은 구분해야 한다.

**📌 동일 VLAN 내부도 통제할 수 있을까?**

- - Microsegmentation의 중요한 목표 중 하나는 동일 VLAN 내부의 장비 간 통신을 제한하는 것이다.
  - 하지만 실제로 이를 구현하려면 해당 트래픽이 지원되는 VEN의 집행 지점을 통과하고, 필요한 하드웨어 기능이 활성화되어 있어야 한다.
  - 트래픽이 VEN을 우회하거나 스위치가 필요한 집행 기능을 지원하지 않는다면 모든 통신을 동일하게 차단할 수는 없다.
  - 특히 여러 제조사 스위치가 혼합된 네트워크에서는 실제 트래픽 경로와 정책 적용 위치를 정확하게 파악해야 한다.

---

**✅ 10. EDR과 Microsegmentation을 함께 사용하면 무엇이 달라질까?**

**📌 어느 하나만으로는 충분하지 않다**

- - EDR은 엔드포인트 내부에서 발생하는 악성 행위를 분석하는 데 강점이 있다.
  - 반면 Elisity는 장비가 네트워크에서 접근할 수 있는 자원의 범위를 제한한다.
  - 두 기술을 함께 적용하면 침입의 탐지와 내부 확산 제한을 서로 다른 보안 계층에서 수행할 수 있다.

|  |  |  |
| --- | --- | --- |
| **공격 시나리오** | **EDR의 역할** | **Elisity의 역할** |
| 악성 파일 실행 | 프로세스·파일 분석 및 차단 | 직접 파일 분석은 수행하지 않음 |
| 감염 PC의 서버 탐색 | 이상 행위 관찰 가능 | 승인되지 않은 통신 경로 제한 |
| SMB를 통한 내부 확산 | 감염·악성 행위 탐지 | 불필요한 SMB 경로 차단 |
| 정상 계정 탈취 | 관련 호스트 행위 분석 | 해당 장비의 허용된 네트워크 범위 제한 |
| 감염 장비 확인 | 악성 상태 판정 | 위험 상태에 따른 접근 권한 축소 |
| 의료장비 등 비관리형 장비 | 에이전트 설치 어려울 수 있음 | 지원 VEN을 통한 네트워크 접근제어 |
| 감염 후 복구 | 프로세스 중지·격리·복구 지원 | 복구에 필요한 통신만 허용하는 정책 지원 |

**📌 가장 중요한 것은 공격이 발견되기 전의 상태다**

- - EDR과의 연동은 감염 사실을 확인한 뒤의 대응을 자동화할 수 있다는 장점이 있다.
  - 하지만 네트워크에서 랜섬웨어의 확산을 줄이려면 감염 이전부터 최소 권한 정책이 적용되어 있어야 한다.
  - 탐지 후 자동 격리만을 믿고 내부 네트워크를 광범위하게 개방해 두었다면, 탐지 지연 동안 공격자가 다른 시스템에 접근할 가능성이 남는다.
  - 따라서 Elisity의 핵심 가치는 단순한 자동 격리 기능보다 **평상시 허용된 통신 경로 자체를 최소화할 수 있다는 점**에 있다.

---

**✅ 11. 실제 도입에서 반드시 검증해야 할 사항**

**📌 자동 격리는 기능의 존재보다 운영 품질이 중요하다**

- - 이론적으로 동적 접근 통제는 유용하지만 실제 기업 네트워크에 적용하려면 여러 제약을 확인해야 한다.
  - 특히 의료장비와 OT 네트워크에서는 보안 강화를 위해 업무가 중단되는 상황을 피해야 한다.
  - 감염된 장비를 무조건 완전히 차단하는 정책보다 복구에 필요한 통신만 남기는 정책이 더 적합할 수도 있다.

|  |  |
| --- | --- |
| **검증 항목** | **확인해야 할 내용** |
| 기본 정책 | Default Allow 상태에서 어떤 통신이 아직 개방되어 있는가? |
| Policy Coverage | 중요한 그룹 사이에 실제 Active 정책이 존재하는가? |
| EDR 연동 | 어떤 위협·감염 상태 속성을 가져오는가? |
| Polling Interval | EDR의 상태 변화가 CCC에 반영되기까지 얼마나 걸리는가? |
| Auto Reclassification | 위험 상태 변경 시 장비 그룹이 자동 변경되는가? |
| Enforcement Latency | 그룹 변경 이후 실제 스위치 차단까지 얼마나 걸리는가? |
| Same-VLAN Enforcement | 동일 VLAN 단말 간 통신도 제한할 수 있는가? |
| L4 지원 | TCP/UDP 포트 단위로 제한할 수 있는가? |
| WAN 장애 | 기존 정책 유지 및 신규 격리 가능 여부 |
| False Positive | 정상 장비가 잘못 격리될 때 복구 방법 |
| Recovery Policy | 복구·관리 서비스가 계속 접근 가능한가? |
| Audit & Logging | 격리 이유, 정책 변경 및 차단 기록을 추적할 수 있는가? |

**📌 특히 세 가지 상황을 시험할 필요가 있다**

- - **정상 장비가 감염된 것으로 잘못 판정된 경우:** 잘못된 격리를 빠르게 해제하고 업무를 복구할 수 있는가?
  - **실제로 감염되었지만 EDR이 탐지하지 못한 경우:** 기존 최소 권한 정책만으로 어느 정도까지 확산을 제한할 수 있는가?
  - **CCC 또는 VE에 장애가 발생한 경우:** 기존 접근제어 정책은 유지되며, 새로운 격리 정책을 적용할 수 있는가?
  - 이 세 가지 상황을 검증하면 Elisity의 기술적 가치를 단순한 제품 소개 수준이 아니라 실제 보안 운영 능력으로 평가할 수 있다.

---

**✅ 결론 — 공격을 찾아내는 것보다 공격자가 이동할 수 있는 범위를 제한하는 것이 중요하다**

- - Elisity의 Microsegmentation은 악성코드의 종류를 직접 판단하는 기술이 아니다.
  - 장비와 사용자의 신원, 보안 상태, 허용된 업무 통신 관계를 바탕으로 네트워크 접근 권한을 제한하는 기술이다.
  - 정상적인 직원의 PC가 랜섬웨어에 감염되더라도, 사전에 설정된 정책이 있다면 공격자가 승인되지 않은 서버에 접근하는 것을 막을 수 있다.
  - EDR이 감염을 확인한 뒤에는 기존에 허용된 접근 권한까지 축소하는 동적 격리 정책도 구현할 수 있다.
  - 하지만 이러한 자동화가 실제로 얼마나 빨리 작동하는지는 EDR의 탐지 성능뿐 아니라 커넥터 갱신 주기와 정책 전달 및 집행 시간에 좌우된다.
  - 또한 Elisity의 기본 정책은 Default Allow이므로, 명시적인 차단 정책을 설계하고 활성화하지 않으면 기대하는 수준의 최소 권한 보안을 얻을 수 없다.
  - 결국 Elisity의 기술적 가치는 장비를 감염 여부에 따라 자동 격리할 수 있다는 사실 하나로 결정되지 않는다.
  - **평상시 얼마나 정교하게 접근 권한을 제한하고, 감염 상태가 변경되었을 때 얼마나 안전하고 신속하게 그 권한을 축소할 수 있는지가 핵심**이다.
  - 지금까지 살펴본 기술은 분명 유용하다.
  - 그러나 이러한 기능을 Elisity만 제공하는 것은 아니다.
  - Illumio, Akamai Guardicore, Zero Networks, ColorTokens, Cisco 등도 각기 다른 방식으로 마이크로세그멘테이션과 동적 접근제어를 구현하고 있다.
  - 따라서 Elisity의 기술적 경쟁력을 판단하려면 다른 업체들이 어떤 방식으로 정책을 집행하며, 추가 장비·에이전트·소프트웨어가 얼마나 필요한지도 비교해야 한다.

> ***다음 5편에서는 「Elisity vs Illumio·Akamai·Zero Networks — 제로트러스트 시장의 진짜 경쟁력」을 통해 기술별 집행 구조, 기존 장비 활용 수준, 정책 세분화, 운영 비용과 차별성을 비교해 보기로 한다.***

**✅ 용어 정리 (Glossary)**

|  |  |
| --- | --- |
| **용어** | **의미** |
| **Microsegmentation** | 장비·신원·워크로드 단위로 네트워크 통신 경로를 세분화하고 제한하는 보안 기술 |
| **Lateral Movement** | 공격자가 최초 침입한 장비에서 다른 PC나 서버로 이동하는 행위 |
| **Policy Group (PG)** | 공통된 신원·속성·보안 조건을 가진 장비나 사용자의 논리적 그룹 |
| **Dynamic Policy Group** | 신원 및 보안 속성의 변화에 따라 장비의 소속이 자동으로 평가·변경되는 정책 그룹 |
| **Static Policy Group** | IP 주소나 서브넷을 기준으로 구성한 고정형 정책 그룹 |
| **Security Profile** | 그룹 간 허용·차단할 프로토콜과 포트 등을 정의한 정책 규칙 |
| **Policy Matrix** | Policy Group 사이의 접근제어 관계를 시각화하고 관리하는 인터페이스 |
| **Policy Set** | 특정 사이트나 운영 환경에 배포하는 정책 집합 |
| **Default Allow** | 별도의 차단 정책이 없으면 해당 통신을 허용하는 기본 정책 동작 |
| **Default Deny** | 명시적으로 허용되지 않은 통신을 차단하도록 설계한 정책 방식 |
| **Final Policy Action** | Security Profile의 개별 규칙과 일치하지 않은 나머지 트래픽을 허용하거나 차단하는 최종 동작 |
| **Simulation Mode** | 실제 패킷을 차단하지 않고 정책 적용 시 예상 영향을 분석하는 모드 |
| **Active Policy** | 실제 네트워크 집행 지점에 적용되는 활성 보안 정책 |
| **Quarantine** | 위험 장비의 네트워크 접근을 제한하고 필요한 관리·복구 서비스만 허용하는 격리 조치 |
| **EDR** | Endpoint Detection and Response. 엔드포인트의 악성 행위와 위협을 탐지하고 대응하는 기술 |
| **Connector** | 외부 보안·자산관리 시스템의 정보를 Elisity로 가져오는 연동 기능 |
| **Polling Interval** | 외부 시스템의 데이터 변경 여부를 주기적으로 조회하는 시간 간격 |
| **Enforcement Latency** | 정책 변경이 실제 네트워크에서 집행되기까지 발생하는 지연 |
| **East-West Traffic** | 기업 내부 장비나 서버 사이의 통신 |
| **North-South Traffic** | 기업 내부망과 외부 네트워크 사이의 통신 |
| **Blast Radius** | 침해 사고가 확산되어 피해를 줄 수 있는 시스템과 자산의 범위 |
| **TCAM** | 스위치 ASIC에서 ACL 등 고속 패킷 분류와 검색에 사용하는 하드웨어 메모리 |
| **PoC** | Proof of Concept. 실제 환경에서 기술의 적용 가능성과 성능을 검증하는 시험 |
