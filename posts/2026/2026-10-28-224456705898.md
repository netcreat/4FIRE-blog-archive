# BB84의 키 확립부터 공개키 암호화와 실제 데이터 보호까지

Published: 2026-10-28T17:24:23+11:00

Original Naver post: https://blog.naver.com/4-fire/224456705898?fromRss=true&trackingCode=rss

---

**✅ 키 확립에서 실제 데이터 암호화까지**

- - **암호화 시스템을 평가하려면 세 단계를 분리해야 한다.**

    - 첫째 비밀키를 어떻게 확립하는가,
    - 둘째 통신 상대를 어떻게 인증하는가,
    - 셋째 실제 데이터를 어떤 알고리즘으로 암호화하는가다.
  - 이 보고서는 Alice가 최초 비트열 **10110010**을 준비해 양자상태로 전송하는 BB84의 전 과정을 재구성한 다음, Eve의 정보량·최종 키 추출·OTP·AES-256-GCM과 PQC의 ML-KEM·ML-DSA를 동일한 보안 체계에서 분석한다.
  - BB84의 Sifting, 오류 정정, Privacy Amplification을 거쳐 완성되는 비밀키와 ML-KEM의 공유 비밀은 생성 원리가 다르지만, 둘 모두 최종적으로 암호화 엔진의 대칭 세션키 재료가 될 수 있다. 양자내성이라는 표현이 곧 키 관리·엔드포인트·인증까지 안전하다는 뜻은 아니다.

---

**✅ 1. 암호화·키 확립·디지털 서명을 먼저 구분한다**

- - **대칭키(Symmetric Key)**는 송신자와 수신자가 동일한 비밀키를 이용해 데이터를 암호화·복호화하는 구조다. AES, ChaCha20, OTP가 이에 속한다.

    - 키를 사용하는 방식이 알고리즘에 내재해 있으므로 AES를 공개키 암호처럼 전환할 수 없다.
  - **비대칭키(Asymmetric Key)**는 공개키와 개인키라는 서로 다른 키를 사용한다.

    - RSA-OAEP는 공개키 암호화, ECDH는 키 합의, ECDSA는 전자서명이다.
    - 모두 공개키 암호학을 이용하지만 실제 기능은 서로 다르다.
  - **암호화(Encryption)**는 기밀성을 보장하는 기능이다.

    - **인증된 암호화(AEAD)**는 기밀성과 메시지 무결성을 함께 다룬다.
    - **서명(Signature)**은 서명자의 공개키로 검증하는 출처 인증·무결성 수단이며 원문을 숨기지는 않는다.
  - **키 확립(Key Establishment)**은 암호화하기 전에 공유 비밀을 마련하는 절차다.

    - ECDH·ML-KEM·QKD는 이 단계에 속하며, 데이터 본문을 직접 암호화하는 AES와 구분해야 한다.
  - **PQC**는 양자컴퓨터를 가정해 안전성을 설계한 암호 기술 계열이고, **QKD**는 양자채널과 인증된 고전채널을 이용한 키 확립 기술이다. 두 용어를 대칭·비대칭 암호 알고리즘과 나란히 놓아서는 안 된다.

| 비대칭 | PQC (ML-DSA / SLH-DSA) | PQC 디지털 서명 | 서명 생성·검증 | 기밀성이나 키 확립 제공하지 않음 |
| 대칭 | QKD (BB84 등) | 양자 기반 공유키 확립 | 양쪽에 동일한 최종 비밀키 공급 | 인증·구현·KMS 보안 가정과 안전한 키율 확인 |

**📌 AES와 RSA는 대칭·비대칭 중 하나를 선택해 작동시키는 알고리즘이 아니다**

- - AES는 동일 비밀키를 사용하는 알고리즘이므로 공개키와 개인키 쌍을 생성하지 않는다. 반대로 RSA는 공개키·개인키 기반의 모듈러 연산 구조로 설계돼 AES처럼 단일 대칭키 스트림 암호로 바꾸어 쓸 수 없다.
  - RSA-OAEP는 암호화 가능한 입력 길이에 제한이 있어 파일 전체를 암호화하기보다 작은 비밀을 감싸는 데 사용돼 왔다. 오늘날의 데이터통신은 대개 공유 세션키를 확보한 뒤 대칭키 암호로 대용량 데이터를 처리한다.
  - ECC는 개별 암호화 알고리즘의 이름이 아니라 타원곡선 공개키 암호학을 통칭한다. ECDH는 키 합의이고 ECDSA는 서명이며, ECIES는 타원곡선 키 합의와 대칭 암호를 결합한 암호화 구조다.
  - AES-256은 Shor 알고리즘으로 RSA·ECC처럼 직접 깨지는 알고리즘이 아니다. Grover 알고리즘은 이론적으로 무차별 키 검색 복잡도를 줄이지만, AES-256의 계산적 보안 여유는 여전히 크다고 평가된다.
  - **표의 QKD ‘대칭키 확립 기술’은 암호 방식 자체의 대칭/비대칭 분류와 다르다.** QKD는 공개키·개인키 쌍으로 데이터를 암호화하는 방식이 아니며, Alice와 Bob이 동일한 최종 비밀 비트열을 확보하도록 하는 키 확립 프로토콜이다.

---

**✅ 2. 양자컴퓨터는 어떤 암호 구조를 공격하는가**

- - **RSA:** 소인수분해 문제를 고전 컴퓨터로 효율적으로 풀기 어렵다는 계산적 가정에 기반한다. 대규모 오류정정 양자컴퓨터의 Shor 알고리즘은 이 문제를 효율적으로 풀 수 있다.
  - **ECDH·ECDHE·ECDSA·ECIES:** ECC의 타원곡선 이산로그 문제에 의존한다. Shor 알고리즘은 충분한 양자 계산 자원이 주어졌을 때 이 수학적 기반을 공격한다.
  - **Shor 알고리즘은 보안의 근거가 아니라 공격 수단**이다. 따라서 기존 공개키 방식의 보안 근거를 Shor라고 적는 것은 잘못이다.
  - **AES·ChaCha20:** 대칭키 암호에는 Shor의 RSA/ECC 공격이 그대로 적용되지 않는다. Grover 알고리즘은 무차별 탐색을 이론적으로 가속하지만, AES-256은 높은 계산적 보안 여유를 유지하는 것으로 평가된다.
  - **ML-KEM·ML-DSA:** 알려진 양자 공격에 견디도록 설계된 계산적 보안 기술이다. QKD는 적절한 장치·인증·보안 증명 가정하에서 양자역학적 특성으로 공유키의 비밀성을 확보한다.
  - 양자내성의 대상은 **데이터 암호화 알고리즘 하나**가 아니다. 공개키 기반 키 확립·인증·키 저장·운용까지 전체 경로를 검토해야 한다.

---

**✅ 3. Alice의 난수는 왜 곧바로 Bob의 공유키가 되지 않는가**

- - Alice가 **10110010**이라는 충분히 예측 불가능한 비트를 만들었다면 Alice 혼자 사용하는 **비밀키 재료**로 볼 수 있다.
  - 하지만 Bob은 이 값을 아직 모른다. Alice만 아는 난수와 Alice·Bob 양쪽이 동일하게 보유한 **공유 비밀키**는 다른 개념이다.
  - QKD의 목적은 Alice가 원본 비트열을 반드시 그대로 복원해 Bob에게 전달하는 것이 아니라, 두 사람이 안전하게 공유할 수 있는 새로운 비밀키를 확립하는 것이다.
  - QRNG(양자 난수 발생기)는 난수를 만드는 장치이고, QKD는 그 난수와 양자 통신·고전 후처리를 결합해 공유키를 확립하는 프로토콜이다. QKD 난수원은 구현에 따라 QRNG 외의 적절한 물리적 난수원도 사용할 수 있다.

**📌 Key Transport와 Key Establishment의 차이**

|  |  |  |
| --- | --- | --- |
| **개념** | **Alice가 하는 일** | **Bob이 얻는 것** |
| Key Transport | 완성한 비밀키를 안전한 수단으로 운반 | Alice가 사전에 정한 동일한 키 |
| BB84 기반 Key Establishment | 무작위 비트를 양자상태로 인코딩해 보내고 함께 후처리 | Sifting·오류 정정·압축 이후 확립된 새로운 공유키 |

- - 엄밀하게는 QKD도 표준과 문맥에서 “키 생성 및 분배”라고 부른다. 여기서 중요한 차이는 “누가 처음 난수를 뽑았는가”가 아니라 **완성된 최종 키를 한쪽이 단순 전달했는가, 양측 프로토콜의 결과로 확립했는가**이다.
  - 이 설명은 Prepare-and-Measure 방식의 대표 사례인 BB84를 기준으로 한다. E91처럼 얽힌 광자쌍을 양측에 분배하는 프로토콜은 Alice가 원본 비트를 먼저 정하는 구조가 아니다.

**✅ 4. BB84는 비트와 기저를 어떻게 양자상태로 바꾸는가**

- - BB84에서 Alice는 매 광자마다 ① 전송하려는 비트값(0 또는 1), ② 비트를 어떤 양자상태로 표현할 것인지 결정하는 **기저(Basis)**를 **각각 무작위로 선택**한다.
  - 편광 기반 설명에서 + 기저는 수평(0°)·수직(90°), × 기저는 대각선(+45°)·반대 대각선(−45°)을 구분하는 측정 방식이다.
  - Alice가 “1”을 보낸다고 하더라도 + 기저에서는 수직 광자로, × 기저에서는 −45° 광자로 표현한다. 비트는 같지만 광자의 물리적 양자상태는 다르다.

|  |  |  |  |

| **기저** | **비트 0** | **비트 1** | **예시** |
| + (Rectilinear) | 수평 편광 0° | 수직 편광 90° | 0 ↔ ─  1 ↔ │ |
| × (Diagonal) | +45° 편광 | −45° 편광 | 0 ↔ ／  1 ↔ ＼ |

- - Bob은 광자를 받는 순간 Alice가 어떤 기저를 사용했는지 아직 모른다. Bob도 각 위치에서 + 또는 × 중 하나를 무작위로 선택해 측정한다.
  - 같은 기저로 이상적인 광자를 측정하면 올바른 비트가 얻어진다. 다른 기저를 선택하면 해당 결과는 0 또는 1이 각각 50% 확률로 나타나므로 Alice의 원래 비트와 일치한다고 보장할 수 없다.

**📌 왜 다른 기저에서 50%가 되는가**

- - Alice가 수평 편광(0°) 광자를 보냈는데 Bob이 ±45° 대각선 기저로 측정한다고 가정한다.
  - 양자역학에서 수평 편광 상태를 +45°와 −45° 상태에 투영하면 확률 진폭의 크기가 각각 1/√2가 된다. 확률은 진폭 제곱이므로 **각각 1/2 = 50%**이다.
  - 이것은 측정기가 부정확해서 생기는 단순한 장비 오차가 아니라, 서로 다른 양자 측정 기저에 대한 근본적인 확률 특성이다.

---

**✅ 5. 기저를 미리 공개하면 왜 BB84의 보안성이 무너지는가**

- - 기저를 Alice가 먼저 공개한다면 Bob은 처음부터 맞는 기저로 측정할 수 있고, 기저 불일치로 비트를 버릴 이유가 없다.
  - **하지만 공개된 기저를 Eve도 광자에 접근하기 전에 알게 된다.** Eve는 같은 기저로 광자를 측정해 비트를 알아낸 다음 같은 상태를 다시 만들어 Bob에게 보낼 수 있다. 이상적인 인터셉트-리센드 모델에서는 이 공격으로 오류가 발생하지 않는다.
  - 표준 BB84에서는 **광자 전송 및 Bob의 수신·측정이 종료된 다음** Alice와 Bob이 고전채널로 기저를 공개해 일치 여부를 확인한다. 비트값 자체는 공개하지 않는다.
  - 기저를 영원히 비밀로 숨기는 것이 목표가 아니다. Eve가 공격할 수 있는 시간 동안은 기저를 알지 못하게 하고, 사후에 기저를 공개해 올바른 위치를 고르는 것이 핵심이다.
  - 기저 정보를 미리 **암호화된 비밀 채널**로 제공하는 변형 설계도 이론적으로 생각할 수 있지만, 사전에 다른 비밀키 또는 추가 보안 가정이 필요하다. 이것을 표준 BB84의 일반적인 동작 방식과 혼동하면 안 된다.

**📌 고전채널은 공개되어도 괜찮은가**

- - 기저, 측정 성공 위치, 일부 오류 정정 정보를 고전채널로 교환하는 것 자체는 QKD 보안 분석에 포함된다. 다만 고전채널은 **반드시 인증**되어야 하며, Eve의 메시지 위조와 세션 가로채기를 막아야 한다.
  - 만약 Eve가 Alice와 Bob 사이에서 서로를 사칭할 수 있다면, 두 사람과 각각 독립된 QKD 세션을 수행하는 중간자 공격(MITM)이 가능하다. 이 경우 양자채널만 안전해도 시스템이 안전하다고 할 수 없다.

**✅ 6. 10110010을 실제로 전송하면 Sifted Key가 어떻게 나오는가**

- - 예제로 Alice의 무작위 비트를 **10110010**로 고정한다. 아래의 Alice 기저, Bob 기저 및 Bob 측정값은 가능한 하나의 **설명용 시나리오**이다.
  - 모든 광자 전송과 측정이 완료되면 Alice와 Bob은 공개 채널(Classical Channel)을 통해 비트값을 제외한 기저 정보만 교환한다.

    - 순서가 매우 중요하다. 광자 전송과 측정이 완료된 후 기저 정보가 교환된다.
  - 각각의 광자에 해당하는 Alice 기저와 Bob 기저를 비교한다. 둘이 같은 위치만 보존하며, 서로 다른 위치는 Bob의 측정값이 우연히 맞았더라도 폐기한다.

|  |  |  |  |  |  |
| --- | --- | --- | --- | --- | --- |
| **위치** | **Alice 비트** | **Alice 기저** | **Bob 기저** | **Bob 측정** | **판정** |
| 1 | **1** | + | + | 1 | **유지** |
| 2 | 0 | + | × | 1 | 폐기 |
| 3 | **1** | × | × | 1 | **유지** |
| 4 | **1** | + | + | 1 | **유지** |
| 5 | 0 | × | + | 0 | 폐기 |
| 6 | **0** | × | × | 0 | **유지** |
| 7 | 1 | + | × | 0 | 폐기 |
| 8 | **0** | + | + | 0 | **유지** |

- - 광자 손실과 측정 잡음이 없는 이상적인 경우이다. 기저가 다를 때 Bob 측정값은 무작위로 나타난다.
  - 기저가 일치하는 위치는 **1, 3, 4, 6, 8번**이다.
  - 따라서 살아남은 비트는 1번=1, 3번=1, 4번=1, 6번=0, 8번=0이며, Sifted Key는 **11100**이다.
  - 이전 대화에서 한 차례 **11000**이라고 계산했던 값은 오류였고, 이 예시의 올바른 결과는 **11100**이다.
  - Sifted Key는 Alice의 원래 8비트를 복원한 값이 아니다. Alice와 Bob의 기저가 일치한 위치를 추려 얻은 중간 키 재료다.

**📌 기저가 불일치했는데 Bob의 측정값이 우연히 맞았다면?**

- - 그 비트도 버린다. Bob과 Alice는 개별 비트가 우연히 정확히 맞았는지를 일반적으로 알고 있지 않으며, 틀린 기저에서 얻어진 결과는 원본 비트에 대한 신뢰할 만한 정보가 아니기 때문이다.
  - 표준적인 대칭 BB84에서 두 기저를 각각 50% 확률로 고르면 광자 수신에 성공한 비트 가운데 기저가 일치하는 비율은 평균 약 절반이다. 이것은 프로토콜의 효율과 관련되며 광자 손실로 인한 폐기는 별도로 발생한다.

**✅ 7. Eve가 광자를 가로채고 나중에 기저를 알면 키를 훔칠 수 있지 않을까**

- - 중요한 문제 제기다. 보안 목표는 Bob이 단순히 광자를 받았는지가 아니라, **Alice와 Bob이 최종적으로 공유한 비밀키를 Eve가 알아내지 못하는가**이다.
  - Eve가 광자를 가로채 임의의 기저로 측정했다가 Bob에게 다시 보내는 공격을 Intercept-Resend라고 한다. Eve가 임의로 선택한 기저는 50% 확률로 Alice의 기저와 일치한다.
  - Eve가 일치한 기저를 선택한 경우에는 Alice의 비트를 정확히 알아내고 같은 광자 상태를 다시 만들 수 있다. 반대 기저였다면 결과는 무작위이며 원래 비트에 대한 확실한 정보를 얻지 못한다.
  - 나중에 Alice와 Bob이 공개한 기저 정보를 듣고 Eve는 자신이 어느 위치를 제대로 측정했는지 확인할 수 있다. 따라서 **Eve가 일부 키 정보는 얻을 수 있다**는 지적은 맞다.

**📌 전형적인 Intercept-Resend 공격에서 QBER가 25%인 이유**

- - **Alice와 Bob의 기저가 일치한 Sifted Key 위치만 대상으로 계산한다.**
  - **Eve가 잘못된 기저를 선택할 확률은 1/2이고, 그 상태를 Bob에게 재전송했을 때 Bob이 Alice의 비트와 다른 값을 측정할 확률은 1/2이다.**
  - **QBER = (1/2) × (1/2) = 1/4 = 25%****가 된다.** **단, Eve가 모든 광자를 이런 방식으로 공격하고 이상적인 BB84 장비를 가정한** **특정 공격의 평균값****이다.**
  - **이 25%를 모든 공격의 필연적인 오류율이나 실제 시스템의 공통 차단 임계값으로 해석하면 잘못이다. 부분적인 공격, 장비 결함, 광자 수 공격, 양자 메모리를 이용하는 더 정교한 공격에서는 분석이 달라진다.**

**📌 Eve가 광자를 보관했다가 기저 공개 후 측정하면?**

- - Eve가 Alice의 미지의 양자상태를 양자 메모리에 그대로 보관하면, 그 광자 자체는 동시에 Bob에게 도착할 수 없다. 표준 프로토콜에서는 Bob의 수신·측정 완료를 확인한 뒤 기저를 공개한다.
  - Eve가 원본 상태를 완벽하게 복사해 사본만 Bob에게 보내려 한다면 미지의 양자상태를 임의로 완벽 복제할 수 없다는 No-Cloning Theorem에 걸린다.
  - 하지만 이것만으로 모든 양자 메모리 공격을 반박할 수는 없다. 현실의 광원은 다광자 펄스 등 이상적 모델에서 벗어날 수 있고, Eve가 양자 정보를 부분적으로 보존하는 집단·결합 공격도 가능하다. 실제 QKD는 이러한 공격 모델과 하드웨어 한계를 고려한 별도의 보안 증명이 필요하다.
  - 특히 “광자를 즉시 측정하지 않고 저장한다면 Bob이 못 받으니 안전하다”라는 단순 논증만으로 실용 시스템의 완전한 안전성을 주장해서는 안 된다.

**📌 Eve가 일부 비트를 알아냈는데도 최종 키가 안전할 수 있는 이유**

- - **QKD는 Eve가 원시 비트에 대해 아무 정보도 얻지 못하도록 보장하는 시스템이 아니다. Eve의 잠재적 정보량을 상한 평가한 뒤** **최종 키를 압축하는** **Privacy Amplification****이 중요한 이유****다.**
  - **오류율과 공개된 오류 정정 정보, 유한 키 길이 및 공격 모델을 반영해 충분히 짧은 키만 추출한다. 안전한 키 길이가 나오지 않으면 해당 세션의 키를 폐기한다.**
  - **결국 보안 판정 대상은 처음 보낸 광자 각각이 아니라, 인증과 후처리를 모두 끝낸** **최종 비밀키****다.**

**✅ 8. Sifted Key를 이용해 원래 10110010을 복원하는가**

- - **아니다.** Sifted Key에서 폐기한 비트를 되찾아 10110010을 복원할 이유가 없다. 필요한 것은 원본과 같은 특정 문자열이 아니라 두 사람이 동일하게 알고 있는 충분히 안전한 난수다.
  - 실제로는 비트와 광자를 계속 생성·측정하고, 여러 블록에서 기저가 일치해 살아남은 비트들을 모아 충분한 길이를 만든다.

|  |  |  |
| --- | --- | --- |
| **광자 전송 묶음** | **Alice의 임의 원본 비트** | **기저 일치 뒤 남은 비트** |
| 1차 | 10110010 | **11100** |
| 2차 | 01101011 | **0101** |
| 3차 | 11000101 | **100** |
| 세 묶음 연결 | 원본 복원 불필요 | **111000101100** (12비트) |

- - 2·3차 선택 위치는 설명을 위해 임의로 정한 예시다. 실제 시스템에서는 훨씬 많은 신호와 통계 검증이 필요하며 12비트는 실사용 보안키가 아니다.

**📌 Sifting 이후에 세 단계가 더 남는다**

- - **① Parameter Estimation(QBER 등):**

    - 일부 정보를 비교해 오류·도청 위험을 추정하고, 안전한 키를 만들 수 있는지 판단한다.
    - 시험용으로 공개한 비트는 더 이상 비밀키 재료로 사용하지 않는다. 공개 방식과 보안 매개변수의 선택은 프로토콜에 따라 달라진다.
  - **② Error Correction / Information Reconciliation:**

    - 같은 위치의 Alice·Bob 비트가 통신 잡음 때문에 달라졌다면 이를 일치시킨다.
    - 이 작업은 버린 비트들을 되살리는 과정이 아니다. 오류 정정 메시지가 Eve에게 공개될 수 있으므로 정보 누출량에 반영한다.
  - **③ Privacy Amplification:**

    - 오류 정정 뒤 남은 비트열을 적절한 해시 처리로 더 짧게 압축해 Eve의 잔여 정보를 제한한다.
    - 예를 들어 중간 키의 길이가 1,000비트여도 최종 안전 키 길이는 1,000비트보다 짧을 수 있다. 얼마만큼 줄이는지는 임의의 고정 비율이 아니라 보안 분석 결과에 따라 정한다.
  - 최종적으로 Alice와 Bob은 동일한 K를 확보한다. K가 256비트 이상으로 충분히 생성되면 KMS가 이를 정책에 따라 나누거나 암호 애플리케이션에 필요한 키 재료를 공급할 수 있다.

    - 이때 Alice가 최초로 생성한 무작위 비트와 최종 비밀키가 다를 수 있다.
    - 최종 키가 Alice의 원래 난수와 다른 것은 난수를 새로 만들어야 해서가 아니라, Bob과 공유하지 못한 비트와 Eve에게 노출됐을 가능성이 있는 정보를 처리하기 때문이다.

> ***QKD의 핵심***
>
> *Key를 전달하는 것이 아닌,* *다른 방법을 통해서 양측이 동일한 키를 유지하도록 하는 것.*
>
> **
>
> *Alice는 이미 무작위 비밀 비트를 가지고 있다.*
>
> *QKD는 그중 Bob과 안전하게 공유할 수 있는 비트를 확보하고, Eve가 일부를 알아냈을 가능성까지 제거해 최종 비밀키를 만드는 기술이다.*
>
> *그리고 핵심은 Eve가 원래의 양자상태를 모르는 상태에서 정보를 얻으려 하면 탐지 가능한 교란이 발생할 수 있다는 사실이다.*
>
> *여기서 더 중요한 것은 QKD가 단순히 오류를 없애는 기술이 아니라는 점이다.*
>
> *오류를 측정해 비밀키를 안전하게 만들 수 있는 상황인지 판단하고, 안전하지 않으면 키 생성을 포기하는 프로토콜이라는 것이 핵심이다.*

**✅ 9. QKD의 최종 키는 KMS를 통해 어떻게 공급되는가**

- - BB84에서 최종 키를 확립한 다음에는 이 비밀키를 누가 저장하고, 어느 애플리케이션에 어떤 식별자로 공급할지 정해야 한다. **QKD의 양자 링크와 KMS는 서로 다른 계층**이다. 반면 다음 절의 ML-KEM은 TLS 같은 프로토콜 안에서 공유 비밀을 직접 키 스케줄에 넣을 수도 있으므로, 반드시 별도 KMS를 거쳐야 하는 것은 아니다.
  - ITU-T Y.3802는 **QKD Module**과 **Key Manager(KM)**를 분리한다. QKD 모듈들이 양자 신호 송수신과 키 추출 후 동일한 키쌍을 확립하고, 그 결과를 각자의 키 관리 계층에 공급한다.
  - KM 내부의 KMA(Key Management Agent)는 키 수신·동기화·길이 조정·형식화·저장·중계와 수명주기 관리를 담당한다. KSA(Key Supply Agent)는 사용자 암호 애플리케이션에 키를 공급한다.
  - 따라서 “QKD가 키를 생성해서 KMS에 준다”는 표현은 네트워크 아키텍처 관점에서는 옳다. 다만 이것이 Alice가 이미 완성한 키 K를 그대로 광자에 싣고 보내는 방식이라는 뜻은 아니다.
  - ETSI GS QKD 014는 애플리케이션이 KME(Key Management Entity)를 통해 키를 요청하고, 상대 애플리케이션이 Key ID를 사용해 대응하는 동일 키를 확보하는 REST 기반 인터페이스를 정의한다.

|  |  |  |
| --- | --- | --- |
| **계층/장치** | **수행하는 기능** | **안전성 관점의 확인사항** |
| QRNG / RNG | 예측 불가능한 난수 생성 | 난수 품질·구현 신뢰 |
| QKD Module (양쪽) | 광자 송수신, 인증된 후처리, 최종 공유키 확립 | 검출기·광원·QBER·양자 공격 가정 |
| KMA / KM / KMS | 키 저장·동기화·중계·포맷·삭제 | 관리 권한·키 저장 보안·중복 사용 금지 |
| KSA / API | 애플리케이션에 Key ID와 키 공급 | API 통신 암호화·접근통제·인증 |
| AES / OTP 엔진 | 실제 사용자 데이터 암호화 | 정확한 키 사용·nonce·무결성 관리 |

**📌 키 전달 API는 QKD와 다르다**

- - ETSI API로 KMS가 애플리케이션에 키를 건네는 절차는 QKD의 양자상태 전송과 다른 계층의 동작이다. 이 구간도 TLS, 접근통제 등 적절한 보안이 필요하다.
  - KMS는 QKD 키 이외에 다른 난수원이나 PQC 등을 이용해 확립한 키를 관리할 수도 있다. QKD는 KMS의 가능한 키 공급원 중 하나다.

**✅ 10. PQC에서 ML-KEM과 ML-DSA가 맡는 역할 및 키 생성 절차**

NIST가 표준화(혹은 초안 단계)로 채택한 PQC 알고리즘 4개를 살펴보도록 하겠다. 알고리즘별로 각...

- - **PQC는 단일한 암호화 알고리즘의 이름이 아니다.**

    - NIST FIPS 203의 ML-KEM은 키 캡슐화(KEM),
    - FIPS 204의 ML-DSA와 FIPS 205의 SLH-DSA는 디지털 서명에 관한 표준이다.
  - **ML-KEM은 비대칭 공개키·개인키 쌍을 사용하지만 결과적으로 Alice와 Bob이 동일한 공유 비밀 S를 갖도록 한다.** 여기서 공개키는 배포해도 되지만 개인키는 생성한 측이 보관해야 한다.
  - ML-KEM의 공유 비밀이 실제 AES 키가 될 때는 세션 문맥·알고리즘 조합에 맞는 KDF 또는 키 스케줄을 사용할 수 있다. KEM 보안뿐 아니라 공개키 인증과 알고리즘 결합도 보안성에 포함된다.

**📌 ML-KEM은 왜 기존의 RSA Key Transport와 구분해야 하는가**

- - RSA Key Transport의 전형적인 형태에서는 Alice가 미리 선택한 비밀값을 Bob의 RSA 공개키로 암호화해 보내고 Bob이 개인키로 복원한다. ML-KEM은 캡슐화 절차 자체가 Alice 측에 공유 비밀 S와 전송용 C를 생성한다.
  - 따라서 "ML-KEM이 이미 만들어 둔 AES 키를 그대로 암호화해 Bob에게 보내는 알고리즘"이라고 단정하면 부정확하다. 실제로 임의의 데이터를 보호하려면 KEM에서 얻은 공유 비밀을 적절한 데이터 암호화 구성에 결합해야 한다.
  - KEM 메시지를 변조하거나 Bob의 공개키를 Eve의 공개키로 바꿔치기하는 공격은 키 확립의 인증 문제에 해당한다. 그러므로 ML-KEM만으로 상대방의 신원까지 자동 검증되는 것은 아니다.

**📌 디지털 서명은 어떤 부분을 보호하는가**

- - ML-DSA와 SLH-DSA는 Alice 또는 Bob의 서명을 만들어 상대방이 유효성을 확인하게 한다. 적절한 신뢰 체계가 있다면 공개키 바꿔치기·프로토콜 메시지 위조를 방어하는 인증 구성요소가 된다.
  - 서명은 암호문의 내용을 숨기지 않는다. 또한 서명이 유효하다고 해서 서명자의 신원이 실제 조직·서비스에 올바르게 연결됐다고 자동 보장되는 것은 아니다. 인증서·키 배포·신뢰 앵커까지 검증해야 한다.
  - 공식 표준: [NIST FIPS 203 (ML-KEM)](https://csrc.nist.gov/pubs/fips/203/final), [FIPS 204 (ML-DSA)](https://csrc.nist.gov/pubs/fips/204/final), [FIPS 205 (SLH-DSA)](https://csrc.nist.gov/pubs/fips/205/final).

**📌** **그렇다면 QKD와 PQC는 어떤 관계인가?**

- - QKD와 ML-KEM은 공유 비밀키를 확립한다는 점에서 기능이 겹친다. 하지만 QKD는 양자 통신장비가 필요하고, ML-KEM은 일반적인 컴퓨터와 네트워크에서 소프트웨어로 구현할 수 있다는 차이가 있다.
  - 또한 ML-DSA는 QKD의 인증에도 활용할 수 있다. 따라서 QKD와 PQC는 반드시 경쟁 관계만은 아니다.

| --- | --- | --- | --- |
| **역할** | **QKD 기반 구성** | **PQC 기반 구성** | **기존 암호화 방식** |
| 공유 비밀키 확립 | BB84 등 QKD | ML-KEM | ECDHE 등 |
| 상대방 인증 | 사전 공유키 인증 또는 PQC 서명 등 | ML-DSA 등 | RSA / ECDSA 서명 |
| 실제 데이터 암호화 | AES-256 / OTP | AES-256 등 | AES-GCM / ChaCha20-Poly1305 |
| 보안 근거 | 양자역학 및 프로토콜 가정 | 수학적 난제의 계산적 어려움 | RSA/ECC: 소인수분해·이산로그 문제의 어려움.  AES: 대칭키 암호의 계산적 안전성 |

**✅ 11. OTP는 어떻게 작동하고 왜 메시지만큼 긴 키가 필요한가**

- - OTP(One-Time Pad)는 가장 단순한 형태의 암호화 중 하나다. 원문 P와 무작위 비밀키 K에 XOR(배타적 논리합)을 적용하면 암호문 C가 된다.
  - **암호화: C = P ⊕ K / 복호화: P = C ⊕ K**이다. XOR를 같은 키로 두 번 하면 원문이 복원된다.

|  |  |
| --- | --- |
| **항목** | **8비트 예시** |
| 원문 P | **10110010** |
| 비밀키 K | **01101101** |
| 암호문 C = P ⊕ K | **11011111** |
| 복호화 C ⊕ K | **10110010** |

**📌 왜 키는 메시지 길이 이상이어야 하는가**

- - 8비트 원문을 완전 비밀성으로 암호화하려면 원칙적으로 8비트의 새로운 무작위 키가 필요하다. 1GB 데이터를 OTP로 암호화하면 1GB의 새로운 비밀키 비트를 소비한다.
  - 완전히 균등한 무작위 키라면 특정 암호문에 대해 가능한 모든 원문이 저마다 대응하는 키 하나를 갖는다. 따라서 암호문을 봐도 원문의 사전 확률이 변하지 않는 **완전 비밀성(Perfect Secrecy)**을 달성한다.
  - 반대로 동일한 짧은 키를 여러 메시지에 재사용하면 C₁ ⊕ C₂ = P₁ ⊕ P₂가 되어 원문 사이의 관계가 드러난다. OTP 보안 조건이 무너진다.
  - OTP는 메시지 기밀성만 제공한다. 공격자가 암호문의 비트를 바꿀 수 있기 때문에 단독으로는 **메시지 무결성·송신자 인증**을 제공하지 않는다. 별도의 올바른 인증 장치가 필요하다.

**📌 메시지마다 키를 새로 만들고 바로 버려야 하는가**

- - 정확히는 “메시지마다 완전히 새로운 키 비트 구간을 사용하고, 한 번 사용한 비트는 다시 쓰지 않는다”는 뜻이다. 하나의 긴 키 풀에서 새로운 구간을 연속으로 잘라 써도 된다.
  - QKD 장비가 매 메시지마다 처음부터 BB84를 시작할 필요는 없다. 지속적으로 비밀키를 공급하고 KMS가 이를 버퍼링한 다음 애플리케이션에서 차례로 소비할 수 있다.
  - Alice와 Bob은 어떤 Key ID와 어느 비트 범위를 소비했는지 일치시켜야 하며, 사용된 비트의 재사용 방지와 안전한 삭제를 보장해야 한다.
  - OTP를 포괄하는 단 하나의 “AES와 같은 암호 알고리즘 FIPS 규격”을 상정하기보다, OTP의 수학적 조건과 이를 실제 네트워크에 키로 공급하는 ETSI·ITU-T 인터페이스 표준을 구분하는 편이 정확하다.

**✅ 12. QKD + OTP와 QKD + AES-256 중 무엇이 현실적인가**

- - OTP는 키를 쓰는 속도가 데이터 속도와 같다. 1Gbps 사용자 데이터를 OTP로 지속적으로 암호화하려면 최소 1Gbps의 새로운 비밀키를 지속적으로 소비해야 한다.
  - 따라서 1Gbps는 1초에 약 125MB, 하루에 약 **10.8TB**의 키 재료가 필요하다는 뜻이다(십진 단위, 추가 인증키·운영 오버헤드 제외).
  - AES-256은 256비트 비밀키 하나로 허용된 키 사용량과 GCM nonce 운용 규칙 내에서 다량의 데이터를 암호화한다. 키를 교체할 때마다 새로운 키 재료가 필요하지만 데이터 전체 길이만큼 QKD 키를 소비하지는 않는다.
  - 그러므로 대부분의 고속 데이터통신에서 QKD의 목적은 OTP 스트림을 데이터 속도만큼 밀어 넣는 것보다, AES 같은 고속 대칭키 암호에 공급할 안전한 키를 확보하는 데 있다.

|  |  |  |
| --- | --- | --- |
| **비교 항목** | **QKD + OTP** | **QKD + AES-256-GCM** |
| 데이터 1GB 보호 | 새로운 비밀키 1GB 필요 | AES 키 256비트와 안전한 nonce·운용 관리 필요 |
| 키 소모 속도 | 데이터 속도와 동일 | 주로 키 교체 주기에 의해 결정 |
| 안전성 성격 | 조건 충족 시 정보이론적 기밀성 | 매우 높은 계산적 양자내성 |
| 무결성 | 별도 인증 필요 | GCM 모드가 인증된 암호화를 제공 |
| 대량 트래픽 적합성 | 키 생산량이 큰 제약 | 상대적으로 매우 실용적 |

- - AES-256이 절대 해독 불가능하다고 수학적으로 증명된 것은 아니다. Grover 알고리즘의 이상적인 검색 이득을 흔히 256비트 키 탐색을 약 128비트 규모의 탐색으로 설명하지만, 실제 양자 자원 비용은 더 복잡하다. NIST 역시 AES-256의 장기적 안전성을 긍정적으로 평가하되 새로운 공격 가능성은 열어 놓는다.
  - 반면 OTP의 완전 비밀성은 올바른 난수·키 길이·일회 사용·키 비밀성·인증 등 조건에서 성립하는 성질이다. 실제 시스템 전체가 공격 불가능해진다는 뜻은 아니다.

**✅ 13. KEM·KDF·AEAD·HPKE를 연결하면 실제 암호 통신이 완성된다**

- - 실제 데이터통신에서는 암호화 그 자체보다 **전체 암호 스택의 연결 관계**가 중요하다. KEM은 공유 비밀을 생성하고, KDF는 트래픽 키를 유도하고, AEAD는 암호문과 인증 태그를 생성하며, 별도의 인증·자격증명 계층은 공개키 소유자를 검증한다.
  - **AES-256-GCM**은 AES 블록암호와 GCM 운용 방식을 결합한 AEAD이다. 같은 암호키를 여러 번 사용할 수 있으나 키·nonce(IV) 조합의 재사용을 피해야 하고, 태그 검증에 실패한 데이터는 승인해서는 안 된다.
  - **ChaCha20-Poly1305**도 대칭키 AEAD로, 대칭키와 nonce를 사용해 기밀성과 무결성을 제공한다. OTP는 이상적인 조건에서 정보이론적 기밀성을 제공하지만, 단독으로 메시지 조작을 막지는 못한다.
  - **HPKE(Hybrid Public Key Encryption)**는 공개키 기반 키 확립(KEM), 키 유도(KDF), 데이터 암호화(AEAD)를 결합한다. 외부 이용자에게는 공개키 암호화로 보이지만 데이터 본문은 내부의 대칭키 AEAD가 보호하는 구조다.

|  |  |  |  |  |
| --- | --- | --- | --- | --- |
| **시스템 구성** | **키 확립** | **트래픽 키 유도** | **실제 데이터 보호** | **인증** |
| 기존 TLS 유형 | ECDHE | HKDF 기반 키 스케줄 | AES-GCM 또는 ChaCha20-Poly1305 | 인증서·서명 |
| PQC KEM 구성 | ML-KEM (또는 적절한 하이브리드) | KDF/키 스케줄 | AES-256-GCM 등 AEAD | ML-DSA 등 적용 가능 |
| QKD 링크 구성 | BB84 등 + 최종 키 추출 + KMS | 설계에 따른 키 할당·유도 | AES-256-GCM 또는 OTP | 인증된 고전채널 필요 |
| QKD+PQC 결합 | QKD 키 재료와 ML-KEM 공유 비밀 | 보안 분석된 결합 함수·KDF | AES-256-GCM 등 | 양자내성 서명/정보이론적 MAC 등 |

**📌 왜 데이터를 굳이 비대칭 암호로 직접 처리하지 않는가**

- - 대규모 데이터를 비대칭 연산만으로 보호하려면 계산 비용과 입력 크기·형식 제약이 커진다. 따라서 공개키 기술은 세션키 확립·캡슐화에 활용하고, 데이터 평면은 대칭키 암호로 처리하는 것이 일반적이다.
  - 1GB 파일도 ML-KEM이 파일 내용을 직접 암호화하는 것은 아니다. Bob의 공개키로 공유 비밀을 확보하고 키를 유도한 다음, AES-GCM 등 AEAD로 파일을 처리한다. 실무에서는 스트리밍·청크·nonce·키 갱신 정책을 추가로 정의해야 한다.
  - [RFC 9180](https://www.rfc-editor.org/rfc/rfc9180): HPKE의 KEM–KDF–AEAD 구조. 원래 RFC 9180에서 제공되는 알고리즘 목록을 곧바로 ML-KEM이 기본 포함된 것으로 해석해서는 안 된다. ML-KEM을 적용하려면 관련 프로파일·명세를 확인해야 한다.
  - [RFC 8446](https://www.rfc-editor.org/rfc/rfc8446): TLS 1.3의 키 스케줄과 인증된 레코드 암호화 구조.

**✅ 14. QKD와 PQC를 모두 사용해도 무엇이 취약해질 수 있는가**

- - 키가 안전하게 확립됐더라도 KMS·API·인크립터·단말에서 키가 유출되면 데이터 기밀성을 잃는다. QKD의 물리적 보안과 PQC의 수학적 보안은 종단 시스템의 침해 위험을 대체하지 않는다.
  - **인증 취약성**은 별개다. QKD의 공개 고전채널은 인증이 필요하다. PQC도 공개키의 소유자와 프로토콜 실행 주체를 안전하게 연결하지 않으면 중간자 공격 위험이 남는다.
  - QKD로 생성된 동일 비밀키 K를 별도 RSA 공개키 암호화로 다시 전송하는 잘못된 설계를 채택하면, 공격자가 그 RSA 암호문을 나중에 해독해 K를 확보할 경로가 생긴다. 이것은 QKD의 기본 동작이 아니라 추가된 취약 경로다.
  - 반대로 충분한 양자컴퓨터가 이후에 기존 서명 알고리즘을 무너뜨린다고 해서, 정상적으로 인증돼 종료된 과거 QKD 세션의 최종 키가 양자채널 기록으로부터 자동 복원되지는 않는다.
  - QKD+PQC 하이브리드에서 필요한 것은 "두 기술이 설치됐다"는 표시가 아니라 **비밀값 결합의 보안 증거, 공개키 인증, KMS의 키 출처·수명주기, 키 부족 시 fallback, 실제 인크립터 정책**이다.

|  |  |  |  |
| --- | --- | --- | --- |
| **위협·실패 지점** | **QKD에서의 영향** | **PQC에서의 영향** | **필요한 통제** |
| MITM / 공개키 바꿔치기 | 고전채널 인증 실패 시 상대방 사칭 | 공개키 소유자 확인 실패 시 잘못된 비밀 확립 | 상호 인증·신뢰 앵커·키 바인딩 |
| KMS·엔드포인트 침해 | 최종 QKD 키의 노출 가능 | ML-KEM에서 유도된 세션키의 노출 가능 | 키 격리, 접근통제, 삭제, 감사 |
| 양자광원·검출기 공격 | 모델 밖의 측면채널·오류 증가 | 해당 없음(물리적 QKD 광학장치 필요 없음) | 하드웨어 보안 평가·파라미터 검증 |
| nonce/키 재사용 | AES-GCM·OTP 사용 시 암호화 실패 가능 | 동일 | 키 수명주기, IV 정책, 키 교체 |
| 회선 단절·키 부족 | 키 생성 중단/서비스 가용성 저하 | 별도 QKD 링크 의존 없음 | 가용성 정책 및 안전한 장애 처리 |

---

**✅ 15. QKD를 쓰면 무조건 안전하다는 주장이 왜 위험한가**

- - 양자역학 원리를 이용한다고 해서 QKD 장비, 광원·검출기, 고전채널 인증, API, KMS, 사용자 단말, 운영자 계정까지 자동으로 안전해지는 것은 아니다.
  - 실제 장비의 광원 다광자 문제, 검출기 측면채널, 구현 불완전성, 광섬유 손실, 서비스거부 공격, KMS 침해, 키 재사용 등은 별도의 위협 모델에 속한다.
  - 특히 도청에 의해 오류가 증가하는 현상은 유용한 경보 신호지만, 서비스 가용성을 보장하는 것은 아니다. 공격자가 양자채널을 방해하면 안전한 키 생산 자체를 중단시킬 수 있다.
  - 정부 기관들의 기술 검토에서도 QKD는 기밀성의 일부만 해결하는 구성요소이며, PQC 대체 여부는 인프라 비용·장비 위험·통합 복잡성까지 포함해 판단해야 한다는 점을 강조한다.

**📌 충분히 강한 양자컴퓨터가 있다는 초기 질문에 대한 최종 답**

|  |  |  |
| --- | --- | --- |
| **키 확립·인증** | **데이터 암호화** | **평가** |
| QKD + 안전한 인증 | OTP + 일회용 무작위 키 | 조건 충족 시 정보이론적 기밀성; 별도 무결성 필요 |
| QKD + 안전한 인증 | AES-256-GCM | 강한 계산적 양자내성, 실용적 고속 암호화 |
| QKD + 취약한 RSA/ECDSA 인증 | AES-256-GCM | 키 자체보다 실시간 인증·MITM 경로가 취약 |
| ML-KEM + 양자내성 인증 | AES-256-GCM | QKD 없이도 알려진 양자공격에 대응 가능 |
| 기존 RSA/ECDH 키 설정 | AES-256-GCM | 양자컴퓨터가 키 설정을 깨면 AES가 강해도 세션 보호 실패 가능 |

- - 결론은 단순하다.

    - **QKD는 키를 확립하는 기술,**
    - **OTP·AES는 그 키로 메시지를 암호화하는 기술,**
    - **PQC는 공개키 기반 키 확립 또는 인증을 양자내성 방식으로 제공하는 기술**이다.
  - QKD의 장점은 비밀키 확립 과정에 양자역학의 물리적 성질을 이용한다는 데 있다. 그러나 충분한 양자컴퓨터가 있더라도 QKD만으로 엔드포인트·인증·네트워크 전체를 완전 방어한다는 주장은 성립하지 않는다.
  - 암호시스템을 설계할 때는 “AES가 안전한가, QKD가 안전한가”를 별개로 묻는 데서 그치지 않고 **키를 누가 만들고, 누가 접근하고, 어떻게 인증하고, 어디에 저장하고, 언제 폐기하는지**까지 추적해야 한다.
