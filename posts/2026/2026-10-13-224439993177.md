**✅ 1. Elisity는 세 가지 계층으로 구성된다**

**📌 핵심은 관리, 제어, 실제 정책 집행의 분리다**

- - Elisity는 클라우드 기반의 중앙 관리 기능과 기업 네트워크에서 동작하는 정책 집행 기능을 분리한 소프트웨어 정의 보안 아키텍처를 사용한다.
  - 가장 중요한 구성요소는 Cloud Control Center(CCC), Virtual Edge(VE), Virtual Edge Node(VEN)다.
  - 이 밖에도 IdentityGraph, Dynamic Policy Engine, Elisity Intelligence와 같은 중앙 분석·정책 기능이 있다.

|  |  |  |
| --- | --- | --- |
| **구성요소** | **주요 역할** | **일반적인 위치** |
| **Cloud Control Center (CCC)** | 중앙 관리, 장비 가시성, 정책 구성, 오케스트레이션 | Elisity Cloud |
| **IdentityGraph** | 사용자·장비·워크로드의 식별 정보 및 보안 상태 통합 | CCC 클라우드 |
| **Dynamic Policy Engine** | 신원 기반 정책 결정과 정책 배포 조율 | CCC 클라우드 |
| **Elisity Intelligence** | AI 기반 장비 분석 및 보안 정책 추천 | CCC 클라우드 |
| **Virtual Edge (VE)** | 텔레메트리 처리, 스위치 관리, 정책 전달 | 로컬 컨테이너·VM 또는 Azure |
| **Virtual Edge Node (VEN)** | 네트워크 정보 수집 및 보안 정책 집행 | 기업 네트워크의 지원 스위치 |

- - CCC는 정책을 정의하고 분석하는 중앙 관리 계층이다.
  - VE는 CCC와 현장의 스위치 사이에서 정보를 교환하고 정책 적용을 조율하는 컨트롤러 역할을 한다.
  - VEN은 실제 트래픽이 지나가는 지점에서 정책을 집행한다.
  - 따라서 **VE와 VEN을 동일한 구성요소로 이해해서는 안 된다.**

****

**📌 Control Plane과 Data Plane의 분리**

- - 기존 네트워크 기술에 익숙한 사람이라면 Control Plane과 Data Plane의 차이로 이해하면 쉽다.
  - CCC와 VE는 Elisity의 정책 관리 및 제어 기능을 수행한다.
  - 실제 패킷의 전달과 접근제어는 VEN의 기존 스위칭 기능으로 수행한다.
  - 따라서 Elisity의 제어 시스템이 모든 사용자 패킷을 직접 검사하거나 중계해야 하는 구조가 아니다.

|  |  |  |
| --- | --- | --- |
| **계층** | **담당 기능** | **실제 처리 대상** |
| Management / Policy | CCC, IdentityGraph, Policy Engine | 장비 신원, 정책, 분석 정보 |
| Control / Orchestration | VE | VEN 텔레메트리, 장비 관리, 정책 설정 |
| Data / Enforcement | VEN | 실제 사용자 패킷 전달 및 Allow/Deny 집행 |

- - 이러한 아키텍처는 기존 스위치가 보유한 하드웨어 기반 패킷 처리 능력을 재활용할 수 있게 한다.
  - 다만 모든 정책이 스위치의 어떤 하드웨어 기능으로 변환되는지는 제조사별로 다르다.

**✅ 2. Virtual Edge와 Virtual Edge Node는 무엇이 다른가?**

**📌 Virtual Edge는 정책 집행 장비가 아니라 컨트롤러다**

- - VE는 Elisity 소프트웨어가 실행되는 환경이다.
  - CCC로부터 보안 정책을 전달받고, 여러 VEN을 관리하며, 스위치에서 수집한 장비 식별 정보와 Flow Telemetry를 처리한다.
  - 다시 말해 VE는 데이터 수집과 네트워크 장비 제어를 연결하는 중간 계층이다.
  - VE는 여러 스위치를 동시에 관리할 수 있으므로, 반드시 스위치 한 대마다 VE 하나를 설치해야 하는 것은 아니다.

**📌 VEN은 기존 스위치가 맡는 역할이다**

- - VEN은 Elisity에 등록된 지원 네트워크 장비를 의미한다.
  - Cisco Catalyst, Arista, Juniper, HPE Aruba의 일부 스위치가 해당한다.
  - 모든 VEN에 별도의 Elisity 컨테이너나 에이전트를 설치해야 하는 것은 아니다.
  - 기존 스위치의 네이티브 기능과 관리 인터페이스를 활용해 텔레메트리를 수집하고 정책을 집행하는 것이 핵심이다.

|  |  |  |
| --- | --- | --- |
| **비교 항목** | **Virtual Edge (VE)** | **Virtual Edge Node (VEN)** |
| 주요 기능 | 정보 수집·처리, 정책 오케스트레이션 | 트래픽 관찰 및 정책 집행 |
| 실행 환경 | 컨테이너, VM, Azure VM | 지원되는 기존 스위치 |
| 사용자 패킷 전달 | 일반적으로 직접 처리하지 않음 | 실제 패킷 전달 |
| Flow Telemetry | VEN으로부터 수신·처리 | 수집 및 전송 |
| 보안 정책 | CCC의 정책을 장비 설정으로 전달 | 네이티브 기능으로 집행 |
| 하나로 여러 장비 관리 | 가능 | 해당 네트워크 지점에서 집행 |
| 추가 소프트웨어 | VE 실행 환경 필요 | 일반적으로 단말 에이전트 불필요 |

**📌 VEN은 일종의 네트워크 프로브 역할도 한다**

- - VEN은 자신에게 연결된 장비와 통신 관계를 관찰한다.
  - NetFlow/IPFIX 등 제조사별 지원 기능을 이용해 Flow 메타데이터를 VE로 전송할 수 있다.
  - VE는 이 정보를 CCC로 전달하여 장비 식별 및 트래픽 가시성에 활용하도록 한다.
  - 그러나 VEN을 단순한 모니터링 프로브라고만 부르기는 어렵다.
  - **VEN은 텔레메트리를 수집하는 동시에 실제 네트워크 접근을 제한하는 집행 지점이기 때문**이다.

**✅ 3. 실제 사용자 트래픽과 제어 트래픽은 서로 다른 경로를 사용한다**

**📌 사용자의 패킷은 클라우드까지 이동하지 않는다**

- - 예를 들어 병원 직원의 PC가 내부 PACS 서버에 접근한다고 가정해 보자.
  - 실제 사용자 패킷은 기존 네트워크 경로를 따라 스위치와 라우터를 지나 PACS 서버로 전달된다.
  - 이때 VEN은 해당 통신에 적용된 보안 정책을 확인하고 허용 또는 차단한다.
  - 반면 텔레메트리 정보는 별도의 제어·관리 경로를 통해 VE로 전달된다.
  - 따라서 VE를 Azure에 배포하더라도 사용자 패킷 전체가 Azure로 전송되는 것은 아니다.

**📌 세 가지 데이터 흐름을 구분해야 한다**

|  |  |  |
| --- | --- | --- |
| **데이터 흐름** | **이동 경로** | **주요 목적** |
| **사용자 트래픽** | PC → VEN → 목적지 서버 | 실제 업무 통신 |
| **텔레메트리** | VEN → VE → CCC | 장비 식별, Flow 분석, 가시성 확보 |
| **정책 및 관리 명령** | CCC → VE → VEN | 보안 정책 설정·갱신 |

- - 텔레메트리에는 일반적으로 출발지·목적지 IP, 포트, 프로토콜, 트래픽 통계 등의 정보가 포함된다.
  - 이는 패킷 Payload 전체를 전달하는 Deep Packet Inspection 방식과는 다르다.
  - 실제로 어떤 정보가 수집되는지는 Cisco, Arista, Juniper 등 장비별 텔레메트리 지원 기능에 따라 달라진다.

**📌 VE와 VEN 사이에는 양방향 통신이 필요하다**

- - VEN이 VE로 NetFlow 정보를 전송하는 것만으로 Elisity의 모든 기능이 구현되는 것은 아니다.
  - VE가 VEN에 접속해 스위치 설정을 읽고 보안 정책을 적용할 수 있어야 한다.
  - 예를 들어 Cisco Catalyst 9800 WLC 연동 문서에는 다음과 같은 통신이 명시되어 있다.

|  |  |  |
| --- | --- | --- |
| **프로토콜** | **방향** | **용도** |
| SSH / TCP 22 | VE → VEN | 관리 및 설정 |
| NetFlow / UDP 9996 | VEN → VE | Flow Telemetry |
| Syslog / UDP 514 | VEN → VE | 장비 이벤트 |
| CTS / TCP 9063 | 양방향 | Cisco TrustSec 관련 통신 |
| SXP / TCP 64999 | 양방향 | 보안 그룹 매핑 정보 교환 |
| HTTPS / TCP 443 | VE → CCC | 중앙 클라우드와 제어·관리 통신 |

- - 위 포트는 Cisco Catalyst 9800 WLC의 공식 배포 예시이며 모든 제조사의 VEN에 동일하게 적용되는 공통 포트 목록은 아니다.
  - 제조사와 장비 유형에 따라 SSH, API, NetFlow, IPFIX 등 실제 필요한 통신 방식이 달라진다.
  - 특히 VE를 클라우드에 설치할 경우 이러한 관리 통신까지 클라우드와 기업 네트워크 사이를 통과해야 한다.

**✅ 4. Virtual Edge와 Container는 같은 것일까?**

**📌 VE는 소프트웨어이고 Container는 실행 환경이다**

- - 이 부분은 기술적으로 혼동하기 쉽다.
  - Virtual Edge는 Elisity의 네트워크 보안 소프트웨어 구성요소를 의미한다.
  - Container는 해당 소프트웨어를 격리된 실행 환경에서 동작시키기 위한 기술이다.
  - VE는 반드시 컨테이너 형태로만 배포해야 하는 것이 아니다.
  - Cisco의 지원 스위치 내부에 컨테이너로 배포할 수도 있고, VMware ESXi나 Microsoft Hyper-V의 가상머신으로 실행할 수도 있다.

|  |  |  |
| --- | --- | --- |
| **구분** | **의미** | **Elisity에서의 활용** |
| Application | 실제 기능을 수행하는 소프트웨어 | Virtual Edge |
| Container | 호스트 운영체제 자원을 활용하는 격리된 실행 환경 | Switch-hosted VE |
| Virtual Machine | 가상 하드웨어와 게스트 OS를 갖춘 실행 환경 | Hypervisor-hosted VE |
| Cloud VM | 클라우드에서 제공하는 가상머신 | Azure-hosted VE |

**📌 Cisco 스위치 자체에서 컨테이너를 실행할 수 있다**

- - Cisco Catalyst 일부 모델은 Application Hosting 기능을 제공한다.
  - 스위치의 CPU, 메모리, 스토리지 자원을 이용해 네트워크 OS와 별도로 애플리케이션을 실행하는 기술이다.
  - Elisity는 이 기능을 이용해 VE 컨테이너를 실행한다.
  - 다만 아무 Catalyst 스위치에나 설치할 수 있는 것은 아니며 모델별 지원 여부와 SSD, IOS XE, 라이선스 요건을 확인해야 한다.
  - 또한 해당 스위치가 VE를 호스팅한다고 해서 반드시 자기 자신만 VEN으로 관리해야 하는 것도 아니다.
  - 한 대의 VE가 다른 여러 스위치를 VEN으로 관리할 수 있다.

**✅ 5. Elisity의 세 가지 VE 배포 모델**

**📌 ① Switch-hosted — 스위치 내부에 VE 컨테이너 배포**

- - Cisco Catalyst 9300 및 9400 등 지원 장비에서 Application Hosting을 통해 VE를 실행한다.
  - 별도의 VE 전용 서버를 구축하지 않아도 된다는 장점이 있다.
  - 스위치 자신을 VEN으로 등록하는 1:1 모델과, 하나의 VE가 여러 VEN을 관리하는 1 모델을 지원한다.
  - 반면 스위치 자체의 CPU·메모리·스토리지 자원에 의존한다.
  - 지원 SSD와 DNA Advantage 등 관련 라이선스가 필요할 수 있다.
  - 스위치 장애가 VE 실행 환경의 장애로 이어질 수 있으므로 이중화 설계를 고려해야 한다.

**📌 ② Hypervisor-hosted — 기존 가상화 인프라에 VE 배포**

- - VMware ESXi 또는 Microsoft Hyper-V에 VE VM을 설치하는 방식이다.
  - 별도의 스위치 컨테이너 호스팅 기능이 필요하지 않다.
  - 가상화 환경에서 CPU, 메모리, 스토리지 자원을 할당하고 여러 스위치를 중앙에서 관리할 수 있다.
  - VE Group을 이용한 이중화 및 Failover 구성에도 유리하다.
  - 하지만 가상화 호스트와 스위치 관리망 사이의 안정적인 통신 경로가 필요하다.

**📌 ③ Azure Cloud-hosted — VE까지 클라우드에 배포**

- - VE를 Microsoft Azure의 VM으로 실행한다.
  - CCC와 VE가 모두 클라우드에 위치하지만, CCC는 Elisity가 제공하는 SaaS이고 VE는 별도의 Azure VM 환경이라는 차이가 있다.
  - Azure VE는 기업 네트워크의 VEN과 VPN, ExpressRoute 등 사설 IP 경로로 연결해야 한다.
  - Elisity 공식 문서는 이 모델이 다른 VE 배포 방식과 핵심 기능 면에서 동일하다고 설명한다.
  - 다만 지리적인 거리와 WAN 의존성이 증가하므로 운영 특성은 달라질 수 있다.

**📌 세 가지 모델의 비교**

|  |  |  |  |
| --- | --- | --- | --- |
| **항목** | **Switch-hosted** | **Hypervisor-hosted** | **Azure-hosted** |
| VE 실행 위치 | 지원 Cisco 스위치 내부 | 온프레미스 가상머신 | Azure VM |
| 별도 VE 서버 | 불필요할 수 있음 | 필요 | Azure VM 필요 |
| 장비 제약 | 호스팅 지원 스위치 필요 | 지원 Hypervisor 필요 | Azure 인프라 필요 |
| VEN과 통신 | 로컬망·라우팅 경유 | 주로 로컬·사내망 | VPN·ExpressRoute 등 |
| CCC 연결 | 필요 | 필요 | 필요 |
| 핵심 보안 기능 | 지원 | 지원 | 지원 |
| VE Group 기반 HA | 배포 유형·버전 제약 | 지원 | 지원되는 VM 기반 구성 |
| 주요 장점 | 별도 VM 인프라 감소 | 확장·운영·이중화 유연성 | 중앙집중형 클라우드 운영 |
| 주요 제약 | 스위치 자원·SSD·라이선스 | 서버·가상화 운영 부담 | WAN 및 클라우드 연결 의존성 |

**📌 VM에 필요한 최소 자원**

|  |  |  |
| --- | --- | --- |
| **자원** | **로컬 VMware / Hyper-V VE** | **Azure VE** |
| vCPU | 8 vCPU | 8 vCPU |
| RAM | 8GB | 16GB |
| Storage | 40GB | OS Disk 64GB 이상 |
| 배포 형태 | OVA / VHDX | Azure Marketplace VM |
| IP 연결 | CCC와 VEN 통신 필요 | CCC 연결 + VEN과 사설 IP 연결 |

- - 위 사양은 공식 배포 문서에 제시된 기본 요구사항이다.
  - 대규모 환경에서 필요한 VE 수량이나 처리 성능은 스위치 수, 관리 범위, 실제 Flow 발생량 등에 따라 별도로 검증해야 한다.

**✅ 6. 로컬 VE와 클라우드 VE의 차이는 무엇인가?**

**📌 CCC는 어차피 클라우드에 있는데 VE를 로컬에 둘 필요가 있을까?**

- - 앞서 살펴본 바와 같이 CCC의 IdentityGraph와 Dynamic Policy Engine은 클라우드에서 작동한다.
  - 따라서 VE를 로컬에 설치한다고 해서 전체 보안 분석과 정책 관리가 로컬에서만 완결되는 것은 아니다.
  - 그렇다면 VE까지 클라우드로 옮기는 편이 더 단순하지 않을까?
  - 이 질문의 답은 VEN에서 수집하는 정보의 처리 위치와 현장 스위치의 제어 경로에서 찾을 수 있다.

**📌 모델 A — VE와 VEN이 모두 로컬에 있는 경우**

- - VEN이 수집한 텔레메트리는 로컬 VE로 전달된다.
  - VE는 데이터를 처리하고 중앙 CCC와 통신한다.
  - CCC에서 결정된 정책은 다시 로컬 VE를 통해 VEN에 전달된다.
  - 즉, VEN과 VE 사이의 관리·텔레메트리 통신을 기업 내부망에서 유지할 수 있다.

**📌 모델 B — VE까지 클라우드에 있는 경우**

- - VEN의 텔레메트리는 사설 WAN 경로를 통해 클라우드 VE에 전달된다.
  - 클라우드 VE는 CCC와 정보를 교환하고 정책을 받아 다시 WAN을 통해 현장 VEN에 전달한다.
  - 실제 사용자 패킷은 기존 로컬 네트워크에서 전달되므로 Azure VE를 반드시 통과하지 않는다.
  - 그러나 텔레메트리와 스위치 관리 트래픽의 WAN 의존성은 커진다.

**📌 두 아키텍처의 실제 차이**

|  |  |  |
| --- | --- | --- |
| **비교 항목** | **로컬 VE + 로컬 VEN** | **클라우드 VE + 로컬 VEN** |
| VEN → VE 텔레메트리 | LAN·사내망 | 사설 WAN 경유 |
| VE → CCC 정보 교환 | 클라우드 연결 | 클라우드 간 통신 |
| VEN 관리 명령 | 사내망에서 전달 | WAN을 통해 전달 |
| 사용자 패킷 전달 | 로컬 데이터 경로 | 로컬 데이터 경로 |
| 중앙 IdentityGraph | CCC 클라우드 | CCC 클라우드 |
| 중앙 정책 결정 | CCC 클라우드 | CCC 클라우드 |
| 신규 장비 식별·정책 갱신 | CCC 연결 및 로컬 VE 상태에 의존 | CCC 연결 및 VEN–Azure 경로에 의존 |
| WAN 장애 시 VEN–VE 통신 | 유지될 수 있음 | WAN 경로가 끊기면 불가능 |
| WAN 대역폭 부담 | VE–CCC 전송 데이터 | VEN–VE 텔레메트리까지 포함 |
| 운영상 장점 | 로컬 제어 경로 유지 | 로컬 VE 인프라 운영 축소 |

- - 가장 중요한 차이는 **VE를 클라우드에 둘 때 VEN의 텔레메트리와 관리 트래픽이 추가로 WAN을 통과한다는 점**이다.
  - 다만 CCC는 어느 모델에서나 클라우드에 있으므로 로컬 VE가 모든 정책 결정을 독립적으로 수행하는 것은 아니다.
  - 또한 로컬 VE가 수집 정보를 얼마나 집계·축약한 뒤 CCC로 전송하는지는 공개 자료만으로 정량화하기 어렵다.
  - 따라서 로컬 VE가 WAN 트래픽을 몇 퍼센트 절감한다거나, 정책 반영이 몇 배 빠르다고 단정할 수는 없다.

**✅ 7. WAN 장애가 발생하면 어떻게 될까?**

**📌 기존 정책 집행과 새로운 정책 갱신은 다르다**

- - 예를 들어 병원과 클라우드 사이의 WAN 연결이 끊어졌다고 가정해 보자.
  - 이때 중요한 것은 이미 스위치에 적용되어 있는 보안 규칙과 새롭게 적용해야 할 정책을 구분하는 것이다.
  - Elisity는 실제 정책을 스위치의 네이티브 기능으로 집행하므로 CCC 또는 VE가 일시적으로 접근 불가능해졌다고 해서 기존의 모든 ACL이 자동으로 사라지는 구조는 아니다.
  - 그러나 새로운 장비의 식별, 변경된 보안 상태에 따른 정책 갱신, 텔레메트리 수집에는 영향이 발생할 수 있다.

|  |  |  |
| --- | --- | --- |
| **장애 상황** | **로컬 VE + VEN** | **클라우드 VE + 로컬 VEN** |
| CCC 연결 장애 | VE–VEN 연결 유지 가능 | VE–VEN 연결은 별도로 유지될 수 있음 |
| 현장–Azure WAN 장애 | VE–VEN 로컬 통신 가능 | VE–VEN 연결 단절 가능 |
| 기존 스위치 정책 | 일반적으로 계속 집행 | 일반적으로 계속 집행 |
| 새로운 중앙 정책 전달 | CCC 복구까지 제한 | 연결 복구까지 제한 |
| 로컬 텔레메트리 수신 | VE가 정상이라면 가능 | Azure 경로 단절 시 제한 |
| 중앙 분석 정보 갱신 | CCC와 통신 불가 시 제한 | 통신 단절 시 제한 |

- - 여기서 로컬 VE가 유리한 부분은 현장 VEN과의 관리 연결을 WAN 장애 중에도 유지할 수 있다는 것이다.
  - 다만 중앙의 새로운 정책 결정이나 클라우드 분석 기능까지 로컬에서 완전히 수행한다는 뜻은 아니다.

**📌 VE Group과 High Availability**

- - Elisity는 Virtual Edge Group 기능을 제공한다.
  - 여러 VE를 하나의 그룹으로 묶고 VEN 관리 역할을 분담할 수 있으며, 특정 VE에 장애가 발생하면 다른 VE가 VEN 관리를 넘겨받을 수 있다.
  - 공식 문서에 따르면 VE Group은 VE 16.x Hypervisor-hosted 배포에서 완전히 지원된다.
  - 반면 1:1 Switch-hosted 방식에서는 Standalone 모델을 사용하는 구성이 존재한다.
  - Cisco StackWise를 이용한 Switch-hosted VE 이중화 역시 별도 구성 방식으로 지원된다.

|  |  |  |
| --- | --- | --- |
| **HA 방식** | **주요 목적** | **주의사항** |
| Cisco StackWise 기반 이중화 | 스위치 호스팅 환경의 가용성 향상 | StackWise 구성과 장애 범위 고려 |
| Hypervisor VE Group | 여러 VE 간 VEN 관리 전환 | 모든 VE가 대상 VEN에 접근 가능해야 함 |
| Azure VE Group | 클라우드 VE의 장애 복구 | 동일 WAN 장애에 대한 대책은 별도 필요 |

- - 특히 모든 VE를 같은 Azure 지역에 배포하고 기업 네트워크와 Azure를 연결하는 단일 WAN 경로만 사용한다면 VE 수량을 늘려도 WAN 단절 문제 자체를 해결할 수 없다.
  - **고가용성은 서버 수량뿐 아니라 네트워크 경로의 독립성까지 고려해야 한다.**

**✅ 8. 모든 스위치가 VE를 실행할 수 있는 것은 아니다**

**📌 VE Container Hosting과 VEN Policy Enforcement는 별개의 지원 항목이다**

- - Cisco Catalyst 9200과 9500은 Elisity의 정책 집행 지점으로 활용할 수 있지만, 공식 호환성 표상 VE 컨테이너 호스팅 대상은 아니다.
  - 반면 지원 Catalyst 9300/9400 계열은 VE 실행과 VEN 역할을 모두 수행할 수 있다.
  - 2026년 10월 기준 공식 호환성 표에는 Catalyst 9350도 VE 호스팅 지원 모델로 등재되어 있다.

|  |  |  |
| --- | --- | --- |
| **Cisco 모델** | **VE 컨테이너 호스팅** | **VEN 정책 집행** |
| Catalyst 9200 계열 | 미지원 | 지원 |
| Catalyst 9300 / 9300L / 9300X | 지원 | 지원 |
| Catalyst 9300LM | 지원 — 별도 SSD 조건 | 지원 여부는 모델별 확인 |
| Catalyst 9350 | 지원 | 지원 |
| Catalyst 9400 | 지원 | 지원 |
| Catalyst 9500 | 미지원 | 지원 |
| Catalyst 9600 | 미지원 | 지원 |
| Catalyst 3650 / 3850 | 미지원 | 지원 |
| Catalyst IE3400 | 미지원 | 지원 |

- - 공식 호환성 자료에서는 Catalyst 9500X 및 9600X의 Flow Telemetry 수집이 지원되지 않는다는 제약도 명시되어 있다.
  - 즉, **VEN 정책 집행을 지원한다는 것과 모든 종류의 텔레메트리까지 동일하게 지원한다는 것은 별개의 문제**다.
  - 또한 모델별 IOS XE 버전과 라이선스 조건이 다르다.

**📌 Cisco 외 제조사도 VEN으로 사용할 수 있다**

- - Elisity는 Cisco 전용 마이크로세그멘테이션 플랫폼이 아니다.
  - Arista, Juniper, HPE Aruba 스위치의 일부 제품에서도 정책 집행을 지원한다.
  - 다만 이러한 제조사들이 VE 컨테이너를 직접 호스팅한다는 의미는 아니다.

|  |  |  |  |
| --- | --- | --- | --- |
| **제조사** | **VE 직접 호스팅** | **VEN으로 활용** | **주요 기술적 제약** |
| Cisco Catalyst | 일부 모델 지원 | 다수 모델 지원 | IOS XE, 라이선스, ASIC/텔레메트리 제약 |
| Arista EOS | 공식 호환성 목록에 없음 | 지원 | MSS 라이선스·TCAM 및 모델별 제약 |
| Juniper EX | 공식 호환성 목록에 없음 | 지원 | GBP/EVPN-VXLAN 조건, L3/L4 제약 |
| HPE Aruba CX | 공식 호환성 목록에 없음 | 지원 | 현재 일부 통합에서 L3 정책만 지원 |

- - Juniper의 직접 연동 문서에는 EX4100/EX4400에서 Layer 4 정책이 지원되지 않고 Layer 3 기반 집행이 중심이라고 설명되어 있다.
  - HPE Aruba CX 연동 문서도 해당 플랫폼의 Layer 4 정책 집행에 제한이 있다고 명시한다.
  - 반대로 Arista는 MSS 기술과 EOS 기능을 이용하며, 일부 모델에서 그룹 수와 TCAM 자원에 제약이 존재한다.
  - 따라서 동일한 CCC와 VE를 사용하더라도 정책 집행의 세밀함과 가시성은 모든 제조사에서 똑같지 않다.

**✅ 9. 그렇다면 실제 네트워크에는 얼마나 많은 장비가 필요할까?**

**📌 VE 한 대로 여러 VEN을 관리할 수 있다**

- - 하나의 사이트에 Catalyst 9300 한 대와 Catalyst 9200 액세스 스위치 여러 대가 있다고 가정해 보자.
  - Catalyst 9300에 VE 컨테이너를 실행하고 해당 스위치 및 여러 Catalyst 9200을 VEN으로 등록할 수 있다.
  - 또는 기존 VMware 인프라에 VE VM을 설치하고 이 스위치들을 모두 VEN으로 등록할 수 있다.
  - 따라서 각 액세스 스위치마다 새 보안 장비를 한 대씩 배치해야 하는 구조는 아니다.
  - **가상의 병원 캠퍼스 구성**

|  |  |  |
| --- | --- | --- |
| **구성요소** | **예시 수량** | **Elisity 적용 방식** |
| Catalyst 9300 | 2대 | VE 호스팅 후보 및 VEN |
| Catalyst 9200 | 30대 | VEN |
| Catalyst 9500 | 2대 | 필요 시 VEN |
| 업무용 PC | 1,000대 | 기존 스위치를 통해 정책 적용 |
| 의료장비·IoT | 400대 | 단말 에이전트 없이 정책 적용 |
| CCC | 고객별 SaaS 환경 | 중앙 관리 |
| VE | 설계에 따라 결정 | 스위치 컨테이너 또는 VM |

- - 이 예시는 배포 방식을 설명하기 위한 가상 구성이다.
  - VE가 몇 대 필요한지는 단순히 스위치 30대 또는 단말 1,400대라는 숫자만으로 결정할 수 없다.
  - 스위치가 발생시키는 텔레메트리량, 사이트 간 연결, 지원되는 정책 수, 장애 복구 목표 등이 함께 고려되어야 한다.
  - 또한 미지원 스위치가 존재하면 지원되는 상위 네트워크 장비를 집행 지점으로 활용하는 설계도 가능하지만, 실제 보호할 수 있는 트래픽의 범위가 달라질 수 있다.

**📌 기존 장비만 사용해도 추가 비용은 발생할 수 있다**

- - Elisity가 기존 스위치를 활용한다는 표현은 추가 인프라 비용이 전혀 없다는 뜻이 아니다.
  - 지원 모델이 아닌 스위치를 교체해야 할 수도 있고, VE 컨테이너용 SSD, 애플리케이션 호스팅 라이선스, 가상화 자원 또는 Azure VM 비용 등이 필요할 수 있다.
  - 특히 스위치 제조사별 기능 지원 수준이 달라 PoC를 통한 검증이 중요하다.

|  |  |
| --- | --- |
| **비용 요소** | **발생 가능 조건** |
| 스위치 교체 | 기존 스위치가 VEN 기능을 지원하지 않는 경우 |
| SSD 구매 | Switch-hosted VE에 지원 스토리지가 필요한 경우 |
| 라이선스 | Cisco App Hosting, Arista MSS 등 |
| 가상화 자원 | Hypervisor-hosted VE 사용 |
| Azure 비용 | Cloud-hosted VE 사용 |
| 네트워크 회선 | Azure와 VEN 간 사설 연결 구성 |
| 운영 비용 | 소프트웨어·정책·스위치 변경 관리 |

---

**✅ 10. Elisity 아키텍처에도 기술적 한계가 있다**

**📌 기존 스위치를 활용한다는 것은 그 스위치의 한계도 함께 가진다는 의미다**

- - 기존 스위치를 활용하면 별도의 Inline 보안 장비를 설치하지 않아도 된다는 장점이 있다.
  - 그러나 스위치의 하드웨어 기능에 의존하므로 ACL·TCAM·보안 그룹 지원 수량이 정책 확장성을 제한할 수 있다.
  - 동일 VLAN 내 통신, VLAN 간 통신, 무선 단말, 클라우드 워크로드가 모두 같은 지점에서 정책 집행을 받는 것도 아니다.
  - 실제 트래픽이 정책 집행 지점을 통과해야 한다는 조건도 중요하다.
  - 예를 들어 특정 네트워크 경로가 VEN을 통과하지 않는다면 해당 VEN에서 직접 차단할 수 없다.

**📌 도입 전에 확인해야 할 기술적 질문**

|  |  |
| --- | --- |
| **검증 항목** | **확인해야 할 사항** |
| 하드웨어 호환성 | 현재 스위치 모델과 OS 버전이 지원되는가? |
| 정책 집행 범위 | 동일 VLAN 및 VLAN 간 트래픽 모두 통제 가능한가? |
| 하드웨어 자원 | TCAM·ACL·Tag 자원에 충분한 여유가 있는가? |
| 텔레메트리 처리 | VEN당 Flow 데이터 발생량과 VE 처리량은 얼마인가? |
| 정책 반영 시간 | 새로운 정책이 실제 스위치에 적용되기까지 얼마나 걸리는가? |
| 고가용성 | VE 장애·WAN 장애에서 어떤 기능이 유지되는가? |
| 관리망 보안 | VE가 스위치 관리 인터페이스에 안전하게 접근할 수 있는가? |
| 운영 충돌 | 기존 ISE, DNAC, Aruba Central 등과 설정 충돌이 없는가? |
| 배포 비용 | SSD, 라이선스, VM, 네트워크 연결 비용은 얼마인가? |

- - 특히 의료기관이나 OT 네트워크처럼 가용성이 중요한 환경에서는 단순히 정책이 적용된다는 사실보다 정책 변경이 기존 서비스에 어떤 영향을 주는지를 검증해야 한다.
  - 새로운 정책을 활성화하기 전에 Simulation Mode로 영향을 파악하고 단계적으로 적용하는 것이 중요한 이유다.

---

**✅ 결론 — Elisity의 강점은 스위치를 새로 만드는 것이 아니라 기존 스위치의 역할을 확장하는 데 있다**

- - Elisity는 기존 네트워크 스위치를 활용해 신원 기반 접근 정책을 집행하도록 설계된 플랫폼이다.
  - CCC는 신원과 정책을 관리하고, VE는 텔레메트리와 정책의 전달 및 장비 관리를 담당하며, VEN은 실제 네트워크 트래픽에 정책을 집행한다.
  - 이처럼 관리와 집행 기능을 분리한 아키텍처 덕분에 기업은 기존 인프라를 최대한 활용하면서 마이크로세그멘테이션을 구현할 수 있다.
  - 다만 모든 스위치가 동일한 기능을 제공하는 것은 아니며, VE의 배포 방식에 따라 WAN 의존성, 가용성, 운영 비용이 달라진다.
  - 또한 기존 스위치를 활용하는 기술 자체가 Elisity만의 독점적인 방식인 것도 아니다. 다른 경쟁사들도 호스트 방화벽이나 네트워크 장비의 기존 기능을 활용하는 방향으로 발전하고 있다.
  - 따라서 Elisity의 경쟁력은 단순히 새 장비가 적게 필요하다는 것보다 **기존 네트워크에서 얼마나 정확하고 세밀하게 정책을 집행할 수 있으며, 이를 얼마나 쉽게 운영할 수 있는지**에서 찾아야 할 것이다.
  - 이번 글에서는 Elisity의 전체 아키텍처를 살펴보았다.
  - 하지만 여전히 가장 근본적인 질문이 남아 있다.
  - **VEN이 수집한 텔레메트리를 VE와 CCC는 실제로 어떻게 분석할까?**
  - MAC 주소와 IP, Flow 정보만으로 장비의 정체를 얼마나 정확하게 파악할 수 있으며, 어떤 위험 행동을 식별할 수 있을까?

**✅ 용어 정리 (Glossary)**

|  |  |
| --- | --- |
| **용어** | **의미** |
| **CCC (Cloud Control Center)** | Elisity의 클라우드 기반 중앙 관리·정책 플랫폼 |
| **VE (Virtual Edge)** | 텔레메트리 수집·처리, 정책 전달 및 스위치 관리를 수행하는 소프트웨어 |
| **VEN (Virtual Edge Node)** | Elisity에 등록되어 텔레메트리를 제공하고 정책을 집행하는 네트워크 장비 |
| **Container** | 애플리케이션을 격리된 실행 환경에서 실행하는 기술 |
| **Application Hosting** | 네트워크 스위치 등의 장비에서 별도 애플리케이션을 실행하는 기능 |
| **Hypervisor** | VMware ESXi 등 가상머신을 실행·관리하는 가상화 계층 |
| **Control Plane** | 네트워크 장비의 관리·정책 제어를 담당하는 논리적 계층 |
| **Data Plane** | 실제 네트워크 패킷을 전달하거나 차단하는 계층 |
| **Telemetry** | 장비에서 수집되어 분석·관리 시스템으로 전달되는 관측 정보 |
| **NetFlow / IPFIX** | 네트워크 Flow 메타데이터와 통계를 수집·전송하는 기술 |
| **CTS (Cisco TrustSec)** | Cisco의 보안 그룹 기반 네트워크 정책 기술 |
| **SGT (Security Group Tag)** | Cisco TrustSec에서 사용하는 보안 그룹 식별 태그 |
| **SXP (SGT Exchange Protocol)** | IP 주소와 SGT 등의 매핑 정보를 교환하는 프로토콜 |
| **TCAM** | 스위치 ASIC에서 ACL·라우팅 등 고속 테이블 조회에 사용하는 메모리 |
| **VE Group** | 여러 VE를 묶어 관리 및 장애 복구에 활용하는 구성 |
| **HA (High Availability)** | 장비·소프트웨어 장애 시에도 서비스를 지속하도록 하는 고가용성 설계 |
| **Distribution Zone** | Elisity에서 장비 그룹 매핑과 정책 집행 범위를 관리하는 논리적 구역 |
| **PoC (Proof of Concept)** | 실제 환경에서 기술의 적용 가능성과 성능을 검증하는 시험 |
