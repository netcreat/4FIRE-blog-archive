**✅ Pinnacle이 뭔대? Iceberg Quantum이 무슨 일을 했길래?**

- - 그동안 수많은 순수 과학자들과 각 기업의 연구자들이 뛰어난 QEC 코드를 개발하고, 논리 큐비트를 만들기 위해 엄청난 노력을 많이 했는데,
  - Iceberg Quantum의 연구는 기존의 그것들과 무엇이 다른 걸까?

**📌 먼저 현실부터**

- - 이전까지 QLDPC는 이런 평가를 받아왔다:
  - 논리큐비트 밀도 좋다

    - 그런데 **계산을 돌리기가 어렵다**
    - magic state 공급 구조가 불명확
    - 병렬화하면 복잡도 폭발
    - 필요한 논리 측정들을 빠르게 못함
  - 즉,
  - “좋은 코드지만, 컴퓨터 구조로 완성되지 못했다.”

**📌 Pinnacle이 새로 한 것 = QLDPC를 “이론”에서 “공장 설계도”로 끌어내림.**

****

**1️⃣ 가장 큰 차이:**

> *❌ 코드 → ⭕ 아키텍처*

- - 이전 연구들:

    - “이 코드 좋아요.”
  - Pinnacle:

    - “좋아. 그럼 RSA를 어떻게 돌릴 건데?”
    - “T-state 어디서 나오는데?”
    - “병렬은?”
    - “메모리는?”
    - “시간 계산은?”
  - 끝까지 밀어붙임.
  - 그래서 이 논문은

    - **decoder**
    - **reaction time**
    - **magic reject rate**
    - **logical cycle**
    - **실제 알고리즘 컴파일**
  - 전부 포함한다.
  - 이게 엄청난 차이.

**2️⃣ 이전 QLDPC의 결정적 약점**

- - 예전 구조들의 공통 문제:

    - **arbitrary logical Pauli measurement가 느렸다.**

      - → 원하는 논리 Pauli를 마음대로 골라서 빠르게 측정할 수 있어야 하는데 예전 QLDPC 구조에서는 그게 느리거나 복잡했다.
  - 그래서:

    - 어떤 연산은 되고
    - 어떤 연산은 못하고
    - 특정 방향으로만 surgery 가능
  - → 범용 컴퓨터가 되기 어려웠음.

**3️⃣ Pinnacle의 핵심 혁신 중 하나**

- - **generalized measurement gadget**

    - 이걸 이용함으로써,
    - 매 logical cycle마다 원하는 어떤 Pauli든 측정 가능.
  - 이게 무슨 의미냐면?

    - Pauli-based computation을 제대로 돌릴 수 있음
    - Clifford 뒤로 밀어버리는 전략 가능
    - T-state injection이 정규화됨
  - 즉, 계산 파이프라인이 만들어짐.

**4️⃣ Magic state 문제 해결**

- - **이전 QLDPC 연구:**

    - distillation 팩토리 어디?
    - 언제 만들고 언제 쓰지?
    - 한마디로 실용성이 부족했다.
  - **Pinnacle:**

    - **Magic Engine 도입하여** 한 블록 안에서:

      - 다음 사이클에 쓸 걸 만들면서
      - 동시에 현재 연산에 공급

        - → steady throughput 확보.
    - 이건 surface code 설계에서나 보던 개념을 QLDPC에 이식한 것.

**5️⃣ 병렬화 문제 해결**

- - 이전:

    - Clifford frame 때문에 processing unit이 서로 얽히면 병렬 깨짐.
  - Pinnacle:

    - **Clifford Frame Cleaning** 몇 번 추가 측정하면
    - → 다시 독립 가능.
  - 이건 실제 컴퓨터 설계에서 엄청 중요.

**6️⃣ 연결성 현실화**

- - **이전 QLDPC 비판:**

    - 결국 멀리 연결해야 하잖아.

      - Surface Code 대비 배선과 광학, 컨트롤이 복잡하여 스케일업에 제한 있다는 의미
  - **Pinnacle 주장:**

    - 아니다.
    - 연결은 **블록 크기 범위**면 충분
    - 라우팅 필요 없음
    - 모듈형 HW 가능

> 자세한 내용은 뒤에서 설명하겠다.

**7️⃣ 그리고 마지막 킬러 포인트 - 실제 숫자를 끝까지 계산했다.**

- - RSA
  - Fermi-Hubbard

    - [용어 정리] 격자 위에서 전자들이 이동(hopping)하고 서로 밀어내는(repulsion) 양자 상호작용을 계산하는 문제.
  - → 필요한 큐비트 / 시간 전부 계산.
  - 이전 논문들은 여기서 멈췄음.

**📌 그래서 업계가 왜 반응할 수 있냐면**

- - 이건 단순 코드 논문이 아니라:

    - "QLDPC로 진짜 컴퓨터 만들면 이렇게 됩니다." 를 보여주는 첫 세대에 가까움.

> *기존* ***QLDPC*** *= 좋은 재료*
>
> ***Pinnacle*** *= 조립된 엔진 + 생산라인*

**✅ 그럼 Surface Code는?**

**📌 Surface code 는 지난 15년 동안**

- - 임계값(threshold) 이해 잘 되어 있고
  - 디코더 성능 축적되어 있고
  - 수술(lattice surgery) 방법 정리되어 있고
  - 매직 스테이트 팩토리 설계 수없이 반복되었고
  - 리소스 계산 체계가 확립되어 있고
  - 실험 데모도 존재
  - **즉, 산업적으로 사용할 준비가 가장 많이 된 코드**

**📌** **Surface code “Factory + Data” (전통 주류)**

- - **구성**

    - “데이터(논리 큐비트 저장/연산 영역)” + “T-state 팩토리(매직 상태 증류 공장)”를 **물리적으로 크게 분리**해서 운영
    - 비(非)클리포드(T) 연산은 결국 T-state 공급량(throughput)에 맞춰 진행 속도가 결정됨(팩토리가 병목이 되기 쉬움)
  - **특징(일반적)**

    - 최근접 2D 격자 친화적(하드웨어 요건 단순)
    - 대신 **논리 1개당 물리 큐비트가 매우 큼** → 총 물리 큐비트가 백만 단위로 튀는 추정이 많았음(논문도 기존 관점으로 언급)

> *qLDPC는 이론적으로 논리 밀도가 좋지만 여러 기술적 한계가 존재했다.*
>
> *다시 말해 수학은 앞서 있었지만 공학은 뒤에 있었다.*

**📌** **Pinnacle(QLDPC) “Processing Unit + Magic Engine(+Memory)” (이 논문)**

- - **구성(모듈 3종)**

    1. **Processing Unit**: QLDPC “브리지드” 블록 + 측정 가젯으로 **매 logical cycle마다 임의의 논리 Pauli 곱 측정** 가능
    2. **Magic Engine**: QLDPC 블록 하나가 “한 사이클에”

       - (병렬로) 이번 사이클 주입(injection)을 수행하면서
       - **다음 사이클에 쓸 고충실도 매직 상태를 동시에 증류/준비**해서
       - → **processing unit 당 매 logical cycle마다 고품질 매직 상태 1개를 지속 공급**하는 구조
    3. **Memory(옵션)**: 저장 전용을 싸게 두고, 포트로 여러 processing unit이 병렬 접근(읽기 중심)
  - **핵심 설계 의도**

    - surface code처럼 “거대한 중앙 팩토리”에 의존하기보다, **유닛 단위로 매직 공급을 내장**하고 병렬 확장(유닛 수 = 병렬도)으로 런타임/큐비트 트레이드오프를 설계
    - 장거리 all-to-all 대신, **연결은 ‘블록 스케일’에서 상수로 제한**되는 방향을 강조(라우팅 의존 최소화)

**✅ RSA-2048에서 “병목”이 어디서 바뀌나?**

- - RSA-2048(쇼어 계열)에서 보통 병목 후보는 크게 4개다.

**📌** **병목 ① 물리 큐비트 총량(공간 오버헤드)**

- - **Surface code**: 논리 1개당 물리 오버헤드가 커서 “백만 단위”가 흔한 추정(논문이 기존 관점을 이렇게 요약)
  - **Pinnacle**: QLDPC로 한 블록에 논리 여러 개를 넣고, 측정 가젯으로 연산을 뽑아내서 **총 물리 큐비트를 한 자릿수 줄이는 게 목표/결과**(RSA-2048을 <100k 물리 큐비트로 제시)
  - ➡️ **병목이 “****큐비트 수”에서 일부 완화**되는 게 1차 변화.

**📌** **병목 ② T-state(매직 상태) 처리량**

- - **Surface code**: 중앙 팩토리가 T-state 생산 속도를 결정 → 데이터가 팩토리를 기다리는 경우가 잦음(클래식한 병목)
  - **Pinnacle**: Magic Engine이 “cycle당 1개”를 계속 뽑아 유닛에 공급하도록 설계

    - 단, distillation은 **reject(실패) 확률**이 있어, 실패 시 한 사이클 쉬는 비용이 생김(논문은 이를 α=(1-pr)⁻¹ 형태로 반영)
  - ➡️ 병목이 “거대 팩토리 규모 설계”에서 “유닛당 안정적 매직 공급 + reject 관리”로 이동.

**📌** **병목 ③ 병렬화(유닛 간 얽힘/클리포드 프레임 문제)**

- - Pauli-based computation은 Clifford를 뒤로 미는 과정에서, 유닛 간 얽힘이 생기면 측정 지원 범위가 커져서 병렬성이 깨질 수 있음(논문이 문제를 직접 설명)
  - Pinnacle은 **Clifford frame cleaning**으로 “필요할 때 유닛을 다시 분리”해 병렬성을 회복하는 메커니즘을 제시
  - ➡️ 병목이 “팩토리 vs 데이터”가 아니라 “분리/결합을 얼마나 싸게 잘 하느냐(클리닝 비용)”로 이동.

**📌** **병목 ④ 고전 제어/디코딩/반응시간**

- - 논문이 리소스 추정에 쓰는 시간 가정:

    - code cycle time tc, logical cycle time, reaction time tr를 정의하고
    - 단순화로 **t****r****=10t****c** 를 둠
  - 또한 성능 근거를 내는 시뮬레이션은 “최적(정확) 디코딩” 성격이 강한데, **실시간 디코더의 구현은 future work**로 남겨둔다고 명시함.
  - ➡️ QLDPC로 큐비트 수를 줄이면, 다음 병목은 상당 확률로 “실시간 디코더/피드포워드 제어”로 올라온다.

**✅ IonQ / Quantinuum / Oxford Ionics — 누가 더 유리한가?**

- - 여기서 “유리”를 **Pinnacle이 요구하는 것**으로 번역하면 3가지임.

    1. **낮은 물리 오류율 레짐(p)**: 논문은 p=10-6를 “이온트랩" 예시로, p=10-3를 “중성원자” 예시로 언급
    2. **짧은 cycle time + 빠른 반응/제어(디코딩 포함)**: **t****r****=10t****c** 가정
    3. **모듈형 확장 + 블록 스케일 연결성 구현 용이**: “연결 길이 스케일이 논리 수에 대해 상수”라는 방향

- - 이 기준으로 **정성적으로**(최신 수치 주장 없이) 보면:
  1. **Quantinuum (QCCD/모듈 설계 관점에서 “아키텍처 친화”)**

     - 장점: QCCD 계열은 “모듈 내부에서 비교적 유연한 상호작용/재배치”를 설계 철학으로 가져가기 쉬워서, **블록 단위 연산/스케줄링**에 강점이 나기 쉬움.
     - 주의: Pinnacle의 최대 리스크(실시간 디코딩/피드포워드)를 실제 제어 루프에 녹이는 역량이 핵심.
  2. **Oxford Ionics (빠른 전자 제어/마이크로파 기반의 “시간축” 강점 후보)**

     - 장점: Pinnacle은 tc–tr–병렬화 트레이드오프가 크기 때문에, 시간축(사이클 타임, 피드포워드)을 공격적으로 줄일 수 있는 방향이면 유리해질 여지가 큼. (논문도 tc가 1µs~1ms 범위일 수 있음을 전제로 런타임/큐비트 트레이드오프를 제시)
     - 주의: 역시 디코더/반응시간이 실전 병목으로 올라옴.
  3. **IonQ (모듈/네트워크/확장 전략과의 접점)**

     - 장점: Pinnacle은 “processing unit을 여러 개로 늘려 병렬화하며, 연결성은 블록 스케일로 제한”이라는 모듈 철학을 강하게 민다.

       - 이런 구조는 **모듈 간 연결(네트워크/인터커넥트)을 아키텍처 레벨에서 중요 변수로 두는 전략**과 접점이 큼.
     - 주의: Pinnacle이 제안하는 병렬 유닛 운영은 “제어/동기/피드포워드”의 시스템 엔지니어링이 전체 성패를 좌우.

>
> *Pinnacle에서는 병목이 (유닛당 매직 공급 안정성 + 유닛 분리/결합(클리닝) + 실시간 디코딩/반응시간) 쪽으로 더 강하게 이동한다.*

>

**✅ Pinnacle과 연동하기 위한 조건**

- - 하드웨어 조건 + 제어/디코딩(고전) + 소프트웨어/컴파일러 + IP/운영

**📌 하드웨어에서 “반드시” 갖춰야 할 것 (이온트랩 관점)**

1. 1. **빠르고 반복 가능한 사이클 구조**

      - Pinnacle은 “코드 사이클(tc) → 여러 번 묶어 logical cycle”로 계속 굴러가고, 반응시간(tr)도 들어감.
      - 논문은 단순화로 **tr = 10·tc** 같은 가정을 두기 때문에, 이걸 현실로 만들려면:

        - 중간측정(mid-circuit measurement)이 안정적이어야 하고
        - 측정 후 **빠른 리셋/재준비**(ancilla 재사용)도 가능해야 하고
        - 동시에 **병렬로 많은 측정/게이트**를 돌릴 수 있어야 함 (가젯/브리지 때문에).
      - 이온트랩은 측정/리셋이 가능하긴 한데, “대규모 병렬 + 짧은 주기”는 시스템 엔지니어링 난도가 확 올라간다.
   2. **블록 내부에서 필요한 상호작용/연결성**

      - 논문은 “All-to-All”이 아니라 **블록 스케일 안에서의 연결이면 된다**고 강조함.
      - 이온트랩에서 이는 보통 두 방향:

        - 같은 트랩(모듈) 내부에서 레이저/마이크로파로 다체 상호작용을 스케줄링하거나
        - 모듈을 나누고 **포토닉 인터커넥트** 같은 걸로 모듈 간 연결을 제한적으로 제공
      - 둘 다 가능성은 있지만, Pinnacle은 “브리지/가젯”이 많아서 **연결·스케줄링 자동화**가 중요해짐.
      - 👉 시스템이 커지면, IonQ의 포토닉 인터커넥트를 이용한 모듈 수 증가가 빛을 발함.
   3. **물리 오류율 레짐(p)과 안정성**

      - 논문은 p=10-3, p=10-4 같은 레짐에서 자원 추정을 보여줌.
      - 이온트랩이 상대적으로 유리하다고들 하는 이유는 **낮은 오류율 가능성**인데, Pinnacle을 실제로 돌리려면:

        - 2큐비트 게이트 오류, 측정 오류, 누설/크로스토크, 드리프트를
        - **장시간(수일~수개월 가능) 동안** 안정적으로 유지해야 함
      - “데모 성능”이 아니라 **운영 성능**이 필요.
      - 👉 충실도가 가장 높은 Oxford가 가장 유리함.
   4. **고전 컴퓨팅 / 전자 장비 추가 필요**

      - Pinnacle의 큰 리스크가 “실시간 디코더”.
      - 논문은 시뮬레이션에서 최적 디코딩 성격을 쓰고, 실시간 디코더는 future work라고 언급
      - 상용으로 돌리려면:

        - 디코딩/피드포워드 계산을 **매 코드 사이클/논리 사이클**마다 처리해야 함
        - 그리고 논문은 reaction time(tr)을 정의해서 반응 시간 제약도 넣음
      - 이건 보통:

        - FPGA/ASIC 기반 컨트롤러
        - GPU 서버 팜(저지연 네트워크)
        - 고속 데이터 수집(DAQ)
      - 같은 고전 하드웨어가 “양자 하드웨어만큼 중요”해진다는 뜻이기도 함.
      - Pinnacle이 아니어도 필요한 요구조건이지만, 그 조건이 더 빡세질 수 있음을 시사.
   5. **“Pinnacle 때문에 생기는” 추가 하드웨어가 있나? (surface Code 대비 변화)**

      1. **(증설)** 병렬 측정 채널/광학계
      2. **(증설)** 모듈 간 포토닉 링크(스위치, 파이버, 주파수 변환/필터 등 옵션)
      3. **(증설)** 실시간 디코딩/피드포워드용 고전 연산 장비(저지연)
      - 반면, surface code처럼 “초대형 중앙 매직 팩토리”를 물리적으로 크게 깔아야 하는 부담은 줄어드는 대신,
      - **유닛 단위로 매직 엔진을 많이 깔고**, 그걸 **스케줄/제어**하는 부담이 커지는 구조임.
      - 👉 단순히 Pinnacle이 있다고 불가능한 걸 가능케 하는 접근이 아니라,
      - 👉 그만큼 시스템 내부적으로 치열하게 정밀한 제어가 필요하기 때문에,
      - 👉 양자 컴퓨터 제조 회사 내부의 소프트웨어 및 하드웨어 연구진들의 실력이 빛을 발해야 한다.

> **IonQ의 네트워크 확장성과 Oxford의 충실도가 이미 합쳐졌는데?**

> ***[용어 정리]***
>
> ***가젯 (gadget)***
>
> *논리 연산을 직접 하지 않고* ***보조 큐비트 + 측정 회로****를 이용해서 원하는 효과를 만들어내는 회로 묶음.*
>
> *일종의 “연산 변환 장치”.*
>
> ******
>
> ***브리지 (bridge)***
>
> *멀리 있는 두 논리 블록을 직접 연결하는 대신 A ↔ bridge ↔ B 식으로 이어주는 중개 블록.*

**📌 고전 제어/디코딩에서 필요한 것 (여기서 진짜 ‘상용화’가 갈린다)**

1. 1. **실시간 디코더(Decoder)**

      - 논문은 시뮬레이션에서 최적해에 가까운 디코딩(혼합정수계획 등)을 써서 논리 오류율을 평가했고, **실시간 디코더는 향후 과제**라고 선을 긋고 있다.
      - 즉, 상용화하려면:

        1. QLDPC에 맞는 **Fast Decoder**(예: BP 계열 + 후처리 등)를 개발/검증
        2. 그걸 **컨트롤러(펌웨어/FPGA/GPU)** 루프에 넣어 tc/tr에 맞춰 돌림
        3. 디코더 실패/지연이 전체 실패로 이어지지 않게 fail-safe 설계
      - 여기서 “그냥 코드화”가 안 되는 이유가 나온다.
      - 디코딩은 ‘알고리즘’이면서 동시에 ‘실시간 시스템"이다.
   2. **피드포워드/반응시간 파이프라인**

      - Pauli-based computation + 측정 기반 흐름이라, 측정 결과가 다음 측정/기저 선택에 영향을 주는 구간이 생긴다(논문은 reaction time을 정의).
      - 즉,

        - 측정 → 디코드/판정 → 다음 펄스/게이트 시퀀스 생성
      - 이 체인이 “끊김 없이” 돌아야 한다.

**📌 소프트웨어/컴파일러에서 필요한 것**

1. 1. **Pinnacle 전용 “FT 컴파일러”**

      - Pinnacle은 일반 회로를 그대로 올리는 게 아니라, **Pauli measurement 중심으로 컴파일**해서 돌린다(논문이 Pauli-based computation을 기반으로 설명).
      - 그러면 필요한 것:

        - 회로(Shor/RSA)를 **T-count 기준으로 스케줄링**
        - Processing Unit 여러 개로 **병렬화/분할**
        - 유닛이 얽힐 때는 **Clifford frame cleaning**을 언제/어떻게 할지 최적화
        - Magic Engine의 reject 확률(pr)을 감안해 **파이프라인 stall**까지 모델링
      - 이건 “라이브러리 몇 개” 수준이 아니라 **컴파일·스케줄·리소스 최적화 스택**이 필요해.
   2. **하드웨어 매핑(HW mapping)과 캘리브레이션 자동화**

      - 가젯/브리지/측정 패턴이 많아지면, 실제 장비에서

        - 어떤 이온들이 데이터/ancilla인지
        - 어떤 커플링을 언제 쓰는지
        - 측정-리셋을 어떻게 interleave하는지
      - 가 복잡해져서, **자동 매핑/자동 캘리브레이션** 없이는 운영이 힘들다.

**📌 “아무나 가져다 쓰나?” → 현실은 IP/표준/엔지니어링 패키지**

- - 상용화가 되면 보통은 이렇게 간다:
  1. **“참조 구현(reference implementation)” + 라이선스**

     - 아키텍처 자체가 특허/노하우로 묶일 수 있고,
     - 최소한 **컴파일러/디코더/가젯 설계**는 패키지로 제공될 가능성이 큼.
     - 기업 고객은 “논문 보고 직접 구현”보다 **검증된 스택을 사서** 쓰려 함.
  2. **인증/검증(verification)**

     - RSA 같은 크립토급 워크로드는 특히

       - 오류 모델 검증
       - 실패확률 상한 추정
       - 보안/안전성(특히 정부/금융)
     - 요구가 강해서, “오픈소스로 알아서” 분위기랑 거리가 있다.

> Pinnacle이 이온트랩에서 상용으로 쓰이려면, 핵심은 **코드(QLDPC) 자체가 아니라**:
>
> **실시간 디코딩 + 피드포워드 제어**
>
> **Pauli 측정 기반 컴파일/스케줄러**
>
> **대규모 병렬 측정/리셋을 버티는 하드웨어 운영 능력**
>
> 이 3개가 “제품”으로 완성돼야 하기 때문에, 아이디어가 있다고 아무나 쓸 수 있는 것은 아님.

**✅** **Pinnacle이 주장하는 연결성 현실화에 대한 고찰**

**📌 연결은 블록 크기 범위면 충분하고 라우팅이 필요없다?**

- - 대부분 연구자들도 처음 Pinnacle을 보면 같은 생각을 한다.

    - QLDPC는 원래 멀리 퍼져 있는데 어떻게 블록 내부 연결만으로 끝내?
  - 겉보기에는 모순처럼 보인다.
  - 하지만 Pinnacle이 쓰는 트릭은 이것이다:

> *논리 연산을 직접 멀리서 하지 않는다.” 대신*
>
> ***측정 + 중개 블록(bridge) 으로 우회****한다.*

**📌 원래 왜 멀리 연결이 필요했나?**

- - QLDPC에서 논리 연산은 보통
  - 여기 있는 물리 큐비트 몇 개 + 저기 있는 물리 큐비트 몇 개를 동시에 만져야 한다.
  - 그래서 직접 연결해야 할 것처럼 보인다.

**📌 Pinnacle의 관점 전환**

- - 질문:

    - 굳이 직접 연결해야 해?
  - 답:

    - 아니, 측정 결과만 있으면 되지.
  - 이게 Pauli 기반 계산의 핵심 철학이다.

**📌 핵심 아이디어 ① - teleportation / lattice surgery 스타일 사고**

- - 논리 정보를 **물리적으로 이동**시키지 않는다.
  - 대신:

    - 얽힘을 만들고
    - 측정하고
    - 프레임 업데이트
  - 하면 효과적으로 연산이 된 것과 동일.
  - 그래서 멀리 있는 큐비트를 직접 연결할 필요가 없어진다.

**📌 핵심 아이디어 ② - 브리지 블록을 만든다**

- - A 블록, B 블록이 멀리 있다고 하자.
  - 직접 연결 ❌
  - 대신:
  - A ↔ bridge ↔ B 로만 연결.
  - bridge는 A/B와 같은 지역 안에 있다.
  - 그리고 측정을 통해 A와 B가 연산된 것과 동일한 효과 를 만든다.
  - 즉, 물리적 연결은 **항상 로컬**.

**📌 핵심 아이디어 ③ - Clifford frame 덕분에 가능**

- - Clifford 연산은 즉시 수행할 필요 없다.

    - → 기록만 해두면 된다.
  - 그래서 복잡한 전역 연산도 실제로는 **로컬 측정 + 나중에 해석**으로 처리 가능.

**📌 그래서 무슨 일이 벌어지냐**

- - 아키텍처 입장에서 보면:

    - processing unit 안에서만 상호작용
    - 필요한 연결 수 = 블록 설계로 고정
    - 시스템 커져도 증가 안 함
  - 이게 논문이 말하는 연결 길이가 logical 수에 대해 상수라는 주장이다.

**📌 쉽게 비유하면**

- - 서울 ↔ 부산 직접 도로 ❌
  - 서울 ↔ 대전
  - 대전 ↔ 부산
  - 측정하고 결과 전달.
  - 물리적으로는 장거리 안 깔아도 논리적으로는 연결된 효과.

**📌 왜 이게 큰 진전처럼 보이냐**

- - 왜냐하면 이게 맞다면:

    - 배선 폭발 안 함
    - 레이저/광학 복잡도 제한
    - 모듈 복제 가능
    - 병렬 확장 쉬움
  - 즉, **이론 코드 → 공장 설계**로 변하는 순간.

**📌 하지만 진짜 질문은 남는다**

- - 그 bridge/측정 과정의 에러와 시간 비용은?
  - 이게 앞으로 실험적으로 증명해야 할 영역.

> ***Pinnacle은***
>
> *멀리 있는 큐비트를 직접 연결하는 대신 로컬 연결 + 측정 + 프레임 업데이트로 동일한 논리 효과를 만든다.*
>
> *그래서* ***장거리 라우팅이 필요 없다****고 주장한다.*

[The Pinnacle Architecture: Reducing the cost of breaking RSA-2048 to 100 000 physical qubits using quantum LDPC codes](https://arxiv.org/html/2602.11457v1)

**✅ 그림 1. 설명 - 병렬 연결의 구성 차이.******

- Examples of the Pinnacle Architecture. These two examples represent specific examples of different space-time trade-offs and code block choices, optimised for RSA-2048 factoring in different hardware regimes.

  - **(a)** allows factoring in one month with a physical error rate of p=10−3  and a code cycle time of tc=1 µs.
  - **(b)** allows factoring in three months with a physical error rate of p=10−4 and a code cycle time of tc=1 ms.
- Shorter runtimes can be achieved by adding more processing units, increasing paralellisation at the cost of additional physical qubits.

**📌 색깔 의미**

- ⚪ **Memory** → 계산하지 않고 논리 상태를 **보관**
- 🩷 **Processing Unit (PU)** → 실제 논리 **연산**이 일어나는 곳
- 🟢 **Magic Engine (ME)** → T state 만들어서 PU에 **공급**

****

**📌 그림 (a) — 작은 시스템**

- - processing unit 1개
  - 물리 큐비트 약 10만 개
  - 세부 구성:

    - Memory ≈ 75k
    - PU ≈ 15k
    - ME ≈ 9k
    - **p = 10****-3**
    - **t****c** **= 1 µs**
  - **의미**

    - 병렬화가 거의 없다.
    - 대신 한 유닛으로 오래 돌린다.
    - 그래서 RSA-2048 분해:
    - 🕒 **약 1개월**.

**📌 그림 (b) — 큰 시스템**

- - PU가 엄청 많다.
  - processing unit 81개
  - 물리 큐비트 약 100만 개
  - 세부 구성:

    - Memory ≈ 62k
    - PU ≈ 10k
    - ME ≈ 2k
    - (※ 이건 유닛 하나 기준)
    - **p = 10****-4**
    - **tc = 1 ms**
  - **의미**
  - PU를 많이 두고 **동시에 작업**한다.
  - 그래서 RSA-2048:
  - 🕒 **약 3개월 → 더 줄일 수 있음**

> *그림(a)와 (b)의 세부 구성을 보면 물리 큐비트가 10배 늘어났지만,* ***tc를 1,000배 느린 조건을 세팅했지만, 1개월 vs 3개월이라는 결과가 나올 수 있다는 것을 보여준다.***
>
> ***1. 느리지만 더 정밀한 하드웨어를 병렬로 구성시에도 유의미한 결과값이 도출됨***
>
> ***2. tc 값을 동일하게 설정할 경우, (b)의 결과값은 단순 비교를 했을 경우 3개월에서 몇 시간으로 단축시킬 수도 있음을 의미함.***

**📌 Magic Engine**

- - **⚪ noisy |T⟩ 투입**

    - 완벽하지 않은 T 상태를 집어넣는다.
    - → 원재료.
  - **🟢 Distillation circuit**

    - 여기서 정제가 일어난다.
    - 여러 개를 써서:
    - 👉 더 깨끗한 |T⟩ 만든다.
  - 중요:

    - 이 작업이 **계속 반복**된다.
    - 멈추지 않는다.

**📌 Processing Unit**

- - 정제된 T를 바로 위의 processing unit에서 사용.
  - 오른쪽에 써 있는 식 Measure P ⊗ Z → R\_{π/4}(P) 구현
  - 즉: T 게이트를 **측정 기반으로 주입**한다.

**✅ 그림 5. 설명 - 병렬성이 언제 깨지고, 다시 회복되는 과정******

- - Clifford frame = 실제로 게이트를 바로 수행하지 않고 “나중에 이렇게 해석하면 된다”라고 기록만 해두는 추적 시스템.

    - 물리적으로 뭔가 복잡한 걸 하지 않고 **회계 장부만 업데이트**한다고 보면 된다.
  - (a) 각 PU가 독립적으로 실행

    - 왼쪽 프레임 = C1, 오른쪽 프레임 = C2
    - 병렬 천국.각자 일하면 된다.
  - (b) 갑자기 CNOT이나 joint measurement가 필요해지면,

    - 프레임이 두 유닛에 걸쳐 **얽혀버린다**.
    - 그럼 이후 연산은?

      - 각자 따로 못 함.
      - 순차적으로 처리해야 한다.
      - 병렬성 깨짐
    - PU를 많이 만들어도 이런 일이 자주 생기면 서로 합쳐지면서 확장의 의미가 줄어든다.
  - (c) 그래서 Pnnacle이 넣은게 Clifford Frame Cleaning

    - 추가 측정을 여러 번 해서 얽힌 프레임을 **정리(clean)** 한다.
    - 비용은 최대 4k 정도의 추가 측정.
    - 시간 좀 들지만 그 다음이 중요.
  - (d) 프레임이 다시 분리된다.

    - 그리고 다시 병렬 실행으로 복귀됨.
