**🚀 OCT / OISL에 실제로 필요한 Optical 기술**

- - 우주 광통신(OCT/OISL)은 지상 광전송과 겹치는 부분이 있지만, 전부는 아니다.

[![](https://mblogthumb-phinf.pstatic.net/MjAyNjAyMjRfMTMg/MDAxNzcxOTM2NDgyNjY3.0o98cVKv73Thw9EhNvqAJVnCtjJKPUNeWW1vdXzKf4Ug.UZv7XCx4SIbQSiTMpAR0yiW1ft6gCej6lqYQx7QIAr8g.PNG/image.png?type=w800)](#)

**1️⃣ Coherent Optical DSP**

- - 고차 QAM
  - 위상 복원
  - FEC
  - BER 최소화
  - 👉 **광 DSP팀 영역**

****

**2️⃣ Narrow Linewidth Laser**

- - 초저 위상 잡음
  - 장거리 coherent detection 필수
  - 👉 광 트랜시버 설계 영역

**3️⃣ Photonic Integration**

- - SiPh (실리콘 포토닉스)
  - 집적화된 광엔진
  - 👉 광칩 팀 영역

**4️⃣ FEC & Coding**

- - 저 OSNR 환경 대응
  - 장거리 전송
  - 👉 DSP 알고리즘 팀 영역

**✅ “Coherent DSP 강자”는 Ciena/Nokia만이냐? Marvell/Broadcom은?**

**📌 플랫폼/시스템 벤더형(자체 DSP·알고리즘 스택 포함)**

- - Ciena: WaveLogic 계열로 **100G~1.6Tb/s per wavelength**까지 coherent optics를 제품군에 녹여서 판매
  - Nokia(및 일부 통신장비사): “망 전체 최적화 + 라인 시스템 + FEC/운용”까지 포함한 **end-to-end 성능 패키지**가 강점

**📌 칩(merchant)·모듈 벤더형(여러 장비사가 사서 쓰는 DSP)**

- - **Marvell**: 스스로 “PAM4, coherent, coherent-lite DSPs”를 한다고 명시 (Inphi 계열 coherent DSP 자산도 이어짐 )
  - **Cisco (Acacia 인수)**: Delphi/Jannu 같은 coherent DSP ASIC 기반의 ZR/ZR+ 플러그어블을 전면에 내세움
  - **Broadcom**: 강점은 현재 공개 자료 기준으로는 **coherent 장거리 DSP라기보다** AI/DC용 **DSP PHY(PAM4 등) 라인**에 더 무게가 있음(예: Sian 계열 200G/lane DSP)

**📌 결론**

- - “코히어런트 DSP”를 **망에서 굴리는 능력**(운용+알고리즘+FEC 포함)까지 보면 Ciena/Nokia 같은 시스템 벤더가 강자.
  - **레이저 통신 단말** 관점에서 “칩/모듈로서 DSP 공급”까지 보면 Marvell 쪽이 핵심 축. (Cisco는 플러그어블이라 제외)
  - Broadcom은 (적어도 공개된 주력 포지션 기준) 장거리 coherent보단 **이더넷/데이터센터 광 PHY DSP** 쪽 색이 더 강함.

**📌 그럼 OCT / OISL은 “망 사업”인가? “링크 사업”인가?**

[![](https://mblogthumb-phinf.pstatic.net/MjAyNjAyMjRfNTYg/MDAxNzcxOTM2NTU4NTU4.k55Gp7sgyzFUjoY-F9pENaF8vaJuvJycePqPIn14or0g.YGgQ2pQ68nGdFhdcSZXFALnelffenglElxZYHLQ21Pkg.PNG/image.png?type=w800)](#)

- - **초기 OISL은 “링크 사업”에 더 가깝다.**

    - **링크 사업은 “point-to-point 물리 링크 성립”이 목적이기 때문에**
    - **네트워크 전체 최적화 능력보다 PHY 안정성과 광학 정밀도가 우선**
    - **따라서 carrier-grade 네트워크 스택이 반드시 필요한 구조는 아니다**
  - OISL에서 필요한 것:

    - Coherent DSP 코어
    - FEC
    - Narrow linewidth laser
    - Beam steering
    - Rad-hard 설계
  - 이건

    - 👉 merchant DSP + 우주 광학 설계팀으로도 가능
  - 즉,

    - Marvell급 DSP + 우주 시스템 엔지니어링이면 충분히 가능
  - **하지만, 규모가 커지면 망 전체 최적화 능력이 필요해진다. 여기서 시스템 벤더 DNA가 강력해진다.**

**📌 그래서 단계별로 다르다**

- - **1단계 (현재)**

    - 링크 중심
    - 수십~수백 위성
    - 제한적 토폴로지
    - 👉 플랫폼 벤더 필요도: 낮음
    - 👉 DSP merchant면 충분
  - **2단계 (대형 constellation)**

    - 수천 위성
    - 동적 토폴로지
    - 광 라우팅
    - QoS
    - 👉 플랫폼 벤더 필요도: 상승
    - 👉 Ciena/Nokia 타입 강해짐

**✅** **우리에게 필요한 건 2가지 다른 관점**

**📌 ① 단말 관점: OCT / OISL을 “링크 제품”으로 만들 때의 합리적 접근**

- - **목표**

    - **작고, 가볍고, 저전력**
    - 링크 성립(획득/추적/유지) 최우선
    - BER/가용성 보장
    - 우주환경(방사선/열/진공) 생존
  - **핵심 설계 철학**

    1. **“기능 최소화(필수만 탑재)”**

       - 위성 단말이 반드시 해야 하는 것:

         - 빔 포인팅/트래킹 제어 루프
         - PHY(MAC 포함 최소 스택)
         - 링크 암호화/상호 인증
         - 로컬 페일오버(이웃 링크 품질 기반)
       - 단말에 넣지 말아야 할 것(초기):

         - 전역 최적화 트래픽 엔지니어링
         - full-mesh 링크상태 라우팅
         - 복잡한 정책 엔진
    2. **“DSP는 merchant + FPGA/SoC로 보강”**

       - FPGA는 도플러 보정, 위상 드리프트 추적, 우주 환경 특화 보정 알고리즘을 빠르게 수정 가능하게 해준다.
       - 초기에는

         - merchant coherent DSP(또는 coherent-lite)
         - FPGA로 도플러/지터/채널 추적 특화
         - 이후 검증되면 ASIC화
       - 이게 시간/리스크/성능의 균형점.
    3. **표준화 포인트를 “인터페이스”로 잡기**

       - 지상 장비처럼 특정 벤더 스택에 lock-in 되면 안 됨
       - 단말은:

         - **링크 레이어 API**
         - **보안 세션 API**
         - **라우팅/정책 API(경량)**
         - 같은 인터페이스 표준이 중요.

**📌 ② 네트워크 확장 관점: 단말이 커버 못하는 영역(‘우주 백본’)에 대한 접근**

- - 단말이 아무리 좋아도, 네트워크가 커지면 “단말로 해결 불가한 문제”가 생긴다.
  - **단말로 못 푸는 문제들**

    - 다중 hop 최적화 (end-to-end latency/throughput)
    - 혼잡 제어(큐/스케줄링)
    - 우선순위(QoS) 충돌 해결
    - 장애 도메인 격리
    - 키 롤오버/정책 변경의 대규모 배포
    - 연합군/다영역 보안 경계(Zero Trust segmentation)
  - 즉:

    - 단말은 “링크 생존”
    - 네트워크는 “전략적 자원 배분”
  - **합리적인 확장 아키텍처**

    1. **분산 + 계층 (LEO 메쉬만으로 끝내지 않음)**

       - LEO: 엣지/메쉬 (단말 중심)
       - MEO/GEO 또는 일부 LEO 슈퍼노드: **네트워크 기능 강화**
       - 지상: 정책 생성/감사/키관리/업데이트
       - 핵심은:

         - **모든 위성이 풀 스택 라우터가 될 필요가 없다**
         - “강화 노드”를 두면 전체 평균 페이로드를 낮출 수 있음
    2. **“예측 기반 제어” (우주의 강점 활용)**

       - 우주는 랜덤이 아니라 **궤도 예측 가능**이 강점이다.
       - 그래서:

         - 전역 경로 후보를 미리 계산
         - 위성은 local failover만
         - 지상은 주기적 업데이트
       - 이게 “중앙집중 없이도 질서 있는 운영”을 만드는 방법.
    3. **‘운용’은 중앙이 아니라 정책 배포 체계**

       - 실시간 명령이 아니라:

         - 정책 컴파일 → 배포 → 로컬 집행
         - 상태 텔레메트리 수집 → 다음 정책 업데이트
       - 즉 NOC는 “조종사”가 아니라 “컴파일러”에 가까워짐.

         - 즉, 실시간 수동 제어가 아니라, 사전 계산된 정책을 배포하는 구조로 진화한다.

**📌 둘을 연결하는 ‘경계면’ 설계가 제일 중요**

- - 두 관점이 분리되려면, 단말과 네트워크 사이에 명확한 계약(Interface)이 있어야 한다.
  - **단말이 네트워크에 제공해야 하는 최소 텔레메트리**

    - 링크 품질(OSNR/SNR, 페이로드 에러, pointing margin)
    - queue depth(혼잡 신호)
    - neighbor availability
    - crypto/session 상태 최소 요약
  - **네트워크가 단말에 내려줘야 하는 최소 정책**

    - 우선순위 클래스(QoS)
    - 허용된 peer 리스트 / 키 업데이트
    - 후보 경로(다음 홉 후보군)
    - 장애 시 행동 룰(로컬 우회 정책)

**✅ OISL 단말 기능 분해표**

**🟢 A. 반드시 필요한 것 (Core Survival Layer)**

- - 이건 없으면 링크 자체가 안 된다.
  - **1️⃣ 광 물리 계층 (Optical PHY Core)**

    - Coherent DSP (또는 coherent-lite)
    - Carrier recovery / Phase tracking
    - Doppler compensation
    - Adaptive modulation (QPSK ↔ 16QAM 등)
    - FEC (hard + soft decision)
    - 👉 여기서 DSP는 “망 최적화”가 아니라 **링크 생존 엔진**이다.
  - **2️⃣ 포인팅/트래킹 제어**

    - Fine pointing loop
    - Beacon acquisition
    - Vibration compensation
    - Link margin monitoring
    - 👉 실제 병목은 DSP가 아니라 이 영역일 가능성 큼.
  - **3️⃣ 최소 네트워킹 (Forwarding Only)**

    - L2/L3 경량 포워딩
    - Neighbor table (직접 인접 위성)
    - 로컬 링크 품질 기반 next-hop 전환
    - 단순 ECMP 수준
    - 👉 full link-state routing
    - 👉 MPLS/Segment Routing
  - **4️⃣ 기본 보안**

    - Link-level encryption
    - Mutual authentication
    - Session key cache
    - 기본 Zero Trust peer enforcement
    - 👉 모든 위성은 edge이기 때문.

**🟡 B. 선택적 기능 (Scalable Layer)**

- - 이건 초기엔 없어도 되지만, 망이 커지면 필요해질 수 있다.
  - **5️⃣ 정책 기반 포워딩**

    - Traffic class tagging
    - Mission-based priority
    - Pre-loaded fallback policy
  - **6️⃣ 제한적 Telemetry**

    - OSNR/SNR
    - Queue depth
    - Drop rate
    - Link availability window
    - 👉 단말은 “상태 요약”만 보고
    - 지상이 전역 최적화.
  - **7️⃣ 제한적 Congestion Control**

    - Simple rate limiting
    - Backpressure signaling
  - 👉 TCP-like full stack

**🔴 C. 단말에 넣으면 안 되는 것 (Heavy Network Layer)**

- - 이건 지상/슈퍼노드 영역이다.

    - 단말에 이 기능들을 넣는 순간, 모든 위성이 코어 라우터가 되고, 페이로드·전력·복잡도가 폭증한다.
  - **Full link-state routing**

    - OSPF/IS-IS flooding
    - 전 위성 topology 계산
  - **Global traffic engineering**

    - 전역 최단경로 계산
    - 실시간 재분배
  - **대규모 Policy engine**

    - 복잡한 ACL matrix
    - 다중 테넌트 세그멘테이션 엔진
  - **대형 암호/HSM 모듈**

    - 키 발행/정책 컴파일

**✅ 우주 네트워크 확장 3가지 시나리오**

**🟢 시나리오 1: 순수 LEO 메쉬**

[![](https://mblogthumb-phinf.pstatic.net/MjAyNjAyMjRfOTkg/MDAxNzcxOTM2NzA3Nzcz.fonESNCLAChQL2A4X_M4rNr-o80m0Ix1L-7EnLxi_4Ug.AbZcB_nJlNvVYSVYWAj5dTZvPNa1jVPbdltGSJByBPwg.PNG/image.png?type=w800)](#)

- - **구조**

    - 모든 위성이 동일
    - 인접 위성과만 OISL
    - 완전 분산 구조
    - 코어 없음
  - **장점**

    - 단순
    - 확장성 좋음
    - 단일 실패 지점 없음
    - 빠른 배치 가능
  - **단점**

    - 네트워크 최적화 어려움
    - 다중 hop latency 증가

>
> 기밀이 강화된 네트워크에서는 굳이 필요 없겠지만, 일명 "개나 소나 다 연결할 수 있게 오픈된 위성 네트워크"에서는 보안이 필수이다.
>
> 그렇다고 모든 LEO 위성에 전부 QKD를 도입하는 것도 현실적으로는 어렵기 때문에, 시나리오별 다양한 구성을 고려해야 할 것이다.
>
> 이를테면 LEO-LEO는 PQC만을, LEO-수퍼노드는 일부 제한적으로 QKD를 고려하고, 그외 노드는 PQC 만 구출을 고려할 수 있다.
>
> MEO/GEO중 Spine 역할을 하는 곳에는 QKD와 PQC 동시 구축도 고려할수 있을 것이다.
>
