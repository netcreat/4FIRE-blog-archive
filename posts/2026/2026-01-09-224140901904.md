**📌 Transformer의 단계별 연산 흐름**

- - 위 그림은 실제 트랜스포머 워크로드에서 GPU와 HBM이 얼마나 많은 데이터 이동을 필요로 하는지 보여준다.

    - **데이터가 HBM에서 GPU로, 다시 GPU에서 HBM으로 오가는 엄청난 왕복**
  - **Multi-head Attention (MHA)**

    - 문장/토큰들 사이의 상호참조를 계산하여 "어디를 봐야 하는지" 결정하는 컴퓨팅, 즉 attention map을 만듦
    - **Memory-bound**

      - **✔ 행렬 곱 많음 (GEMM 기반)**
      - **✔ Softmax 포함**
      - **✔ KV Read 필요**

|  |  |  |
| --- | --- | --- |
| **단계** | **연산** | **Memory Access** |
| ① | Q,K,V 생성 | HBM → GPU |
| ② | QKᵀ | HBM → GPU → HBM |
| ③ | softmax | HBM → GPU → HBM |
| ④ | A×V | HBM → GPU → HBM |
| ⑤ | Out-Projection | HBM → GPU → HBM |

**📌 그럼 왜 이게 memory-bound를 의미하냐?**

- - - 트랜스포머에서는 SOFTMAX와 QKT와 A×V에서 특히 FLOPs 대비 Bytes가 많아서 AI가 떨어짐.
  - 즉:

    - ✔ 연산은 상대적으로 적고
    - ✔ 데이터는 계속 오가고
    - ✔ reuse는 거의 없음
  - 따라서 AI 낮음 → Memory-bound

**📌 더 중요한 포인트: 주범은 QK****T****와 KV Cache 접근**

- - QKT는 다음 두 이유 때문에 AI를 더 낮춤:

    - ① Q와 K는 모델 파라미터가 아니라 input dependent → reuse 거의 없음
    - ② 결과(Logit)는 HBM에 다시 저장됨 → 또 fetch
  - 또한 inference에서는 KV cache가 사용되면서:

    - A × V
  - 연산이 매 step마다 HBM 접근을 필요로 함
  - 즉 decoding 시점에서 특히:

    - Compute보다 Memory BW가 더 중요한 구간

**📌 축의 의미**

- - **x축 → Arithmetic Intensity (FLOPS / Byte)**

    - : 연산량 대비 메모리 접근량
  - **y축 → Performance (TFLOP/s)**

    - : 실제 수행된 계산 성능
  - **Arithmetic Intensity(AI) 정의**

    - Arithmetic Intensity (연산 밀도)는 데이터 1 Byte당 수행된 연산량을 나타내는 비율을 나타낸다.

- - - 즉, 연산량 대비 메모리 접근량을 나타낸다.

      - 값이 높을수록 "연산 많고 메모리 읽기 적은" 계산 친화적 workload
      - 값이 낮을수록 "연산은 적고 메모리 읽기 많은' workload

**📌 Roofline의 구조**

- - Roofline 모델은 두 영역으로 나뉨:
  - **(1) Memory-bound 영역**

    - low arithmetic intensity
    - 성능이 **메모리 대역폭**에 의해 제한
    - 즉 연산기가 놀고 있음 (데이터 기다리느라)
  - **(2) Compute-bound 영역**

    - high arithmetic intensity
    - 성능이 **연산 피크 성능**에 의해 제한
    - 메모리는 이미 충분히 빠름
  - 두 영역을 나누는 경계는:
  - Computation–Bandwidth Ratio = Peak FLOPS / BW

    - 여기선 GPU-HBM 시스템 기준으로 **117.19 FLOPS/Byte**

**📌 GEMM = General Matrix-Matrix Multiplication**

- - **행렬 × 행렬 곱**을 의미하는 가장 기본이면서도 가장 중요한 수치 연산이다.
  - 수식으로 쓰면:

    - C=A×B
  - 행렬 크기가 각각

    - A : M×K
    - B : K×N
  - 이라면 결과 C는 M×N
  - 업계에서 GEMM은 아예 **하드웨어 성능을 대표하는 벤치마크**로 쓰임
  - GEMM은 연산량 대비 데이터 이동량(=Arithmetic Intensity)가 매우 중요한 workload

**📌 GPU-HBM(V100)기준 값**

- - Peak Compute = **120 TFLOPS/s**
  - HBM BW = **1.024 TB/s**

- - Arithmetic Intensity가 **117.19보다 크면**

    - → HBM이 데이터를 충분히 공급 가능
    - → Compute가 병목
    - → **Compute-bound**
  - Arithmetic Intensity가 **117.19보다 작으면**

    - → 연산기가 데이터를 기다림
    - → Memory가 병목
    - → **Memory-bound**

****

**📌 Com-BW Ratio란 무엇인가?**

- - 풀어서 쓰면:

    - Compute-to-Bandwidth Ratio
    - 연산장치(Compute)가 데이터를 처리하는 속도 대비, 메모리가 데이터를 공급하는 속도(Bandwidth)가 어느 정도인가를 나타내는 비율
  - 수식으로는:

- - 단위는 FLOPS/Byte
  - Com-BW Ratio는 소프트웨어가 아니라 **하드웨어가 정하는 수치**다.

    - V100 : ~117
    - A100 : ~200+
    - H100 : ~360+
  - 실제 AI

    - GPT-3 inference AI ≈ 5~20 FLOPS/Byte
    - GPT-3 training AI ≈ 50~200 FLOPS/Byte
    - BERT inference AI ≈ 3~30 FLOPS/Byte
    - CNN inference AI ≈ 10~100 FLOPS/Byte
    - Llama 7B inference AI ≈ 6~25 FLOPS/Byte
  - Memory-bound → 그래서 compute unit이 놀고 있음 → 그래서 FLOPS 늘려도 성능 안 나옴

> ***요즘 반도체는 계산기가 아니라 메모리/패키징 전쟁이 되었다.***
>
> ***Compute scaling이 의미가 없어짐***

- - 그래서 NVIDIA가 compute core 늘리는 것보다

    - **✔ HBM 스택 증가**
    - **✔ TSV/Interposer**
    - **✔ CXL/NVLink**
    - **✔ UCIe/Chiplet**
    - **✔ CoWoS/SoIC/Foveros**
  - 같은 BW 쪽에 돈을 퍼붓는 것.

**✅ 최근 업계의 움직임**

**📌 아키텍처의 scaling 방향**

- - memory-side scaling에 훨씬 더 많은 공을 들임

|  |  |
| --- | --- |
| **세대** | **BW 증가** |
| HBM2 → HBM2E | +40% |
| HBM2E → HBM3 | +70% |
| HBM3 → HBM3E | +70% |
| HBM3E → HBM4 | 예정 +~90% |
| HBM4 → HBM5 | 예정 +~100% |

**📌 FlashAttention과 KV-cache 최적화의 등장**

- - FlashAttention의 목적은 정확히 Arithmetic Intensity를 인위적으로 올리고 memory traffic을 줄이기 위함
  - 만약 compute-bound였다면 이런 기법이 필요 없음.
  - KV-cache compression, PagedAttention, sparsity, quantization 또한 모두 **memory 문제 해결 전략**

****

**📌 최신 칩 설계 방향**

- - 각 주요 플레이어의 설계 목표를 보면:

    - NVIDIA → HBM 증가 + NVLink-C2C + on-package SRAM + TensorCore reuse
    - Google TPU → systolic array로 reuse 극대화
    - Cerebras → SRAM on-wafer로 DRAM 병목 제거
    - Graphcore → distributedmem + partitioning
    - Tesla Dojo → huge SRAM tile로 global memory 접근 억제
    - Groq → deterministic dataflow로 memory stall 제거
  - 모두 “compute보다 memory”에 집중

**🏭산업 변화랑도 정확히 맞아떨어짐**

- - 현재 NVIDIA/Google이 다음에 돈을 쓰는 이유:

    - FlashAttention → KV streaming 감소 → AI 증가
    - PagedAttention → memory locality 증가
    - Quantization → memory traffic 감소
    - Prefetching → stall 감소
    - SRAM On-chip 증가 → reuse 증가
    - Hopper/H100 → HBM3 + NVLink 증가
    - Blackwell/B200 → HBM3E + coherence fabric
  - 즉 compute가 아니라 memory path를 강화 중.
