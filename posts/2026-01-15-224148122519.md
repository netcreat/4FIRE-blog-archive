**✅ High Bandwidth Flash (HBF)**

**출처 : 카이스트 테라랩**

**📌 전체 구조 요약**

- - 여러 NAND 층(128-layer NAND)을

    - → **수직으로 16단 스택** 하고
    - → **TSV(Through Silicon Via)** 로 수직 연결
    - → 밑에 컨트롤/인코딩/전원 회로(Base die)를 둠
  - 즉 이건 **HBM의 DRAM 버전 → NAND로 만든 느낌**

****

**📌 128 Layer NAND 단위 셀**

- - 128층 구조 안에서:

    - WL (Word Line)
    - BL (Bit Line)
    - Peripheral (RW/CTRL/PWR)
  - 이런 식으로 구성됨
  - **쉽게 말하면:**

    - WL/BL는 메모리 셀 선택
    - TSV는 DRAM 버스 역할
    - Peripheral은 메모리 컨트롤러 mini-version

**📌 LLM inference에 맞는 이유**

- - LLM inference는 다음 필요:

    - Read-only (weights)
    - Random chunk access
    - 매우 큰 모델 (20B~500B tokens)
    - 메모리 대역폭 요구 큼
    - 온디바이스 inference 중요
  - DRAM/HBM 대신 NAND 사용 시 장점:

|  |  |  |
| --- | --- | --- |
| **항목** | **HBM** | **HBF** |
| 비용 | 매우 비쌈 | 저렴 |
| 용량 | 수십 GB | TB 가능 |
| 전력 | 높음 | 매우 낮음 |
| latency | 매우 낮음 | 높음 |
| 대역폭 | 매우 높음 | 높음 |
| 사용성 | training | inference |

**✅ HBM-HBF Architecture**

[![](https://mblogthumb-phinf.pstatic.net/MjAyNjAxMTVfNjEg/MDAxNzY4NDc3MjExMjMz.0WRjLZ93WouPNqo2OgwKv8yoqmPZMmFbE1OJO-Cq0Bcg.yIWXJIbxwgT7NRvlIAVeOn4yQOjEF_iP8Ms3fyKIqHcg.PNG/image.png?type=w800)](#)

**출처 : 카이스트 테라랩**

**📌** **전체 컨셉**

- - HBM-HBF Architecture
  - **즉:**

    - **HBM = 고대역폭, 저용량, 저지연 (training·compute용)**
    - **HBF = 고용량, 저전력, 고대역폭 (inference·storage용)**
  - **둘을 같은 GPU substrate/Interposer 위에서 결합함**

****

**📌** **Memory Capacity 확장 포인트**

- - **Total Memory Capacity → 17.6 TB**
  - 즉 HBM만으로 불가능한 TB급 메모리를 패키지 내부에서 확장하는 구조임
  - GPU에 HBM4 8개를 붙여도 288GB
  - 그런데 LLM inference는 이미 다음 요구에 있음:

    - 70B 모델 → FP16 140GB
    - 175B 모델 → FP16 350GB
    - 500B 모델 → FP16 1TB 이상
    - Multi-token 병렬 시 → 수 TB 필요
    - 그래서 SSD → PCIe → GPU 메모리로 불러오는 기존 구조로는 병목 발생
    - **→****이걸 패키지 안에서 해결하려는 설계가 HBF**

****

**📌** **대역폭 및 용량 구조**

- - **GPU-HBM**

    - BW : 24 TB/s × 8 = 192 TB/s
    - Capacity : 16 TB
  - **HBM-HBF**

    - BW : 12 TB/s × 8 = 96 TB/s
    - Capacity : 1.6 TB
  - **HBF의 용량은 HBM 대비 10배 가량 많고, 대역폭은 50%**

    - **HBF는 HBM의 Paging / Weight Prefetch / Model Cache 역할 수행**

****

**📌** **전력적인 장점**

- - Flash/HBF는 HBM 대비

|  |  |  |
| --- | --- | --- |
| **항목** | **HBM** | **HBF** |
| 비용 | ↑ | ↓↓↓ |
| 용량 | ↓ | ↑↑↑ |
| 전력 | ↑↑ | ↓ |
| 지연 | ↓ | ↑ |
| BW | ↑↑↑ | ↑ |

**📌** **HBM Multi-tower vs HBM-LPDDR vs HBM-HBF**

- - HBF 이용시 저장 용량과 대역폭이 다른 방식에 비해 월등히 우세

**✅ HBF, 게임체인저인가?**

**📌 왜 HBF가 필요한가? (문제 정의)**

- - LLM inference는 이미 세 가지 병목에 부딪힘:

    - 용량 병목 (capacity)
    - 대역폭 병목 (bandwidth)
    - 비용/전력 병목 (TCO)
  - 현실 기준으로 보면:

    - 175B 모델 → 350~400GB
    - KV Cache 병렬 → 1TB~2TB
    - multi-model multi-tenant → 4~10TB 필요
    - serving infra → 24/7 uptime
  - 따라서 HBF는 역할이 명확함:

    - **HBM = compute buffer**
    - **HBF = model + cache storage**

****

**📌 HBF의 장애 요인**

- - **Latency (지연)**

    - Flash/HBF는 DRAM/HBM 대비 Latency 100~500배 느림
    - 해결책 후보:

      - KV-cache locality
      - speculative fetch
      - FlashAttention
      - chunked attention
      - async prefetch
      - unified memory model (CXL)
      - SRAM/HBM staging
    - 이 기술들이 이미 등장 중
  - **Bandwidth (대역폭)**

    - Flash 단일 칩 → 10~20GB/s 수준

      - **위에서 언급된 HBM-HBF BW 12TB/s는 단지 대역폭 비율을 맞추기 위한 모델링 값임. 일명 꿈수치**
    - HBM 단일 스택 → 3~24TB/s
    - 대역폭 갭 해결 방식:

      - TSV stacking (3D NAND → HBF)
      - parallel channels (CXL 2.0/3.0)
      - on-package PHY (×8 lanes)
      - memory fabric switching
    - NAND vendors는 여기에서 경쟁 중
  - **Write endurance (쓰기 내구성)**

    - LLM inference는 read-heavy라 괜찮지만
    - training은 write-heavy라 불리함
    - 따라서 초기는 inference only → training 제외
  - **Software Stack**

    - Flash Tier를 쓰려면 SW가 따라와야 함:

      - PyTorch / XLA / CUDA / Triton
      - KV paging policy
      - graph compiler
      - scheduler
    - Meta, Google, OpenAI는 이미 internal 구현 중

---

**✅ 어떤 업체가 유리한가? (경쟁 구도)******

- - Samsung
  - SK hynix
  - Micron
  - SanDisk
  - HBM7/HBF의 실제 공급자는 여기가 결정

**📌 TSV + Stacking (3D Packaging)**

- - HBM에서 배운 경험이 여기서 중요해짐.
  - TSV 기반 스택 구현 가능한 업체:

|  |  |
| --- | --- |
| **업체** | **TSV 경험** |
| Samsung | HBM (TSV), X-Cube |
| SK hynix | HBM TSV 세계 최강 |
| Micron | HBM2/3 경험 |
| Kioxia (Toshiba Memory) | NAND CuA (Cu-to-Cu bonding) |

- - 특히 NAND는 이미 176~232/238 layer 3D 구조라서 TSV/Hybrid bonding과 궁합이 있음.
  - 여기서 **TSV 스택 경험으로 가장 강한 업체는** **SK hynix**임.

**📌** **PHY + I/O + Controller**

- - HBF의 본질은 **Flash를 HBM처럼 대역폭화**하는 것이므로
  - I/O 및 PHY 설계가 핵심 Bottleneck.
  - 이 영역에서 강한 업체는 다음:

|  |  |
| --- | --- |
| **업체** | **이유** |
| SanDisk | SSD 컨트롤러 FW 최강 |
| Samsung | Mobile + Enterprise SSD IP |
| SK Solidigm | NVMe Enterprise optimized |
| Micron | Data center SSD 경험 |

- - 특히 **SanDisk**는 이 부분에서 매우 강함.
  - 컨트롤러 기술은 이 게임에서 가장 undersold된 영역임.

**📌** **종합**

|  |  |
| --- | --- |
| **Layer** | **경쟁자** |
| NAND | Samsung, SK, Micron, WD |
| TSV/Stack | SK, Samsung, Micron, SanDisk |
| Controller | **SanDisk**, Samsung, Micron, SK |
| Packaging | TSMC, Samsung Foundry, Intel, ASE |
| SW | NVIDIA, Meta, Google, OpenAI, AMD |

- - **Full vertical integration**

    - 그 조건을 모두 만족하는 업체는 단 두 곳

      - Samsung과 SK hynix

        - NAND 제조
        - TSV 경험
        - HBM 생산
        - SSD 제품
        - 컨트롤러/패키징
        - Ecosystem O2O 가능
    - 특히 SK는 가장 유리

      - HBM 세계 최강자
      - NAND (Solidigm) 보유

        - Intel NAND & SSD 사업부를 SK hynix가 2021년 인수
      - TSV packaging 경험
      - CXL Memory까지 진출
  - **Flash 컨트롤러 + SSD firmware**

    - LLM 시대에는 Flash 컨트롤러가 오히려 승부처

      - **SanDisk** 최강

        - LLM inference Flash Tier는 storage가 아니라 **cache/streaming subsystem** 성격을 가짐
