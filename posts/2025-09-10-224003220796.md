# 양자 운영체제(Quantum Operating Sytem)의 필요성과 현주소

싱가포르에 기반은 둔 양자 소프트웨어 개발 스타트업인 Horizon Quantum - 이하 HQ)이 dMY를 통해 나스닥에 스팩상장할 계획이다. dMY는 IonQ 스팩상장 회사로, 현 CEO 이자 Chairman인 Nicolo De Masi도 dMY 출신이다. HQ의 스팩 상장은 2025년 말까지 약 5억 달러의 가치로 마무리 될 것으로 예상된다.

HQ는 다양한 양자 하드웨어 간의 호환성을 지원하는 차세대 양자 프로그래밍 도구(컴파일러, 런타임 환경)를 개발한다. 목표는 응용 프로그램 병목(applications bottleneck)해소이며, 이를 통해 양자 컴퓨팅의 활용성을 강화하는 것이 핵심 전략이다. Microsoft의 Windows처럼, HQ는 세계 최초의 **양자 운영체계**(Quantum Operating System - 이하 **QOS**) 기반을 마련하는 것을 지향한다.

**Dr. Joe Fitzsimons**가 CEO로, 그는 싱가포르의 이론물리학 교수직과 함께 **유니버설 블라인드 양자 컴퓨팅(universal blind quantum computing)** 기술의 공동 발명자이기도 하다. 회사는 MIT, Oxford, Caltech 등 출신의 연구 인력들과 실무 경험이 풍부한 기술 및 경영 전문가들로 구성되어 있다.

> **유니버설 블라인드 양자컴퓨팅(Universal Blind Quantum Computing - UBQC)**은 양자 클라우드 시대와 양자 네트워크 보안의 핵심 기술중 하나로, 클라우드에 있는 양자컴퓨터를 이용해도 사용자의 입력, 알고리즘, 출력이 모두 비밀로 유지되도록 하는 양자 암호 프로토콜이다.
>
> 양자컴퓨터가 성능대비 제반설비요구사항도 많을 뿐만 아니라 매우 비싸기 때문에 클라우드를 통해 사용하는 요구사항 또한 많아질 것으로 예상됨에 따라, 사용자가 원격 접근시 큐비트 상태, 연산 알고리즘 및 출력 결과등이 노출되지 않게 하는 보안 기술이다.
>
> 예를 들어, 신약 설계, 암호 해독, 비밀 알고리즘등을 클라우드 기반 양자컴퓨터에서 실행할 경우 특히 요구되는 사항이다.

---

**✅****운영체제 필요성**

현재는 각 업체별로 제공하는 SDK(Software Development Kit)가 사실상 앱과 하드웨어 사이를 중개하기 때문에 벤더 종속성이 심해서 하드웨어별 코드 호환은 불가능하다.

**💡****현재 “운영체제”라고 부르기 힘든 이유**

전통적 OS처럼, 하드웨어 불문으로 프로그램을 실행하는 계층은 없는 상황이다.

- - QPU 아키텍처의 다양성

    - 자체 하드웨어에 맞춘 폐쇄형 설계의 SDK
  - 양자 OS에 요구되는 자원 관리 기능 미비

    - 프로세스 스케줄링, 메모리 관리, I/O 추상화, 드라이버 통합
    - 에러율 관리(QEC), 큐비트 매핑, 동적 라우팅, 다중 사용자 세션 지원등이 표준화되지 않음

**💡****개발 요구 vs 응용 실행 요구 — 무엇이 더 많을까?**

|  |  |  |
| --- | --- | --- |
| **구분** | **개발 요구(Dev-Oriented)** | **응용 실행 요구(App-Oriented)** |
| **주체** | 알고리즘 연구자, 양자 소프트웨어 개발자 | 제약·금융·머티리얼, AI, 시뮬레이션 등 **산업 사용자** |
| **주요 작업** | 양자 알고리즘 구현, 회로 최적화, 하드웨어 제어 | 완성된 앱 실행, 시뮬레이션 결과 활용 |
| **플랫폼 종속성** | 상대적으로 높음 → Qiskit, Cirq, TKET 등 선택 | 상대적으로 낮음 → “결과”만 필요 |
| **현재 비중(2025)** | **개발 요구 > 실행 요구** | 실행 환경은 아직 제한적 |
| **향후 비중(2030+)** | 개발 비중 점차 낮아짐 | **실행 요구 급증** 예상 |

**💡****“운영체제”가 필요한 시점은 언제일까?**

- - **지금은 OS 필요성 낮음**

    - 대부분 기업/연구자가 **특정 QPU**만 대상으로 알고리즘을 개발하고 실험하는 개발 요구가 더 많은 단계
    - 예: IonQ QPU에서 Qiskit으로 개발 → 다른 QPU 고려하지 않음
  - **미래에는 OS 필요성 급증**

    - 2028 - 2030년 이후 논리 큐비트 100 - 1,000개급 QPU 등장 → “실제 업무”에 투입 가능
    - 기업 입장에서는 **특정 QPU 벤더 종속**을 피하고 싶어 함
    - 예: 제약사가 양자화학 시뮬레이션을 할 때 IonQ와 Quantinuum을 번갈아 사용 가능해야 함
    - 이때 필요한 게 **Cross-QPU 런타임/OS**임.

**💡****향후 전망**

|  |  |  |
| --- | --- | --- |
| **시기** | **소프트웨어 스택 전망** | **특징** |
| **현재 (2025)** | SDK 중심, 벤더 종속 | Qiskit, Cirq, Braket 등으로 하드웨어 직접 지정 필요 |
| **단기 (2026~2027)** | **Cross-HW Runtime** 시작 | HQ Triple Alpha, Classiq, Riverlane Deltaflow 같은 범용 런타임 등장 |
| **중기 (2028~2030)** | **양자 OS 초기 버전** | 논리 큐비트 레벨에서 OS가 QEC 및 스케줄링 담당 |
| **장기 (2030+)** | **표준화된 양자 OS** | 하드웨어·네트워크·앱 완전 분리, 멀티-QPU 및 분산 양자 네트워크 지원 |

**✅****운영체제에 대한 접근법**

**💡****범용 운영체제가 불가능해 보이는 이유**

- - 지금 당장은 OS를 만들 수 없는 세 가지 큰 장애물이 있다.
  - **ISA(Instruction Set Architecture)의 부재**

    - 고전 컴퓨터 세계에서 Windows, Linux가 모두 동작하는 이유는 ISA(예: x86, ARM)가 표준화돼 있기 때문.
    - 반면 양자컴퓨터에는 **공통 ISA가 없다**.

      - IBM QPU에서는 **OpenQASM** 기반
      - Quantinuum은 **TKET IR**
      - IonQ는 자체 **API Layer**
      - QuEra는 **Braket SDK + Rydberg 전용 펄스**
    - → **CPU에서 ARM ↔ x86 에뮬레이션을 하는 Rosetta 같은 계층조차 없음**.
  - **에러 정정(QEC) 방식의 차이**

    - 어떤 운영체제를 만들려면 논리 큐비트와 물리 큐비트의 매핑 전략이 표준화되어야 함.
    - 하지만 플랫폼별로 QEC 전략이 다름:

      - IBM → Surface Code + Lattice Surgery
      - Quantinuum → Color Code + Tesseract Code
      - IonQ → Bacon-Shor + BB Codes
      - Oxford Ionics → Microwave-driven Low-overhead Code
      - QuEra → Neutral Atom 기반 Bosonic Lattice Code
    - QEC가 다르면 **논리 큐비트 자원 모델 자체가 호환되지 않음**.
  - **동적 자원 관리 미지원**

    - 전통 OS는 메모리, I/O, 프로세스 스케줄링을 중앙에서 관리하지만,
    - 현재 QPU는 **1인 전용 모드**로 동작해요.

      - 예: IBM QPU 예약하면 다른 사용자는 실행 불가.
      - 프로세스 멀티태스킹, 논리 큐비트 동적 분할 기능 없음.

**💡****이미 움직이는 표준화 흐름**

|  |  |  |
| --- | --- | --- |
| **표준화 계층** | **현재 상황** | **참여 기업** |
| **QIR (Quantum Intermediate Representation)** | LLVM 기반, MS 주도 | Microsoft, Quantinuum, IonQ, HQ 등 |
| **OpenQASM 3.0** | IBM 주도, 게이트 기반 공통 언어 | IBM, AWS Braket |
| **Deltaflow OS** | Riverlane이 추진 중인 QPU용 범용 런타임 OS | Riverlane, Rigetti, Quantinuum |
| **TKET IR** | Quantinuum 주도, 오픈소스화 | Quantinuum, Classiq, HQ |

> **LLVM** = **Low Level Virtual Machine**
>
> 원래는 “저수준 가상 머신”에서 출발했지만, 지금은 의미가 확장돼서 사실상 **범용 컴파일러 인프라스트럭처**임
>
> LLVM은 중간 표현(IR, Intermediate Representation)을 중심으로 동작하는 **모듈식 컴파일러 프레임워크**
>
> 프로그램 언어와 하드웨어 **ISA(Instruction Set Architecture)를 분리해 줌**

**💡NVIDIA의** **CUDA-Q가 이미 제공하는 것 아닌가?**

- - NVIDIA가 2023년에 발표한 **양자-고전 하이브리드 컴퓨팅 프레임워크**인 CUDA-Q의 목표는 **GPU·CPU·QPU를 단일 플랫폼에서 통합 실행**하는 것이다.
  - **전통 GPU HPC 클러스터 위에서 양자 알고리즘을 실행할 수 있도록 설계된 플랫폼이라는 것이 포인트**
  - **[양자 알고리즘 SDK] → [CUDA-Q 컴파일러 & 런타임] → [QPU / GPU / CPU 리소스] → [하드웨어]**

|  |  |  |
| --- | --- | --- |
| **기능** | **CUDA-Q** | **기존 SDK(Qiskit, Cirq 등)** |
| **하드웨어 추상화** | 단일 API → IonQ, Quantinuum, IBM, QuEra 등 통합 | 각 SDK별 독립 |
| **GPU-QPU 통합** | CUDA와 동일 환경에서 GPU/QPU 리소스 동시 사용 | GPU 활용 불가 |
| **Cross-HW IR** | QIR 기반, LLVM 최적화 지원 | SDK별 자체 포맷 |
| **네트워크 지원** | NVLink 기반 QPU-클러스터 연결 | 미지원 |
| **에코시스템** | HPC + AI + Quantum 완전 통합 | 하드웨어/SDK 종속 |

**💡****CUDA-Q의 강점**

- - **GPU·QPU 하이브리드 최적화**

    - 예: VQE, QAOA, QML 같은 하이브리드 알고리즘은 **QPU보다 GPU 사용량이 더 많음**.
    - CUDA-Q는 기존 CUDA 인프라를 그대로 사용하므로, **엔비디아 AI GPU 클러스터에서 바로 양자 알고리즘 실행** 가능.
  - **Cross-HW 표준화 주도**

    - CUDA-Q는 **LLVM 기반 QIR**을 그대로 채택 → MS, Quantinuum, IonQ, HQ까지 모두 호환 가능.
    - 사실상 **QIR 생태계의 핵심 허브** 역할.
  - **생태계 독점**

    - 이미 전 세계 AI, HPC 클러스터의 80% 이상이 CUDA 기반.
    - CUDA-Q가 SDK 통합까지 완성하면, **양자 애플리케이션의 표준 진입점**이 CUDA로 고정될 가능성이 큼.

**✅****CUDA-Q vs Horizon Quantum (HQ)**

**💡****개요**

- - **CUDA-Q**: GPU-QPU-CPU를 하나의 프레임워크로 엮는 **하이브리드 런타임/SDK**
  - **HQ (Triple Alpha)**: 하드웨어 추상화를 앞세운 **Cross-QPU 실행 환경(“양자 OS” 지향)**

|  |  |  |
| --- | --- | --- |
| **축** | **CUDA-Q** | **Horizon Quantum (HQ)** |
| 포지션 | 하이브리드 컴퓨팅 통합( GPU↔CPU↔QPU ) | Cross-QPU 앱 실행/포팅 레이어 |
| 주요 레이어 | 앱/SDK ↔ 컴파일러/런타임 ↔ (GPU/QPU 드라이버) | 앱/SDK ↔ **중간 IR(Triple Alpha)** ↔ 벤더 드라이버 |
| IR/표준 | **QIR/LLVM**, OpenQASM 등 폭넓게 흡수 | 자체 IR 중심(+ QIR 호환 지향) |
| 언어/SDK | C++/Python, 기존 **CUDA**와 공존, Qiskit/Cirq 브리지 | Python 중심 API(벤더 불문 실행 목표) |
| 스케줄링 | GPU/CPU/네트워크 자원까지 고려한 **잡 스케줄링** | 논리·물리 큐비트 맵핑/라우팅 **상위 레벨 스케줄링** |
| QEC 연계 | 시뮬/디코더와 연동(상위 레벨) | **논리 큐비트 추상화** 지향(상위 정책) |
| GPU 통합 | **최강점**(기존 CUDA 생태계 그대로) | 간접(필요시 외부 가속기 연동) |
| 멀티-벤더 | IonQ/Quantinuum/IBM/QuEra/Rigetti/Xanadu 등 **광범위** | “하드웨어 불문” 목표(통합 범위 **확장 중**) |
| 클라우드 연계 | 기존 HPC/AI 클러스터와 자연스런 통합 | 클라우드/QPU API를 **공통 런타임**로 흡수 |
| 성숙도 | **가장 성숙/대형 생태계** | 기능 확장 중(“양자 OS” 비전) |
| 강점 | 표준/생태계/성능/폭넓은 호환 | 개발자 경험·이식성·벤더 추상화 |
| 한계/리스크 | 엔비디아 스택 중심성(의존성) | 생태계·파워가 상대적 약세 |

**💡****주요 QPU 벤더 호환성 (현황/지향)**

|  |  |  |
| --- | --- | --- |
| **벤더** | **CUDA-Q** | **HQ** |
| IonQ(이온트랩) | 파트너 연동 사례 다수(클라우드) | **지원/지향**(클라우드 커넥터 경유) |
| Quantinuum(이온트랩) | QIR/브리지 경유 연동 | **지원/지향** |
| IBM(초전도) | 브리지/커넥터 기반(정책에 따라) | **목표**(정책/라이선스 영향) |
| QuEra(중성원자) | Braket/커넥터 경유 연동 | **지원/지향** |
| Rigetti(초전도) | 다수 워크플로 사례 | **지원/지향** |
| Xanadu(광자) | 펌/커넥터 연동 | **지원/지향** |
| Pasqal/Atom | 커넥터 연동 | **지향** |

**💡****결론 — CUDA-Q가 유리한 이유**

- - **범용성**: QIR 기반 Cross-QPU 호환성 이미 확보
  - **성능**: GPU-QPU 하이브리드 최적화 지원 → HQ보다 속도 우위
  - **생태계**: CUDA와 AI/HPC 개발자 풀을 그대로 흡수
  - **표준성**: LLVM-QIR, OpenQASM, Cirq, Qiskit까지 **폭넓은 SDK 호환성**

**✅****HPC 중심의 생태계 vs 양자 컴퓨터 중심의 생태계**

**💡****CUDA-Q의 동작 철학**

- - CUDA-Q는 **NVIDIA CUDA 생태계**를 그대로 활용하면서, **QPU를 선택적으로 호출**하는 구조.
  - **핵심 아이디어**

    - **주 계산 엔진** = GPU / CPU (HPC 클러스터)
    - **보조 계산 엔진** = QPU (필요할 때만 호출)
    - SDK/런타임은 **CUDA 스택 위에 얹혀 있음**
    - QPU는 마치 “외부 가속기(Accelerator)”처럼 동작

**💡****CUDA-Q의 설계 배경**

|  |  |  |  |
| --- | --- | --- | --- |
| **알고리즘** | **GPU 연산 비중** | **QPU 연산 비중** | **CUDA-Q의 활용 방식** |
| **VQE** (Variational Quantum Eigensolver) | 약 85% | 약 15% | GPU에서 파라미터 최적화 → QPU로 해밀토니안 측정 |
| **QAOA** (Quantum Approx. Optimization) | 약 80% | 약 20% | GPU에서 코스트 함수 최적화 → QPU에서 상태 준비 |
| **QML** (Quantum Machine Learning) | 70~90% | 10~30% | GPU에서 모델 학습/백프로파게이션 → QPU에서 커널 연산 |
| **QEC 시뮬레이션** | 90% | 10% | GPU에서 디코딩 → QPU에서 피드백 적용 |

- - 양자 알고리즘 중 **NISQ(근거리 미래 양자)** 워크로드의 70~90%는 **고전 연산(GPU)** 비중이 압도적
  - QPU를 직접 제어하지 않고, **CUDA-Q 런타임**이 **클라우드 API + QIR 레이어**를 통해 호출하는 구조
  - QPU는 사실상 가속기(Accelerator)처럼 동작

**💡****QPU 중심 생태계로의 전환 조건**

- - QPU가 HPC를 보조하는 게 아니라, **QPU 중심**으로 패러다임이 바뀌려면 **세 가지 기술 장벽**을 넘어야 한다.
  - **오류율(Fidelity) 혁신**

    - 현재 양자 게이트 오류율:

      - IonQ Ba-137 QCCD ≈ 10-4 ~ 10-3
      - Quantinuum H2 ≈ 10-3
      - QuEra 중성원자 ≈ 10-3~10-2
    - **논리 큐비트 단위에서 10****-6** **수준**까지 가야 함.
    - 여기서 중요한 기술:

      - **QEC**: Surface Code, Color Code, qLDPC, Bacon-Shor, BB5/BB6 등
      - **CliNR, Zero-Noise Extrapolation, Active Reset** 같은 **오류 완화(EM)** 기술
  - **논리 큐비트 스케일업**

    - 현재 물리 큐비트 수:

      - Quantinuum H2: 56
      - IonQ Forte: 35
      - QuEra Aquila: 256
      - PsiQuantum 목표: 1M (포토닉 QPU)
    - **논리 큐비트** 기준으로 **1,000개 이상** 확보돼야 완전한 QPU 중심 생태계 가능.
    - 각 업체별 로드맵 기준으로 2028~2030년 사이가 **QPU 중심 전환 가능성의 분기점**.
  - **소프트웨어·운영체제 표준화**

    - QPU 중심 생태계로 가려면 **양자 운영체제**가 필요.
    - **현재 상황**

      - Qiskit(IBM), Cirq(Google), TKET(Quantinuum), Braket(AWS) → 전부 벤더 종속
      - QPU 간 **호환성 없음**
    - **필요 조건**

      - LLVM 기반 **QIR** 표준 확산
      - **Cross-QPU 런타임** (HQ Triple Alpha, CUDA-Q, Riverlane Deltaflow 등)
      - 논리 큐비트 관리까지 OS 수준에서 지원
    - 표준화 성공 시, 앱 개발자는 **QPU 벤더를 의식하지 않고** 양자 애플리케이션 개발 가능.
  - 진짜 양자 운영체제(QOS) 등장 → **HQ, Microsoft Azure Quantum** 같은 플레이어가 핵심 역할 가능

**💡****주요 플레이어별 역할 비교**

|  |  |  |  |
| --- | --- | --- | --- |
| **구분** | **MS (Azure Quantum)** | **CUDA-Q** | **HQ (Triple Alpha)** |
| **포지션** | Cross-QPU 운영환경 | HPC+GPU 하이브리드 런타임 | QPU 간 앱 호환 레이어 |
| **핵심 기술** | **QIR + Azure Quantum Runtime** | CUDA + QIR | Triple Alpha IR |
| **범위** | QPU 멀티벤더 통합, SDK 표준화 | HPC ↔ QPU 연동 | 앱 포팅 단순화 |
| **유형** | 상위 OS-like 런타임 | 런타임/SDK | 상위 OS-like 런타임 |
| **강점** | QIR 표준 주도, Cross-QPU 스케줄링 | HPC·AI 생태계 압도 | QPU 벤더 종속성 해소 |

- - MicroSoft와 Horizon Quantum 모두 하드웨어 제어 기능은 없는 풀 스택 모델이 아니기 때문에, 하위 계층 제어 기능을 지원하는 Riverlane Deltaflow.OS + Control 이나 Quantum Machines의 OPX 제품군과의 조합이 필요하다.

**💡****CUDA(HPC) 락인의 영향**

- - **CUDA 락인의 결과**

    - 사용자는 이미 CUDA 생태계에 익숙 → **CUDA 기반 워크로드로 개발**하는 편이 자연스러움
    - 예: VQE, QAOA, QML → GPU에서 파라미터 최적화 → QPU 호출 → CUDA-Q에서 자동 지원
    - 이렇게 되면 “양자컴 운영체제”보다는 **CUDA 생태계 내부에 QPU가 흡수되는 구조**가 될 가능성이 큼.
  - **Microsoft, HQ와의 경쟁 구도**

    - MS Azure Quantum은 **QIR 기반 Cross-QPU 표준**을 밀고 있음
    - NVIDIA CUDA-Q는 **HPC 생태계 락인**을 바탕으로 **“디팩토 표준(De facto standard)”**이 될 수 있음
    - 결국 **CUDA vs QIR** = **HPC 중심 vs QPU 중심** 경쟁 구도

**💡****QPU 중심 생태계 전환 가능성**

- - **제약 조건 3가지**

    1. **QPU 성능** → 물리 큐비트 수 → 논리 큐비트 확보

       - 지금은 QPU 단독으로 해결 가능한 문제 거의 없음
    2. **QEC(오류 보정) 상용화**

       - 1,000~10,000 논리 큐비트 확보 전까지는 **고전컴 보조 필수**
    3. **양자 네트워크 확산**

       - 원격 얽힘 + 분산 QPU 필요 → 아직 초기 단계
  - **QPU 중심 생태계 가능성**

    - **2030년 전후**

      - IonQ, Quantinuum, PsiQuantum 등에서 **1,000 논리 큐비트급 QPU** 가능성
      - 양자화학, 신소재, 금융 시뮬레이션에서 QPU가 **메인 연산 엔진**으로 부상
    - **그 이후(2035+)**

      - 분산 양자 네트워크 + 클러스터링으로 QPU 중심 생태계 가속화
  - **하지만 HPC를 완전히 대체하기는 어려움**

    - 고전컴의 **전처리·후처리·최적화**는 여전히 GPU·CPU에서 필요
    - QPU 단독 OS라기보다는 **하이브리드 OS**가 주류가 될 가능성이 높음

**✅****맺음말**

- - 현재 운영 중인 양자컴퓨터에는 벤더별 SDK가 사실상의 OS 역할을 하기 때문에 전통적 의미의 운영체제의 필요성이 낮기 때문에, QC를 위한 풀스택 OS를 거론하는 것이 아직은 시기상조일지도 모른다.

  - 현재로서는 풀스택을 지원하는 업체는 없기 때문에, 향후 요구사항에 따라 인수/합병이 일어날 수 있는 개연성도 염두해 둘 필요가 있겠다.
